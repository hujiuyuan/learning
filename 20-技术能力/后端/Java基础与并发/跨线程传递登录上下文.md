# 跨线程传递登录上下文

技能点：[[Java并发与虚拟线程]] · 通用技能：[[Java基础与并发]]

**一句话**：登录上下文不会自动跨线程；在主线程抓不可变快照，到 worker 里显式绑定，作用域结束自动释放——不要在线程池线程里读 `RequestContextHolder`，也不要依赖 `InheritableThreadLocal`。

## 方法总纲

1. **在主线程抓快照**：只取业务需要的字段（userId、tenantId、角色、traceId），组成不可变 DTO；不要把 `HttpServletRequest`、`SecurityContext` 原对象传进线程池。
2. **选传播机制**：短生命周期、严格嵌套 → `ScopedValue`；需要长期存活/动态修改 → `ThreadLocal` + `TaskDecorator`；任务少且边界清晰 → 直接当参数传。
3. **在 worker 内部绑定**：`ScopedValue.where(CTX, snapshot).run(() -> task())`；绑定发生在任务执行线程，不是提交线程。`ScopedValue` 不会从父线程自动继承。
4. **只读快照**：作用域内不修改 DTO；要改就新建对象，避免多个任务共享可变状态。
5. **作用域自动释放**：`run()` 退出即解绑；`ThreadLocal` 必须在 `finally` 里 `remove()`，线程池线程会复用。
6. **定时任务/消息消费另算**：没有请求线程，上下文来自任务参数/消息头；消费前绑定，处理完释放。
7. **测试**：作用域内读得到、作用域外回落/为空；真实线程池跑一次，别只用同步 mock 证明。

## 机制取舍

| 方案 | 适合 | 代价/失败模式 |
| --- | --- | --- |
| 显式参数 | 任务少、边界清晰 | 方法签名变长，漏传就空 |
| `ThreadLocal` + `TaskDecorator` | 已有 ThreadLocal 体系、需要可变 | 忘记 `remove` 会泄漏/串号；线程池复用脏值 |
| `ScopedValue` | 生命周期严格嵌套、只读快照、虚拟线程 | Java 21 preview，编译/测试/运行都要 `--enable-preview`；不自动跨线程 |
| 消息头/任务参数 | MQ、定时任务、跨服务 | 每个生产/消费点都要记得带上；缺省值可能落到错误租户 |

项目选 `ScopedValue`：上下文是一次请求的快照、只读、生命周期嵌套，正好匹配；代价是 preview 限制和「必须手动绑定」。

## 反例

- **异步线程直接读 `RequestContextHolder`**：线程绑定，worker 没有请求，返回 null。
- **依赖 `InheritableThreadLocal`**：只在线程创建时继承；线程池线程早就创建好，拿不到新请求的值。
- **把 `HttpServletRequest` 传进线程池**：请求可能已结束/回收，且把 Web 容器对象泄漏到业务线程。
- **`ThreadLocal` 不 `remove`**：线程池复用后，下一个任务读到上一个用户的租户/身份。
- **作用域内修改共享 DTO**：多个任务看到彼此的半更新状态。
- **只在同步 mock 里测**：`ExecutorService` 被换成同步执行，等于没证明跨线程传播。

## 边界

- ScopedValue 是 Java 21 preview，升级 JDK 要先验证。
- 导出/导入测试用同步执行器替换线程池，真实虚拟线程上的传播没有被测试证明。
- `@Async` 的日志/邮件任务没走 ScopedValue，而是调用方预取参数传入；不是所有异步路径都适合作用域注入。
- 没有做过线程池拒绝/任务取消时上下文清理的专项测试。
