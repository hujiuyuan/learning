# 线程池参数与异步编排

技能点：[[Java并发与虚拟线程]] · 通用技能：[[Java基础与并发]]

**一句话**：线程池的参数不是「拍几个数」，而是「任务类型 + 下游容量 + 过载策略」的函数；异步编排真正难的是异常、上下文和线程池选择，不是 `thenApply` 的 API。

## 方法总纲

1. **先分任务类型**：CPU 密集（计算/序列化）用固定小池；IO 密集（DB/HTTP/S3）用较大池或虚拟线程；混合任务拆开，别用一个池兜所有。
2. **再定上限**：并发数由下游容量决定（DB 连接池、S3 配额、第三方限流），不是 CPU 核数；队列长度是「允许多少等待」，必须有界。
3. **定拒绝策略**：业务任务用 Abort/CallerRuns，拒绝要可观测；日志/指标类可 Discard，但不能静默丢业务。
4. **上下文显式传播**：登录用户、租户、TraceId、MDC 在主线程抓快照，异步线程恢复；`@Async` 不传播 ThreadLocal/事务。
5. **事务边界分开**：异步线程没有事务上下文；要「提交后做」用 `afterCommit`，要「一起回滚」就不要异步。
6. **编排选对算子**：`thenApply` 是同步转换，`thenCompose` 是串行异步，`thenCombine` 是并行合并；IO 任务传自己的 executor，不用公共 ForkJoinPool。
7. **异常与超时**：`exceptionally/handle/whenComplete` 必须有一个；`orTimeout/completeOnTimeout` 设上限；`submit` 返回的 Future 要有人看。

## 参数速查

| 参数 | 作用 | 常见错法 |
| --- | --- | --- |
| `corePoolSize` | 常驻线程数 | 设太大，空闲也占资源 |
| `maximumPoolSize` | 峰值线程数 | 配无界队列，max 永远用不上 |
| `workQueue` | 等待队列 | 无界队列把过载推迟到 OOM |
| `keepAliveTime` | 非核心线程空闲回收 | 核心线程默认不回收 |
| `handler` | 拒绝策略 | 默认 Abort 没接，异常被吞 |
| `threadFactory` | 线程命名/异常处理 | 线程名默认 pool-N，排查困难 |

## 编排示例（原则）

```java
// 两个独立 IO 并行，再合并；必须传自己的 executor，不用 commonPool
CompletableFuture<A> fa = CompletableFuture.supplyAsync(() -> loadA(), ioPool);
CompletableFuture<B> fb = CompletableFuture.supplyAsync(() -> loadB(), ioPool);
CompletableFuture<C> fc = fa.thenCombine(fb, this::merge)
    .orTimeout(3, TimeUnit.SECONDS)
    .exceptionally(ex -> fallback(ex));
```

- `thenApply` 里的异常会变成 failed future，不处理就静默丢；`whenComplete` 只观察，不吞异常。
- `thenCompose` 用于「上一步结果决定下一步异步调用」，不是 `thenApply` 返回 `CompletableFuture` 的嵌套。
- 公共 `ForkJoinPool.commonPool()` 线程数少，IO 任务会饿死其他并行流；自定义池按任务类型隔离。

## 反例

- 无界 `LinkedBlockingQueue` + 大 `max`：队列永远不满，max 不生效，过载变 OOM。
- `@Async` 方法同类自调用/private：代理不生效，任务同步执行。
- 异步线程直接读 `SecurityContextHolder`/`RequestContextHolder`：上下文为空或串号。
- 事务里提交异步任务：主事务回滚，异步任务照跑。
- `CompletableFuture` 不传 executor：IO 任务跑在 commonPool，阻塞其他任务。
- 线程池没有监控：活跃数/队列/拒绝数都看不到，出事只能猜。

## 边界

- 项目没有对线程池做压测，参数按任务类型和下游容量估，不是实测最优。
- 虚拟线程的 pinning/监控只在原理层，没有生产观测数据。
- 没做过多池隔离/动态调参/线程池治理平台。
