# 任务幂等

技能点：[[Outbox]] · 方法：[[幂等键与占位]] · 通用技能：[[事务与状态一致性]]

**什么时候会遇到**：定时任务被手动重跑、失败重试、执行器超时换机；消息至少一次重投；用户重复提交；支付渠道重复回调。

## 判断顺序

1. **重复从哪来**：调度重试 / 手动触发 / 换机重跑 / 消息重投 / 用户重试 / 回调重放。先列出所有来源。
2. **幂等键是什么**：业务主键、事件三列键、`(jobId, targetType, targetKey, windowKey)`、`(taskId, fromStatus)`。键选错，去重就是错的。
3. **占位在哪**：和副作用同一个事务，还是先提交占位再做副作用？后者会留下「标记已写、事情没做」的永久空洞。
4. **重复时返回什么**：跳过、返回首次结果、转人工。三种语义要明确，不能一律抛错。
5. **崩溃恢复**：租约多久过期？过期后谁回收？旧持有者的晚到写入怎么挡？
6. **验证**：有没有并发/崩溃/重放测试，还是只测了正常路径？

## 手段

- **定时任务条件占位**：`muou-server/src/main/java/com/voidtech/muou/service/JobRunMarker.java:34-61` 定义复合键和「必须在事务内调用」；`muou-server/src/main/java/com/voidtech/muou/service/impl/JobRunMarkerImpl.java:32-38` 用 `MANDATORY` 拒绝事务外调用；`muou-server/src/main/resources/db/migration/V14__job_run_marker.sql:19-31` 复合主键；真正执行 `ON CONFLICT DO NOTHING` 的是 `muou-server/src/main/java/com/voidtech/muou/dao/mapper/JobRunMarkerMapper.java:23-30`。
- **占位与副作用同事务**：`muou-server/src/main/java/com/voidtech/muou/job/AuthReloadTenantStep.java:58-68`，`claim` 返回 false 直接跳过，返回 true 才重建；重建失败整个事务回滚，占位也回滚。
- **Outbox 租约回收**：`muou-backend/muou-common/muou-common-app/src/main/java/com/voidtech/muou/common/tx/outbox/TxOutboxDispatcher.java:29-42` 的 `SKIP LOCKED` + `lease_until`；`muou-server/src/main/java/com/voidtech/muou/job/OutboxDispatchJob.java:39-48` 每轮先回收过期租约。
- **状态机 CAS + 重读**：`smart-server-wms3/src/main/java/com/track/wms/service/impl/TaskFlowEngine.java:104-127`、`:138-158`；`smart-server-wms3/src/test/java/com/track/wms/service/impl/TaskFlowEngineTest.java:94-127` 验证「CAS 0 行 + 已是目标态 → 幂等跳过；非目标态 → 抛」。
- **支付回调**：`muou-backend/muou-server-billing/muou-billing-app/src/main/java/com/voidtech/muou/billing/service/payment/callback/PaymentCallbackRecorder.java:71-92` 先拿咨询锁、按 `(provider, merchant_id, provider_event_id)` 查重放；`muou-backend/muou-server-billing/muou-billing-api/src/main/java/com/voidtech/muou/billing/api/constant/payment/PaymentCallbackResults.java:10-23` 定义 `accepted/replayed/amount_mismatch/already_paid/manual_review` 五档。
- **验证**：`muou-server/src/test/java/com/voidtech/muou/service/JobRunMarkerIT.java:34-59` 无事务调用抛异常、同键第二次返回 false；`muou-backend/muou-server-billing/muou-billing-app/src/test/java/com/voidtech/muou/billing/component/PaymentCallbackComponentTest.java:207-250` 同键重放与并发只认领一次；`muou-backend/muou-common/muou-common-app/src/test/java/com/voidtech/muou/common/tx/outbox/TxOutboxCrashRecoveryTest.java:117-139` 故意让副作用做两次。

## 反例 / 边界

- **反例 1：占位先单独提交**。`muou-server/src/main/java/com/voidtech/muou/service/JobRunMarker.java:27-32` 写明后果：标记已写、提醒没发，重跑因为标记在而跳过，提醒永久消失。
- **反例 2：假设消息只投一次**。`muou-backend/muou-common/muou-common-app/src/test/java/com/voidtech/muou/common/tx/outbox/TxOutboxCrashRecoveryTest.java:117-139` 的测试消费端故意不幂等，结果同一申请开出两张订单；这正是消费端必须幂等的理由。
- **反例 3：CAS 0 行一律抛错**。并发对手已经推进到目标态时，抛错会回滚整个外层事务；`smart-server-wms3/src/main/java/com/track/wms/service/impl/TaskFlowEngine.java:115-124` 改为重读后幂等跳过，非目标态才抛。
- **边界**：支付真实渠道未接，只有桩/离线网关；这里只证明回调幂等，不证明支付上线。`muou-backend/muou-server-billing/muou-billing-app/src/main/java/com/voidtech/muou/billing/config/payment/PaymentGatewayStartupGuard.java:15-24` 还只是启动期防呆。
- **边界**：`JobRunMarker` 目前只有 `AuthReloadTenantStep` 一个真实调用点；11 个任务没有全部落地，其中 outbox 投递和文章发布走的是租约/终态抢占，不是占位表。
- **边界**：租约依赖数据库 `now()`；跨库/时钟偏差场景没有验证。

## 现在的规矩

- 定时任务一律 `claim` + 副作用同事务；`claim` 用 `MANDATORY` 机器化，不靠 code review。
- 消息消费端必须幂等；Outbox 只承诺至少一次。
- 状态推进用 CAS；0 行先重读，再决定幂等跳过还是抛错。
- 支付回调按三列键去重，终态只写一次；乱序/重复走 `manual_review` 而不是二次入账。
- 幂等键必须包含「窗口」：会随续期变化的目标，把到期日嵌进 `windowKey`。
