# 事务与状态一致性基础

## 1. 事务与 ACID

**一句话**：原子性、一致性、隔离性、持久性分别靠 undo/redo、约束、锁/MVCC 和日志保证；隔离性越强，并发越低。

要能回答：

- ACID 分别靠什么实现？
- 四种隔离级别分别解决脏读、不可重复读、幻读中的哪些？
- MySQL 默认隔离级别是什么？PostgreSQL 呢？
- 快照读和当前读的区别？
- 分布式事务和本地事务的边界在哪？

**笔记**：

- 原子性靠 undo log 回滚；持久性靠 redo log/ WAL 崩溃恢复；隔离性靠锁 + MVCC；一致性是业务约束 + 数据库约束（唯一键、外键、CHECK）共同保证的结果，不是某一个日志单独给的。
- 隔离级别：RU 允许脏读；RC 解决脏读，但同一事务两次读可能不同；RR 解决不可重复读，MySQL InnoDB 默认；Serializable 串行化，最强最慢。PostgreSQL 默认 RC，RR 在 PG 里是快照隔离，幻读行为与 MySQL 不同。
- 快照读读 Read View 对应的历史版本，不加锁；当前读读最新已提交版本并加锁（`FOR UPDATE`、`UPDATE`、`DELETE`）。RR 下快照读靠 MVCC 避免幻读，当前读靠 Next-Key Lock 锁间隙。
- 本地事务的边界是「同一个数据库连接/同一个资源」；跨库、跨服务、跨消息中间件就不在本地事务里。跨资源要么 2PC/XA，要么 TCC/Saga，要么本地消息表 + 最终一致；不能把 `@Transactional` 当成跨服务事务。

## 2. Spring 事务

**一句话**：`@Transactional` 通过 AOP 代理开启/提交/回滚事务；代理没生效、异常没抛出、异常类型不匹配，都会让事务失效。

要能回答：

- `@Transactional` 的 `propagation` 有哪几种？`REQUIRED`、`REQUIRES_NEW`、`NESTED` 的区别？
- 默认对哪些异常回滚？`rollbackFor` 怎么配？
- 同类自调用为什么失效？怎么解决？
- `private` 方法、`final` 方法为什么不能加事务？
- 事务提交后还能做业务操作吗？`TransactionSynchronization` 怎么用？
- 只读事务真的只读吗？

关联：[[Spring事务]]、[[事务失效]]

**笔记**：

- 传播级别：`REQUIRED` 有事务就加入、没有就新建（默认）；`REQUIRES_NEW` 挂起当前事务、新建独立事务，内外互不影响；`NESTED` 在当前事务里开保存点，内层失败回滚到保存点，外层可继续；`SUPPORTS` 有就加入、没有就非事务；`NOT_SUPPORTED` 挂起事务；`MANDATORY` 必须有事务否则抛；`NEVER` 必须没有事务。
- 默认只回滚 `RuntimeException` 和 `Error`；checked exception 要在 `@Transactional(rollbackFor = Exception.class)` 显式声明。catch 后不回抛、转成别的异常，也不会回滚。
- 同类自调用不走代理；`private` 方法不能被 JDK/CGLIB 代理；`final` 方法不能被 CGLIB 重写。解决：拆 Bean、`TransactionTemplate`、`AopContext.currentProxy()`。
- `afterCommit` 在事务提交后执行，此时连接可能还没归还；回调里写库要用 `REQUIRES_NEW`，否则 `REQUIRED` 会加入已提交事务、内层 commit 变 no-op。`TransactionSynchronization` 可注册 `beforeCommit/afterCommit/afterCompletion`。
- `readOnly = true` 是给驱动/ORM 的优化提示，不是「禁止写」的保险；某些驱动/ORM 会跳过 flush，写行为不可靠。只读事务适合纯查询，不要在里面写。

## 3. 事务边界设计

**一句话**：事务只包住「必须一起成功或失败」的数据库写操作；远程调用、文件上传、消息发送尽量放在事务外或改用补偿。

要能回答：

- 一个事务里最多应该包多少操作？大事务有什么危害？
- 为什么不要在事务里调用 HTTP/RPC？
- 事务里发消息会有什么问题？消息丢了或重复了怎么办？
- 事务边界和服务层、Controller 层怎么对应？
- 嵌套事务和保存点（savepoint）怎么用？

**笔记**：

- 事务越小越好：大事务持有锁久、undo 大、回滚慢、连接占用久，容易拖垮并发。一个事务只包「必须原子」的数据库写，查询、远程调用、文件 IO 尽量放外面。
- 事务里调 HTTP/RPC：对方成功、本地回滚，或本地成功、对方失败，都会不一致；远程调用还可能超时、重试、幂等。正确做法是本地事务 + Outbox/补偿，或先调远程再本地（接受反向不一致）。
- 事务里发消息：消息可能先发后回滚（消息到了、业务没成），也可能业务成了、消息没发。用本地消息表/Outbox 和业务同事务写，提交后再投递；消费端幂等。
- 事务边界放 Service 的 public 方法，Controller 只做参数/响应，不写业务事务；一个 Service 方法只开一个事务，不要把多个聚合的写硬塞进一个大事务。
- 保存点 `Savepoint` 允许内层失败回滚到保存点、外层继续；`NESTED` 就是保存点语义。保存点不是新事务，外层回滚仍会带走内层。

## 4. 分布式事务

**一句话**：2PC 强一致但阻塞、性能差；TCC 用业务补偿换性能；Saga 用长流程补偿；多数互联网业务最终选「本地事务 + 消息/Outbox + 幂等」。

要能回答：

- 2PC、3PC 的流程和缺点？
- TCC 的 Try/Confirm/Cancel 分别做什么？空回滚、悬挂、幂等怎么处理？
- Saga 和 TCC 的区别？补偿失败怎么办？
- 本地消息表、事务消息、Outbox 各解决什么问题？
- CAP 和 BASE 在事务设计里怎么体现？

**笔记**：

- 2PC：协调者问所有参与者 prepare，全部 yes 再 commit，否则 rollback；缺点是同步阻塞、协调者单点、prepare 后参与者锁资源。3PC 加 canCommit 阶段、超时也提交，降低阻塞但仍有不一致窗口。
- TCC：Try 预留资源（冻结库存/额度），Confirm 确认扣减，Cancel 释放预留。空回滚（Cancel 先于 Try 到）、悬挂（Try 后到，Cancel 已执行）、幂等（重复 Confirm/Cancel）都要在业务层处理，通常用事务控制表记录状态。
- Saga：每个服务本地事务 + 对应补偿动作，按顺序执行，失败反向补偿。没有隔离性，中间状态对外可见；补偿失败要重试/人工。适合长流程、跨服务多、能接受最终一致。
- 本地消息表：业务写和消息记录同库同事务，后台投递；事务消息（RocketMQ 半消息）由 MQ 保证「本地事务成功才投递」；Outbox 是本地消息表的通用实现。三者都靠消费端幂等消化重复。
- CAP：分区容忍下，强一致和可用二选一；BASE 是基本可用、软状态、最终一致。事务设计要明确「哪些操作必须强一致、哪些可以最终一致」，不能全站一个口径。

## 5. Outbox 与最终一致性

**一句话**：Outbox 把「业务写」和「消息记录」放在同一个本地事务，再由后台任务投递；保证不丢，靠幂等保证不重。

要能回答：

- Outbox 表应该有哪些字段？状态机怎么设计？
- 投递任务怎么避免多副本重复投递？`SKIP LOCKED` 解决什么？
- 投递失败怎么重试？重试次数、退避、死信怎么设？
- 消费者怎么保证幂等？去重键放哪？
- Outbox 会不会成为性能瓶颈？怎么清理历史数据？

关联：[[Outbox]]、[[Outbox落地]]

**笔记**：

- 字段：id、聚合类型/ID、事件类型、payload、状态（pending/sent/dead）、重试次数、next_retry_at、lease_until、trace_id、created_at、sent_at；业务唯一键防重复写入。状态机只允许 pending→sent/dead，重试不改业务状态。
- 多副本投递用 `SELECT ... FOR UPDATE SKIP LOCKED` 抢批 + 租约；拿到行后更新 lease_until，其他实例跳过。租约过期说明实例可能死了，允许重投；重投可能重复，消费端必须幂等。
- 失败重试用指数退避 + 最大次数；超过转 dead，人工/告警处理。不要无限重试打爆下游；dead 表要可查询、可重放。
- 消费者幂等：业务唯一键/消息 ID 去重表，或状态 CAS；重复消息返回首次结果/跳过，不重复扣款/发货。去重键要和业务唯一约束一致。
- Outbox 会成为写热点：表持续增长、索引膨胀、投递扫表。按时间分区/归档已发送记录，限制单批大小，监控积压；不要在同一张表上做全表 count。

## 6. 幂等与状态机

**一句话**：幂等是「同一请求执行多次，结果一致」；实现靠唯一键、状态机 CAS、去重表或 token，不能靠「查一下再写」。

要能回答：

- 幂等键怎么生成？放在请求头、body 还是数据库唯一索引？
- 先查后写为什么在并发下不幂等？CAS 怎么解决？
- 状态机允许哪些迁移？非法迁移怎么处理？
- 重复请求返回第一次结果还是报错？
- 消息重复、回调重复、用户重复点击分别怎么防？

关联：[[任务幂等]]、[[TaskFlowEngine]]

**笔记**：

- 幂等键来自业务唯一标识（订单号 + 操作类型、支付流水号、客户端生成的 requestId）；放请求头/body，落库加唯一索引。没有业务唯一键时，客户端生成 UUID 当幂等键，服务端持久化。
- 先查后写：两个请求同时查到「不存在」，都插入/都执行，唯一索引可能挡住一个，但业务副作用可能已经发生。CAS 用 `UPDATE ... WHERE status = from`，受影响行数为 0 就说明别人先改了；插入用唯一键冲突。
- 状态机明确「哪些状态能走哪些边」；非法迁移抛业务异常，不静默改状态。状态机只判合法性，并发赢家仍靠 CAS/唯一键。
- 重复请求返回第一次结果还是报错是契约：查询类返回相同结果；创建类返回已有记录/409；支付类必须返回首次结果，不能重复扣款。要在接口文档写清。
- 消息重复用消费去重表/幂等键；回调重复用业务单号 + 状态 CAS；用户重复点击用前端防抖 + 后端幂等键，前端防抖不能当唯一保障。

## 7. 一致性与补偿

**一句话**：强一致、最终一致、弱一致是业务选择；选最终一致就必须设计补偿、对账和人工兜底。

要能回答：

- 什么业务必须强一致？什么业务可以最终一致？
- 补偿事务和回滚的区别？
- 对账任务怎么设计？发现不一致怎么处理？
- 超时、网络分区、部分失败分别怎么处理？
- 幂等 + 重试 + 对账三件套分别防什么？

**笔记**：

- 强一致：钱、库存扣减、权限变更等不允许中间态被看到；最终一致：通知、积分、搜索索引、日志等可以延迟。选最终一致就要接受「短时间内不一致」，并给业务/客服可见的状态。
- 回滚是撤销未提交的本地事务；补偿是已提交后的反向业务动作（退款、释放库存），可能失败、可能部分成功，必须幂等、可重试、可人工。
- 对账：按业务日期/批次拉双方流水，按唯一键比对，差异分类（单边、金额、状态），自动补单/人工处理；对账任务本身要幂等、可重跑、有阈值告警。
- 超时：不知道对方成没成，不能盲目重试；用查询接口/业务单号确认，或让操作幂等。网络分区：两边都可能继续处理，需要版本/状态 CAS 防双写。部分失败：记录每一步状态，补偿已成功的步骤。
- 幂等防重复、重试防 transient 失败、对账防「以为成功/以为失败」的长期偏差；三者缺一不可，不能只靠重试。
