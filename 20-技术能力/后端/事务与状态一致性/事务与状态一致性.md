# 事务与状态一致性

**一句话**：事务只管住同一个数据库连接；跨线程、跨进程、跨外部系统的「一致」要靠提交后副作用、本地消息表、幂等和 CAS 自己补。

## 一、理论：一致性靠哪几层

1. **本地事务**：同一连接上的多条写，要么全提交，要么全回滚；ACID 只在单库单事务内成立。
2. **事务边界**：只有经过 Spring 代理的调用才开事务（`@Transactional` / `TransactionTemplate`）；自调用、private 方法、`@Async` 线程都不在事务里。
3. **提交后副作用**：邮件、S3、通知这类外部动作不能回滚，放到 `afterCommit`；回调里再写库要开 `REQUIRES_NEW`。
4. **跨进程**：本地消息表（Outbox）把「发消息」变成「和业务同库同事务写一行」，投递器异步搬运；语义是至少一次。
5. **幂等**：至少一次意味着消费端必须按幂等键去重；定时任务的重试、手动触发、超时换机同样要幂等。
6. **CAS**：`UPDATE ... WHERE id=? AND status=?`，受影响行数为 0 就说明状态已被别人改过；0 行怎么处理是业务契约。
7. **租约**：带过期时间的抢占（`lease_until`），崩溃实例留下的行到期后被别的实例回收；旧持有者的晚到写入要靠租约比对挡掉。
8. **分布式事务**：XA/Seata 能跨库，但成本高；muou 只在 5 个服务的 11 个入口用 XA，其余仍用「本地事务 + Outbox 最终一致」。

### COLA 状态机：显式转换表 + CAS 分工

- **四台机器**：预装、现装、移动三台任务状态机（按 `TaskTypeEnum` 取）+ 一台出货状态机（id `SHIPPING_TASK`）；每台在 `@PostConstruct` 里 build 一次并缓存，启动后只读（`StateMachineConfig.java:43-55`、`ShippingStateMachine.java:32-69`）。
- **转换表就是文档**：`externalTransition().from(A).to(B).on(EVENT)` 一条边一行；批量边用 `fromAmong(...).to(...)`；条件边用 `.when(ctx -> ...)`，比如「异常中 --解决异常--> 待领取/进行中」按 `ctx.preStatus` 分流（`StateMachineConfig.java:104-123`）。
- **action 是空操作**：`NOOP` 只让状态机返回目标状态，不落库；真正的 DB 副作用在 service 拿到目标状态后做。这样状态机不依赖 DAO/事务，单测不用起 Spring 上下文（`StateMachineConfig.java:39-41`；`ShippingStateMachine.java:28-30`、`:75-83`）。
- **`verify` 与 `fireEvent` 分开**：`verify(from,event)` 只判断「这条边存不存在」，不评估 `when` 条件；`fireEvent` 才执行条件。所以调用方可以先 verify 给出明确错误，再用 fire 处理条件失败（`StateMachineConfig.java:82-93`）。
- **非法流转转业务异常**：`setFailCallback(new AlertFailCallback<>())` 让非法/条件不命中抛 `TransitionFailException`，`fire` 捕获后翻译成 `TASK_STATUS_INVALID` / `SHIPPING_STATUS_ILLEGAL`，不泄漏成 500（`StateMachineConfig.java:121-123`、`ShippingStateMachine.java:62-82`）。
- **静态工厂是进程级**：同一 JVM 第二个 Spring 上下文（多测试类、上下文 refresh）再 build 同名机器会抛 `StateMachineException`；处理是取回已注册实例，不能吞掉异常留 `null`，否则后一个上下文流转直接 NPE 或误判类型不匹配（`StateMachineConfig.java:57-77`；`ShippingStateMachine.java:37-68`）。
- **单测共享一台机器**：`ShippingStateMachineTest` 用 `new + init()`，全类共用一个静态实例，因为机器 ID 全局只能注册一次；状态机无内部状态，多测试方法共享只读实例安全（`src/test/java/com/track/wms/config/ShippingStateMachineTest.java:13-29`）。

#### 选型与取舍：为什么用 COLA 状态机，不用 if-else/Spring StateMachine

- **if-else**：状态少时最直接，但边一多就散在 service 各处，新增一个状态要改 N 个 `if`，且「哪些边合法」没有单一清单；测试只能逐条调用，覆盖不全就漏。COLA 把边集中成一张表，新增状态只改一处。
- **Spring StateMachine**：功能更强（层次状态、持久化、分布式），但为此引一套运行时和更多概念；项目只需要「有限状态 + 事件 + 条件 + 非法回调」，COLA 更轻。
- **代价**：多一个库（`cola-component-statemachine 5.0.0`）；静态工厂的全局 ID 在测试/多上下文下要特殊处理；状态/边爆炸时一张表会变长，要按任务类型拆机器（项目已经按类型拆了三台）。
- **与 CAS 的分工**：状态机判「这条边合法」，CAS 判「这次写入是不是第一个赢家」。两个并发请求都通过状态机校验，只有一个 `UPDATE ... WHERE status=from` 能成功；状态机不替代 CAS，CAS 也不表达整张转换图（`TaskFlowEngine.java:52-54`、`:115-124`）。
- **与 Seata 的分工**：状态机是单服务内的业务状态流转；Seata XA 管跨服务/跨库的数据一致性。两者不在同一层，不能拿状态机当分布式事务，也不能拿 XA 替代状态合法性校验。
- **什么时候反悔**：状态/边继续膨胀、需要层次状态/并行状态 → 评估 Spring StateMachine 或按领域拆多台；团队不熟 COLA、静态工厂测试成本高 → 退回显式 switch + 表驱动校验。当前四台机器、边数有限，COLA 的收益大于成本。

## 三、归纳：一致性检查清单

1. **边界**：入口经过代理吗？自调用、private、`@Async` 是否绕开事务？
2. **回滚**：抛的是不是运行时异常？checked exception 有没有 `rollbackFor`？有没有 catch 后不回抛？
3. **提交后动作**：是不是 `afterCommit`？回调里写库用 `REQUIRES_NEW` 了吗？
4. **外部 IO**：邮件/S3/PDF/HTTP 在事务里吗？超时会不会拖住或回滚主事务？
5. **跨进程写**：消息和业务写在同一库同一事务吗？投递器失败会重试吗？
6. **重复投递**：消费端幂等键是什么？重复时返回首次结果、跳过还是转人工？
7. **定时任务**：失败重试、手动触发、超时换机三种情况，幂等键覆盖了吗？
8. **并发状态**：CAS 的前置状态是什么？0 行时重读还是直接抛？
9. **崩溃恢复**：租约多久？过期谁回收？旧持有者的晚到写入怎么挡？
10. **验证**：有真库回滚/并发/崩溃测试吗，还是只断言注解存在？

### 三条红线

- 不要把「有 `@Transactional`」当成「回滚已验证」：注解只是前提，回滚要真库失败路径才能证明。
- 不要把邮件、S3、HTTP 调用放进业务事务里等它成功：外部系统不参与回滚。
- 不要假设消息只投一次：Outbox 的契约是至少一次，消费端必须幂等。

## 四、回到理论：为什么这些规则成立

- 事务上下文绑定在**线程 + 数据源连接**上；换线程、换数据源、脱离代理，上下文就断。
- `afterCommit` 执行时外层事务已提交但连接尚未归还，`REQUIRED` 会判定「已有事务」，内层 commit 变 no-op；所以必须 `REQUIRES_NEW`。
- Outbox 不消灭重复，只消灭「业务成功、消息丢失」；它把不确定窗口从「发消息」挪到「投递」，再用幂等消化重复。
- CAS 依赖数据库行锁把「读-判-写」压成原子；租约是给 CAS 加过期时间，让崩溃实例的锁能自动释放。
- 这些原则换成 JPA、Go 的 `sql.Tx`、消息队列的消费组，结论一样：先定边界，再定幂等键。

## 五、边界

- 单库本地事务 + Outbox 最终一致是主线；XA/Seata 只在 muou 五个服务的 11 个入口落地，且全部 XA，没有生产 AT/TCC，也没有做过 TC 故障演练。
- Outbox 的本地消息表要求业务表和消息表同库；跨库写入没有做过。
- smart 的 `reserveLocation` 只有反射断言注解存在，测试自己承认 Mockito 驱动不了真实回滚，见 `smart-server-wms3/src/test/java/com/track/wms/service/impl/WarehouseReserveLocationTest.java:363-376`；本次只找到 `mergeSave` 一处真回滚 E2E。
- TaskFlow 的改造计划复选框未勾选，但代码和测试已存在；本页按代码/测试写，不按计划写。
- 支付真实渠道未接，只有桩/离线网关；回调幂等有测试，但不能写成「支付已上线」。
- 没做过跨服务 saga 编排、RocketMQ 事务消息（半消息）的生产落地。
