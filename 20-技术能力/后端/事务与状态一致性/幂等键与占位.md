# 幂等键与占位

技能点：[[Outbox]] · 通用技能：[[事务与状态一致性]]

**一句话**：幂等不是「再查一次」，是「用唯一键/条件占位把并发和重放挡在副作用之前」；键选错、占位和副作用不同事务，都会留下永久空洞。

## 方法总纲

1. **列重复来源**：调度重试、手动触发、换机重跑、消息至少一次、用户重复点击、渠道回调重放。每个来源的键可能不同。
2. **选幂等键**：业务主键 + 操作类型 + 窗口；支付回调用 `(provider, merchant_id, provider_event_id)`；任务用 `(jobId, targetType, targetKey, windowKey)`；状态推进用 `(id, fromStatus)`。
3. **落唯一约束**：键必须在数据库有唯一索引/复合主键；只靠应用内存/Redis 去重，重启/多副本就失效。
4. **占位与副作用同事务**：`INSERT ... ON CONFLICT DO NOTHING` 或条件 `UPDATE ... WHERE status=from` 和业务写在同一事务；占位提交了、副作用没做，就是「标记已写、事情没做」的永久空洞。
5. **定义重复语义**：查询类返回首次结果；创建类返回已有记录/409；支付类返回首次结果，不能二次扣款；无法判断的进人工。
6. **崩溃恢复**：租约/占位过期后谁回收？旧持有者晚到写入怎么挡（版本号/租约比对）？
7. **验证**：并发测试、重放测试、崩溃恢复测试；只测正常路径不算。

## 判断顺序

- **先问「重复会造成什么」**：多扣钱、多发消息、多建记录，还是只是多跑一次空转？后果决定要不要强幂等。
- **再问「有没有业务唯一键」**：有就用业务键；没有就让客户端生成 requestId/UUID，服务端持久化。
- **再看「占位放哪」**：和副作用同库同事务；跨服务/消息场景用去重表/状态 CAS。
- **最后看「重复返回什么」**：跳过、返回首次结果、409、转人工——接口契约要写清。

## 反例

- **先查后写**：两个请求同时查到「不存在」，都执行；唯一索引可能挡住一个，但副作用可能已经发生。
- **占位先单独提交**：标记已写、提醒没发；重跑因为标记在而跳过，提醒永久消失。
- **只靠 Redis 去重**：Redis 重启/主从切换丢 key，重复请求穿透。
- **CAS 0 行一律抛错**：并发对手已推进到目标态，抛错会回滚外层事务；应重读后幂等跳过，非目标态才抛。
- **幂等键不含窗口**：续期/重跑后目标变了，旧键挡住新操作。
- **消费端假设消息只投一次**：Outbox 契约是至少一次，不幂等就会重复开单/重复扣款。
