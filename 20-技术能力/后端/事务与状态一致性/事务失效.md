# 事务失效

技能点：[[Spring事务]] · 方法：[[事务边界核对]] · 通用技能：[[事务与状态一致性]]

**什么时候会遇到**：方法上明明有 `@Transactional`，异常也抛了，库里却留下半截数据；或者提交后回调里写库，日志没报错但数据没落。

## 判断顺序

1. **调用经过代理吗**：同类 `this` 调用、private/final 方法、`@Async` 线程都不经过 Spring 代理，事务不会开。
2. **异常真的抛出去了吗**：catch 后不回抛、转成别的异常、只打日志，回滚不会发生。
3. **异常在回滚范围吗**：默认只回滚 `RuntimeException`/`Error`；checked exception 需要 `rollbackFor = Exception.class`。
4. **传播级别对吗**：`afterCommit` 里写库用 `REQUIRED` 会加入已提交事务，内层 commit 变 no-op；必须 `REQUIRES_NEW`。
5. **是不是只读事务**：`readOnly = true` 不禁止写，但驱动/ORM 可能跳过 flush，写行为不可靠。
6. **是不是同一个数据源**：事务绑定在连接上；换数据源/跨库，事务上下文就断。

## 手段

- **自调用拆 bean**：`muou-server/src/main/java/com/voidtech/muou/job/AuthReloadTenantStep.java:19-23` 写明同类调用不走代理、事务不会开，所以把「一个租户一步」拆成独立 bean；`:58-68` 在独立 bean 上开事务后调 `claim`。
- **private 方法用 TransactionTemplate**：`smart-server-wms3/src/main/java/com/track/wms/service/impl/InfoServiceImpl.java:8924-8930`、`smart-server-wms3/src/main/java/com/track/wms/service/impl/OperationLogArchiveServiceImpl.java:112-123` 都有「private 方法上的 `@Transactional` 不生效」的注释。
- **checked 异常加 rollbackFor**：`smart-server-wms3/src/main/java/com/track/wms/service/impl/WarehouseServiceImpl.java:1004`、`:1343`。
- **afterCommit + REQUIRES_NEW**：`smart-server-wms3/src/main/java/com/track/wms/service/impl/SafetyAckServiceImpl.java:106-125` 为归档单独组装 `TransactionTemplate` 并设 `PROPAGATION_REQUIRES_NEW`；`:236-261` 用它包 files/goods_files 两次写库。
- **提交后发信**：`smart-server-wms3/src/main/java/com/track/wms/common/util/TxCommitUtil.java:25-41` 只注册 `afterCommit`，回滚不触发；`smart-server-wms3/src/test/java/com/track/wms/service/impl/ImportMailTxTest.java:112-165` 验证提交才发、回滚不发。
- **真回滚**：`smart-server-wms3/src/test/java/com/track/wms/service/impl/MergeSaveTxE2eTest.java:190-214` 用 spy DAO 让第 3 条插入失败，断言旧规则还在、新规则一条不写。

## 反例 / 边界

- **反例 1：只断言注解存在**。`smart-server-wms3/src/test/java/com/track/wms/service/impl/WarehouseReserveLocationTest.java:363-376` 自认「Mockito 无法驱动真实事务回滚，退而求其次做反射断言」；它只能证明声明了边界，不能证明回滚。
- **反例 2：把 catch Throwable 当成通用写法**。`smart-server-wms3/src/main/java/com/track/wms/service/impl/SafetyAckServiceImpl.java:262-271` 的 catch 是 `afterCommit` 里的刻意设计（PDF 失败不影响签到），不是事务方法；同样写法放进事务方法会让回滚失效。
- **反例 3：业务写与日志不同事务**。`smart-server-wms3/src/main/java/com/track/wms/service/impl/InfoServiceImpl.java:873-875` 明确写「saveInfo 没有 `@Transactional`，`record()` 又是 `@Async`，两者不保证原子」。
- **反例 4：事务内异步**。`smart-server-wms3/src/main/java/com/track/wms/service/impl/UserServiceImpl.java:393` 把操作日志改成同步写入，原因就是「不用 `@Async` recorder，解决 `@Transactional` 内被吞问题」。
- **边界**：`readOnly = true` 只在 `smart-server-wms3/src/main/java/com/track/wms/service/impl/TrailerDemandServiceImpl.java:83`、`:105` 的查询上用，没有写操作验证。
- **边界**：`@Transactional` 与 `@Async` 同方法没做过；不确定线程池拒绝时异常去哪。

## 深层原理

- **`@Transactional` 的本质是代理 + 连接绑定**：Spring 给 Bean 生成代理，代理在方法前后向 `DataSourceTransactionManager` 要连接、关自动提交、把连接绑定到当前线程（`TransactionSynchronizationManager`）；业务代码里的 `DataSourceUtils.getConnection()` 拿到同一个连接。代理没经过（自调用/private/final/非 Spring Bean），或换了数据源/线程，绑定就断。
- **传播级别决定「加入还是新建」**：`REQUIRED` 加入当前事务；`REQUIRES_NEW` 挂起当前事务、从连接池另取连接；`NESTED` 在当前连接上开保存点。`afterCommit` 时外层事务已提交但连接可能还没归还，`REQUIRED` 会误判「已有事务」，所以回调写库必须 `REQUIRES_NEW`。
- **回滚规则是异常类型 + 是否抛出**：默认只回滚 `RuntimeException`/`Error`；checked exception 要 `rollbackFor`；catch 后不回抛，代理看不到异常，不会回滚。`readOnly` 只是给驱动/ORM 的提示，不是写保护。
- **异步/跨线程不传播事务**：`@Async` 在新线程执行，事务上下文（ThreadLocal）不会过去；事务里提交异步任务，异步线程看到的是另一个连接/事务。要「提交后再做」用 `afterCommit`，要「一起回滚」就不要异步。

## 现在的规矩

- 事务方法只放在经代理的 public 入口；private/同类调用一律 `TransactionTemplate` 或拆 bean。
- 业务写方法默认 `rollbackFor = Exception.class`。
- 提交后副作用走 `afterCommit`；回调里写库用 `REQUIRES_NEW`，且不篡改共享 `TransactionTemplate` 的传播级别。
- 邮件/S3/PDF/HTTP 不放进业务事务。
- 事务验证要么真库 E2E，要么明确标注「只有注解断言」，不混写。
