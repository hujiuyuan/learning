# 敏感字段揭示

技能点：[[PII加密]] · 通用技能：[[安全与审计]]

**一句话**：详情接口永远只给掩码；要看明文走单次揭示——事由必填、字段白名单、一次访问一行留痕、解密与留痕同事务，响应只带 30 秒清屏时限，服务端不留第二份。

## 方法总纲

1. **两条路分开**：整批明文走导出（全量模式 + `pii_reveal` 能力 + `audit_log` 的导出行）；一屏之内展开一格走单次揭示（`sensitive_access_log`）。详情读永远不给明文。
2. **能力独立**：`pii_reveal` 与 `read` 分开——能看掩码不等于能看明文；调用方（member）再叠自己的 `member.pii.reveal`。
3. **事由必填**：`reason` 为空一律拒写——既不返回明文，也不落留痕。
4. **字段白名单**：一次只展开请求列出的那几格（证件号、手机、电邮），不多给；不在白名单的字段直接拒绝。
5. **一次访问一行**：同一个人连续展开两次就是两条留痕，各填各的事由，不按人按天合并。
6. **同事务**：解密与写留痕在同一个本地事务；写留痕失败就整次展开失败，不允许「明文给出去、留痕没落上」。
7. **不留第二份**：明文只在这一次响应里存在，不缓存、不落库、不回写；响应带 `expireSeconds=30`，调用方到期/关页/切人立即清除。
8. **留痕去对表**：读取明文记 `sensitive_access_log`（动作 `view` + 字段子表）；`audit_log` 只记「谁改了什么」。

## 判断顺序

- **这次是整批还是单格**：整批走导出与导出审计；单格走揭示与访问留痕。两条路都要落痕，落的地方不同。
- **调用方有没有这一档能力**：`pii_reveal` 与 `read` 分开判；没有就拒绝，不靠前端隐藏按钮。
- **事由有没有**：空值拒绝，不能默认「业务查询」。
- **字段在不在白名单**：只解密请求列出的字段，按字段逐条落留痕子表。
- **留痕和明文是不是一个事务**：不是就改成一个；写留痕失败必须让整次展开失败。
- **明文会不会被留住**：服务端只给响应和显示窗口，缓存责任在调用方；不能把明文写进日志或数据库。

## 反例

- **详情接口返回明文**：最容易被日志、前端缓存、截图带出去；详情只给掩码。
- **先返回明文、异步补留痕**：留痕失败时明文已经出去了，无法追责。
- **留痕失败仍返回明文**：等于把审计变成可选项。
- **按人按天合并留痕**：同一天多次展开只记一条，取证时说不清哪次看了什么。
- **把单格展开记进 `audit_log`**：`audit_log` 记变更，读取明文归 `sensitive_access_log`，两张表的读面不同。
- **前端缓存明文超过显示窗口**：服务端无法替前端清屏，但响应必须给出明确的到期秒数，不能由调用方猜。

## 边界

- 只覆盖证件号、手机、电邮三种字段；`snapshot=request` 只能展开在途更正申请里的证件号新值。
- 已匿名化的档案不再展开。
- 服务端只给显示窗口，不控制前端是否按时清屏；前端行为没有服务端验证。
- 只做过 member → archive 这条链路；其他服务没有接入单次揭示。
