# PII加密

所属通用技能：[[安全与审计]]

**一句话**：用 AES-256-GCM 做字段级信封加密，用 HMAC 哈希列保留精确查重，用启动体检把密钥错误挡在第一批数据之前。

## 方法总纲

1. **先分级，再加密**：加密列不能模糊搜索、排序、范围查询。只给「合规要求高 + 只需要精确查重」的字段上加密（L1 证件号）。
2. **加密**：每条数据一把 DEK；AES-256-GCM；12 字节随机 IV；128 位认证标签；密文按 `[IV][密文][TAG]` 拼。
3. **信封**：DEK 用 KEK 包裹，版本串随密文一起存；解包时版本不符直接失败，不回退。
4. **查重**：另建 HMAC-SHA256 哈希列（类型码|国籍|归一化号码），pepper 按版本取。
5. **展示**：掩码落列或模板化生成；审计只放 `{mask, ref}`。
6. **启动体检**：环境名、公开测试密钥指纹、包裹解包自检，一个不过就启动失败。

## 我会的部分

- **AES-GCM 参数**：IV 12 字节（NIST SP 800-38D 推荐）、TAG 128 位（上限）、密钥必须正好 32 字节（`PiiCipher.java:17-23,99-104`）。
- **IV 每次现取随机数**：同一明文两次密文必须不同；GCM 复用 IV 能异或出明文差（`PiiCipher.java:50-51`，测试 `PiiCipherTest.java:29-37`）。
- **Cipher 复用**：`Cipher.getInstance()` 比一次加解密还贵，且 Cipher 非线程安全，所以按线程各留一份 ThreadLocal（`PiiCipher.java:26-32`）。
- **错误分类**：密文太短、密钥长度错、解密失败都抛带错误码的 SystemException，不吞成裸异常（`PiiCipher.java:78-88`，测试 `PiiCipherTest.java:40-100`）。
- **信封加密**：每条记录 `newDek()` → `wrapDek()` → 存 `[magic][版本][包裹的 DEK][密文]`；解密先按版本解包，再解业务密文（`IdNoVault.java:18-29`）。
- **文件密钥**：properties 里读 `kek` 与 `pepper.N`；主代码只放公开测试密钥的 SHA-256 指纹，不放密钥本身（`FileKeyProvider.java:24-25,40-66`）。
- **版本不回退**：`unwrapDek` 版本对不上直接抛，不用当前 KEK 重试，否则「密钥配错」会被掩盖成一次成功解密（`FileKeyProvider.java:84-92`）。
- **启动体检**：BeanPostProcessor 对每个 KeyProvider 逐个查，SmartInitializingSingleton 把懒加载的也取出来查；预发/生产挂公开测试密钥直接拒绝启动（`KeyProviderGuard.java:29,47-63,78-95`）。
- **密钥缺失即拒绝**：`KeyProvider` 不在就抛错，绝不回落到明文（`IdNoVault.java:15-16`）。

## 选型与取舍

### 为什么在应用层做字段级信封加密

| 方案 | 防谁 | 代价 | 项目里的位置 |
| --- | --- | --- | --- |
| TDE/磁盘加密 | 偷磁盘/备份文件的人 | 数据库进程和 DBA 看到的仍是明文；挡不住 SQL 注入/越权查询 | 未单独用 |
| 数据库列加密（pgcrypto 等） | 拿到表数据的人 | 密钥在数据库/连接里；模糊搜索、掩码、应用层密钥轮换都受限 | 未选 |
| 应用层信封加密（当前） | 拿到库/备份但拿不到 KEK 的人；DBA 也看不到明文 | 应用要管 DEK/KEK、版本、哈希列、掩码列；加密列不能模糊/范围查 | 选定 |
| 令牌化（Tokenization） | 原值完全不落业务库 | 多一套令牌服务；查询/展示都要回查 | 未选 |

选应用层是因为威胁模型包含「库被拖、备份泄露、DBA 越权」：TDE 只保护静态文件，数据库进程仍有明文；应用层加密让密文离开应用就是不可读。代价是查询能力下降，所以只给「只需要精确查重」的 L1 证件号加密，手机号/邮箱按 ADR-0009 明文，不搞「全库加密」。

### 为什么 AES-GCM + 随机 IV + HMAC 哈希列

- GCM 是 AEAD，一次完成加密和完整性校验；随机 IV 保证同一明文每次密文不同，防模式分析。代价是密文不可比较，不能当等值键。
- 需要精确查重就另建 HMAC-SHA256 哈希列（类型码|国籍|归一化号码 + pepper）；HMAC 而不是裸 SHA，防彩虹表；pepper 按版本取，版本随密文存。
- 不用确定性加密（同一明文同一密文）做查重：它会泄露频率分布，攻击者能做频率分析；HMAC 列只暴露「是否相等」，不暴露密文模式。

### 为什么现在用文件 KeyProvider，不上 KMS

文件 KeyProvider 让密钥不跟密文同库，启动体检能挡住「预发/生产挂公开测试密钥」；KMS 没接是因为当前没有 KMS 可用性和轮换流程。代价是密钥文件要自己保护、轮换要自己做、KMS 不可用时没有缓存降级。

### 代价与反悔条件

- 加密列不支持模糊搜索、排序、范围查询；要支持就得上可搜索加密/令牌化/独立搜索索引，成本和泄露面都变大。
- 每次读 L1 都要解密，列表页必须取掩码列；没做过性能压测。
- 没做 KEK/DEK 轮换演练；只有版本字段和「错版本失败」。
- 如果合规要求覆盖手机号/邮箱 → 扩分级和加密列，先评估查询需求；如果接入 KMS → 换 KeyProvider，保留 `KeyProviderGuard` 和版本语义；如果需要范围/模糊查询 → 不要硬加密，改令牌化/搜索索引。

## 边界

- 只实现了 `file` 一种 KeyProvider；KMS/Secret Manager 未接（`PiiCryptoConfig.java:39-60`）。
- 没做 KEK/DEK 轮换流程和演练；只有版本字段与「错版本失败」。
- 没做密钥使用审计、访问计数、KMS 不可用时的缓存降级。
- 只覆盖 L1 证件号；手机号/邮箱按 ADR-0009 明文（设计输入），不在实战范围。
- 没做过性能压测；每次读取 L1 都要解密，列表页应取掩码列。
- 加密列不支持模糊搜索、排序、范围查询；可搜索加密没做过。
