## 1. 安全模型与威胁建模

**一句话**：安全目标是机密性、完整性、可用性；威胁建模先列资产、入口、攻击者能力，再定防护和残余风险。

要能回答：

- CIA 三要素分别指什么？和业务风险怎么对应？
- STRIDE 六类威胁分别是什么？
- 攻击面怎么枚举？信任边界画在哪？
- 认证、授权、加密、审计分别在防什么？
- 纵深防御和最小权限怎么落到系统设计？

笔记：

- CIA：机密性（不该看的看不到，靠加密/权限）、完整性（不该改的改不了，靠签名/校验/事务）、可用性（该用的用得上，靠限流/冗余/备份）。业务风险按「泄露、篡改、停服」三类对应。
- STRIDE：Spoofing 冒充（认证）、Tampering 篡改（完整性校验）、Repudiation 抵赖（审计）、Information disclosure 泄露（加密/权限）、Denial of service 拒绝服务（限流/容量）、Elevation of privilege 提权（授权）。
- 攻击面枚举：所有入口（HTTP、消息、定时任务、文件上传、管理后台、第三方回调）+ 所有信任边界（浏览器→网关、网关→服务、服务→DB、服务→第三方）。跨边界的数据都要校验和鉴权。
- 认证证明「你是谁」，授权决定「你能干什么」，加密保护「传输/存储中的内容」，审计记录「你干了什么」。四者不能互相替代：有认证不等于有授权，有加密不等于有审计。
- 纵深防御：网关鉴权 + 服务内方法级鉴权 + 数据层租户过滤 + 审计；一层被绕过还有下一层。最小权限：服务账号只给需要的库/表/操作，用户只给需要的功能，密钥只给需要的服务。

## 2. 加密与哈希

**一句话**：加密可逆、哈希不可逆；对称加密快、非对称加密适合密钥交换和签名；AES-GCM 同时提供机密性和完整性。

要能回答：

- 对称加密和非对称加密的区别？各自典型算法？
- AES 的 CBC、GCM 模式有什么区别？为什么推荐 GCM？
- IV/Nonce 为什么不能重复？重复会泄露什么？
- 哈希、加盐哈希、HMAC 分别用在哪？
- 数字签名和加密的区别？
- 信封加密（DEK/KEK）解决什么问题？

关联：[[PII加密]]

笔记：

- 对称加密（AES、ChaCha20）加解密同一把钥匙，快，适合大量数据；非对称（RSA、ECC）公钥加密私钥解密、私钥签名公钥验签，慢，适合密钥交换和签名。
- CBC 需要填充、逐块链式，IV 错误会连带影响后续块，且不提供完整性；GCM 是 AEAD，一次完成加密 + 认证，能发现篡改，推荐新系统用 GCM。GCM 的 nonce 绝不能在同一密钥下重复，重复会泄露明文异或并可能被伪造。
- 哈希（SHA-256）用于完整性/指纹；密码存储用加盐慢哈希（bcrypt/scrypt/Argon2），不能直接用 SHA；HMAC 是带密钥的哈希，用于消息认证和「加密字段的盲索引」。
- 数字签名用私钥签、公钥验，证明「谁发的、没被改」；加密用公钥加密、私钥解密，保护内容。签名不保密，加密不证明身份。
- 信封加密：每条数据用随机 DEK 加密，DEK 再用 KMS 里的 KEK 加密后随密文存；轮换只需换 KEK 重新包 DEK，不用重加密全部数据。DEK 泄露影响单条，KEK 不出 KMS。

## 3. 密钥管理

**一句话**：密钥不能硬编码在代码或配置里；要用 KMS、密钥库或环境注入，并支持轮换、版本和访问审计。

要能回答：

- 密钥应该存在哪？环境变量、配置文件、KMS、HSM 各有什么风险？
- 密钥轮换怎么做？旧数据怎么解密？
- 密钥版本和密文版本怎么关联？
- 谁能访问密钥？怎么审计？
- 密钥泄露后的应急流程？
- 开发、测试、生产环境密钥怎么隔离？

关联：[[PII加密落地]]

笔记：

- 环境变量：进程可见，dump/日志/子进程可能带出；配置文件：容易进仓库、进镜像；KMS：访问受 IAM 控制、有审计、可轮换，但依赖网络和云；HSM：硬件防导出，成本最高。生产密钥优先 KMS/HSM，至少不进代码和镜像。
- 轮换：新密钥加密新数据，密文头带密钥版本，解密按版本取旧密钥；旧密钥保留到所有旧密文过期/重加密完成，再禁用、删除。
- 密钥版本必须和密文绑定（密文格式 `version + nonce + ciphertext + tag`），否则轮换后无法判断用哪把钥匙。
- 访问控制：按服务/环境授权，最小权限；KMS 的每次解密都有审计日志；应用侧记录「谁在什么时候解了什么」。
- 泄露应急：立即禁用/轮换密钥、评估影响范围（哪些密文、哪些日志）、重加密、通知、复盘；不能只换密钥不查泄露路径。
- 环境隔离：开发/测试/生产用不同密钥和不同 KMS 权限；测试数据不能用生产密钥加密；本地开发用假密钥或 mock KMS，不能把生产凭证发给开发机。

## 4. 敏感数据与 PII

**一句话**：PII 要先分类分级，再决定加密、脱敏、访问控制和保留期限；不是所有字段都值得加密。

要能回答：

- 什么是 PII？哪些字段属于敏感数据？
- 加密、脱敏、掩码、令牌化分别适合什么场景？
- 加密后的字段还能查重、搜索、排序吗？怎么做？
- 日志、错误信息、导出文件里怎么防泄露？
- 数据保留期限和删除权怎么实现？
- 测试数据怎么脱敏？

关联：[[PII加密]]、[[PII加密落地]]、[[加密与查重]]

笔记：

- PII 是可识别到自然人的信息：姓名、手机、身份证、邮箱、地址、银行卡、生物特征，以及能间接识别的组合（生日 + 邮编 + 性别）。先分类分级（公开/内部/敏感/高敏），再定措施。
- 加密可逆、适合需要还原的场景；脱敏/掩码不可逆或部分隐藏，适合展示和日志；令牌化用无意义 token 替换原值，原值存独立 vault，适合支付卡等强监管数据。
- 加密字段不能直接 `LIKE`/范围查询/排序；查重和等值查询用「盲索引」——对规范化后的值做 HMAC，存哈希列并建索引；范围查询只能另存可分桶的派生列或放弃。
- 日志、错误信息、导出文件是最常见的泄露点：统一脱敏器、禁止打印请求体/响应体原文、异常信息不回传敏感字段、导出走审批和水印。
- 保留期限：按法规/业务定 TTL，到期删除或匿名化；删除权要覆盖主表、从表、备份、日志、导出文件，并留下删除审计。
- 测试数据脱敏：生产数据不直接进测试；用生成器造数据，或对生产数据做不可逆脱敏（替换/泛化/打乱）后再用；测试环境也按敏感数据管理。

## 5. OWASP 与常见漏洞

**一句话**：注入、失效的访问控制、加密失败、SSRF、XSS、CSRF、反序列化、依赖漏洞是最常见的 Web 风险；防护要落在框架和流程里。

要能回答：

- OWASP Top 10 最新版有哪些类别？
- SQL 注入、命令注入、SSRF 分别怎么防？
- 越权（IDOR）怎么产生？怎么测？
- XSS 的存储型、反射型、DOM 型区别？
- CSRF 和 SameSite 的关系？
- 反序列化漏洞怎么产生？怎么避免？
- 依赖漏洞怎么扫描和升级？

笔记：

- OWASP Top 10（2021）：失效的访问控制、加密失败、注入、不安全设计、安全配置错误、易受攻击的组件、认证失败、软件和数据完整性失败、日志与监控失败、SSRF。
- SQL 注入用参数化查询/预编译，不拼字符串；命令注入避免 shell，用参数数组 + 白名单；SSRF 对目标 URL 做协议/域名/IP 白名单，禁止访问内网和云元数据地址。
- 越权（IDOR）是「只校验登录、不校验归属」：改 URL 里的 id 就能看别人的数据。测法是换账号/换租户改 id；防法是服务端按当前用户/租户过滤，不信任前端传的归属字段。
- XSS：存储型（恶意内容入库）、反射型（URL 参数回显）、DOM 型（前端 JS 拼接）。防法是输出编码 + CSP + 富文本白名单，不靠输入过滤。
- CSRF 利用浏览器自动带 cookie：防法是 CSRF token + SameSite cookie + 关键操作二次确认；纯 token 认证的 API 风险较低。
- 反序列化漏洞来自「把不可信数据还原成对象并触发方法」：避免原生反序列化不可信数据，用 JSON + 类白名单，升级有漏洞的库。
- 依赖漏洞用 SCA 工具（Dependabot/Renovate/OWASP Dependency-Check）持续扫描，按严重级别和可达性升级；不能只看「有没有告警」，要看是否真的被调用。

## 6. 审计日志

**一句话**：审计日志记录「谁在什么时候对什么做了什么、结果如何」；要防篡改、可追溯、可检索，并按规定保留。

要能回答：

- 审计日志和普通业务日志的区别？
- 必须记录哪些字段？操作前后值要不要记？
- 日志防篡改有哪些手段？哈希链、只追加、独立存储？
- 审计日志写失败要不要影响业务？同步写还是异步写？
- 审计日志怎么查询和归档？保留多久？
- 代登录、平台管理员操作怎么记？
- 审计日志里能不能存 PII？

关联：[[审计日志]]、[[审计归档]]

笔记：

- 审计日志回答「谁、何时、从哪、对什么、做了什么、结果如何」，用于追责和合规；业务日志用于排查和监控。两者目的不同，不能互相替代。
- 必记字段：操作者（用户/服务/代登录来源）、时间、来源 IP/设备、操作类型、目标对象（类型 + id）、结果（成功/失败/错误码）、请求标识。敏感操作记变更前后值，但要脱敏。
- 防篡改：只追加、独立存储/独立账号、哈希链（每条带前一条哈希）、定期锚定；应用账号不能改/删审计表。
- 写失败：合规要求高的操作应「审计失败则业务失败」（同事务或强一致）；一般操作可异步 + 本地落盘兜底，但不能静默丢。同步写增加延迟，异步有丢失窗口。
- 查询与归档：按时间/操作者/对象建索引，热数据在线查、冷数据归档到对象存储；保留期限按法规/合同，到期不可恢复删除。
- 代登录/平台管理员：必须记「实际操作者 + 被代操作者 + 授权来源」，否则追责时只剩被代账号。
- 审计日志里尽量不存完整 PII：存 id + 脱敏值；确需存原值时要加密并限制访问，否则审计库本身成了泄露源。

## 7. 安全开发流程

**一句话**：安全不是上线前扫一次，而是需求、设计、编码、测试、部署、运营每个阶段都有检查点。

要能回答：

- 威胁建模应该在什么阶段做？
- 代码审计、SAST、DAST、依赖扫描分别查什么？
- 渗透测试和漏洞扫描的区别？
- 漏洞分级和修复 SLA 怎么定？
- 安全配置基线包括哪些？
- 事件响应流程是什么？

笔记：

- 威胁建模在设计阶段做：画数据流、标信任边界、按 STRIDE 列威胁、定缓解措施和残余风险；越晚发现，修复越贵。
- SAST 扫源码（注入、硬编码密钥、危险 API），不用运行；DAST 扫运行中的应用（URL、表单、认证后的接口）；依赖扫描看第三方库；三者覆盖不同层，不能互相替代。
- 渗透测试是人工模拟攻击，能发现逻辑漏洞（越权、业务绕过）；漏洞扫描是工具按规则跑，覆盖广但浅。上线前/重大变更做渗透，日常做扫描。
- 漏洞分级按「可利用性 × 影响」：严重（可直接拿数据/提权）立即修，高危限期，中低危排期；SLA 要写进流程并有例外审批。
- 安全配置基线：最小端口/账号、关闭默认口令、TLS 配置、CSP/安全头、日志脱敏、备份加密、依赖版本；用配置扫描持续核对。
- 事件响应：发现 → 分级 → 遏制（隔离/禁用）→ 取证 → 修复 → 恢复 → 复盘；提前准备联系人、凭证轮换、对外沟通模板。
