# 登录态与踢线

技能点：[[Spring Security]] · 方法：[[keyVer踢线校验]] · 通用技能：[[认证与授权]]

**什么时候会遇到**：同一账号多设备登录、改密、禁用、删除、租户停用、代登录，前端突然收到「登录已失效 / 账号已在别处登录 / 密码已重置」。

## 判断顺序

1. **先分端**：keyVer、单端 refresh 槽、踢线原因三个键都带 `loginSys`；WMS 与 PDA 各自独立，先确认是哪一端。
2. **再看 keyVer**：token 里的 `keyVer` 与 Redis `user:key:{userId}:{loginSys}` 比对；不一致时读 `user:kick:reason:{userId}:{loginSys}`，有原因按原因返回，没有原因返回 `KEY_VER_MISMATCH`。
3. **看单端登录槽**：Redis `login:refresh:{userId}:{loginSys}` 存当前 refresh jti；token 的 `rjti` 不等时，再看 60 秒轮换宽限指针，仍不等才判 `KICKED_OUT`。
4. **看账号状态**：Redis 状态缓存优先，缺失或异常回查 DB；账号禁用、软删直接拒绝。租户停用或删除走 `kickAllByTenant` 撤销 keyVer，最终仍表现为 keyVer 失配加 `TENANT_*` 原因。
5. **看代登录**：token 带 `actorUserId` 时，effective user 的 keyVer 和 actor 的 keyVer 都要过；actor 不匹配直接拒。

## 手段

- **登录踢同端旧会话**：登录时 bump 该端 keyVer，并写 `OTHER_DEVICE`。证据：`smart-server-wms3/src/main/java/com/track/wms/service/impl/AuthServiceImpl.java:116-117`、`smart-server-wms3/src/main/java/com/track/wms/service/impl/UserServiceImpl.java:681-683`
- **改密踢本人**：bump 全端 keyVer + 清本人 refresh，写 `PASSWORD_RESET`；不删代登录该账号的管理员会话。证据：`smart-server-wms3/src/main/java/com/track/wms/service/impl/UserServiceImpl.java:290-303`
- **禁用/删除**：`atomicDel` 删除各端 keyVer + 清 refresh + 写 `ACCT_DISABLED`/`ACCT_DELETED`，并踢掉正在 impersonate 该账号的管理员。证据：`smart-server-wms3/src/main/java/com/track/wms/service/impl/UserServiceImpl.java:239-241`、`smart-server-wms3/src/main/java/com/track/wms/service/impl/UserServiceImpl.java:908-940`
- **刷新续期**：刷新时重读 keyVer、滑动续期 keyVer TTL，避免活跃用户因 keyVer 过期被误踢。证据：`smart-server-wms3/src/main/java/com/track/wms/service/impl/AuthServiceImpl.java:311-325`
- **代登录**：actor keyVer 严格比对，Redis 异常时拒绝；被扮演者只有撤销类原因才踢管理员。证据：`smart-server-wms3/src/main/java/com/track/wms/config/JwtSecurityFilter.java:218-259`、`smart-server-wms3/src/main/java/com/track/wms/common/enums/KickReasonEnum.java:37-42`

## 反例 / 边界

- **只删 refresh 槽不够**：access token 仍然有效；必须 bump keyVer 才能让已签发的 access token 立刻失效。
- **只 bump keyVer 不写 reason**：前端只能提示「登录失效」，说不出「被禁用」还是「别处登录」；原因键的 TTL 是 access TTL + 60 秒。
- **Redis 不可用时降级放过**：keyVer 和单端校验 catch 异常后放行，靠 DB 状态兜底；这不是强一致，Redis 故障期间撤销会延迟。
- **`0 == 0` 视为匹配**：被代登录账号从没登录过或 keyVer 缓存丢失时是 0；真正的禁用/删除靠 `atomicDel + reason` 捕获，DB 状态再兜底。
- **代登录不抢单端槽**：impersonate token 不做 `LOGIN_REFRESH` 比对，否则会拿 target 的槽去判 admin 的会话。
- **轮换宽限不等于不踢**：只放过「上一代 jti」，改密或禁用后的旧 jti 即使在宽限窗口内也照踢。

## 现在的规矩

- 新增踢线场景必须同时做三件事：bump 对应端 keyVer、写 kick reason、清 refresh 槽；只做一件都会留下漏洞或错误提示。
- 每端独立，不要把 WMS 的 keyVer 用到 PDA。
- 代登录失效按 actor 判定：actor 被禁、被删、重新登录 → imp token 立即失效；target 本人重登或改密 → 不踢管理员。
- 过滤器的 Redis 降级策略要显式写明：哪些校验 fail-open、哪些 fail-closed。
