## 1. 认证与授权

**一句话**：认证回答「你是谁」，授权回答「你能做什么」；认证失败是 401，授权失败是 403。

要能回答：

- 认证和授权的边界在哪？为什么不能把授权判断交给前端？
- 401 和 403 分别对应什么场景？客户端应该怎么处理？
- 身份认证、会话管理、权限判断三者的先后顺序？

关联：[[认证与授权]]

笔记：

- 认证证明「你是谁」，授权决定「你能做什么」。前端的按钮隐藏/菜单过滤只是体验，真正的授权必须在服务端每个入口执行；前端可见性不能当安全边界。
- 401 是「没认证/凭证无效」：没登录、token 过期、签名不对。客户端应跳登录或刷新 token。403 是「认证了但没权限」：角色/数据范围不够，重试没用，应提示无权限。
- 顺序：先认证（解析凭证、验签、查会话/版本）→ 建身份上下文 → 再对本次请求做授权（接口权限 + 数据范围）→ 最后执行业务。授权放在业务查询里，不能只放网关。
- 网关鉴权只管「能不能进这个服务」，服务内还要做方法级/数据级鉴权；否则内网调用、消息消费、定时任务都绕过了网关。
- 认证失败和授权失败的响应要区分，但不要泄露「用户是否存在」「角色是什么」这类枚举信息。

## 2. 会话与令牌

**一句话**：Session 把状态放服务端，靠 Cookie 引用；JWT 把身份签进令牌，服务端无状态，但签发后不能自然失效。

要能回答：

- Cookie/Session 和 Token 各自的优缺点？分布式部署时各有什么问题？
- JWT 由哪三段组成？签名解决了什么，没解决什么？
- `exp`、`iat`、`nbf`、`aud`、`iss` 分别是什么？
- JWT 如何撤销？黑名单、短过期 + 刷新令牌、版本号各自代价是什么？
- Token 放 Cookie、localStorage、内存分别有什么风险？

关联：[[keyVer踢线校验]]、[[登录态与踢线]]

笔记：

- Session 状态在服务端，Cookie 只带 sessionId；分布式部署要共享存储（Redis）或粘性会话，否则换实例就掉登录。JWT 把身份签进令牌，服务端无状态、易横向扩展，但签发后在过期前一直有效。
- JWT 三段：header（算法）、payload（claims）、signature（对前两段的签名）。签名保证内容没被改、来源可信，不保证内容保密（payload 只是 Base64），也不解决撤销和重放。
- `exp` 过期时间、`iat` 签发时间、`nbf` 生效时间、`aud` 受众、`iss` 签发者；校验时要验签名、`exp/nbf`、`iss/aud`，不能只解析 payload。
- 撤销：黑名单（要存储和查询，失去无状态优势）、短过期 + refresh token（撤销窗口小，但要管刷新令牌）、版本号/keyVer（用户表存版本，token 带版本，改密/踢线时版本 +1，校验时比对）。
- 存放：Cookie 加 `HttpOnly + Secure + SameSite` 能防 JS 读取和部分 CSRF，但要防 CSRF；localStorage 易被 XSS 读取；内存最安全但刷新丢失。没有零风险，按威胁模型选。
- 单端登录/踢线本质是「服务端能失效令牌」：keyVer 或会话表，登录时比对版本，旧令牌全部失效。

## 3. 密码与凭证

**一句话**：密码只能哈希不能加密；用带盐、可调成本的算法（bcrypt/Argon2），不要用 MD5/SHA 直接存。

要能回答：

- 哈希、加密、编码的区别？
- 为什么 bcrypt 要存盐和成本因子？彩虹表怎么防？
- 撞库、暴力破解、 credential stuffing 分别怎么防？
- 多因素认证（MFA）有哪几类因子？
- 密码重置令牌应该怎么生成、存哪、多久过期？

笔记：

- 哈希是单向摘要，加密可逆，编码只是表示转换（Base64 不是加密）。密码只能哈希，不能加密或编码存储。
- bcrypt/Argon2 为每个密码生成随机盐并存进结果字符串，盐防彩虹表（预计算哈希表），成本因子让暴力破解变慢；校验时从存储值里取盐和参数重算。
- 撞库是「别的站泄露的账号密码拿来试」，靠 MFA、异常登录检测、泄露密码库比对；暴力破解靠限流、锁定、验证码、慢哈希；credential stuffing 本质是撞库的自动化版本。
- MFA 三类因子：知道什么（密码/PIN）、拥有什么（TOTP/硬件密钥/手机）、是什么（指纹/人脸）。MFA 不能防钓鱼，FIDO2/WebAuthn 能。
- 重置令牌：高熵随机值（≥128 bit），只存哈希，单次使用，短 TTL（15–60 分钟），绑定用户，使用后失效并踢掉旧会话；不能把用户 id/邮箱直接编码进令牌。
- 密码策略：长度优先于复杂度，检查常见弱密码，不在前端做「强度提示」当唯一防线。

## 4. 授权模型

**一句话**：RBAC 按角色授权，ABAC 按属性判断，ReBAC 按关系判断；业务系统常用 RBAC 打底，数据范围用属性过滤补。

要能回答：

- RBAC、ABAC、ReBAC 的区别和适用场景？
- 角色、权限、资源、动作、主体分别是什么？
- 「能用」和「能授」为什么要拆开？
- 最小权限、默认拒绝、职责分离分别怎么落地？
- 数据级权限和接口级权限有什么区别？只做接口级会漏什么？

关联：[[RBAC权限模型]]、[[权限模型]]

笔记：

- RBAC：用户→角色→权限，权限是「资源 + 动作」；简单、易管理，适合功能权限。ABAC：按主体/资源/环境属性判断（部门、密级、时间、IP），灵活但规则难维护。ReBAC：按关系图判断（文档 owner、团队 parent），适合协作/层级资源。
- 角色、权限、资源、动作、主体：主体（用户/服务）拥有角色，角色绑定权限，权限描述「对什么资源做什么动作」；资源要稳定标识，动作要可枚举。
- 「能用」和「能授」拆开：能使用某功能不等于能把该权限授予别人；授权利是独立权限，否则普通管理员可以给自己/别人提权。
- 最小权限：默认拒绝，按需授权，权限有期限；职责分离：高危操作（创建角色 + 分配权限、付款 + 审批）不能由同一人完成。
- 接口级权限只控制「能不能调这个接口」，不控制「能看哪些行/字段」；只做接口级会漏 IDOR/数据范围越权——同一接口换 id 就能看别人数据。
- 数据级权限要在查询条件里落实（租户、部门、owner、数据范围），不能查出来再在内存过滤；后者容易在分页/导出/统计里漏。

## 5. Web 攻击面

**一句话**：认证系统要同时防 CSRF、XSS、会话固定、开放重定向和令牌泄露；无状态 JWT 不等于自动安全。

要能回答：

- CSRF 的攻击过程？SameSite、CSRF Token、双重提交 Cookie 分别怎么防？
- XSS 如何窃取 Token？HttpOnly 能防住哪些、防不住哪些？
- 会话固定攻击是什么？登录后为什么要换 Session ID？
- 开放重定向和 OAuth 回调地址校验有什么关系？
- CORS 配置错误会带来什么后果？

笔记：

- CSRF：用户已登录站点 A，访问恶意站点 B，B 自动向 A 发请求，浏览器自动带 A 的 Cookie。防法：SameSite=Lax/Strict（现代浏览器默认 Lax）、CSRF Token（服务端校验）、双重提交 Cookie（Cookie 和请求体/头里的 token 一致）。
- XSS 能读 localStorage 里的 token，也能以用户身份发请求；HttpOnly 只防「JS 读 Cookie」，防不了「在页面里代用户操作」。XSS 的根本防线是输出编码 + CSP + 富文本白名单。
- 会话固定：攻击者先拿到一个 sessionId，诱导受害者用它登录；登录后不换 id，攻击者就共享了会话。登录成功必须换新 sessionId。
- 开放重定向：登录后 `redirect` 参数可跳到任意站，常被用于钓鱼/OAuth 授权码窃取；回跳地址必须白名单校验。OAuth 的 `redirect_uri` 必须精确匹配注册值。
- CORS 错误：`Access-Control-Allow-Origin: *` 配合 `credentials` 无效；动态反射任意 Origin + 允许凭证，等于让任何站点读用户数据。只允许可信源，按需暴露方法/头。

## 6. 标准协议

**一句话**：OAuth2 是授权框架，OIDC 在其上补了身份层；SSO 是企业内多系统共享登录态的统称。

要能回答：

- OAuth2 的四种授权模式分别适合什么客户端？
- 授权码模式为什么需要 PKCE？
- access token、refresh token、id token 分别是什么？
- OIDC 的 `sub`、`iss`、`aud`、`nonce` 各起什么作用？
- SAML 和 OIDC 的区别？企业 SSO 通常怎么选？

笔记：

- OAuth2 四种模式：授权码（有后端的 Web 应用，最常用）、隐式（历史/SPA，已不推荐）、密码（受信任的第一方客户端，逐步淘汰）、客户端凭证（服务间无用户）。PKCE 是授权码模式的增强，防授权码被拦截。
- 授权码模式需要 PKCE：公共客户端（SPA/移动端）没有 client secret，授权码可能被截获；PKCE 用 code_verifier/code_challenge 绑定发起方。
- access token 访问资源，refresh token 换新 access token（长期、要保护、可撤销），id token 是 OIDC 的身份声明（JWT，给客户端读用户信息）。
- OIDC：`sub` 用户唯一标识（iss + sub 才全局唯一）、`iss` 签发者、`aud` 受众（必须包含 client_id）、`nonce` 防重放（绑定请求）。
- SAML 用 XML 断言，企业 IdP 生态成熟；OIDC 用 JSON/JWT，移动端/现代 Web 友好。企业 SSO 常按 IdP 能力选：传统企业多 SAML，新系统多 OIDC。
- SSO 本质是「多个系统共享一个 IdP 的登录态」，不是某个协议；同域可用共享 Cookie，跨域用 OIDC/SAML 跳转。

## 7. 多租户身份

**一句话**：租户身份必须进入令牌和每一次数据查询；平台账号（tenant=null）要走单独分支，不能靠前端传参决定看谁的数据。

要能回答：

- 租户 ID 应该放在 token、请求头还是 session？
- 平台账号和租户账号的权限边界怎么划？
- 代登录时，业务身份和真实操作人为什么要分开记录？
- 跨租户访问的漏洞通常出现在哪些入口？

关联：[[代登录实现]]、[[平台账号与NULL]]

笔记：

- 租户 ID 放签名 token（或服务端 session），由认证环节写入上下文；请求头可传但必须和 token 允许范围校验。绝不能由前端参数决定看哪个租户。
- 平台账号（tenant=NULL）和租户账号走不同分支：平台可跨租户但仅限平台入口，租户账号只能看自己租户；权限边界在服务端判断。
- 代登录要同时记「业务身份（被代账号）+ 真实操作人（平台账号）+ 租户」，审计以后者为准，否则出事查不到人。
- 跨租户漏洞高发入口：列表/详情（改 id）、导出（文件内容/路径）、缓存 key、异步任务、搜索、文件下载、日志查询、批量操作；这些路径常绕过主查询的租户过滤。
- 测试用「A 写 B 查」的反向用例覆盖每个入口；只测 A 能看到自己的数据，证明不了隔离。
