## 1. 时间的基本概念

**一句话**：时刻（instant）是绝对时间点，时区（zone）是展示规则，偏移（offset）是某时刻某地与时区的差；夏令时让偏移随日期变化。

要能回答：

- UTC、GMT、时区、偏移分别是什么？为什么有了 UTC 还要时区？
- 同一个 `LocalDateTime` 在不同时区代表同一时刻吗？
- 夏令时（DST）切换时，哪些本地时间不存在、哪些重复？
- 时间戳（epoch）有没有时区？单位秒和毫秒怎么区分？
- ISO 8601 里 `Z`、`+08:00`、`[Asia/Shanghai]` 各表示什么？

笔记：

- UTC 是世界时间标准；GMT 是英国所在时区，日常与 UTC 等值；时区是「地区 + 偏移规则 + 夏令时规则」；偏移是某时刻某地与 UTC 的差值，会随 DST 变化。
- `LocalDateTime` 只是墙钟读数，没有时区就不能确定时刻。`2026-01-01 09:00` 在北京和纽约是两个不同瞬间；必须配 `ZoneId` 才能转成 `Instant`。
- DST 春季拨快：本地时间有一段「不存在」（如 02:00–03:00 跳过）；秋季拨回：有一段「重复」（如 01:00–02:00 出现两次）。存在性/歧义只能靠时区规则判断。
- epoch 时间戳是「从 1970-01-01T00:00:00Z 起的秒/毫秒数」，本身没有时区；秒（10 位）和毫秒（13 位）要分清，混用会差 1000 倍。
- ISO 8601：`Z` 表示 UTC；`+08:00` 表示偏移；`[Asia/Shanghai]` 是时区 ID（Java `ZonedDateTime` 的格式），带 ID 才能正确处理 DST，只有偏移不够。

## 2. Java 时间 API

**一句话**：`Instant` 表示时刻，`LocalDateTime` 表示无时区的墙钟，`ZonedDateTime`/`OffsetDateTime` 带时区或偏移；业务里先选对类型。

要能回答：

- `Instant`、`LocalDateTime`、`LocalDate`、`ZonedDateTime`、`OffsetDateTime` 分别适合什么？
- `Date`、`Calendar` 有什么历史坑？为什么新代码不用？
- `ZoneId` 和 `ZoneOffset` 的区别？
- 时间加减、截断、比较用什么方法？为什么不要用 `==`？
- `Duration` 和 `Period` 的区别？

关联：[[UTC与业务时区]]

笔记：

- `Instant`：机器时刻（UTC），适合存储、比较、日志；`LocalDateTime`：无时区墙钟，适合「业务本地时间」的表单/规则；`LocalDate`：只有日期；`ZonedDateTime`：时刻 + 时区规则，适合跨时区展示/转换；`OffsetDateTime`：时刻 + 固定偏移，适合只关心偏移的协议/存储。
- `Date`/`Calendar` 可变、月份从 0 开始、`SimpleDateFormat` 非线程安全、默认时区隐式依赖；新代码用 `java.time`。
- `ZoneId` 是地区规则（含 DST，如 `America/New_York`），`ZoneOffset` 是固定偏移（如 `+08:00`）；用 `ZoneId` 才能正确处理夏令时。
- 加减用 `plusDays/plusHours`，截断用 `truncatedTo`，比较用 `isBefore/isAfter/compareTo`；`==` 比的是对象引用，不是时间值。`equals` 对 `ZonedDateTime` 还比时区，跨时区同一时刻可能不 equals，比较时刻用 `isEqual`/`Instant`。
- `Duration` 是时间量（秒/纳秒，适合「3 小时」），`Period` 是日期量（年/月/日，适合「3 个月」）；跨 DST 加 `Duration.ofDays(1)` 与 `Period.ofDays(1)` 结果可能不同。

## 3. 数据库时间类型

**一句话**：PostgreSQL 的 `timestamptz` 存时刻，`timestamp` 存墙钟；MySQL 的 `DATETIME` 不带时区，`TIMESTAMP` 受会话时区影响。

要能回答：

- PostgreSQL `timestamp` 和 `timestamptz` 的区别？底层怎么存？
- MySQL `DATETIME` 和 `TIMESTAMP` 的区别？2038 问题是什么？
- 数据库会话时区怎么影响读写？JDBC 连接参数怎么设？
- 为什么同一个值在不同客户端查出来不一样？
- 存 epoch 毫秒和存 `timestamptz` 各有什么利弊？

笔记：

- PostgreSQL `timestamp`（without time zone）存墙钟读数，不存偏移；`timestamptz` 存的是时刻，内部按 UTC 存，查询时按会话 `TimeZone` 显示。`timestamptz` 不是「带时区字符串」，而是「绝对时刻」。
- MySQL `DATETIME` 存墙钟、不受会话时区影响，范围 1000–9999；`TIMESTAMP` 存 UTC、读写按会话 `time_zone` 转换，范围到 2038（32 位秒）。2038 问题来自 `TIMESTAMP` 的存储上限。
- 会话时区影响 `TIMESTAMP`/`timestamptz` 的显示和写入解释；JDBC 用 `connectionTimeZone`（新驱动）/`serverTimezone`（旧）和 `preserveInstants` 控制转换。连接参数不统一，同一个值不同客户端查出来会不一样。
- 存 epoch 毫秒（bigint）：绝对、无歧义、跨库一致，但可读性差、失去数据库时间函数/索引范围查询的直观性；存 `timestamptz`：可读、可做时间运算，但要求所有连接会话时区一致。
- 选型：需要绝对时刻（创建/支付/日志）用 `timestamptz` 或 epoch；需要「当地营业时间」这类墙钟语义（每天 9 点开门）用 `timestamp`/`DATETIME` + 单独存时区 ID。

## 4. 序列化与反序列化

**一句话**：JSON 里推荐带偏移或 UTC 的 ISO 8601 字符串；Jackson 的时区配置、`@JsonFormat` 和全局 ObjectMapper 要统一。

要能回答：

- Jackson 默认怎么序列化 `Instant`、`LocalDateTime`、`Date`？
- `WRITE_DATES_AS_TIMESTAMPS` 打开和关闭有什么区别？
- `@JsonFormat(pattern=..., timezone=...)` 作用在哪一层？
- 反序列化时没带时区，Jackson 按什么补？
- 前后端约定用 UTC 还是本地时间？各有什么代价？

关联：[[InstantNyTypeHandler]]

笔记：

- Jackson 默认把 `Instant`/`Date` 写成 epoch 数字（`WRITE_DATES_AS_TIMESTAMPS` 默认开）；关掉后写 ISO 字符串。`LocalDateTime` 默认写 `yyyy-MM-dd'T'HH:mm:ss`，不带偏移。
- `WRITE_DATES_AS_TIMESTAMPS` 关闭：可读、跨语言清晰，但体积大、前端要解析 ISO；打开：紧凑、无歧义，但可读性差，调试不直观。
- `@JsonFormat(pattern=..., timezone=...)` 作用在字段/类型的序列化上；`timezone` 只对带时区的类型（`Date`、`ZonedDateTime`）生效，对 `LocalDateTime` 不会「补时区」。
- 反序列化没带偏移：`LocalDateTime` 保持墙钟；`Instant` 按 UTC 解释（Jackson 默认）；`ZonedDateTime` 需要 zone 信息，否则报错或按默认。全局 ObjectMapper 要统一配置，不能每个字段各写一套。
- 前后端用 UTC：无歧义、跨时区正确，代价是前端必须按用户时区格式化，展示层不能偷懒；用本地时间：展示简单，但跨时区/ DST 会歧义，存储和传输容易错。推荐传输 UTC/带偏移，展示按用户时区。

## 5. JDBC、MyBatis 与类型处理器

**一句话**：JDBC 驱动负责 Java 类型和数据库类型的转换；MyBatis `TypeHandler` 可以接管某类型的读写，但全局注册会影响所有字段。

要能回答：

- `PreparedStatement.setTimestamp` 和 `setObject(LocalDateTime)` 有什么区别？
- MyBatis `TypeHandler` 的注册方式？全局注册和字段级注册的优先级？
- 读写用不同时区会发生什么？
- 批量写入时时间字段怎么保证一致？
- 数据库函数 `now()`、`CURRENT_TIMESTAMP` 返回什么时区？

关联：[[InstantNyTypeHandler]]、[[WMS时区统一改造]]

笔记：

- `setTimestamp` 把 `java.sql.Timestamp` 按驱动/会话时区转成数据库类型；`setObject(LocalDateTime)` 走 JDBC 4.2，映射到无时区类型；`setObject(OffsetDateTime)` 映射到 `timestamptz`。选错方法会多一次隐式转换。
- MyBatis `TypeHandler` 可全局注册（`typeHandlersPackage`/`configuration`）或字段级指定（`resultMap` 的 `typeHandler`、`#{}` 的 `typeHandler`）；字段级优先于全局。全局注册影响所有同类型字段，改之前要全量回归。
- 读写用不同时区：写入按会话 A 解释、读出按会话 B 解释，时刻会平移；`TIMESTAMP`/`timestamptz` 最明显，`DATETIME`/`timestamp` 不转换但会存错墙钟。
- 批量写入用同一连接/同一会话设置；批处理跨连接池借到不同会话时区，时间字段会不一致。
- `now()`/`CURRENT_TIMESTAMP`：PostgreSQL 的 `timestamptz` 返回事务开始时刻，显示按会话时区；`timestamp` 返回会话时区的墙钟。MySQL `NOW()` 返回会话 `time_zone` 的当前时间。跨时区系统建议显式传时间，不依赖数据库默认。

## 6. 时区转换与夏令时

**一句话**：转换必须同时有「时刻 + 源时区 + 目标时区」；只拿 `LocalDateTime` 做转换，DST 切换时会出错。

要能回答：

- 把纽约时间转成 UTC 的步骤？为什么不能直接减 5 小时？
- DST 春季跳过的一小时，`atZone` 会怎么处理？
- DST 秋季重复的一小时，怎么判断是第一次还是第二次？
- 跨时区统计「每天的订单量」应该按哪个时区分组？
- 定时任务在 DST 切换日会执行几次、漏几次？

关联：[[会话时区无关]]

笔记：

- 纽约时间转 UTC：把「本地日期时间 + `America/New_York`」组成 `ZonedDateTime`，再 `withZoneSameInstant(ZoneOffset.UTC)`。不能直接减 5 小时，因为纽约夏令时是 UTC-4、冬令时是 UTC-5。
- DST 春季跳过的一小时：`atZone` 对不存在的本地时间通常顺延到间隙之后（如 02:30 → 03:30），不会报错；要检测可以用 `ZoneRules.getValidOffsets` 判断。
- DST 秋季重复的一小时：`atZone` 默认取较早的偏移；要区分第一次/第二次用 `withEarlierOffsetAtOverlap`/`withLaterOffsetAtOverlap`，或直接存 `Instant` 避免歧义。
- 跨时区统计「每天订单量」：先定业务时区（租户/门店所在时区），按该时区切日，再把每天的起止转成 UTC 范围查库；按 UTC 切日会把当地跨日订单算错。
- 定时任务在 DST 切换日：按本地 cron 调度，春季可能少一次、秋季可能多一次（同一墙钟出现两次）；关键任务按 UTC 调度，或按「上次执行时间 + 间隔」补偿，并保证幂等。

## 7. 前端与展示

**一句话**：后端统一传 UTC 或带偏移的时间，前端按用户时区格式化；不要在前后端各转一次。

要能回答：

- 浏览器 `Date`、`Intl.DateTimeFormat` 怎么处理时区？
- 用户时区从哪里拿？浏览器自动识别和用户手动设置怎么共存？
- 表格、图表、导出文件分别应该显示什么时区？
- 只传 `yyyy-MM-dd HH:mm:ss` 会丢什么信息？
- 跨时区用户看同一个报表，口径怎么统一？

笔记：

- 浏览器 `Date` 内部是 epoch 毫秒，`toLocaleString`/`Intl.DateTimeFormat` 按指定 `timeZone` 格式化；不指定就用系统时区，测试/CI 环境可能不同。
- 用户时区：`Intl.DateTimeFormat().resolvedOptions().timeZone` 拿浏览器推断值，同时允许用户手动覆盖并存到偏好；两者冲突时以手动设置为准。
- 表格/图表按用户时区展示；导出文件要在表头/文件名标注时区（如 `2026-10-30 09:00 (America/New_York)`），否则跨时区收到文件无法解读。
- 只传 `yyyy-MM-dd HH:mm:ss` 丢了偏移/时区，接收方只能猜；同一字符串在不同时区是不同时刻，跨系统对接必须带 `Z` 或偏移。
- 跨时区报表要定义「报表时区」：通常按业务发生地/租户时区统计，页面显示该口径；不能每个用户看到不同的汇总数字，否则对账对不上。
