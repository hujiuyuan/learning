# 会话时区无关

技能点：[[InstantNyTypeHandler]] · 方法：会话时区隔离（待建） · 通用技能：[[时区与时间序列化]]

**什么时候会遇到**：容器里的 MySQL 默认时区不是业务时区；`CURRENT_TIMESTAMP` 落库后比预期差几小时；本地跑绿、CI 跑红；有人想用 JDBC 的 `serverTimezone` 一把梭。

## 判断顺序

1. **这个值是谁生成的？** Java 绑定的参数，还是 MySQL 自己算的默认值/`NOW()`。
2. **Java 生成**：`InstantNyTypeHandler` 绑的是 `LocalDateTime` 字面量，驱动不转换，所以免疫会话时区。
3. **MySQL 生成**：`DEFAULT CURRENT_TIMESTAMP`、`ON UPDATE CURRENT_TIMESTAMP`、`NOW()` 都跟随会话时区。
4. **会话时区谁设的？** 连接池 `connection-init-sql`、容器 `default-time-zone`、还是 JDBC URL。
5. **测试有没有显式钉住？** 不钉就等于在测「容器默认值」，换台机器结论就变。

## 手段

- 在 `SessionTzSafeItTest` 里用 Hikari 的 `connection-init-sql` 给每条连接执行 `SET time_zone = '-09:00'`（`SessionTzSafeItTest.java:83-84`），故意选一个夸张偏移，任何二次转换都会被放大。
- 测试表同时建两类列：`at DATETIME`（走 handler）和 `def_at DATETIME DEFAULT CURRENT_TIMESTAMP`（MySQL 生成）（`:99-103`）。
- **断言一：handler 免疫**。UTC `2026-07-01T12:00:00Z`（纽约 EDT 08:00）写入后，`DATE_FORMAT` 读原值必须是 `2026-07-01 08:00:00`，不能被 `-09:00` 二次转换成 03:00；读回实体必须等于原 `Instant`（`:110-125`）。
- **断言二：默认值跟随会话时区**。`def_at` 必须接近当前 `-09:00` 墙钟，±3 分钟容差（`:127-142`）。
- 无 Docker 时整类跳过：`@Testcontainers(disabledWithoutDocker = true)`（`:53`）。
- 两个断言合起来证明：同一连接里，「显式绑定的值」和「MySQL 生成的值」走两套时区逻辑，不能混为一谈。

## 反例 / 边界

- 测试用的是固定偏移 `-09:00`，不是 `America/New_York`；它不证明命名时区、也不证明 DST 切换。
- 只证明了这两列、这一种 handler；没有证明全库所有表和所有生成时间。
- 没覆盖 `TIMESTAMP` 列；`TIMESTAMP` 的换算规则和 `DATETIME` 不同。
- 没验证 `serverTimezone` 参数的影响。仓库主代码没配它，但部分集成测试的连接串里写了 `serverTimezone=UTC`，是另一套机制，不能用本测试的结论去推。
- 不证明生产会话时区就是纽约；生产值由部署变量注入，属于配置问题，不是本测试能覆盖的。

## 现在的规矩

- 任何依赖 MySQL 生成时间的列，必须显式设置连接会话时区，不靠容器默认。
- 测试里显式 `SET time_zone`，把环境变量变成测试前提。
- 「TypeHandler 绑字面量、免疫会话时区」这条底线不能破；一旦改成让驱动转 `Timestamp`，两套逻辑会互相污染。
- 新增时区测试时，至少同时断言「显式写入的原值」和「MySQL 生成值的时区」。
- 测试不能以「没抛异常」或「非空」判成功，必须断言具体墙钟字符串和往返 `Instant`。
