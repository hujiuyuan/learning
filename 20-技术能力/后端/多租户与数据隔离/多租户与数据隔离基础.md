## 1. 多租户模型

**一句话**：三种主流模型是「一租户一库」「一租户一 schema」「共享表 + tenant_id」；隔离性越强，运维成本和资源浪费越高。

要能回答：

- 三种模型各自的隔离级别、成本、扩展性？
- 共享表模式下，tenant_id 应该建什么索引？
- 租户规模差异很大时怎么选模型？
- 租户数据删除、归档、迁移分别怎么做？
- 混合模型（大客户独立库、小客户共享）怎么路由？

笔记：

- 独立库：隔离最强（备份、迁移、故障都独立），成本最高（每库连接池、迁移、监控），适合大客户/强合规；独立 schema：中等隔离，同实例共享资源，迁移按 schema 跑；共享表 + `tenant_id`：隔离最弱，成本最低，扩展最容易。
- 共享表的索引以 `tenant_id` 开头：`(tenant_id, 业务唯一键)`、`(tenant_id, 查询条件)`；只有业务键没有租户前缀，查询会跨租户扫描。
- 租户规模差异大用混合：大客户独立库/schema，小客户共享表；租户注册表记录「租户 → 数据源/schema」，访问前按租户路由。
- 删除：共享表按 `tenant_id` 删（软删/硬删/归档）；独立库直接 drop；schema 单独 drop。归档先导出再删，保留期按合同。
- 迁移：共享表按租户导出/导入；独立库 dump/restore；跨模型迁移要停写或双写，不能直接搬行。
- 混合路由的代价：两套迁移脚本、两套连接池、两套监控；路由错会把租户写到错误的库，必须有租户-数据源映射的强校验和测试。

## 2. 租户上下文传播

**一句话**：租户 ID 从登录凭证进入请求上下文，再进入数据访问层；任何一段丢了，都会变成跨租户查询。

要能回答：

- 租户 ID 应该放在 token、Session、请求头还是线程上下文？
- 异步线程、线程池、定时任务里怎么拿到租户？
- 消息队列的生产者和消费者怎么传租户？
- 租户上下文和事务边界是什么关系？
- 平台管理员跨租户操作时，上下文怎么表达？

关联：[[MySQL租户字段]]

笔记：

- 租户 ID 放签名 token（JWT/会话）里，由认证环节解析；请求头可传「当前租户」但必须和 token 允许的范围校验，不能直接信任前端。线程上下文（ThreadLocal/ScopedValue）承载一次请求内的租户。
- 异步线程/线程池：提交任务时抓租户快照，任务执行前恢复（`TaskDecorator`、`ScopedValue`）；不能靠 `ThreadLocal` 自动继承。
- MQ：生产者在消息头/载荷写 `tenantId`，消费者消费前设置上下文；没有租户的消息要显式拒绝或走平台分支，不能默认落到某个租户。
- 租户上下文要在事务/连接获取之前设置：连接池可能带会话变量（RLS），设置晚了策略读不到；事务内切租户要避免，必要时用独立事务。
- 平台管理员跨租户：上下文用显式「平台模式 + 目标租户」两个字段表达，查询时目标租户为空表示全租户（仅平台权限），所有跨租户操作写审计；不能把平台账号伪装成某个租户账号。

## 3. 应用层过滤

**一句话**：应用层过滤靠拦截器/插件自动拼 `tenant_id`；灵活但依赖代码路径全覆盖，漏一条 SQL 就漏数据。

要能回答：

- MyBatis 租户插件在 SQL 的哪个阶段改写？insert/update/delete 分别怎么处理？
- 哪些表要排除？全局表、字典表、平台表怎么标记？
- 手写 SQL、`@Select` 注解、存储过程会不会被插件覆盖？
- 跨租户查询（平台视角）怎么显式放行？
- 怎么防止前端传入的 tenant_id 覆盖上下文？

关联：[[MySQL租户字段]]、[[租户插件落地]]、[[平台账号与NULL]]

笔记：

- MyBatis 租户插件在 SQL 解析阶段改写：select 的 where、update/delete 的 where 加 `tenant_id = ?`，insert 补 `tenant_id` 列和值；改写在执行前，手写 XML 和 `@Select` 只要经过同一解析器也会被改写。
- 排除表：全局字典、平台配置、迁移记录等用插件忽略列表或 `@InterceptorIgnore(tenantLine = "true")` 标记；白名单要显式维护，不能靠表名猜。
- 存储过程、数据库函数、`UNION` 子查询、复杂动态 SQL 可能漏改；这类路径要么避免，要么在测试里用反向用例覆盖。
- 跨租户查询（平台视角）用显式忽略注解 + 权限校验 + 审计，不能提供「传 tenant_id 就查别的租户」的通用接口。
- 防覆盖：服务端从上下文取租户，忽略/覆盖请求体里的 `tenantId`；DTO 不暴露租户字段，或反序列化后强制重置。
- 插件不是万能的：原生 JDBC、批量脚本、其他数据源可能绕过；上线前用「A 写 B 查」的集成测试验证每条入口。

## 4. 数据库行级安全（RLS）

**一句话**：PostgreSQL RLS 由数据库强制加策略，应用即使漏写条件也查不到别的租户；代价是连接上下文、策略设计和运维复杂度。

要能回答：

- RLS 的 `ENABLE`、`FORCE`、`POLICY` 分别是什么？
- `USING` 和 `WITH CHECK` 的区别？分别管读还是写？
- 租户 ID 怎么传给数据库？`set_config` 和会话变量怎么选？
- 为什么表 owner 默认绕过 RLS？`FORCE` 解决什么？
- 连接池复用连接时，租户上下文怎么清理？
- RLS 对性能有什么影响？索引怎么建？

关联：[[PostgreSQL RLS]]、[[RLS落地]]

笔记：

- `ENABLE ROW LEVEL SECURITY` 开启表的策略检查；`FORCE` 让表 owner 也受策略约束（默认 owner 绕过）；`POLICY` 定义谁能看/写哪些行。
- `USING` 过滤已存在的行（select/update/delete 的可见性），`WITH CHECK` 校验写入/更新后的新行；只写 `USING` 不写 `WITH CHECK`，插入可能写到别的租户。
- 租户 ID 用事务级设置：`SET LOCAL app.tenant_id = '...'` 或 `set_config('app.tenant_id', ..., true)`；事务结束自动失效，连接池复用不会串租户。会话级设置必须手动清理，容易漏。
- 表 owner 默认绕过 RLS，应用连接不能用 owner；用受限角色 + `FORCE`，否则策略形同虚设。
- 连接池：`SET LOCAL` 绑事务最安全；如果用会话变量，借出/归还都要重置，否则 A 租户的连接被 B 租户复用会读到 A 的数据。
- 性能：策略谓词要能走索引，`tenant_id` 建索引（通常复合索引首列）；策略里避免函数/类型转换，否则退化为全表扫描。RLS 增加的是每行策略判断，简单等值谓词开销很小。

## 5. 跨租户风险点

**一句话**：跨租户漏洞常出在缓存、异步任务、导出、搜索、文件存储和日志这些「主查询之外」的路径。

要能回答：

- 缓存 key 为什么必须带 tenant_id？
- 异步导出/导入怎么保证只处理当前租户的数据？
- 文件 URL、对象存储路径怎么防越权访问？
- 全文搜索/向量检索怎么加租户过滤？
- 日志和审计里怎么避免把 A 租户数据给 B 租户看？
- 数据库唯一索引要不要带 tenant_id？

笔记：

- 缓存 key 必须带 `tenant_id`（如 `tenant:{id}:user:{userId}`）；漏了会把 A 租户的缓存给 B 租户。删除/更新也要按同 key 失效。
- 异步导出/导入：任务入参记租户，执行时设置上下文，查询按租户过滤；导出文件名/对象路径带租户前缀，下载鉴权校验归属。
- 文件/对象存储：路径按 `tenant/{tenantId}/...` 组织，下载走签名 URL + 服务端鉴权；不能只靠 URL 不可猜。
- 全文搜索/向量检索：索引里存 `tenant_id`，查询加过滤条件（ES filter、向量库 metadata filter）；只在应用层过滤、检索后再筛，会泄露数量和排序信息。
- 日志/审计：按租户分字段存储，查询接口按当前租户过滤；平台日志聚合要脱敏，避免运维界面跨租户泄露。
- 唯一索引要带 `tenant_id`：`(tenant_id, code)` 而不是 `code` 全局唯一；否则 A 租户占了编码，B 租户不能用。全局唯一（如手机号跨租户）要单独设计并明确业务规则。

## 6. 平台账号与全局数据

**一句话**：平台账号（tenant=null）和租户账号走不同分支；全局表不参与租户过滤，但必须显式白名单。

要能回答：

- 平台账号能看所有租户数据，这个能力怎么限制和审计？
- `tenant_id = null` 和 `tenant_id = 0` 有什么区别？哪个更安全？
- 全局字典表和租户自定义字典怎么共存？
- 平台账号创建的的数据归谁？
- 代登录时租户上下文怎么切换？

关联：[[平台账号与NULL]]

笔记：

- 平台账号跨租户能力必须限定在明确入口（平台管理后台/运维接口），每次操作记「平台账号 + 目标租户 + 操作」；普通租户接口不接受平台身份直接访问。
- `tenant_id = NULL` 表示「无租户/平台级」，`0` 是一个普通数值，可能和真实租户 id 冲突；用 NULL + 明确分支更安全，字段允许 NULL 并用 `IS NULL` 判断。
- 全局字典表不参与租户过滤，租户自定义字典用 `tenant_id` 覆盖/扩展；查询时先取租户自定义，再回退全局。
- 平台账号创建的数据要明确归属：要么归平台（tenant NULL），要么要求指定目标租户；不能默认归某个租户。
- 代登录：保存「实际操作者（平台账号）+ 被代账号 + 租户」，上下文切到被代租户，但审计记实际操作者；退出代登录要恢复原上下文。
- 平台账号的权限也要最小化：能跨租户不等于能删库；高危操作二次确认 + 审批 + 审计。

## 7. 测试与验证

**一句话**：租户隔离必须用「A 租户写入、B 租户查询」的反向用例证明；只测 A 租户能查到自己的数据，证明不了隔离。

要能回答：

- 租户隔离测试应该覆盖哪些入口（列表、详情、导出、更新、删除）？
- 怎么造两个租户的数据？怎么断言 B 查不到 A？
- 平台账号的测试和普通租户的测试有什么不同？
- RLS 策略怎么测？怎么证明策略真的生效？
- 回归时怎么防止新接口漏加租户条件？

关联：[[租户隔离测试]]

笔记：

- 每个租户相关入口都要有反向用例：列表、详情、导出、更新、删除、批量操作、文件下载；只测「A 能查到自己的」证明不了隔离。
- 造两个租户的数据（A、B 各一条），用 A 的上下文请求 B 的 id：期望空列表/404/403，且响应里不含 B 的字段；更新/删除后 B 的数据仍在。
- 平台账号测试单独一组：能跨租户查、能指定租户写、高危操作被审计；普通租户账号不能走平台分支。
- RLS 测试要用受限角色（非 owner）连接，设置错误/缺失租户变量时查不到数据；只测 owner 连接等于没测。
- 防回归：新接口默认走统一 Service/DAO 层（插件覆盖），code review 检查手写 SQL；关键模块加 ArchUnit/静态规则，禁止裸 JDBC。
- 定期跑全量隔离用例，新增表要加入插件白名单/策略迁移；漏建策略的表用测试扫描发现。
