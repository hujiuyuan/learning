# 多租户与数据隔离

**一句话**：租户隔离不是「表上有 `tenant_id`」就完成；应用层过滤和数据库 RLS 各挡一段，平台账号与 NULL 行的可见性必须显式定义，漏掉的路径会静默越权。

## 一、理论：隔离发生在哪一层

1. **应用过滤**：在 SQL 生成/改写阶段追加 `tenant_id = ?`，MyBatis-Plus 的 `TenantLineInnerInterceptor` 属于这层。它只看得到 MyBatis 执行的语句：实体 CRUD、wrapper、mapper XML 都会尝试改写；`JdbcTemplate` 不经过它；解析失败的语句会被跳过。
2. **数据库 RLS**：策略写在表上，由会话变量决定行可见性；应用漏了条件它仍返回零行。这是 PostgreSQL 专有能力，MySQL 没有等价物，只能靠应用层。
3. **两层不是二选一**：应用层负责给出「当前租户是谁」，数据库层负责「即使你忘了也查不到」。任何一层失效，另一层才兜底。
4. **平台账号**：`tenant_id` 为空通常代表平台/超管。它看全量、看 `IS NULL` 行、还是只能看平台行，是业务定义，必须在查询里写死。
5. **fail-closed**：取不到租户时应「一行都查不到」，而不是「不加条件、放行全表」。这是隔离与看运气的分水岭。
6. **索引打头**：高频查询的联合索引把 `tenant_id` 放首列，过滤才能用上索引；选择性极低的场景，加了未必用得上。

## 二、实际使用：我在两个项目里各做了一半

- **muou（PostgreSQL）**：数据库 RLS + 应用层拦截两道。`TenantAwareTransactionManager` 在每个事务开始把租户写进会话变量，取不到就写空串，RLS 谓词求值为 NULL、返回零行（`muou-backend/muou-common/muou-common-app/src/main/java/com/voidtech/muou/common/tx/tenant/TenantAwareTransactionManager.java:19,63-71`）；迁移里 `ENABLE` + `FORCE` + `USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)`（`muou-backend/muou-server-notify/muou-notify-app/db/migration/message/V202609231221__notify_rls_notify_type_and_template.sql:8-16`）。应用层 `MuouTenantLineHandler` 在 SQL 里再拼等值条件，没租户上下文时注入查不到的哨兵 UUID（`muou-backend/muou-common/muou-common-app/src/main/java/com/voidtech/muou/common/persistence/MuouTenantLineHandler.java:20-30,63-66`）。详见 [[RLS落地]]。
- **smart（MySQL）**：只有应用层。`WmsTenantLineHandler` 维护全局表清单，平台账号（`tenantId=null`）整表跳过，其余表追加 `tenant_id = ?`（`smart-server-wms3/src/main/java/com/track/wms/config/WmsTenantLineHandler.java:35-107`）。解析失败时 `SafeTenantLineInnerInterceptor` 跳过过滤而非中断请求，代价是这一次查询没有租户条件（`smart-server-wms3/src/main/java/com/track/wms/config/SafeTenantLineInnerInterceptor.java:16-39`）。详见 [[多租户拦截]]。
- **平台账号与 NULL**：smart 的通知查询写 `tenant_id = ? OR tenant_id IS NULL`，平台账号只查 `IS NULL`（`smart-server-wms3/src/main/resources/mapper/NotificationMapper.xml:44-47`）；`goods.tenant_id` 99.98% 为 NULL，严格等值会把结果清零，只能在 `TenantIgnore` 后手写 `(tenant_id = ? OR IS NULL)`（`smart-server-wms3/src/main/resources/mapper/GoodsMapper.xml:14-27`）。详见 [[平台账号与NULL]]。
- **测试**：跨租户 count/update/delete、平台全量、白名单漂移都有 IT 或架构测试（`smart-server-wms3/src/test/java/com/track/wms/config/TenantIsolationIT.java:104-140,240-395`；`muou-backend/muou-common/muou-common-app/src/test/java/com/voidtech/muou/common/arch/TenantIgnoreTablesCheckTest.java:12-48`）。详见 [[租户隔离测试]]。

## 三、归纳：租户过滤检查清单

拿到一条数据访问路径，按顺序问：

1. **caller 是谁**：租户账号、平台账号、定时任务、匿名入口。平台/任务有没有显式上下文？
2. **这条 SQL 经过拦截器吗**：实体 CRUD / wrapper / XML 裸 SQL / `JdbcTemplate`。后两者要自己写租户条件。
3. **表在忽略清单吗**：为什么忽略——没有 `tenant_id` 列、确需跨租户、还是通过父表隔离？理由要能写出来。
4. **NULL 行怎么算**：平台账号、历史未回填数据、平台保留租户。用 `= ?` 还是 `= ? OR IS NULL`，按业务语义定。
5. **跨租户有没有闸**：`TenantIgnore` / `@InterceptorIgnore` 之外，上游有没有归属校验或平台入口审计？
6. **数据库有没有兜底**：PostgreSQL 表启了 RLS 吗？启了 `FORCE` 吗？执行角色有没有 `BYPASSRLS`？
7. **测试能不能抓回归**：跨租户不可见、本租户可见、平台可见、count 同口径、白名单漂移各一条。

### 三条红线

- 不能因为「表上有 `tenant_id`」就认为隔离完成：裸 SQL、跳过清单、解析失败都能绕开。
- 不能让「取不到租户」等于「放行」：应用层要给查不到的值，数据库层要让 NULL 谓词不成立。
- 不能把平台账号的可见范围交给默认行为：`IS NULL`、全量、只读，都要在 SQL 或服务层写死。

## 四、回到理论

- 应用层拦截是**语句级改写**，依赖 SQL 形态；数据库 RLS 是**表级策略**，不关心 SQL 怎么写。覆盖面对不上，所以需要两层。
- 会话变量是连接级的：事务开始写入、事务结束失效，连接回池不能带脏值（muou 用事务级 `set_config(..., true)`，`TenantAwareTransactionManager.java:23-24`）。
- 隔离的默认值决定安全下限：默认拒绝（哨兵/空串/零行）多一次「查不到」的排查成本，少一次越权。
- 平台账号是「合法的跨租户」，不是「没有租户」；把它建模成 NULL 还是独立角色，决定后续每条 SQL 的写法。

## 五、边界

- RLS 只在 muou（PostgreSQL）落地，且只落了 A 型私有表；B 型共享表策略仍是设计（`muou-server/docs/03-3-RLS与多租户数据隔离.md:84-102`）。
- MySQL 侧没有数据库兜底，smart 的隔离完全依赖应用层；27 个 mapper XML 里 16 个仍手写 `tenant_id =`，不能写「全仓隔离完成」。
- 没做过分库分表、独立 schema/独立库的多租户；没做过租户数据搬迁与合并。
- muou 的 iam 有 52 个数据访问实现，其中 32 个是 `JdbcTemplate`，不在拦截器射程内（`MuouTenantLineHandler.java:23-25`）。
