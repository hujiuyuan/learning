# 软删除

技能点：[[MyBatis-Plus]] · 方法：[[软删除过滤]] · 通用技能：[[数据访问与ORM]]

**什么时候会遇到**：表上有 `deleted_at`，查询却把删掉的行捞回来；或者过滤条件写重了，活着的行反而漏掉。

路径说明：下文 `smart/...` 相对 `/Users/hujiuyuan/workspace/voidtech/smart/`；`smart-server-wms3/...` 是该目录下的服务仓。

**一句话**：软删除不是「加个标记」；它要先回答四个问题——删除时间是不是业务事实、删除后还要不要查/恢复/审计、活跃行和历史行怎么放、唯一约束怎么落地。项目里核心业务表用 `deleted_at`，日志表用 `deleted TINYINT`，操作日志用归档表；三种选择对应三种不同问题，不是三套随手写的代码。

## 一、先判断：删除时间是不是业务事实

| 问题 | 是 → 选 | 否 → 选 |
| --- | --- | --- |
| 需要知道「什么时候删的」、按删除时间审计/清理/同步吗？ | `deleted_at DATETIME` | `deleted TINYINT` |
| 删除后要恢复、或要保留一段可恢复窗口吗？ | `deleted_at` + 恢复条件 | 只需要隐藏，不需要恢复 |
| 活跃行少、历史行多，历史还很少查？ | 归档表 / 分区 / 冷存储 | 原表软删 |
| 有业务唯一键，且删除后要允许重建同名记录？ | 生成列 / 部分唯一索引 | 应用层查重 + 锁 |

这四个问题决定字段类型和存放位置，不是先选 `deleted_at` 再补理由。

## 二、为什么核心表是 `deleted_at`，不是 `is_delete`

### 2.1 项目里的原始决策

账号权限改造方案写得很直接：

- 「软删除：`deleted_at DATETIME`（NULL = 未删除），不用 `deleted TINYINT`」（`smart/plan/账号权限认证体系改造方案.md:66`）。
- 「`status` 与 `deleted_at` 职责分离」（`:87-90`）：`status=0` 是禁用，可以再启用；`deleted_at IS NOT NULL` 是已删除，不允许登录且不可恢复。两件事不能用一个布尔字段表达。
- 关键决策记录再次确认：「`deleted_at` | 软删除标记 | 与 `status` 职责分离」「软删除 | `deleted_at DATETIME` + `@TableLogic` | 与 Legacy 一致」（`:1392-1394`）。

Legacy 表本来就用 `is_del` / `deleted_at` 混着（`smart-server-wms3/legacy-wms-api.md:180`）；新表沿用时间戳，是为了和旧数据、旧查询口径对齐，不是为了赶时髦。

### 2.2 时间戳比布尔多出来的三件事

1. **保留删除时刻**：审计要看「谁在什么时候删的」；保留期/归档/清理要按 `deleted_at < cutoff` 扫；增量同步可以拿删除时间当 tombstone。布尔只有「删没删」，这些都要另加一列，等于最后还是要时间。
2. **重复删除幂等，且不覆盖第一次删除时间**：项目里用 `whereNull('deleted_at')` 当守卫，已经删过的行更新 0 行，原 `deleted_at` 不被覆盖（`smart/docs/superpowers/plans/2026-07-20-omp-merge-reconcile-phase2.md:43`、`:61`）。布尔重复删除也幂等，但第一次删除的时间已经丢了。
3. **区分「禁用」和「删除」**：`status=0` 可恢复启用；`deleted_at` 非空是终态。账号表如果只有 `is_delete`，仍然要再加 `status`；两个布尔字段的组合比「状态 + 时间」更难读，也更容易出现 `status=0, is_delete=1` 这种自相矛盾的行。

### 2.3 布尔不是错的，适用条件不同

项目里并不是一刀切：

- `io_record`（导入导出记录）用 `deleted TINYINT DEFAULT 0`（`smart/docs/superpowers/specs/2026-06-01-async-export-design.md:33`、`:56`）。
- `move_log`（移动日志）同样用 `deleted TINYINT`，靠全局逻辑删除配置，不加 `@TableLogic`（`smart/docs/superpowers/specs/2026-06-16-move-log-design.md:31`、`:72`）。
- 全局配置是 `logic-delete-field: deleted`、`logic-delete-value: 1`、`logic-not-delete-value: 0`（`smart-server-wms3/src/main/resources/application.yml:129-131`）。

这两类表只需要「隐藏」，不需要知道删除时刻，也不需要靠删除时间做恢复/审计，所以用 1 字节的 `TINYINT` 更直接。代价是项目里同时存在两套口径：新写查询/实体时，必须先确认这张表用的是 `deleted_at` 还是 `deleted`。这不是免费的选择，是在「字段更贴业务」和「全库统一」之间取了前者。

**如果当时选了 `is_delete`，后来又要删除时间会怎样**：加一列 `deleted_at` 只能从上线那一刻开始记；历史行为什么时间删的，已经无法还原。删除时间一旦是业务事实，就应该在第一次建表时留下。

## 三、为什么用 `NULL` 时间，不用固定值

`deleted_at DATETIME NULL` 的写法是：`NULL` = 未删除，非空 = 删除时刻；MyBatis-Plus 用 `@TableLogic(value = "NULL", delval = "NOW()")`（`Car.java:59`、`Trailer.java:157` 等）。

它的好处是语义直接：插入时不用写哨兵值，查询用 `IS NULL`，不会出现「0 到底代表未删除还是 1970 年删除」的歧义。代价有两个，必须在建索引/唯一键时正面处理：

1. **MySQL 的唯一索引把多个 `NULL` 视为不同值**。所以 `UNIQUE(tenant_id, name, deleted_at)` **不能**阻止两条同名活跃记录——它们的 `deleted_at` 都是 `NULL`，唯一键认为互不相同。想用唯一索引保护活跃行，只有三种做法：
   - MySQL 生成列：`active_name = IF(deleted_at IS NULL, name, NULL)`，再 `UNIQUE(tenant_id, active_name)`；活跃行有值，已删行为 `NULL`，可以重复删除/重建。
   - 固定哨兵值：`deleted_at DATETIME NOT NULL DEFAULT '1970-01-01 00:00:00'`，活跃行都用同一个哨兵，`UNIQUE(tenant_id, name, deleted_at)` 才能挡住活跃重复；代价是每次插入都要写哨兵、查询从 `IS NULL` 变成等值比较，且要防止业务误写这个日期。
   - PostgreSQL 的部分唯一索引：`CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`，这是最干净的写法（项目在 PostgreSQL 侧用部分索引，见 `PostgreSQL.md:41`）。

2. **`deleted_at` 单独建索引几乎没用**：绝大多数行是 `NULL`，选择性极低。项目里把它放在联合索引尾列，例如 `(tenant_id, status, deleted_at)`、`(tenant_id, name, deleted_at)`（`smart/docs/superpowers/specs/2026-06-09-trailer-type-dict-design.md:60-61`）；`goods` 的 `idx_tenant_stock_deleted_at` 首列是 `tenant_id`，但 99.98% 为 `NULL`、cardinality 只有 6，索引救不了查询（`smart/docs/2026-07-16-测试数据库卡顿排查报告.md:94-97`）。要么把删除条件放进联合索引的可用位置，要么用部分索引。

项目当前没有给这些业务名加数据库唯一约束，而是应用层查重 + 分布式锁（`trailer-type-dict-design.md:28`、`:145`；账号邮箱查重 `账号权限认证体系改造方案.md:350`）。所以 `NULL` 的唯一键问题还没有在生产咬人；但一旦要加唯一索引，不能照抄 `UNIQUE(..., deleted_at)`。

## 四、为什么不把删除行单独存一张归档表

| 维度 | 原表软删 | 单独归档表 |
| --- | --- | --- |
| 写路径 | 一条 `UPDATE` | `INSERT` 归档 + `DELETE` 原表，必须同事务/可补偿 |
| 读路径 | 每条查询都要带 `deleted_at IS NULL` | 活跃表干净，查询不用带删除条件 |
| 历史查询 | 原表直接查，JOIN 不变 | 要 UNION/跨表查，关联关系可能断 |
| 唯一约束 | 受 `NULL` 唯一键语义影响 | 活跃表唯一键干净 |
| 空间/索引 | 删除行继续占表、撑大索引 | 主表小，索引密 |
| 恢复 | `UPDATE deleted_at = NULL` | 要从归档表搬回，可能撞唯一键 |
| 失败模式 | 忘写过滤 → 已删数据泄漏 | 搬到一半失败 → 丢数据或重复 |
| 适用 | 行数不大、要保留关联/审计/恢复 | 历史量大、历史很少查、有明确保留期 |

项目里真正用归档表的是**操作日志**，不是业务表：`OperationLogArchiveServiceImpl` 每天 3 点把 180 天前的日志按租户打包成 zip 传到 S3，写 `operation_log_archive` 元数据，再在同一个事务里删原表记录（`OperationLogArchiveServiceImpl.java:52`、`:85-90`、`:101-124`）。代码注释把失败模式写清楚了：先传 S3 再删库，上传失败则日志未删、下轮重跑；删日志和写归档记录必须原子，否则会出现「日志已删、归档记录丢失、S3 文件成孤儿」的不可逆数据丢失（`:112-124`）。

这正是归档表适合的场景：日志量大、历史很少查、保留期明确。业务表（车辆、挂车、月台、用户）不适合照搬：它们的行要被外键/业务查询 JOIN，删除后还可能恢复，搬到归档表会让所有关联查询和恢复路径都变复杂。**归档表不是「更高级的软删除」，它是用写路径复杂度和跨表查询成本，换主表体积和索引密度。**

如果业务表删除量真的很大，正确做法通常是「先软删，再按保留期归档/硬删」，而不是删除时立刻搬表：软删保留短期可恢复和审计，后台任务按 `deleted_at < cutoff` 批量归档/清理。项目账号删除明确「不可恢复」（`账号权限认证体系改造方案.md:90`），所以它没有恢复窗口；但「不可恢复」是业务规则，不是 `deleted_at` 自动带来的能力。

## 五、项目里的四种口径

| 场景 | 字段/做法 | 为什么 | 证据 |
| --- | --- | --- | --- |
| 核心业务表（Car/Trailer/Dock/ShippingTask/User/Goods） | `deleted_at` + `@TableLogic(value="NULL", delval="NOW()")` | 删除时间是业务事实；要和 `status` 分离；重复删除不覆盖首次时间 | `Car.java:59`、`Trailer.java:157`、`账号权限认证体系改造方案.md:66`、`:87-90` |
| 历史表/无注解表（Files、MergeFile） | 手动 `.isNull(deletedAt)` | 历史 schema 没有统一注解；读口必须自己带条件 | `FilesDaoImpl.java:40-41`、`MergeFileDaoImpl.java:36` |
| 操作记录（io_record、move_log） | `deleted TINYINT` + 全局配置 | 只需要隐藏，不需要删除时刻；跟随全局 `deleted` 配置 | `application.yml:129-131`、`async-export-design.md:33,56`、`move-log-design.md:31,72` |
| 操作日志（operation_log） | 归档表 + S3 + 元数据表 | 量大、历史少查、保留期明确；软删会让主表继续膨胀 | `OperationLogArchiveServiceImpl.java:52,85-124` |

## 六、实现时真正会咬人的地方

- **实体 CRUD 自动过滤，裸 SQL 不会**：`@TableLogic` 只作用于 MyBatis-Plus 生成的 SQL；XML/`@Select`/DTO/Map 投影必须手写 `deleted_at IS NULL`。项目里 `TrailerMapper.xml:109` 的注释就明确「原生 XML 无 @TableLogic 自动软删过滤」，`Files`、`MergeFile` 也出现过漏过滤（`FilesSoftDeleteItTest.java:37-44`）。
- **测试不能只断言「删掉的不回」**：查询被过度收窄成空集也会通过。项目专项 IT 同时断言「删掉的不回」和「活着的照回」（`FilesSoftDeleteItTest.java:41-44`、`:104-132`），再验可见性过滤、投影取 id（`:122-170`）。
- **唯一键/COUNT/导出都要按活跃行口径**：软删行还在表里，`COUNT(*)`、导出、唯一性校验如果忘了过滤，结果都会偏。`deleted_at` 本身不解决这个问题，只是给你一个可过滤的列。
- **软删除不等于合规删除**：行还在，邮箱、手机号、地址等 PII 也还在。需要「被遗忘权」或保留期到期时，仍然要做硬删/匿名化；这是另一个任务，不能拿 `deleted_at` 交差。
- **时间精度要统一**：新表用 `DATETIME(3)`（`unavail-reason-config-design.md:92`），老表有 `DATETIME`，比较/排序时不要假设都是同一精度。

## 七、现在的规矩

- 新业务表：删除是业务事件 → `deleted_at DATETIME(3) NULL` + `@TableLogic(value="NULL", delval="NOW()")`；`status` 单独表达启用/禁用。
- 纯操作记录：只需要隐藏、不需要删除时间 → `deleted TINYINT` + 全局配置；在建表说明里写清用哪套口径。
- 需要「活跃行唯一」→ 生成列/部分唯一索引/应用层查重 + 锁；不要用 `UNIQUE(..., deleted_at)` 假装能挡住重复。
- 历史量大、历史很少查、保留期明确 → 归档表 + 对象存储；上传成功再删原表，元数据和删除同事务。
- 所有裸 SQL、DTO/Map 投影手动带 `deleted_at IS NULL`；专项 IT 双向断言。
- 合规硬删/匿名化单独做，不混在软删里。
