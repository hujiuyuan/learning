# 插件链

技能点：[[MyBatis-Plus]] · 通用技能：[[数据访问与ORM]]

**一句话**：多个 `InnerInterceptor` 按注册顺序依次改写同一条 SQL；顺序决定语义，绕开实体/语句的 SQL 不受任何一环保护。租户必须在分页之前，否则 count SQL 不带租户条件，分页总数会跨租户。

## 方法总纲

1. **先列插件**：项目注册了哪些、各自改什么（租户、分页、乐观锁、防全表）。
2. **再定顺序**：租户 → 分页 → 乐观锁 → 防全表更新；租户在分页前，保证分页生成的 count 也带租户条件；其余按「先过滤、后分页、再并发控制」排。
3. **确认作用面**：插件只改写经过 MyBatis 执行器的 SQL；XML 裸 SQL 仍在链上，但实体注解（软删、乐观锁）不一定生效。
4. **维护排除清单**：全局字典、平台表、无 `tenant_id` 列的表、需要跨租户的表、已手动过滤的 JOIN 表，都要显式维护；白名单不靠表名猜。
5. **处理解析失败与歧义**：JSqlParser 解析不了方言语法时不能静默跳过，至少 warn + 监控；JOIN 同名列会被重复追加，加入跳过清单或给别名。
6. **逃生舱可审计**：跨租户读取用 `TenantIgnore.call`，`finally` 恢复；禁止调用方直接拿 `InterceptorIgnore` 绕开。
7. **验证**：对每个插件写一条能证明「生效」和「不生效」的测试，不靠读配置下结论。

## 实际使用

`MybatisPlusConfig.java:33-51` 的链：

1. `SafeTenantLineInnerInterceptor` + `WmsTenantLineHandler`：追加租户条件，解析失败时跳过。
2. `PaginationInnerInterceptor(DbType.MYSQL)`：拼 `LIMIT`、生成 count，`maxLimit=1000L`。
3. `OptimisticLockerInnerInterceptor`：`@Version` 更新时带版本条件。
4. `BlockAttackInnerInterceptor`：拦截无 where 的全表 update/delete。

注释写明租户必须在分页前，原因就是 count SQL 也要过租户改写（`MybatisPlusConfig.java:36-37`）。

## 顺序为什么不能反

| 顺序 | 结果 |
| --- | --- |
| 租户 → 分页 | count 和 data SQL 都带租户条件，总数正确 |
| 分页 → 租户 | 分页先算 count（无租户），再被租户改写 data，总数跨租户 |
| 乐观锁在租户前 | 更新语句先改 version，租户再追加条件，通常仍可用，但失败重试语义要确认 |
| 防全表更新在租户前 | 无 where 的 update 可能先被拦截/改写，错误信息不准确 |

## 判断顺序

- **新增插件**：插在租户之后、分页之前，还是分页之后？先问它是否要影响 count。
- **SQL 没生效**：先确认走的是实体/wrapper 还是 XML；再看插件是否被 `InterceptorIgnoreHelper` 临时关掉。
- **顺序疑似错**：拿一条带租户的列表 SQL，看 count 里有没有 `tenant_id`；没有就是顺序或解析问题。
- **只在某些表失效**：查租户全局表清单、`TenantIgnore`、以及 JSqlParser 是否解析失败。
- **结果被清零**：检查是否对 `tenant_id` 大量为 NULL 的表用了严格 `eq`，应 `TenantIgnore` 后手写 `(tenant_id = ? OR tenant_id IS NULL)`。

## 反例

- 租户插件放在分页后面：列表带租户、count 不带，total 偏大。
- 以为注册了乐观锁就有并发保护：没有 `@Version` 字段，插件不生成版本条件。
- 以为注册了防全表更新就安全：没有测试或用例，等于只有配置。
- XML 裸 SQL 里手写 `tenant_id`，又叠加租户插件：条件重复，解析复杂时还可能漏。
- 解析失败静默跳过：请求继续，但这次查询没有租户过滤；日志只有 warn，线上很难发现。
- 严格 `eq` 打空 NULL 行：`goods.tenant_id` 99.98% 为 NULL，插件注入 `tenant_id = ?` 会把结果清零。
- JOIN 同名列追加两次：`fba_carrier` 已有 `tenant_id` 且 DAO 手动 `eq`，插件再追加导致歧义/重复条件。
- 逃生舱滥用：38 处 `TenantIgnore` 没有审查，等于租户过滤形同虚设。
- 以为插件全覆盖：27 个 mapper XML 里 16 个仍手写 `tenant_id =`，复杂 JOIN 仍是裸 SQL。

## 边界

- 本项目的链只验证了租户和分页；乐观锁、防全表更新是「注册未使用」。
- `SafeTenantLineInnerInterceptor` 解析失败会跳过租户过滤（`SafeTenantLineInnerInterceptor.java:33-39`），这是可用性取舍，也是隔离缺口。
- 复杂 JOIN/JSON 语法仍可能绕过插件，不能宣称全仓隔离完成。
- 存量手动 `tenant_id` 过滤与插件条件并存，只是冗余，不是覆盖证明。
- 没做过多数据源、分库分表下的插件链。
