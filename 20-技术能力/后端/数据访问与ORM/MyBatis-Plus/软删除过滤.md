# 软删除过滤

技能点：[[MyBatis-Plus]] · 通用技能：[[数据访问与ORM]]

**一句话**：软删除过滤不是「查询加个 `deleted = 0`」，而是先定删除语义（时间戳/布尔/归档表），再保证自动 CRUD、XML 裸 SQL、COUNT、导出、唯一校验全部按同一口径过滤；漏一条路径就漏数据。

## 方法总纲

1. **先定删除语义**：删除时间是不是业务事实？要不要恢复/审计/按时间清理？是 → `deleted_at`；只需要隐藏 → `deleted TINYINT`；量大、历史少查、保留期明确 → 归档表。选型细节见 [[软删除]]。
2. **再定字段与注解**：`deleted_at NULL` + `@TableLogic(value = "NULL", delval = "NOW()")`，或全局 `deleted` 配置；`status` 单独表达启用/禁用，不要和删除混用。
3. **数清读路径**：`BaseMapper` 自动过滤只管 MyBatis-Plus 生成的 SQL；XML/`@Select`/DTO/Map 投影/原生 JDBC 都要手写 `deleted_at IS NULL`。
4. **处理唯一约束**：MySQL 唯一索引把多个 `NULL` 当不同值，`UNIQUE(..., deleted_at)` 挡不住活跃重复；用生成列、固定哨兵或 PG 部分唯一索引；没有约束就应用层查重 + 锁。
5. **统一聚合口径**：`COUNT(*)`、导出、统计、唯一性校验都要带未删除条件；`deleted_at` 单独建索引选择性极低，放进联合索引可用位置或部分索引。
6. **测试双向断言**：既断言「删掉的查不到」，也断言「活着的照常查到」；只测前者，过度过滤会伪装成通过。

## 判断顺序

- **先问「删除后还要不要这条数据」**：要关联/恢复/审计 → 原表软删；只要留底 → 归档表；只要隐藏 → 布尔。
- **再问「谁生成 SQL」**：走 `BaseMapper`/`Wrapper` → 注解生效；XML/注解 SQL/手写 JDBC → 手动条件，别假设插件覆盖。
- **再问「有没有唯一键」**：有 → 先解决活跃行唯一，再谈过滤；没有 → 应用层查重。
- **最后问「哪些地方会聚合/导出」**：COUNT、报表、导出、同步，逐个加条件并写测试。

## 反例

- **只加注解不查裸 SQL**：`TrailerMapper.xml` 原生 XML 没有 `@TableLogic` 自动过滤，查询照常返回已删行。
- **`UNIQUE(tenant_id, name, deleted_at)`**：活跃行 `deleted_at` 都是 `NULL`，唯一键认为互不相同，同名活跃记录仍能插入。
- **`deleted_at` 单独建索引**：99% 为 `NULL`，选择性极低，优化器不用；应放联合索引或部分索引。
- **忘记 COUNT/导出**：列表过滤了，总数和导出仍包含已删行，前端分页/对账对不上。
- **把软删当合规删除**：行还在，PII 还在；被遗忘权/保留期到期要另做硬删/匿名化。
- **重复删除覆盖首次时间**：更新时不加 `deleted_at IS NULL` 守卫，第二次删除会改写首次删除时间，审计失真。

- [[软删除]] — 为什么核心表用 `deleted_at`、三种口径、唯一键与归档表的完整取舍

## 边界

- 项目没有给业务名加数据库唯一约束，活跃行唯一靠应用层查重 + 分布式锁，未在生产验证唯一索引方案。
- 软删行的 PII 硬删/匿名化没有落地。
- 时间精度不统一（新表 `DATETIME(3)`、老表 `DATETIME`），跨表比较未做专项验证。
