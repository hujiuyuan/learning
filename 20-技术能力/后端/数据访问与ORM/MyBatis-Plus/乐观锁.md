# 乐观锁

技能点：[[MyBatis-Plus]] · 方法：[[插件链]] · 通用技能：[[数据访问与ORM]]

**什么时候会遇到**：两个请求同时改同一行，后写的把先写的覆盖；或者以为「注册了乐观锁插件」就安全了。

## 判断顺序

1. **先看有没有版本列**：实体有 `@Version`、表有 `version` 字段，`updateById` 才会带 `where version=?`；只注册插件等于没启用。
2. **没有版本列时靠什么**：条件更新（`where status=旧状态`）也是乐观并发控制；关键是检查受影响行数，0 行就报冲突。
3. **读-判断-写是不是防线**：先 `getById` 判断空闲、再更新，只能给友好提示；真正的防线是那条带条件的 UPDATE。
4. **冲突后怎么办**：重试、报错还是幂等跳过，要按业务定；不能吞掉 0 行继续往下走。

## 手段

- **有版本列**：实体加 `@Version`，更新走 `updateById`；影响行数 0 视为冲突。
- **无版本列**：`LambdaUpdateWrapper` 带源状态条件，例如 `eq(Dock::getWorkStatus, IDLE)`，返回行数必须等于 1。
- **冲突提示**：0 行统一抛业务错误（如 `DOCK_ALREADY_OCCUPIED`），不要静默成功。
- **幂等推进**：已经到目标状态时显式跳过；和「冲突报错」分开，别把两者混成一个分支。

## 反例 / 边界

- `OptimisticLockerInnerInterceptor` 已注册（`MybatisPlusConfig.java:44-45`），但仓库里搜不到 `@Version`；所以 MyBatis-Plus 的乐观锁在本项目**没有实际使用**。
- `DockServiceImpl.assign` 先读月台判断空闲（`DockServiceImpl.java:732-734`），这只是友好提示；并发防线在 `occupyIfIdle` 的 `where work_status=IDLE`（`DockDaoImpl.java:69-87`）。
- 状态推进同样用 `transitTo(dockId, from, to)`，0 行就抛；不先读后写。
- 释放/回退等低并发终态走读-改-写，没有 CAS；这是按并发强度做的取舍，不是通用安全做法。
- 月台没有唯一索引、没有分布式锁，完全靠条件 UPDATE；换成「先查再改」就会超卖。

## 现在的规矩

- 并发写状态一律先问「有没有版本列」；没有就用条件更新 + 检查行数。
- 0 行必须当冲突处理，不能当成功。
- 读出来判断只用于提示，不用于保证正确性。
- 不把「插件已注册」写成「乐观锁已启用」。
