# 租户插件落地

技能点：[[MyBatis-Plus]] · 项目：[[smart WMS]] · 2026-06

场景：[[多租户拦截]]

## 我想干什么

把租户过滤收进数据访问层，避免每个 DAO 手写 `tenant_id`；平台账号保持全量可见；分页 count 与列表同口径。

## 我干了什么

- 注册四个拦截器，租户排第一（`MybatisPlusConfig.java:33-51`）。
- 实现 `WmsTenantLineHandler`：全局表清单 + 平台模式 + 表名归一化（`WmsTenantLineHandler.java:35-107`）。
- 包一层 `SafeTenantLineInnerInterceptor`：解析失败不中断请求（`SafeTenantLineInnerInterceptor.java:28-67`）。
- 提供 `TenantIgnore.call` 逃生舱（`TenantIgnore.java:30-36`），全仓 38 处使用。
- 测试：`WmsTenantLineHandlerTest.java:28-145`（平台/租户/全局表/反引号/大写）、`TenantIsolationIT.java:104-138`（A 租户传 B 的 tenantId 仍被插件过滤）、`OrphanOccupyItTest.java:224-250`（带登录态线程里 TenantIgnore 仍能跨租户）、`BondedListItTest.java:323`（page.total 只算本租户）。

## 犯了什么错 / 误判

以下都能从代码注释和回归测试找到依据：

1. **表名带反引号或大写时匹配不到全局表**：JSqlParser 保留原始写法，清单是全小写。解决是匹配前剥离反引号 + 小写（`WmsTenantLineHandler.java:100-107`；回归测试 `WmsTenantLineHandlerTest.java:104-121`）。
2. **JSqlParser 解析 MySQL JSON `->` 失败会中断请求**：包 Safe 层，解析失败改为跳过过滤（`SafeTenantLineInnerInterceptor.java:16-19, 33-39`）。代价是这一次查询没有租户过滤。
3. **`fba_carrier` 带 `tenant_id`，JOIN 时插件追加条件会撞歧义列**：加入跳过清单，由 DAO 显式 `eq`（`WmsTenantLineHandler.java:80-82`；测试 `WmsTenantLineHandlerTest.java:57`）。
4. **误以为插件能覆盖全仓**：存量 DAO 仍有大量手动 `eq("tenant_id")`（`WmsTenantLineHandler.java:21-23`），27 个 mapper XML 里 16 个仍写 `tenant_id =` 过滤条件；复杂 JOIN 依旧是裸 SQL。

## 怎么解决

- 能用插件改写的单表/简单 wrapper 交给插件；跳过清单只收「无 `tenant_id` 列」「确需跨租户」「已有显式过滤」三类。
- 跨租户查询统一走 `TenantIgnore.call`，不让调用方手写 `InterceptorIgnore`。
- 复杂 XML 裸 SQL 自己写租户条件；`goods` 这种 99.98% NULL 的表，手写 `(tenant_id = ? OR tenant_id IS NULL)`（`GoodsMapper.xml:14-27`）。
- 用 IT 验证：跨租户不可见、count 同口径、带登录态时 TenantIgnore 仍生效。

## 现在的规矩

- 新表有 `tenant_id` 且不是全局表：不进清单，让插件过滤。
- 平台账号（`tenant_id` 为空）：全量模式，SQL 里显式表达 `IS NULL`。
- 跨租户读取必须 `TenantIgnore` + 上游归属校验。
- 不写「全仓租户隔离已完成」；插件只覆盖它能解析、且表在清单外的语句。
