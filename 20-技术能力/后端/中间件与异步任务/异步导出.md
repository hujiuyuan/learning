# 异步导出

所属通用技能：[[中间件与异步任务]]

**一句话**：把「同步查全量再写 Excel」拆成「建记录拿 id → 后台翻页写盘 → 上传 → 回填状态」，用记录表承载生命周期，用信号量保护下游。

## 方法总纲

1. 主线程只做三件事：抓登录上下文、建 `io_record`（PROCESSING）、拿接纳许可；拿不到就标失败并抛 `EXPORT_QUEUE_FULL`。
2. 工作线程：拿执行许可 → 翻页取数 → FastExcel 写临时文件 → 上传 S3 → `markDone`；任何异常 `markFailed`。
3. 进度写 Redis（失败不影响主流程），终态写数据库；前端轮询记录列表。

## 我会的部分

- **提交**：`submit` 同步建记录并返回 `recordId`（`ExportServiceImpl.java:85-95`）；登录上下文在主线程抓快照（`:86`），异步线程用 `ScopedValue` 绑定（`:118`）。
- **执行器**：每个任务一个虚拟线程（`ExportPoolConfig.java:41-44`）；`destroyMethod="shutdown"` 显式指定，避免 Spring 推断 `close()` 无界阻塞停机（`:31-39`）。
- **两道限流**：接纳许可 = 并发 + 排队，`tryAcquire` 非阻塞，满即拒绝（`ExportPoolConfig.java:57-63`、`ExportServiceImpl.java:101-112`）；执行许可 = 并发，虚拟线程内 `acquire` 排队（`ExportPoolConfig.java:65-71`、`ExportServiceImpl.java:117`）。
- **翻页**：`PAGE_SIZE=2000`（`ExportServiceImpl.java:45`）；按 `total` 判定终止，空页兜底，防止「本页不满 2000 就误判末页」（`:162-169`）。
- **写盘上传**：FastExcel 写临时文件 → `s3PresignUtil.putObject` → `markDone`（`:172-175`）；临时文件在 finally 删除（`:200-203`）。
- **进度**：Redis 存 `written/total`，TTL 1 小时，读写失败只 warn（`ExportProgressStore.java:32-47`、`RedisConstant.java:222-225`）。
- **失败**：取数异常、中断、过载都 `markFailed` 存 i18n key（`ExportServiceImpl.java:104-111`、`:197-199`；`IoRecordServiceImpl.java:113-120`）。
- **接入面**：设计清单 14 个标准分页导出（`smart/docs/superpowers/specs/2026-06-01-async-export-design.md:228-245`、`smart/docs/superpowers/plans/2026-06-01-async-export.md:978`）；当前代码有 20 处 `submit` 调用，含 Info/Warehouse 动态列导出（`InfoServiceImpl.java:7701`、`WarehouseServiceImpl.java:3516`）。
- **测试**：正常返回 id（`ExportServiceImplTest.java:118`）、过载拒绝（`:121`）、翻页截断回归（`:133`）、biz 映射与 handler 挂载（`InfoExportAsyncTest.java:30`、`:67`）。

## 选型与取舍

### 为什么用「记录表 + 虚拟线程」，不用同步导出/消息队列/Spring Batch

| 方案 | 优势 | 代价 | 项目里的位置 |
| --- | --- | --- | --- |
| 同步导出 | 实现最简单、调用方直接拿文件 | 请求线程被大查询/写盘/上传占住，超时、内存高；并发几个就把 Tomcat 打满 | 未选 |
| 记录表 + 虚拟线程（当前） | 同步只建记录拿 id；状态可查、可重试/回收；虚拟线程扛阻塞 IO；不依赖 MQ | 要维护记录表/状态机/reaper；下游容量仍要自己限 | 选定 |
| 消息队列 + 消费者 | 削峰、解耦、可横向扩消费者 | 多一套 MQ 运维；任务状态仍要落库；消费重复要幂等 | 未选，RocketMQ 只做事件驱动 |
| Spring Batch | 分片、重试、跳过、作业仓库成熟 | 引入批处理框架和作业配置；当前只有单表 xlsx 导出，过重 | 未选 |

记录表不是为了「异步」，是为了「可查询的生命周期」：提交、执行、成功/失败、进度、重试都要有地方落。MQ 只负责传输，不负责状态；没有记录表，消息丢了/重复了调用方查不到。

### 为什么用虚拟线程，不是固定大小线程池

导出是阻塞 IO（翻页查库、写 Excel、传 S3），虚拟线程在阻塞时让出载体线程，代码仍是同步写法；固定池要按「并发 × 下游容量」配，配大了打爆 DB/S3，配小了排队。虚拟线程降低的是线程成本，不是下游容量——所以并发仍由两道 Redisson 信号量控制（`ExportPoolConfig.java:57-71`、`ExportServiceImpl.java:101-118`）。

### 为什么两道闸门 + Redis 进度

- 接纳许可 = 并发 + 排队，拿不到立刻 `EXPORT_QUEUE_FULL`，不让请求无限堆；执行许可 = 并发，真正保护 DB/S3。两个数分开，才能表达「允许多少在跑、允许多少在等」。
- 用 `RPermitExpirableSemaphore` 而不是 JVM `Semaphore`：多副本共享配额，节点崩溃租约到期自动归还；普通 `RSemaphore` 没有自动归还，节点被杀会永久丢许可（`ExportPoolConfig.java:46-55`）。
- 进度写 Redis 而不是每页写库：翻页频率高，写库会放大事务/锁；进度丢了不影响终态，终态仍以 `io_record` 为准（`ExportProgressStore.java:32-47`）。

### 代价与反悔条件

- 单 sheet、无取消、无文件过期清理；超过 104 万行要分 sheet，当前没做。
- 30 分钟许可租约 + 30 分钟 reaper 阈值假设「租约到期 = 执行者已死」；超长导出会被 reaper 误杀，之后 `markDone` 又覆盖。导出变长就要调大阈值或分段。
- 如果导出变成「多 sheet、可取消、可重试编排、需要分片」→ 评估 Spring Batch/队列消费者；如果只是少量小文件、同步可接受 → 退回同步，省掉记录表和 reaper。

## 边界

- 只导出 xlsx，单 sheet；超过 104 万行要分 sheet，没做。
- 不做文件过期清理、不做多 sheet、不做导出取消。
- 关机时在途任务直接放弃，`io_record` 靠 `IoReaperJob` 30 分钟后回收（`IoReaperJob.java:32-63`）；不是优雅排空。
- 导出内容不 i18n，只有错误提示按请求语言翻译。
- 单次导出超过 30 分钟时，许可租约和 reaper 阈值都会先到期；代码假设「租约到期 = 执行者已死」，这个假设对超长导出不成立。
