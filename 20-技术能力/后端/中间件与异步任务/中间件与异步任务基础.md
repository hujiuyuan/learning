## 1. 线程池

**一句话**：线程池先填 core，再入队，队列满才扩到 max，超过 max 触发拒绝策略；参数要按任务类型和下游容量定。

要能回答：

- core、max、queue、keepAlive、拒绝策略分别怎么影响行为？
- 无界队列为什么让 max 失效？
- 四种拒绝策略分别适合什么场景？
- CPU 密集和 IO 密集任务的线程数怎么估？
- 线程池怎么做监控？活跃数、队列长度、拒绝数说明什么？
- 线程池满了，调用方应该阻塞、降级还是失败？

**笔记**：

- 提交任务：核心线程未满建核心线程；核心满入队；队列满扩到 max；max 满拒绝。`keepAlive` 管非核心线程空闲回收（`allowCoreThreadTimeOut` 可让核心也回收）。无界队列（`LinkedBlockingQueue` 不传容量）会让队列永远不满，max 永远用不上，过载被推迟到 OOM。
- 拒绝策略：Abort 抛 `RejectedExecutionException`（默认，调用方必须处理）；CallerRuns 让提交线程自己跑（降速，但可能阻塞请求线程）；Discard 静默丢；DiscardOldest 丢最旧。业务任务用 Abort/CallerRuns，监控拒绝数；静默丢只适合可丢的日志/指标。
- CPU 密集约 N+1；IO 密集约 2N 或按 `N × (1 + 等待时间/计算时间)` 估；最终靠压测和监控。线程太多上下文切换、内存涨；队列太长会把过载藏起来，延迟飙升。
- 监控：活跃线程数、队列长度、拒绝数、任务耗时、池大小；活跃高 + 队列涨说明容量不足，拒绝数说明过载已经发生。Micrometer/Actuator 可暴露。
- 满了怎么办：拒绝并快速失败（保护下游）、调用方阻塞排队（降速但占线程）、降级（返回缓存/默认值）。没有通用答案，按业务 SLA 选；不能让无界队列替你决定。

## 2. 异步任务与上下文

**一句话**：`@Async` 把方法丢到另一个线程执行；ThreadLocal、SecurityContext、请求属性都不会自动过去，必须显式传播。

要能回答：

- `@Async` 生效条件？同类自调用为什么失效？
- Spring 默认 `Executor` 是什么？为什么不建议用默认的？
- 异步任务的异常怎么捕获？`AsyncUncaughtExceptionHandler` 管什么？
- 事务上下文能传播到异步线程吗？
- 登录用户、租户、TraceId 怎么传到异步线程？
- 异步任务的返回值 `Future`/`CompletableFuture` 怎么处理超时？

关联：[[ScopedValue上下文]]、[[异步导出]]

**笔记**：

- `@Async` 靠代理生效：方法必须 public、从代理对象调用、Bean 由 Spring 管理、启动了 `@EnableAsync`。同类自调用、private/final 方法不生效，和 `@Transactional` 一样。
- Spring Boot 默认用 `applicationTaskExecutor`（`ThreadPoolTaskExecutor`），但如果没有合适 Bean，可能退到 `SimpleAsyncTaskExecutor`（每次新建线程、无上限）。项目里显式声明线程池，避免默认执行器不可控。
- `@Async` 方法返回 `void` 时异常没人接，用 `AsyncUncaughtExceptionHandler` 记录；返回 `Future/CompletableFuture` 时调用方要 `get/join` 并处理异常，否则异常被吞。
- 事务上下文绑定线程，不会传播到 `@Async` 线程；异步线程里写库是另一个事务/连接。需要「提交后异步」用 `afterCommit` 再提交任务；需要同一事务就別异步。
- 登录用户、租户、TraceId 放 ThreadLocal 不会自动过去；主线程抓快照，异步线程显式恢复（`ScopedValue`、`TaskDecorator`、MDC 复制）。项目用 `ScopedValue` 绑定登录上下文，见 [[ScopedValue上下文]]。
- `Future.get(timeout)` 要设超时；`CompletableFuture` 用 `orTimeout`/`completeOnTimeout`；线程池队列积压时，超时只能让调用方放弃，任务还在跑，要配合取消/幂等。

## 3. 虚拟线程

**一句话**：虚拟线程由 JVM 调度，阻塞时让出载体线程；适合 IO 密集、大量并发的任务，不适合 CPU 密集或长时间 `synchronized` 阻塞。

要能回答：

- 平台线程和虚拟线程的区别？虚拟线程怎么调度？
- 虚拟线程为什么不能池化？
- pinning 是什么？哪些操作会 pin 住载体线程？
- 虚拟线程适合什么、不适合什么？
- 虚拟线程下 ThreadLocal 有什么问题？
- 虚拟线程和响应式编程怎么选？

关联：[[Java并发与虚拟线程]]

**笔记**：

- 平台线程一对一映射 OS 线程；虚拟线程由 JVM 调度到少量载体线程（ForkJoinPool），阻塞时卸载，载体去跑别的虚拟线程。创建成本低，可以一个任务一个。
- 不能池化：池化会限制并发、让虚拟线程排队，失去意义；用 `Executors.newVirtualThreadPerTaskExecutor()`，每个任务新建。
- pinning：虚拟线程在 `synchronized` 块/JNI/native 调用里阻塞时不能卸载，载体被占住；大量 pinning 会退化。用 `ReentrantLock` 替代长 `synchronized`，避免在锁里做 IO。
- 适合 IO 密集（HTTP、DB、文件）、高并发请求；不适合 CPU 密集（还是要有界线程池）、长时间计算。
- 虚拟线程的 ThreadLocal 每个线程一份，数量大时内存高；用 `ScopedValue` 或显式参数。项目里用 `ScopedValue` 传上下文。
- 响应式（WebFlux/Reactor）用非阻塞 API + 事件循环，适合流式/背压；虚拟线程让阻塞代码也能高并发，适合现有 MVC 迁移。CPU 密集/复杂流处理响应式更合适。

## 4. Redis 与分布式锁

**一句话**：Redis 常用作缓存、锁、计数和信号量；分布式锁要解决互斥、过期、续期、误删和脑裂。

要能回答：

- Redis 常用数据结构和典型场景？
- `SET NX EX` 怎么实现锁？为什么 value 要放唯一标识？
- 锁过期了业务没执行完怎么办？看门狗怎么续期？
- 解锁为什么要用 Lua 保证原子性？
- Redisson 的 `RLock`、`RSemaphore`、`RPermitExpirableSemaphore` 分别适合什么？
- Redis 主从切换时锁会丢吗？RedLock 解决了什么、没解决什么？

关联：[[Redisson]]

**笔记**：

- String 计数/缓存、Hash 对象、List 队列、Set 去重、ZSet 排行榜/延迟队列；Bitmap/HLL/GEO/Stream 是扩展结构。缓存模式、过期淘汰、持久化见 [[Redis 基础]]。
- `SET key uniqueValue NX EX ttl`：NX 互斥、EX 防死锁、uniqueValue 防误删。解锁 Lua 比对 value 再删，保证「比较 + 删除」原子。
- 锁过期业务没完：看门狗定时续期（Redisson 默认 30 秒锁、10 秒续）；进程 pause/续期线程挂仍可能过期，业务要有幂等/版本兜底。
- `RLock` 可重入锁（Hash 存持有者 + 重入次数）；`RSemaphore` 普通信号量，没有自动归还；`RPermitExpirableSemaphore` 带租约，节点崩溃到期自动归还，适合导出/导入限流。
- Redis 主从异步复制：主库写锁后宕机，从库可能没收到，提升后锁丢失；RedLock 向多个独立实例加锁降低风险，但仍有时钟漂移/暂停/网络延迟问题。强一致场景用 ZooKeeper/etcd/数据库唯一约束。

## 5. 消息队列

**一句话**：MQ 解耦、削峰、异步；核心语义是投递至少一次/至多一次/恰好一次，业务必须自己处理重复和顺序。

要能回答：

- 消息队列的三种投递语义分别怎么实现？
- 消费者 ack 的时机怎么选？先 ack 后处理会丢什么？
- 消息重试、死信队列、延迟消息分别怎么用？
- 怎么保证消息顺序？分区键怎么选？
- 消息堆积怎么排查、怎么扩容？
- 事务消息和本地消息表各解决什么问题？

**笔记**：

- 至多一次：先 ack 再处理，进程崩了消息丢；至少一次：处理完再 ack，失败重投，可能重复；恰好一次：靠事务/幂等 + 去重，MQ 本身很难保证「端到端恰好一次」。业务默认按至少一次设计。
- ack 时机：处理成功再 ack；先 ack 后处理会丢消息，处理失败也不会重投。消费失败要 nack/重试，超过次数进死信。
- 重试：指数退避，限制次数；死信队列存无法处理的消息，人工/补偿；延迟消息用于超时取消/定时提醒，不是普通重试。
- 顺序：同一分区/队列内有序，分区键选业务主键（订单号/用户 ID）；跨分区不保证。全局有序代价高，通常只要求「同一业务实体有序」。
- 堆积：看消费速率 vs 生产速率、分区数、消费者数、单条处理耗时；扩容消费者/分区、优化慢消费、降级非核心消息。堆积时先保护下游，不要盲目扩容打爆 DB。
- 事务消息：MQ 半消息 + 本地事务 + 回查，保证「本地事务成功才投递」；本地消息表/Outbox 把消息和业务同库同事务，后台投递。两者都靠消费端幂等。

## 6. 定时任务

**一句话**：单机定时任务用 cron/`@Scheduled`；多副本必须加分布式锁或选主，否则会重复执行。

要能回答：

- cron 表达式怎么写？时区怎么影响执行时间？
- `@Scheduled` 默认线程池多大？长任务会阻塞什么？
- 多副本怎么保证只执行一次？锁的粒度怎么定？
- 任务执行到一半宕机怎么办？补偿和重跑怎么设计？
- 错过触发时间（misfire）怎么处理？
- XXL-Job 的路由策略、阻塞策略、失败重试怎么配？

关联：[[XXL-Job]]、[[定时任务多副本锁]]

**笔记**：

- cron 是「分 时 日 月 周」，时区由 JVM/调度器决定；容器 UTC、业务东八区会让「每天 3 点」变成北京时间 11 点，必须显式指定时区。
- `@Scheduled` 默认单线程调度器，一个长任务会阻塞其他定时任务；要配 `TaskScheduler` 线程池，或把长任务丢到异步执行器。
- 多副本：每个副本都会触发，必须分布式锁/选主；锁粒度按任务/业务键，不能一把大锁锁所有任务。抢锁失败静默跳过，不要让错误日志刷屏。
- 执行到一半宕机：任务要幂等/可重跑，状态落库；下次触发或 reaper 回收中间态。不能假设「任务一定跑完」。
- misfire：错过的触发怎么补？`@Scheduled` 没有复杂 misfire 策略；XXL-Job/Quartz 可配「立即补一次/忽略/顺延」。补跑要幂等，不能重复扣款。
- XXL-Job：路由策略（轮询/故障转移/分片广播）、阻塞策略（单机串行/丢弃后续/覆盖之前）、失败重试次数；分片广播适合大批量数据处理，每个分片处理一部分。

## 7. 背压与限流

**一句话**：异步系统必须有上限；信号量、队列长度、连接池、限流算法都是背压手段，没有上限就会被流量打穿。

要能回答：

- 背压是什么？没有背压会发生什么？
- 信号量和线程池队列的区别？
- 漏桶、令牌桶、滑动窗口分别适合什么？
- 限流应该放在网关、服务还是下游？
- 过载时应该拒绝、排队还是降级？
- 怎么观测排队时间和拒绝率？

关联：[[导出背压]]

**笔记**：

- 背压是「下游处理不过来时，让上游感知并降速/拒绝」；没有背压，请求堆在无界队列/线程池，延迟涨、内存涨，最后 OOM 或雪崩。
- 信号量控制「同时处理数」，队列控制「等待数」；信号量满直接拒绝/阻塞，队列满才拒绝。两者要一起算：接纳 = 并发 + 排队，否则队列无限涨。
- 漏桶：固定速率流出，适合平滑流量；令牌桶：按速率放令牌，允许突发；滑动窗口：统计最近窗口的请求数，适合精确限流。业务限流常用令牌桶/滑动窗口。
- 限流放网关（全站入口，粗粒度）、服务（接口级，细粒度）、下游（保护 DB/第三方）；多层限流，额度逐层收窄。只在一层限流，其他层仍可能被打穿。
- 过载：拒绝（快速失败，保护自己）、排队（降速但占资源）、降级（返回缓存/默认值/异步受理）。按业务选，不能所有接口都排队。
- 观测：排队时间、拒绝率、并发数、队列长度、下游错误率/延迟；没有这些指标，限流参数只能拍脑袋。
