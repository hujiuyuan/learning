# 定时任务多副本锁

技能点：[[Redisson]] · 方法：分布式锁 · 通用技能：[[中间件与异步任务]]

**什么时候会遇到**：服务上了多副本，或者滚动发布时 staging 与旧 active 共存；`@Scheduled` 在每个进程里都会到点触发，同一任务被跑了 N 次。

## 判断顺序

1. 列出所有 `@Scheduled` 方法（本仓库 5 个类、8 个方法）。
2. 逐个看有没有分布式锁；锁 key 是否稳定、是否带前缀。
3. 看抢锁失败怎么处理：抛异常污染错误日志，还是静默跳过。
4. 看锁的租约：固定 leaseTime 还是看门狗？任务可能跑多久？
5. 看任务本身：重复执行会写坏数据吗？空转吗？有 `updated N rows` 日志吗？

## 手段

- **统一封装**：`RedisLockUtil.withLock(key, action)`，waitTime=3s，不传 leaseTime 启用看门狗；抢不到抛 `SYS_BUSY`（`RedisLockUtil.java:18`、`:29`、`:39-56`）。
- **抢锁失败静默**：捕获 `SYS_BUSY` 记 info 后 return，其余异常照常抛（`OmpTenantBackfillJob.java:53-62`）。测试断言抢锁失败时不碰 DB（`OmpTenantBackfillJobTest.java:80-84`）。
- **锁包住整个临界区**：锁在事务外，`finally` 里 `isHeldByCurrentThread` 再 unlock（`RedisLockUtil.java:50-55`）。
- **既有裸写法**：`NotificationScheduler` 直接 `getLock` + `tryLock(0, 300, SECONDS)`，失败 return（`NotificationScheduler.java:58-62`）。
- **锁 key 常量化**：`RedisConstant.LOCK_OMP_BACKFILL`、`LOCK_IO_REAPER` 等（`RedisConstant.java:197-209`）。
- **部署窗口**：`switch.sh` 滚动部署时 staging 与旧 active 最长共存 180 秒，两者同连一个库且都跑定时任务（`OmpTenantBackfillJob.java:46-49`）。

## 反例 / 边界

- **锁只防重复，不防无效**：`OmpTenantBackfillJob` 每小时 9 条全表 UPDATE，5 天跑了 1,114 次、7,736 秒、更新 0 行；加了锁仍然每小时空转 57 秒，见 [[测试库整点卡顿]]、[[定时任务与数据库负载]]。
- **自停守卫未实现**：诊断报告建议「上轮 0 行就跳过后续扫描 + 降频到每天」，当前代码仍是每小时整点跑，没有任何自停或降频逻辑（`OmpTenantBackfillJob.java:51`、`:66-158`）。
- **固定 300s 租约**：`NotificationScheduler` 的任务跑超 5 分钟，锁会自动释放，另一个副本会进来重复跑；`RedisLockUtil` 的看门狗没有这个问题。
- **锁的粒度**：锁住整个任务，任务慢时其他副本等 3 秒后跳过；不需要「排队执行」，跳过就是预期。
- **单机多线程**：`@Scheduled` 默认单线程，同一 JVM 内不会并发；但手工触发或接口触发会，锁仍然需要。

## 深层原理

- **Redisson 看门狗是「租约 + 定时续期」**：默认锁 30 秒、每 10 秒续一次；只要持有线程活着，锁不会过期。但 JVM 长时间 GC/STW、线程被挂起、网络分区超过租约，续期没发生，锁就过期，另一个副本会进来——此时两个执行者可能同时写。锁的互斥只在「租约有效」期间成立。
- **Redis 主从是异步复制**：主库写锁成功后还没同步到从库就宕机，从库提升后锁消失；另一个客户端能拿到同一把锁。RedLock 向多个独立实例加锁降低概率，但仍有时钟漂移/暂停/网络延迟问题；强一致场景要用数据库唯一约束/ZooKeeper/etcd。
- **锁只防重复，不防无效**：空转任务有锁也照样每小时扫全表；锁解决「谁跑」，不解决「该不该跑」。任务本身要幂等、要记录 `updated N rows`、长期 0 行要降频/自停。
- **固定租约 vs 看门狗**：`tryLock(0, 300, SECONDS)` 是固定 5 分钟租约，任务跑超 5 分钟锁自动释放，另一个副本会重复跑；`RedisLockUtil.withLock` 不传 leaseTime 启用看门狗，适合长任务。选哪种取决于「任务最长执行时间是否可预估」。

## 现在的规矩

- 每个 `@Scheduled` 都必须有分布式锁，包括「看起来只读」的任务。
- 抢锁失败一律静默跳过，不打 error、不上抛。
- 长任务优先用 `RedisLockUtil`（看门狗），不要手写固定租约。
- 任务必须记录 `updated N rows`；长期 0 行要降频或自停（这条尚未落地）。
- 多副本上线前先确认 `switch.sh` 的共存窗口和锁 key 是否一致。
