# S3 与对象存储

所属通用技能：[[中间件与异步任务]]

**一句话**：S3 协议把文件当对象存，业务只拿 key；项目里用预签名 URL 让前端直传/直下，后端不中转大文件。

路径说明：以下路径相对 `smart-server-wms3/src/main/java/com/track/wms/`。

## 方法总纲

1. **业务只存 key**：数据库存对象 key，不存完整 URL；endpoint 变了只改配置。
2. **上传用预签名 PUT**：前端拿 URL 直接传 S3，后端不占带宽和内存。
3. **下载用预签名 GET**：短过期 URL，避免 bucket 公开读。
4. **大文件走分片**：初始化 uploadId → 每片预签名 → 合并；失败要 abort。
5. **contentType 别乱传**：AWS SigV4 不签未列出的头，阿里云 OSS V4 会签 `Content-Type`；两套实现不对称。
6. **key 要可定位**：按业务/租户/日期分层，避免大目录和冲突。

## 选型与取舍

### 为什么用对象存储，不用本地磁盘/NFS

- 对象存储把文件从应用服务器剥离：应用重启/扩容不丢文件，多副本共享同一份 key，预签名 URL 还能让前端绕过后端直传/直下。
- 代价：多一个外部依赖和网络延迟；权限、生命周期、跨区域、限流都要单独运维；强一致/事务性不如数据库，删文件/写记录不能同事务。
- 本地磁盘/NFS 更简单，但多副本共享、扩容、备份都要自己做；项目文件量/多副本需求超过本地盘能承受的范围，所以选对象存储。

### 为什么用预签名 URL，不让后端中转

- 后端中转大文件会占线程、内存和带宽，导出/导入的并发会被文件传输拖死；预签名 PUT/GET 让客户端直连对象存储，后端只签名和记录 key。
- 代价：URL 泄露即在过期前可访问；bucket 权限、CORS、contentType 要配对；前端要处理分片/重试/取消。项目用短过期 URL + 不公开 bucket 降低风险。
- 如果文件很小、或必须由后端做病毒扫描/内容审查，中转更合适；当前大文件导出/导入多，预签名更划算。

### 为什么用分片上传，不一次性 PUT

- 大文件一次性 PUT 失败要重传整个文件；分片可以只重传失败片，合并前还能校验 partNumber 顺序。
- 代价：要维护 uploadId、分片状态、失败 abort；断点续传/过期清理要另做。项目只做到初始化/签名/合并/中止，没有完整断点续传状态机，边界里写明了。
- 小文件用分片反而增加请求数；项目按文件大小/场景选择，单文件直传仍保留 `put(byte[])`/`put(File)`。

### 为什么业务存 key，不存完整 URL

- endpoint/桶名/域名会变（本地 MinIO、测试 localstack、生产 OSS/S3），存完整 URL 会把环境绑死；存 key + 配置生成 URL，迁移只改配置。
- 代价：每次读要生成预签名 URL，多一次签名开销；key 设计要可定位（业务/租户/日期），否则大目录/冲突。
- 如果 URL 永久不变且公开读，存 URL 更简单；项目 bucket 不公开，必须动态签名。

### 什么条件下会反悔

- 需要 CDN/跨区域加速 → 加 CDN/多区域复制，预签名 URL 的域名/权限要重配。
- 文件合规要求病毒扫描/内容审查 → 改成后端中转或上传后扫描，预签名直传的链路要加回调。
- 分片失败/断点续传成为常态 → 补完整状态机和过期清理；当前只做基础分片。

## 我会的部分

- **统一抽象**：`FileStore` 接口屏蔽 AWS S3 / MinIO / 阿里云 OSS 差异，`S3FileStore` 是包私有实现（`common/util/S3FileStore.java:28-29`、`common/util/FileStore.java:1-60`）。
- **预签名 PUT**：设置过期时间，返回 URL；`contentType` 在 AWS 实现里刻意忽略（`S3FileStore.java:63-73`）。
- **预签名 GET**：按 key 生成短过期下载 URL（`S3FileStore.java:98-106`）。
- **直传/直读**：`put(byte[])`、`put(File)` 用于后端已有内容；`get(key)` 返回流，调用方负责关闭（`S3FileStore.java:75-96`）。
- **分片上传**：`initMultipart` 拿 uploadId，`presignParts` 给每片签名，`completeMultipart` 按分片号升序合并，`abortMultipart` 清理（`S3FileStore.java:108-148`）。
- **分片顺序**：合并前按 partNumber 排序，不能依赖 Map 迭代顺序（`S3FileStore.java:130-141`）。
- **endpoint 兼容**：配置了 endpoint 就开 path-style，兼容 MinIO/localstack；否则用 AWS 虚拟主机地址（`S3FileStore.java:50-58`）。
- **异常翻译**：`NoSuchKeyException` 转成业务 `NoSuchObjException`，上层不依赖 AWS SDK（`S3FileStore.java:89-96`）。

## 边界

- 没有做过 bucket 生命周期、版本控制、跨区域复制、CDN 加速。
- 没有做过分片断点续传的完整状态机；只做了初始化/签名/合并/中止。
- 没有做过分片大小调优和大文件压测。
- 没有做过对象存储的权限策略（IAM Policy、Bucket Policy）设计。
- 没有在生产环境处理过 S3 限流和重试。
