# 全局异常与统一响应

技能点：[[Spring MVC]] · 方法：CoreControllerAdvice（待建） · 通用技能：[[Spring应用与接口契约]]

**什么时候会遇到**：接口要统一返回格式；同一个错误在不同接口返回不同 code；404/405 被兜成 500；前端只能靠 HTTP 状态判断成败。

## 判断顺序

1. 异常从哪来（框架/业务/未知），再映射到哪个 code（HTTP 段还是业务段）。
2. message 从哪来：`ResultCode` → `messageCode` → i18n；不用 `ex.getMessage()`。
3. HTTP 状态和日志：项目统一 200、body `code` 为准；用户输入错 `warn`，系统错 `error` + 堆栈。

## 手段

| 异常 | 处理器 | body code | message 来源 | 日志 |
| --- | --- | --- | --- | --- |
| `NoHandlerFoundException` / `NoResourceFoundException` | `CoreControllerAdvice.java:72-79`、`:90-97` | 404 | `NOT_FOUND` i18n | warn |
| `HttpRequestMethodNotSupportedException` | `:81-88` | 405 | `METHOD_NOT_ALLOWED` i18n | warn |
| `MethodArgumentNotValidException` | `:119-136` | 400 | 第一个 field error 的 `defaultMessage` 当 i18n key | warn |
| `HandlerMethodValidationException` | `:99-117` | 400 | 第一个 error 的 `defaultMessage` 当 i18n key | warn |
| `BindException` | `:152-160` | 400 | field error 的 `defaultMessage` | warn |
| `ConstraintViolationException` / `UnexpectedTypeException` | `:145-150`、`:138-143` | 400 | 固定 code 名对应的 i18n | 无 |
| `IllegalArgumentException` | `:162-167` | 400 | **`ex.getMessage()` 自由文本** | warn |
| `NullPointerException` / `Exception` | `:169-175`、`:64-70` | 500 | `INTERNAL_SERVER_ERROR` i18n | error + 堆栈 |
| `BusinessException` | `:177-194` | 保真业务码 | `messageCode` i18n；null 时退化 `INTERNAL_ERROR` | warn |

**统一包装**：`beforeBodyWrite` 依次放行 null、swagger/webjars、actuator、String（转 JSON）、Resource、已是 `Result`、`@IgnoreResponse`，其余包成 `Result.success`（`CoreControllerAdvice.java:201-245`）。

**HTTP 200 + body code 的取舍**：

- 现状：所有 handler 只返回 `Result`，不设 HTTP 状态；代码注释直接写「HTTP 200（与其他 handler 统一）」（`CoreControllerAdvice.java:72`、`:81`、`:90`）。
- 测试锁住：不存在的路径断言 `status().isOk()` + body `code=404`（`CoreControllerAdviceNotFoundTest.java:56-75`）。
- 好处：延续老 PHP 的 `{code,message,data}` 全 200 风格（`docs/API-endpoints-legacy.md:163-190`、`plan/GlobalExHandler与CoreControllerAdvice合并计划.md:27`），前端一套拦截器处理所有错误。
- 代价：HTTP 语义丢失，网关/监控/重试/缓存只看得到 200；成功码也从老系统的 `0` 变成 `200`（legacy 文档 `:169` vs `Result.java:78`），前端要同时接受 0 和 200（plan `:138-139`）。这是兼容取舍，不是 REST 最佳实践，新项目不要照抄。

**i18n**：请求语言 → 默认语言 → 返回 key 本身，三级降级（`I18nUtil.java:37-51`）；语言从 `?lang=` 取，缺省 en（`:71-87`、`application.yml:105-107`）；message 文件 basename 是 `i18n/message`（`application.yml:24-28`）。

**登录路径特殊日志**：`isLoginPath()` 判断 URI 是否包含 `/admin/login`（`CoreControllerAdvice.java:54-62`），但 WMS3 的登录接口是 `/api/v1/login`（`AuthController.java:39`、`:51`）。按代码推断，这个分支在当前服务不会命中；未跑运行时验证。

## 反例 / 边界

- 失败路径不要复制这两种写法：`IllegalArgumentException` 的 handler 还在回 `ex.getMessage()` 自由文本（`:166`）；`FilesController.java:101-115` 还有 4 处手写 `Result.error(String)`，code 固定 500、文案绕过 i18n。
- 404 想进 advice，必须开 `spring.mvc.throw-exception-if-no-handler-found` 并关静态资源映射（`application.yml:19-23`）；不要包装 actuator/swagger，会破坏探针状态码和 OpenAPI 解析，代码里显式放行（`:210-220`）。
- 405 处理器没有测试；`CoreControllerAdviceNotFoundTest` 只在注释里提到 405（`:26`），实际只测了 404。

## 现在的规矩

1. 业务失败抛 `new BusinessException(ResultCode.X)`；带参数用 `(ResultCode, Object[])`。
2. 前端消息只来自 messageCode 的翻译；动态细节进日志。
3. controller 不 catch，要么正常返回，要么抛。
4. 新增错误码先确认号段，再跑 `ResultCodeUniquenessTest`（`:34-56`）。
5. 404/405 继续返回 HTTP 200，除非前端和网关一起改。
