# 参数校验

技能点：[[Spring MVC]] · 方法：[[Bean Validation 入参校验]] · 通用技能：[[Spring应用与接口契约]]

**什么时候会遇到**：接口收前端参数，要在进业务前挡住空值、格式错、越界值；或者校验失败后前端拿到的提示和 code 不对。

## 判断顺序

1. 参数在哪：body / query / path / multipart。
2. 用哪种校验：DTO 字段注解（`@Valid`）还是方法参数注解（类级 `@Validated`）。
3. 失败抛哪个异常：body → `MethodArgumentNotValidException`；query DTO → `MethodArgumentNotValidException` 或 `BindException`；`@RequestParam` → `HandlerMethodValidationException` 或 `ConstraintViolationException`（取决于是否被 AOP 代理，项目里未验证）。
4. message 是 i18n key 还是字面量。
5. 有没有嵌套对象：每层都要 `@Valid`。
6. 测试断言的是 body code 还是只断言 HTTP status。

## 手段

- **body 校验**：`@Valid @RequestBody`（`CompanyController.java:53`、`LoginLogController.java:43`、`WarehouseController.java:98`）。
- **query DTO**：`@Valid WarehouseListReq request`（`WarehouseController.java:82`）。
- **直接参数**：类级 `@Validated`（`WarehouseController.java:46`）+ `@NotNull @RequestParam`（`:175`、`:212`、`:226`、`:240`、`:308`、`:322`，共 6 处）。
- **消息就是 key**：`@NotBlank(message = "COMPANY_CODE_REQUIRED")`（`CompanyCreateReq.java:17`）、`LIST_TYPE_REQUIRED`/`LIST_TYPE_PATTERN`（`WarehouseListReq.java:27-29`）。
- **嵌套校验**：`@Valid @NotNull PageInfo page`（`LoginLogPageReq.java:18-20`）。
- **异常到 code**：
  - `MethodArgumentNotValidException` → `BAD_REQUEST`(400)，取第一个 field error 的 `defaultMessage` 当 i18n key（`CoreControllerAdvice.java:127-135`）。
  - `HandlerMethodValidationException` → `PARAMS_INVALID`(400)，取第一个 error 的 `defaultMessage`（`:108-116`）。
  - `ConstraintViolationException` → `VALIDATION_INVALID_PARAMETER`(400)，固定文案（`:145-150`）。
  - `BindException` → `BAD_REQUEST`(400) + field `defaultMessage`（`:152-160`）。
- **只回第一条错误，不回字段名**：两个 validation handler 用 `findFirst()`，`BindException` 取 `getFieldError()`，`ConstraintViolationException` 直接回固定文案。
- **登录路径特殊日志**：`isLoginPath()` 判 `/admin/login`（`:54-62`），WMS3 登录是 `/api/v1/login`（`AuthController.java:39`、`:51`），该分支按代码推断不会命中。

## 反例 / 边界

- 别在 controller 手写 if 返回 `Result.error`：`FilesController.java:101-115` 有 4 处，code 固定 500，不是参数错误的语义。
- 别只加约束不加 `@Valid`：`@RequestBody` 不加 `@Valid` 不触发校验。
- `@RequestParam` 上的约束全仓只出现在 `WarehouseController`（6 处），且类上有 `@Validated`；别的 controller 没有这类型约束，不要以为方法参数注解会自动生效。
- **四个 handler 的 body code 都是 400**（`BAD_REQUEST`、`PARAMS_INVALID`、`VALIDATION_INVALID_PARAMETER` 的数字码都是 400），前端只能靠 message 区分，不能靠 code。
- 业务规则校验（时间先后、枚举组合、状态前置）不硬塞进注解：项目用 `BusinessException(LOG_TIME_REVERSED)` 这类具体码（`ResultCode.java:210-215`）。
- message key 缺翻译时，`I18nUtil` 降级返回 key 本身（`I18nUtil.java:44-50`），前端会看到 `COMPANY_CODE_REQUIRED` 这种字符串。
- 现有 e2e 断言偏松：有的只断言 HTTP status ∈ (200,400) 或 body `code != 200`（`AbstractPdaTrailerUnavailE2eTest.java:124-141`），锁不住具体码和文案。

## 现在的规矩

1. body 参数一律 DTO + `@Valid` + 字段注解。
2. `message` 写 i18n key，四个文件都要补：`message.properties`、`_en`、`_es`、`_zh_CN`。
3. 直接绑 `@RequestParam` 的必填参数，集中在类级 `@Validated` 的 controller 里（当前只有 `WarehouseController`）。
4. 跨字段/业务规则进 service，抛具体 `ResultCode`。
5. 新增校验补一条断言 body code 的测试，不只断言 HTTP status。
