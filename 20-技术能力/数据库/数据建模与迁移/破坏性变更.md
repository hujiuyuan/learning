# 破坏性变更

技能点：[[Flyway与多仓迁移]] · 方法：扩展 → 双写 → 切换 → 清理 · 通用技能：[[数据建模与迁移]]

**什么时候会遇到**：要改列名、改类型、删列、加非空列；或者多个服务共用一个库，发布不能同时停机。

## 判断顺序

1. **这个库有数据、且版本已发出去吗？** 有 → 只能做加法，不能原地改。
2. **新旧两版代码能同时跑吗？** 不能 → 先加新列/新表，让两版都能读写。
3. **读方什么时候切？** 双写 → 切读 → 确认没有旧读方，才允许删旧列。
4. **能不能不删？** 能保留就保留；`DROP COLUMN` 是最后一步，不是第一步。
5. **关联完整性靠什么？** 代码保证，不建外键——硬删一行不该带走别处的审计与历史。

## 手段

- 改列名/改类型：加新列 → 双写 → 切读 → 下一个版本删旧列，分三次发布（`muou-backend/muou-app-ops/databases/迁移编写约定.md:66-67`、`README.md:71-72`）。
- 迁移只能往前：已发布的版本不改，不写 `DROP COLUMN` 到刚发的版本里（同上）。
- 静态门禁：`validate-migrations.sh` 扫到 `DROP COLUMN` 直接失败（`muou-backend/muou-app-ops/databases/validate-migrations.sh:12-16`）。
- 列注释随建表一起写；缺注释 CI 判红（`迁移编写约定.md:64`、`validate-migrations.sh:18-50`）。
- 不建外键：关联降级成普通索引，引用完整性由代码保证（`迁移编写约定.md:65`、`README.md:66-72`）。
- 跨库不许连表，不是自己库的数据走服务接口（`README.md:73`）。

## 反例 / 边界

- **空库上的直接 drop 不算三次发布**：iam 的 `person_id → psn` 迁移直接 `DROP COLUMN` + `ADD COLUMN`，文件头写明「本单按空库交付……若要在已有数据的环境执行，按分三次发布走，本份不能直接照搬」（`muou-server-iam/muou-iam-app/db/migration/core/V202609211809__iam_psn_rename.sql:7-9`）。
- **同一批里先建新表再删旧列**：`V202609211808` 建 `iam_account_terms_consent`，`V202609211810` 删 `iam_account` / `iam_invite` 的六列 `terms_*`；文件头写明「新落点先存在，再撤旧列」（`.../V202609211810__iam_drop_terms_columns.sql:11-13`）。这是空库交付下的顺序保证，不是生产上的三次发布。
- **门禁只覆盖 ops 仓自己的迁移**：服务仓的 446 份迁移没有同等的静态扫描（`README.md:65` 写的是「CI 全 schema 扫描」，实现只扫 `migration/<db>`）。
- 没做过有数据的大表在线改列；没验证过双写期间的数据一致性。

## 现在的规矩

- 已发布库只做加法；删列/改名分三次发布。
- 新表先建、旧列后删，顺序写在文件名和迁移头注释里。
- 不建外键，关联完整性由代码保证。
- 建表必须带注释，缺注释即红。
- 生产执行人审 SQL，不跟着服务部署自动跑。
