# 数据建模

所属通用技能：[[数据建模与迁移]]

**一句话**：先定表的分层、主键和编号，再写建表 SQL，最后逐字段落字典——三层都对齐了，迁移才不会返工。

## 方法总纲

1. **分层**：平台共享（无 `tenant_id`）/ 租户业务 / 配置 / 日志 / 技术，五层决定隔离方式与存放位置。
2. **主键**：`uuid` + UUIDv7 应用侧生成，列名 `<实体单数>_id`。
3. **业务编号**：单独一列（`psn` / `no` / `code`），对外只暴露它。
4. **字段**：类型、可空、默认、注释逐列写清；横切五列统一。
5. **落迁移**：建表 SQL + 索引 + 注释 + RLS 策略放同一个迁移文件。

## 我会的部分

### 五层分层

`muou-server/docs/02-1-表设计.md:3` 把全库分五层：

| 层 | 特征 | 例子 |
| --- | --- | --- |
| ① 平台共享 | 无 `tenant_id`，平台受控服务访问 | `tenant` / `person` / `cert` |
| ② 租户业务 | 有 `tenant_id`，承载 PII/资金 | `account` / `order` / `identity` |
| ③ 配置 | 租户副本或平台预设 | `member_type` / `field_lib` / `form` |
| ④ 日志 | append-only、按月分区 | `audit_log` / `login_log` |
| ⑤ 技术 | 投递、幂等、发号、任务 | `outbox_event` / `idempotency_key` / `numbering_sequence` |

带不带 `tenant_id`、启不启 RLS 是建表前就要登记的结构决策（`muou-server/docs/03-3-RLS与多租户数据隔离.md:34`）。

### 建表 SQL + 逐字段字典

每张表在同一节里给两样东西（以 `tenant` 为例，`muou-server/docs/02-1-表设计.md:1233-1330`）：

- **建表 SQL**：列定义、`CHECK`、注释语句；
- **字段字典**：`# / 字段 / 类型 / 必填 / 默认 / 说明 / 出处`（`:1296`）。

字典的「出处」列把每个字段锚回 PRD 或 DDL 约定，避免「这个字段为什么存在」只能问作者。

### UUIDv7 应用侧主键

- 类型 `uuid`，DDL 不写 `DEFAULT`，禁 `bigserial` / 自增 / 雪花（`muou-server/docs/02-0-建表通用约束.md:245-248`）。
- 应用侧生成：`UuidUtil.nextId()`，前 48 位是毫秒时间戳，B-tree 插入接近追加写（`muou-server/src/main/java/com/voidtech/muou/common/util/UuidUtil.java:8-52`）。
- MyBatis-Plus 用 `IdType.INPUT`，在 DaoImpl 里显式赋值；`@TableId` 不能省，列名不是 `id`（`02-0-建表通用约束.md:264-289`）。

### 业务编号独立成列

- `psn` / `no` / `code` 与主键分列；编号在业务事件发生时才分配，主键不能等（`02-0-建表通用约束.md:293`）。
- 对外只暴露业务编号，不暴露主键——UUIDv7 前 48 位是时间戳，暴露即泄露创建时间（同上）。

### 不建外键

- 现行多仓约定：关联降级成普通索引，引用完整性由代码保证（`muou-backend/muou-app-ops/databases/迁移编写约定.md:65`、`README.md:66-72`）。
- 实际四份 init 里 `FOREIGN KEY` 计数为 0；退役目录里的旧外键不能照抄（`README.md:69-70`）。

### 列注释门禁

- 每张表 + 每个非自明列必须有 `COMMENT ON`，与建表写在同一个迁移里（`02-0-建表通用约束.md:65`、`:308`）。
- 静态校验扫建表脚本，缺注释即失败（`muou-backend/muou-app-ops/databases/validate-migrations.sh:18-50`）；全 schema 版本见 `MigrationTest#每张表和每个列都有注释`（`muou-server/src/test/java/com/voidtech/muou/migration/MigrationTest.java:422-430`）。

## 选型与取舍

| 选择 | 为什么 | 代价/失败模式 | 什么时候反悔 |
| --- | --- | --- | --- |
| UUIDv7 应用侧主键 | 分布式可生成、全局唯一、时间前缀让 B-tree 插入接近追加；对外不暴露自增规模 | 16 字节比 bigint 大；前 48 位泄露创建时间；应用必须记得赋值 | 单库小表、极致存储/索引密度 → bigint 自增；需要完全不可猜 → 随机 UUID + 独立业务编号 |
| 业务编号独立成列 | 对外只暴露 `psn/no/code`，规则可改；主键不承载业务含义 | 多一列 + 唯一索引；编号生成要防并发/重号 | 内部表、无对外编号需求 → 可省 |
| 五层分层（平台/租户/配置/日志/技术） | 建表前就决定要不要 `tenant_id`、要不要 RLS，避免后期加列/改隔离 | 分层判断错会导致跨层 JOIN/迁移返工；文档与迁移可能不一致 | 单租户产品 → 可简化；租户隔离改成独立库 → 分层要重划 |
| 不建外键 | 多仓/分库/批量导入不受约束阻塞；引用完整性由代码 + 对账保证 | 代码漏校验会产生孤儿行；删除/归档要自己扫关联 | 单库核心账务表、要求数据库级强一致 → 建外键 |
| 范式化为主、按查询冗余 | 业务库写多、要求一致；列表/报表再把展示字段冗余成物理列 | 冗余列要同步，漏更新会展示旧值 | 分析型/读多写少 → 宽表/星型模型 |
| 租户隔离用 `tenant_id` + RLS | 数据库强制过滤，应用漏条件也查不到别租户 | 连接上下文/策略/运维复杂度；owner 绕过要 `FORCE` | 租户少且合规要求独立备份 → 独立库/schema |

## 边界

- 五层与表清单来自设计文档，部分表还没有 Flyway 迁移；文档自己也标了「清单行数与推导数对不上」（`02-1-表设计.md:45`）。
- 02-0 的「建外键」是单体期口径，已被多仓约定推翻；两版并存，照现行约定写。
- 没有实际 MySQL 建表经验；这套字段类型映射是 PostgreSQL 口径。
