## 1. 建模层次

**一句话**：概念模型描述业务实体和关系，逻辑模型落到表、列、键，物理模型考虑索引、分区、存储引擎。

要能回答：

- 概念模型、逻辑模型、物理模型的区别？
- ER 图里的实体、属性、关系、基数怎么表达？
- 一对一、一对多、多对多怎么落表？
- 继承关系有哪几种落表方式？
- 建模时怎么和业务方对齐口径？

笔记：

- 概念模型：业务实体和关系（客户、订单、商品），不关心表；逻辑模型：表、列、主外键、约束；物理模型：索引、分区、存储引擎、数据类型。三层逐步落地，别一上来画表。
- ER 图：实体是矩形，属性是椭圆/字段列表，关系是菱形，基数用 1:1、1:N、M:N 标注；M:N 必须落中间表。
- 一对一：共享主键或唯一外键；一对多：多的一方持有外键；多对多：中间表（可带关系属性，如数量、时间）。
- 继承落表：单表（所有字段一张表 + 类型列，查询简单、字段稀疏）、每类一张表（公共字段重复）、 joined（父表 + 子表，规范化但查询要 join）。
- 和业务对齐：统一术语表（客户/用户/会员是不是一回事）、明确状态机和边界、确认历史是否需要留痕、确认删除语义（真删/软删/归档）。口径不一致，后面所有字段都白设计。

## 2. 范式与反范式

**一句话**：1NF 去重复列，2NF 去部分依赖，3NF 去传递依赖；反范式用冗余换查询性能，代价是一致性维护。

要能回答：

- 1NF、2NF、3NF、BCNF 分别解决什么问题？
- 什么时候应该反范式？冗余字段怎么保证一致？
- 宽表和范式化表各适合什么场景？
- 维度建模的星型、雪花模型是什么？
- 缓慢变化维（SCD）怎么处理？

笔记：

- 1NF：字段原子、不存重复组；2NF：非主属性完全依赖整个联合主键（消除部分依赖）；3NF：非主属性不依赖其他非主属性（消除传递依赖）；BCNF：每个决定因素都是候选键。
- 反范式：为了少 join/少聚合，冗余存储（如订单里存用户名、商品名）。代价是源数据变更要同步，方案有应用双写、触发器、定时对账；没有同步机制就别冗余。
- 宽表适合分析/报表/读多写少，一次查询少 join；范式化适合 OLTP、写多、要求一致。数仓常用宽表/星型，业务库保持范式。
- 星型模型：事实表（度量 + 维度外键）+ 维度表（描述属性）；雪花模型是维度表再规范化。星型 join 少、查询快，雪花省空间但 join 多。
- SCD：Type 1 直接覆盖（不保留历史）；Type 2 加版本行（`valid_from/valid_to/is_current`，保留历史）；Type 3 加「上一值」列（只留一版历史）。按是否需要追溯选。

## 3. 键与标识

**一句话**：主键唯一标识一行，业务键唯一标识业务对象；自增主键短、有序，UUID 全局唯一但索引开销大。

要能回答：

- 自然键和代理键怎么选？
- 自增 ID、UUID、UUIDv7、雪花 ID 各自的优缺点？
- 分布式系统为什么需要全局唯一 ID？
- 业务编号和主键为什么要分开？
- 联合主键什么时候用？有什么代价？
- 外键要不要建？各有什么利弊？

关联：[[UUIDv7与业务编号]]

笔记：

- 自然键是业务上有意义的唯一值（身份证、订单号）；代理键是无意义的主键（自增/UUID）。代理键稳定、短、与业务解耦；自然键省一列但业务规则变了会改主键。
- 自增：短、有序、索引友好，单库简单；UUIDv4：全局唯一、不可猜，随机写入导致页分裂/索引膨胀；UUIDv7：时间前缀、近似有序，兼顾；雪花 ID：时间 + 机器 + 序列，有序、需机器号管理。
- 分布式需要全局唯一 ID：多库/多服务/离线生成，不能依赖单库自增；还要考虑不可猜（对外暴露）、有序（索引/排序）、长度。
- 业务编号（订单号/客户号）和主键分开：业务编号可读、可对外、规则会变；主键只做内部标识。混用会把业务规则绑死在主键上。
- 联合主键适合中间表/关系表（`user_id, role_id`）；代价是所有引用它的外键/索引都要带两列，更新/迁移更麻烦。
- 外键：数据库保证引用完整性，防脏数据；代价是插入顺序/锁/级联/分库分表/批量导入性能。互联网业务常不建物理外键，靠应用校验 + 定期对账；强一致核心表可以建。

## 4. 字段与约束

**一句话**：字段类型够用就好，约束尽量交给数据库；`NOT NULL`、唯一索引、检查约束是最便宜的数据质量保障。

要能回答：

- `INT`、`BIGINT`、`DECIMAL`、`FLOAT` 怎么选？金额为什么不用浮点？
- `CHAR`、`VARCHAR`、`TEXT` 的区别？
- 时间、枚举、布尔、JSON 字段怎么设计？
- `NULL` 和空字符串的区别？`NULL` 对索引和唯一约束有什么影响？
- 唯一约束和唯一索引的区别？
- 软删除和唯一索引怎么共存？

笔记：

- 整数用 `INT`（约 21 亿）够用就别 `BIGINT`；可能超/分布式用 `BIGINT`。金额用 `DECIMAL/NUMERIC` 精确十进制，浮点是二进制近似，会出现 0.1+0.2≠0.3。
- `CHAR(n)` 定长、不足补空格，适合固定长度（国家码）；`VARCHAR(n)` 变长、有上限；`TEXT` 大文本、无实际上限。大多数用 `VARCHAR`，别用 `CHAR` 存变长。
- 时间用 `timestamptz`（PG）/`DATETIME`（MySQL）存时刻，墙钟语义单独存时区；枚举用 lookup 表或 `VARCHAR + CHECK`，数据库 enum 改值麻烦；布尔用 `BOOLEAN/TINYINT(1)`；JSON 用 `JSONB` 且只放扩展字段。
- `NULL` 是「未知/不存在」，空字符串是「有值但为空」；`NULL` 参与比较结果是 unknown，`=` 匹配不到，要用 `IS NULL`。唯一索引里多个 `NULL` 通常允许（PG/MySQL），唯一约束不拦 NULL。
- 唯一约束是逻辑约束，底层用唯一索引实现；唯一索引是物理结构。PG 可建部分唯一索引/表达式唯一索引，MySQL 8 不支持部分索引。
- 软删除 + 唯一索引：PG 用部分唯一索引 `WHERE deleted_at IS NULL`；MySQL 用「删除时把唯一列改成 `code#id`」或加 `deleted_at` 进联合唯一（默认 0/固定值），或生成列只在未删除时有值。

## 5. 索引设计

**一句话**：索引为查询服务；联合索引按最左前缀匹配，区分度高的列靠前，覆盖索引能避免回表。

要能回答：

- 主键索引、唯一索引、普通索引、联合索引的区别？
- 联合索引的列顺序怎么定？
- 哪些查询用不上索引？
- 索引越多越好吗？写放大和空间成本怎么权衡？
- 前缀索引适合什么字段？
- 怎么发现无用索引？

关联：[[索引失效]]

笔记：

- 主键索引唯一且非空；唯一索引保证唯一、可多列；普通索引只加速查询；联合索引按列顺序匹配，可覆盖多个查询前缀。
- 列顺序：等值条件列在前，范围/排序列在后；区分度高（不同值多）的列靠前；但要看实际查询，别为「区分度」牺牲最常用的等值前缀。
- 用不上索引：列上有函数/表达式、隐式类型转换、`LIKE '%x'`、`OR` 跨无索引列、低选择性（返回大部分行）、统计信息过期。
- 索引不是越多越好：每个索引增加写放大、空间、优化器选择成本；写多读少的表控制索引数量，定期清理无用索引。
- 前缀索引适合长字符串（URL、邮箱），只索引前 N 个字符，省空间但区分度下降、不能覆盖查询；`ORDER BY`/覆盖索引需要完整列。
- 发现无用索引：MySQL `sys.schema_unused_indexes`、PG `pg_stat_user_indexes.idx_scan`；结合慢查询和业务周期看，别只看一周数据就删。

## 6. 迁移原则

**一句话**：迁移要版本化、可重复执行、向前兼容；生产变更优先「扩展-回填-切换-收缩」，避免一次破坏性变更。

要能回答：

- 版本化迁移和幂等迁移的区别？
- 为什么迁移脚本一旦执行就不能改？
- 加列、删列、改类型、改名的安全顺序？
- 大表加索引/加列怎么避免锁表？
- 双写、回填、切换、下线四步怎么配合？
- 迁移失败怎么回滚？回滚脚本要不要写？

关联：[[破坏性变更]]

笔记：

- 版本化迁移：每个脚本有唯一版本号，按序执行一次；幂等迁移：脚本可重复执行（`IF NOT EXISTS`/upsert）。生产要两者结合：版本管顺序，脚本尽量幂等。
- 已执行的脚本不能改：Flyway 校验和会失败，且生产已执行，改了也不生效；修正用新版本脚本。
- 安全顺序：加列先加可空/带默认（大表注意锁）→ 回填 → 加约束；删列先停代码读写 → 再删；改类型用新列 + 双写 + 回填 + 切换；改名用新列过渡，别直接 rename 依赖代码。
- 大表加索引：MySQL 用 Online DDL/`ALGORITHM=INPLACE` 或 gh-ost/pt-osc；PG 用 `CREATE INDEX CONCURRENTLY`（不能事务内）。加列在 MySQL 8 可 instant，老版本会重建表。
- 双写/回填/切换/下线：新老结构同时写 → 回填历史 → 读切新 → 停双写 → 删旧。每一步可独立回滚，避免一次大爆炸。
- 回滚：能写回滚脚本就写（删列/改类型往往不可逆，只能前滚修复）；迁移前备份、在预发跑一遍、生产分批执行并观察。

## 7. Flyway 与多仓协作

**一句话**：Flyway 用版本号管理迁移，校验和防篡改；多仓共库时，版本号要全局不冲突，收集和发布要有统一入口。

要能回答：

- Flyway 的 `versioned`、`repeatable`、`baseline` 分别是什么？
- 校验和（checksum）冲突怎么处理？
- 多服务共库时，迁移目录和版本号怎么划分？
- 生产环境该不该让应用自动执行迁移？
- 迁移脚本怎么评审、怎么在预发验证？
- 多仓收集时怎么保证顺序和完整性？

关联：[[Flyway与多仓迁移]]、[[多仓迁移落地]]

笔记：

- Flyway `versioned`（V1__xxx.sql，按版本执行一次）、`repeatable`（R__xxx.sql，校验和变就重跑，适合视图/函数）、`baseline`（已有库初始化基线，跳过之前的版本）。
- 校验和冲突：说明脚本被改过；不要 `repair` 了事，先确认生产实际结构，用新脚本修正；`repair` 只修元数据，不修数据。
- 多服务共库：按服务/模块划分版本号段（如 1000+、2000+）或目录，统一在一个迁移仓库收集；版本号全局唯一、顺序可预测。
- 生产自动迁移：可以应用启动执行，但要加锁（Flyway 自带）、审批、备份；更稳的是独立迁移 Job，应用只校验版本。
- 评审/预发：脚本走 code review，预发用生产快照跑一遍，测耗时/锁；大表变更单独演练。
- 多仓收集：CI 汇总各仓迁移到统一目录，检查版本重复/缺口，按序执行；产物带清单和校验和，避免漏脚本。

## 8. 数据库类型选型：关系型/嵌入式/NoSQL

**一句话**：先看数据形状和一致性要求，再看规模和运维——强关系 + 事务选关系型，单机单文件选嵌入式，文档/搜索/宽列这些「形状不固定或检索方式特殊」的场景才轮到 NoSQL；不是「数据量大就上 NoSQL」。

要能回答：

- 关系型、文档型（MongoDB）、搜索引擎（Elasticsearch）、键值/宽列存储各适合什么数据形状和查询？
- 什么时候「先上 PostgreSQL 的 JSONB」比换 MongoDB 更划算？
- 嵌入式数据库（SQLite）和客户端-服务端数据库的边界在哪？多写者、网络访问、并发写分别会怎样？
- 选 NoSQL 要额外承担什么：最终一致、无 join、运维组件、团队技能、备份恢复？
- 全文搜索用数据库 `LIKE`/全文索引，和上 Elasticsearch，分界点是什么？

项目里的分工：

- **MySQL**：smart WMS 的业务库，团队熟、运维工具链齐；代价是复杂查询/JSON 能力不如 PostgreSQL（见 [[MySQL]]）。
- **PostgreSQL**：muou 的主库，用到了分区、约束、`SKIP LOCKED` 这类能力；代价是团队要熟悉 PG 的差异（见 [[PostgreSQL]]）。
- **SQLite**：NovelForge 的本地库，单文件、WAL、随应用走；代价是单写者、`Send` 非 `Sync`、没有网络访问（见 [[SQLite]]）。
- **NoSQL 未落地**：MongoDB/Elasticsearch 只作学习中，没有项目证据。当前数据是强关系 + 事务，规模也没到「关系型撑不住」；引入它们要多一套一致性模型、运维组件和备份方案，收益不成立。
- **反悔条件**：出现「字段形状随租户/内容类型大幅变化、关系查询很少」→ 评估文档型或 JSONB；出现「全文检索/聚合分析成为主查询」→ 评估 Elasticsearch/OpenSearch，而不是继续给 `LIKE` 加索引；出现「单机写入扛不住」→ 先分库分表/读写分离，再考虑换存储模型。

笔记：

- 关系型：强关系、事务、约束、join、报表；文档型（MongoDB）：嵌套/可变结构、按文档读写、弱 join；搜索引擎（ES）：全文检索、聚合、日志；键值/宽列：超大规模简单键访问、高写入。
- 先试 PostgreSQL JSONB：数据仍有主键/关系/事务，只是部分字段可变；换 MongoDB 会失去 join/事务/约束，多一套运维。只有「文档是聚合根、关系很少、结构差异大」才值得换。
- SQLite 是嵌入式：单文件、进程内、无网络；适合桌面/移动/单机工具。多写者、跨机访问、高并发写要客户端-服务端数据库；WAL 提升并发读，但写仍是单写者。
- NoSQL 的额外成本：最终一致（读己之写/事务缺失）、无 join（应用组装/冗余）、运维组件、团队技能、备份恢复、监控。收益不明确时不上。
- 全文搜索分界：数据量小、检索简单用数据库全文索引/`pg_trgm`；需要分词、相关度排序、聚合、高亮、海量日志再上 ES。ES 不是主库，要做数据同步和一致性兜底。
