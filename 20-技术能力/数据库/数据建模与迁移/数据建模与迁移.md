# 数据建模与迁移

**一句话**：表结构只有一个真理源；建模先定主键、编号、分层与约束，迁移再按「单向、可收集、可复核」的方式落库。

## 一、理论：建模和迁移各管什么

1. **唯一真理源**：schema 只在设计文档里定义，DDL 和迁移是它的产物。改表先改文档，再生成/手写迁移，最后在库上验证；不能反过来从库里反推。
2. **技术主键与业务编号分离**：主键负责引用与稳定；业务编号负责对外展示与检索。编号在业务事件发生时才分配，主键不能等它。
3. **范式是默认，反范式是交易**：事实表先按 3NF；冗余列只在「读多写少 + 有明确刷新口子」时引入。会进 WHERE / 唯一 / 外键的值必须提升为固定列，不能埋进 JSON。
4. **约束放哪一层要一次定死**：唯一性放业务层还是数据库、引用完整性靠外键还是代码、软删还是状态位，都是单向门，后面改成本极高。
5. **迁移是单向门**：已发布的迁移不改；破坏性变更走「加新列 → 双写 → 切读 → 删旧列」；生产执行的是人审过的整合 SQL，不是 ORM 自动改表。
6. **一个库可以由多个仓库写**：版本号要跨仓库不撞，schema 变更要能收集、排序、复核。

## 二、实际使用：muou 的建表与迁移

- **真理源**：`muou-server/docs/02-1-表设计.md:3` 写明「本文是全库唯一 schema 真理源」，分五层（平台共享 / 租户业务 / 配置 / 日志 / 技术）；每张表在同一节里给建表 SQL + 逐字段字典（如 `tenant`，`02-1-表设计.md:1233`、`:1296`）。
- **通用约束**：字段类型、横切列、软删、唯一性、外键、注释集中在 `muou-server/docs/02-0-建表通用约束.md`；主键 `uuid` + 应用侧 UUIDv7，列名 `<实体单数>_id`（`:52`）。
- **主键生成**：`UuidUtil.nextId()` 纯 JDK 实现、同一毫秒内单调递增（`muou-server/src/main/java/com/voidtech/muou/common/util/UuidUtil.java:52`）；实体用 `IdType.INPUT`，在 DaoImpl 显式赋值（`02-0-建表通用约束.md:264-272`）。
- **业务编号独立成列**：`psn` / `no` / `code` 与主键分列，对外只暴露编号（`02-0-建表通用约束.md:293`）。
- **不建外键**：现行多仓约定是关联降级为普通索引、完整性由代码保证（`muou-backend/muou-app-ops/databases/迁移编写约定.md:65`、同目录 `README.md:66-72`）；实际生成的四份 init 里 `FOREIGN KEY` 计数为 0（`README.md:69`）。
- **迁移交付**：core 库由 iam / member / platform / content 四个仓库共写（`迁移编写约定.md:9-19`）；版本号用 `V<yyyyMMddHHmm>`；`collect.sh` 收集各仓脚本拼成 `build/<库>.sql`，生产由人执行（`collect.sh:5-23`、`迁移编写约定.md:4`）。
- **不是 MySQL**：muou 选型时 MySQL 被否决（`muou_arch/adr/0004-database-and-migration.md:38`），这套经验落在 PostgreSQL；我在 MySQL 上只有查询优化经验（[[查询性能优化]]、[[MySQL]]），没有迁移落地案例。

## 三、归纳：建表与迁移检查清单

拿到「加一张表 / 改一个字段」时按顺序问：

1. **分层**：新表属于平台共享、租户业务、配置、日志还是技术？带不带 `tenant_id`、要不要 RLS，先登记再写迁移。
2. **主键**：技术主键是否 `uuid` 应用侧生成？业务编号是否单独一列、在业务事件时才分配？
3. **对外**：接口暴露的是业务编号还是主键？暴露 UUIDv7 等于泄露创建时间。
4. **约束**：唯一性放业务层锁还是数据库？引用完整性靠代码还是外键？软删是否真的需要？
5. **类型**：金额 `numeric` + 币种、时间 `timestamptz`、枚举 `text`、长度用 `CHECK`；每一条都要和 Java 类型对上。
6. **注释**：表注释 + 每个非自明列注释与建表写在同一个迁移里。
7. **版本号**：多仓共库用时间戳，不排 V23 / V24。
8. **破坏性**：已发布库上只做加法；删列/改名分三次发布。
9. **整合**：新迁移能被 `collect.sh` 收到，`build/<库>.sql` 重出并提交；manifest 能复核来源与顺序。
10. **验证**：空库跑一遍、有数据的环境按 expand-contract 演练；注释与唯一性各有测试。

### 三条红线

- 不要从库里反推 schema：文档才是真理源，库只是执行结果。
- 不要用业务编号当主键：编号晚于主键产生，且格式会变。
- 不要在已发布库上直接 `DROP COLUMN` / 改类型：先加新列，再切读，最后删。

## 四、回到理论

- **真理源唯一**是为了让「谁改了哪张表」只有一个答案；多仓共库时，答案还要能被收集成一份可复核的顺序脚本。
- **主键/编号分离**是把「稳定引用」和「人类可读」两种需求拆开；合在一起，任何编号规则调整都会变成主键变更。
- **约束分层**决定失败时的表现：数据库约束是硬失败，业务层锁是 409；选哪一层要看「冲突是不是业务语义」。
- **迁移单向**是因为生产回滚只能恢复结构、恢复不了数据；所以破坏性变更必须让新旧两版代码在同一个窗口里共存。
- 这些原则换库不换：PostgreSQL 的 `uuid`、MySQL 的 `char(36)`、Oracle 的 `RAW(16)` 只是类型名不同。

## 五、边界

- 没有 MySQL 迁移落地案例；MySQL 只在选型里被否决。
- 没有做过分库分表、跨库外键、Online DDL 大表变更、数据回填/双写演练。
- muou 的「建外键」和「不建外键」两版口径并存：单体期 02-0 要求建外键，现行多仓约定明确不建；本页按现行约定写，旧文档只当历史。
- `_all/` 公共表展开机制在 `collect.sh` 里存在，但目录当前只有 `.gitkeep`，没有实际公共表脚本。
- 列注释门禁在 ops 仓的静态校验里落地，服务仓的 446 份迁移目前没有同等扫描（见 [[多仓迁移落地]]）。
