# 租户字段与查询过滤

技能点：[[MySQL]] · 方法：[[SQL 优化]] · 通用技能：[[查询性能优化]]

**什么时候会遇到**：多租户表、平台账号 `tenant_id` 为 null、分页/导出/统计多入口，租户条件容易漏。

## 判断依据

- `tenant_id` 是否 `NOT NULL`？平台账号（`tenant_id IS NULL`）写租户级资源会撞约束。
- 过滤条件是否散在各入口？只在 Controller/某个 Service 加，导出/分页/统计会漏。
- NULL 的语义是什么？平台账号看全部，还是子公司看不到 NULL 行？

## 手段

- 写侧：需要租户的写口统一用 `requireTenantId()`，平台账号直接返回 `TENANT_REQUIRED`。
- 读侧：数据访问层统一加 tenant 条件；caller 为 null 不过滤，非空严格匹配。
- 历史数据：决定是否 backfill；不 backfill 就明确「老数据只对平台可见」。
- 索引：`tenant_id` 打头的联合索引对高选择性查询有用；命中比例极高时没用。

## 反例

- `login_log` 原来完全没有租户隔离，任何有 `log:list` 的账号能看全部日志。
- 只在 Controller 过滤，导出/分页/统计三个入口漏，导致越权可见。
- 调用方各自传 `tenant_id`，登录成功/匿名/登出/代登录四种语义会乱。

## 现在的规矩

- 租户条件收在数据访问层，调用方不传 `tenant_id`。
- 写侧 `requireTenantId()`，读侧按 caller 分流。
- NULL 行的可见性要写清楚，不靠默认行为。
