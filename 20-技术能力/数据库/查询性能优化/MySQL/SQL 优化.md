# SQL 优化

技能点：[[MySQL]] · 通用技能：[[查询性能优化]]

**一句话**：先量化「谁在吃数据库时间」，再判断问题属于写法、索引、数据模型还是任务负载，选对应手段，改完复测。

## 优化顺序（不要跳步）

1. **量化**：用 `performance_schema.events_statements_summary_by_digest` 按 `SUM_TIMER_WAIT` 排，先看谁吃掉了百分比；不只看慢日志。
2. **定位时间窗**：持续慢，还是整点/定时任务窗口慢？先问「几点卡」，再看 SQL。
3. **分类**：
   - 单条 SQL 慢 → 执行计划、索引、扫描行数
   - 整体负载高 → 定时任务、连接数、锁、IO
   - 列表页慢 → JOIN、JSON 解析、排序、分页、`SELECT *`
   - 写入慢 → 索引数量、事务大小、锁等待
4. **判断索引是否有效**：选择性、扫描行数、是否命中；命中比例极高时，全表扫描可能是正确决策，加索引救不了。
5. **先改写法，再改模型**：去 JOIN、去 JSON、去 `SELECT *`、去前导 `%`、分页/排序、批量；写法改不动再冗余列/加索引/归档/分表。
6. **复测**：同一数据集、同一时间窗，改前改后对比；一次只改一个变量。

## 现象 → 先查什么

| 现象 | 先查什么 | 不要先做什么 |
| --- | --- | --- |
| 整点卡 | 定时任务、时间窗 | 加索引 |
| 列表页慢 | JOIN、JSON、`SELECT *`、排序 | 加缓存 |
| 单条 SQL 慢 | 执行计划、索引、扫描行数 | 凭感觉改 SQL |
| 写入慢 | 索引数量、事务大小、锁等待 | 加机器 |
| 租户查询异常 | tenant 条件、NULL 语义 | 在 Controller 里补条件 |

## 手段清单

| 场景 | 首选手段 | 什么时候用 | 反例/边界 |
| --- | --- | --- | --- |
| [[慢查询定位]] | performance_schema 按总耗时排 | 不知道谁慢 | 只看慢日志会漏 5 秒以下 |
| [[索引失效]] | 改写法 / 生成列+索引 | 前导 `%`、函数、类型不一致 | WHERE 命中 99.98% 时加索引没用 |
| [[字段调整与冗余]] | 去 JOIN + 冗余列 | 列表要 JOIN/解析 JSON | 冗余列必须有刷新口子 |
| [[分页与排序]] | 覆盖索引、限制排序字段 | 大表翻页/多字段排序 | `COUNT(*)` 大表本身慢 |
| [[定时任务与数据库负载]] | 停/降频/自停守卫 | 0 行任务、整点尖峰 | 不要先加索引掩盖空转 |
| [[租户字段与查询过滤]] | 数据访问层统一加 tenant 条件 | 多租户表 | 调用方各自拼会漏 |

## 三条红线

1. **不要先加索引**：先量化，再判断；索引不是万能，命中比例高时全表扫描是正确选择。
2. **不要用缓存掩盖慢查询**：缓存是第二步，先把 SQL/模型问题看清。
3. **不要一次改多个变量**：改完复测，否则不知道哪个改动有效。

## 一句话判断

先问「几点卡」，再问「谁吃时间」，最后才问「SQL 怎么写」。
