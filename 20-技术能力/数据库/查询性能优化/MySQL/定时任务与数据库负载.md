# 定时任务与数据库负载

技能点：[[MySQL]] · 方法：[[SQL 优化]] · 通用技能：[[查询性能优化]]

**什么时候会遇到**：数据库整点/周期性卡顿，CPU/IO 尖峰，但单条 SQL 看起来都不慢。

## 判断依据

- 先看时间窗：是不是每小时/每天固定时间卡？
- 用 `performance_schema` 按总耗时排，看是否同一个 job 反复出现。
- 看任务日志的 `updated N rows`：长期 0 行说明任务空转。
- 看单轮耗时和扫描行数：扫描行数远大于更新行数，就是无效扫描。

## 手段

- 停掉空转任务：先证明它更新 0 行、结构上不可能成功。
- 保留兜底语义：加自停守卫（上轮 0 行就跳过）+ 降频（每小时→每天）。
- 修数据/继承路径：如果任务本来该成功，先解决导致 0 行的数据问题。
- 不要先加索引：空转任务的全表扫描不是索引问题。

## 反例

- `OmpTenantBackfillJob` 每小时跑 57 秒，5 天 1,114 次、7,736 秒，占全库查询时间 66%，更新 0 行。
- `goods.tenant_id IS NULL` 命中 99.98%，索引选择性为零，加索引救不了。
- 以为全表扫描污染 buffer pool；控制实验证伪（LRU midpoint insertion）。

## 现在的规矩

- 定时任务必须记录 `updated N rows`；长期 0 行加自停。
- 整点卡顿先查定时任务，再查 SQL。
- 停任务前先证明它没有产出；有产出就修数据/继承路径，不要直接停。
