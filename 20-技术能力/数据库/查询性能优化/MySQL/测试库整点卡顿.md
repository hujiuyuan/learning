# 测试库整点卡顿

技能点：[[MySQL]] · 项目：[[smart WMS]] · 2026-07-16 · 通用技能：[[查询性能优化]]
场景：[[慢查询定位]]、[[定时任务与数据库负载]]、[[索引失效]]

## 我想干什么

测试库每小时整点卡一次，先找出是谁在吃数据库。

## 我干了什么

- 没只看慢日志，直接查 `performance_schema.events_statements_summary_by_digest`，按 `SUM_TIMER_WAIT` 排。
- 发现 `OmpTenantBackfillJob` 系列 5 天跑了 1,114 次、总共 7,736 秒，占全库查询时间 66%；单轮约 57 秒，`goods` 一条占 50 秒。
- 任务日志每张表都写 `updated 0 rows`，5 天一次没落下。
- 查数据：`goods` 203 万行，`tenant_id` 和 `node_id` 都有 99.98% 为 NULL；`node` 5 万行里只有 128 行有 `tenant_id`；JOIN 实际可匹配 0 行。
- 做 buffer pool 控制实验：预热后 `COUNT(*)` 0.704s → 跑那条 `UPDATE goods`（0 行）51.1s → 再 `COUNT(*)` 0.368s，反而更快。

## 犯了什么错 / 误判

1. 一开始想「加索引 / 调 buffer pool」解决。实际 `WHERE tenant_id IS NULL` 命中 99.98%，索引选择性为零，优化器选全表扫描是正确决策；buffer pool 早已从 128MB 调到 2GB，这个杠杆已经拉过了。
2. 慢日志 `long_query_time=5` 会把 5 秒以下的问题藏掉，真正的证据在 `performance_schema`。
3. 容器是 UTC、宿主机是 CST，慢日志 `# Time: ...Z` 是 UTC，差点把「32 分钟前的慢查询」读成「8 小时内没有慢查询」。
4. 一度以为全表扫描会把 buffer pool 里的热页冲掉。控制实验证伪：InnoDB 的 LRU midpoint insertion 会把扫过的页放进 old 子链，不会挤掉热页。

## 怎么解决

报告给了三个选项，本次只诊断、未改代码：

| 方案 | 说明 | 风险 |
| --- | --- | --- |
| A. 停掉 job | 移除 `@Scheduled` 或加开关默认关闭 | 零风险：已证明更新 0 行，结构上不可能成功 |
| B. 自停守卫 + 降频 | 改成每天一次；上轮 0 行就跳过后续扫描 | 低，保住兜底语义 |
| C. 先解决 `goods.node_id` 为空 | 99.98% 的 goods 没有 `node_id`，继承路径可能选错 | 要先厘清 tenant_id 该怎么继承 |

## 现在的规矩

- 先按 `performance_schema` 的总耗时找大头，不只看慢日志。
- 索引不是万能：WHERE 命中比例极高时，全表扫描是正确选择。
- 定时任务必须看 `updated N rows`；长期 0 行的任务要加自停。
- 慢日志时间戳先确认时区，再读时间。
