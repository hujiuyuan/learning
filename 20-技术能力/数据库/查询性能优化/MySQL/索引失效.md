# 索引失效

技能点：[[MySQL]] · 方法：[[SQL 优化]] · 通用技能：[[查询性能优化]]

**什么时候会遇到**：明明有索引，查询还是慢；或者加了索引也没用。

## 常见失效写法

| 写法 | 为什么失效 | 怎么办 |
| --- | --- | --- |
| `LIKE '%x%'` | 前导通配，无法走索引 | 全文索引/搜索引擎；或改成前缀匹配 |
| `WHERE DATE(col) = ...` / 函数包列 | 列上做运算，索引失效 | 改成范围查询，或生成列+索引 |
| `OR` 连接不同列 | 可能退化为全表扫描 | 拆成 UNION，或确保每列都有索引 |
| 类型不一致 | 隐式转换，索引失效 | 参数类型与列类型一致 |
| `ORDER BY json_col` | 对 JSON 排序，无法用普通索引 | 冗余成物理列，或生成列+索引 |
| 选择性极低 | 命中比例高，优化器选全表扫描 | 不要加索引；改模型/任务 |

## 关键判断：加索引有没有用

看**选择性**：`WHERE` 条件命中行数 / 总行数。

- 命中比例低（比如 < 5%）→ 索引有意义。
- 命中比例极高（比如 99.98%）→ 优化器选全表扫描是正确决策，加索引救不了。
- 反例：`goods.tenant_id IS NULL` 命中 203 万 / 203 万，`idx_tenant_stock_deleted_at` 首列是 `tenant_id`，cardinality 只有 6，索引选择性为零。

## 深层原理

- **索引只对「能映射成有序区间」的条件有用**：B+ 树按索引列排序，等值/前缀/范围能定位到连续区间；`LIKE '%x%'` 没有确定前缀，只能全索引扫描；`DATE(col)=...` 对列做函数运算，索引里存的是原值，无法按函数结果定位。
- **优化器比的是成本，不是「有没有索引」**：走二级索引要读索引页 + 回表读聚簇索引；如果命中行数占比高（低选择性），全表扫描顺序读反而更便宜。`EXPLAIN` 的 `rows` 是估算，统计信息过期/数据倾斜会让它选错；`ANALYZE TABLE` 只能缓解，不能保证。
- **覆盖索引和索引下推是两件事**：覆盖索引让查询列全在索引里，不回表；索引下推（ICP）把 `WHERE` 中能在索引上判断的条件下推到存储引擎，减少回表，但不改变索引能定位的区间。`Using index` 是覆盖，`Using index condition` 是 ICP。
- **`OR` 的坑在「每个分支都要能走索引」**：`a=1 OR b=2` 如果 b 没索引，优化器可能直接全表扫描；拆成两个走索引的查询再 `UNION`，或给两个列都建合适索引。`ORDER BY json_col` 没有索引可依，只能 filesort。

## 现在的规矩

- 先看执行计划和扫描行数，再决定加不加索引。
- 不在列上做函数/运算；必须做就上生成列+索引。
- JSON 字段不进列表过滤/排序。
- 命中比例极高时，先怀疑任务/模型，不要先加索引。
