# 慢查询定位

技能点：[[MySQL]] · 方法：[[SQL 优化]] · 通用技能：[[查询性能优化]]

**什么时候会遇到**：数据库整体变慢、整点卡顿、列表页慢，但不知道是哪条 SQL。

## 判断顺序

1. **先看时间窗**：持续慢还是整点/定时任务窗口慢？先问「几点卡」。
2. **按总耗时排**：`performance_schema.events_statements_summary_by_digest` 按 `SUM_TIMER_WAIT` 排，直接看谁吃掉了百分比。
3. **看扫描行数**：`SUM_ROWS_EXAMINED / COUNT_STAR`，扫描行数远大于返回行数就是可疑。
4. **再看慢日志**：慢日志适合看尖峰，不适合找大头；`long_query_time=5` 会漏掉 5 秒以下。
5. **核对时区**：容器 UTC vs 宿主机 CST，慢日志 `# Time: ...Z` 是 UTC。

## 关键 SQL

```sql
SELECT LEFT(DIGEST_TEXT,60), COUNT_STAR,
       ROUND(SUM_TIMER_WAIT/1e12,1) AS tot_s,
       ROUND(SUM_ROWS_EXAMINED/COUNT_STAR) AS avg_scan
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME='track-test'
ORDER BY SUM_TIMER_WAIT DESC LIMIT 12;
```

## 反例 / 边界

- 只看慢日志：会漏掉 5 秒以下但高频的查询，也会把整点 57 秒的空转任务当成「偶发」。
- 只看单条 SQL：不一定是 SQL 写法问题，可能是定时任务、锁、连接数、IO。
- 不看时区：会把「32 分钟前的慢查询」读成「8 小时内没有慢查询」。

## 深层原理

- **`performance_schema` 的 digest 是「归一化 SQL 的累计账本」**：同一模板（字面量替换成 `?`）聚合 `COUNT_STAR`、`SUM_TIMER_WAIT`、`SUM_ROWS_EXAMINED`，从实例启动/上次 truncate 开始累计。它按总耗时排，能找「高频但单次不慢」的查询；慢日志按单次阈值，天然漏掉这些。
- **总耗时 = 单次耗时 × 次数**：一条 0.1 秒的查询每秒 100 次，比一条 5 秒的查询每小时 1 次更吃 DB；所以先看 `SUM_TIMER_WAIT`，再看 `SUM_ROWS_EXAMINED/COUNT_STAR` 判断扫描是否异常。
- **慢日志是采样，不是全量**：`long_query_time` 以下不记，`log_slow_admin_statements`/`log_queries_not_using_indexes` 另开；尖峰时间点、锁等待、临时表/文件排序更适合从慢日志看。两者互补，不能只用一个。
- **时间窗和时区先对齐**：容器 UTC、业务东八区，慢日志 `# Time: ...Z` 是 UTC；不换算会把「32 分钟前」读成「8 小时内没有」。`performance_schema` 的累计值还要注意 truncate 时间，否则会把历史账算到当前窗口。

## 现在的规矩

- 先按总耗时找大头，再按扫描行数判断可疑 SQL。
- 慢日志只用来补尖峰和时间点，不用来排总账。
- 读慢日志前先确认时区。
