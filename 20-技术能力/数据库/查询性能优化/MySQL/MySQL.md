## 我会的部分

- 用 `performance_schema.events_statements_summary_by_digest` 按总耗时找「谁吃掉了 DB 时间」，不只看慢日志。
- 判断索引是否有效：看选择性、扫描行数；知道 `WHERE tenant_id IS NULL` 命中 99.98% 时，全表扫描是正确决策，加索引救不了。
- 列表查询去 JOIN：把展示字段冗余成物理列，列表不解析 JSON。
- JSON 字段的坑：前导 `%` 的 LIKE、`ORDER BY JSON`、`SELECT *`。
- 租户字段：`NOT NULL` 与平台账号 `null` 的冲突；分页过滤按 caller 身份分流。
- 时区：容器 UTC vs 宿主机 CST，慢日志时间戳先确认时区。

## 选型与取舍

| 选择 | 为什么 | 代价/失败模式 | 什么时候反悔 |
| --- | --- | --- | --- |
| InnoDB 而不是 MyISAM | 事务、行锁、MVCC、崩溃恢复；业务表需要回滚和并发写 | 索引/数据占空间更大，count(*) 要扫描 | 只读、可重建的日志/统计表才考虑其他引擎 |
| `DATETIME` 而不是 `TIMESTAMP` | 不受会话时区影响、没有 2038 上限；业务存墙钟/本地时间更直观 | 不存时区，跨时区要应用层转换；范围查询要自己保证口径 | 需要绝对时刻且团队统一 UTC 时，改用 `TIMESTAMP` 或存 epoch |
| `utf8mb4` | 支持 emoji/生僻字，避免 3 字节 `utf8` 截断 | 索引键更长，老版本行格式限制 | 纯 ASCII 的内部表可省空间，但统一字符集更省心 |
| JSON 只放扩展字段 | 结构可变、避免频繁加列；MySQL 8 可函数索引 | 查询/排序/更新整块都贵，索引受限，约束弱 | 字段开始被频繁查询/统计 → 拆正式列或关联表 |
| 共享表 + `tenant_id` | 成本低、扩容简单、跨租户统计方便 | 隔离靠代码/插件，漏一条 SQL 就跨租户 | 大客户/强合规 → 独立库或 schema；数据量撑不住 → 分库分表 |
| 不建物理外键（项目约定） | 避免插入顺序/锁/分库分表/批量导入的约束 | 引用完整性靠代码，可能产生孤儿数据 | 核心强一致表、单库阶段可以建；跨库必须放弃 |

判断顺序：先问「这张表要不要事务/行锁」→ InnoDB；再问「时间是不是绝对时刻」→ `DATETIME`/`TIMESTAMP`/epoch；再问「字段会不会被查询」→ 正式列 vs JSON；最后问「租户规模和合规」→ 共享表 vs 独立库。
