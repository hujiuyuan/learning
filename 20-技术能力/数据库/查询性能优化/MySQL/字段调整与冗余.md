# 字段调整与冗余

技能点：[[MySQL]] · 方法：[[SQL 优化]] · 通用技能：[[查询性能优化]]

**什么时候会遇到**：列表查询要 JOIN 多张表、解析 JSON，写法优化到头还是慢；或者列表要展示的字段散在来源单里。

## 判断顺序

1. 先试写法：去 JOIN、去 JSON、去 `SELECT *`、加时间范围/排序索引。
2. 写法改不动，再看模型：把列表展示/筛选字段冗余成物理列。
3. 冗余前先定刷新口子：创建时落值、编辑时刷新；没有刷新口子的冗余列会变脏。

## 冗余列的规矩

- 只冗余「列表要展示/筛选」的字段，不按「详情用不用」定。
- 创建 + 编辑两个口子都要刷新。
- 冗余列要能追溯到来源单；详情仍查来源单。
- 生成逻辑要幂等：先查是否已存在，再 create。
- 冗余不是复制整张表；只加列表需要的列。

## 反例 / 边界

- `ACCT STATUS` 一开始按「详情才用」决定不冗余，后来列表要展示/筛选，推翻决定，改成冗余 + 双写。**列表字段的范围要按列表需求定。**
- 只加冗余列、不挂编辑刷新 → 来源单改了，列表还是旧值。
- 生成逻辑不幂等 → 编辑一次生成一条重复任务。

## 现在的规矩

- 列表字段全部冗余成物理列；列表查询不 JOIN、不解析 JSON。
- 冗余列必须有明确的刷新口子：创建 + 编辑。
- 详情才查来源单；列表不查。
- 生成前先查是否已存在，保证幂等。
