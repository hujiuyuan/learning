# 分页与排序

技能点：[[MySQL]] · 方法：[[SQL 优化]] · 通用技能：[[查询性能优化]]

**什么时候会遇到**：大表分页、`COUNT(*)`、多字段排序、按 JSON 字段排序。

## 判断依据

- 小分页 + 走索引：`LIMIT 20` 走 `idx_created_at` 实测 0.044s，没问题。
- `COUNT(*)`：热数据 0.4–0.7s，冷数据 ~1.5s；大表 COUNT 本身贵，不要每次分页都精确 COUNT。
- `ORDER BY JSON`：对 200 万行排序，~50s；普通索引救不了。
- `SELECT *`：传输和内存都放大，撞 `max_execution_time=120000` 会被强制中断。

## 手段

- 分页查询只取需要的列，禁止 `SELECT *`。
- 排序字段限制在白名单；默认按主键/创建时间倒序。
- 列表要展示/排序的 JSON 字段，冗余成物理列（见 [[字段调整与冗余]]）。
- 精确 COUNT 很贵时，用估算/缓存/单独统计表；不要每次翻页都 COUNT 全表。
- 深分页没有证据，不展开；有大表翻页需求时再单独验证。

## 反例

- `ORDER BY data->"$.CODE"` 排序 200 万行，~50s。
- `SELECT * FROM common` 撞 `max_execution_time=120000`，被强制中断。
- 每次分页都 `COUNT(*)` 全表，热数据也要 0.4–0.7s。

## 深层原理

- **`LIMIT offset, n` 的成本是 O(offset + n)**：MySQL 要先读出前 offset 行再丢掉，翻到第 10 万行就要扫 10 万行；`offset` 越大越慢，和 `n` 无关。延迟关联先用覆盖索引取主键（只读索引、不回表），再按主键 JOIN 取整行；游标分页用 `WHERE id > last_id ORDER BY id LIMIT n`，直接定位起点，但不能跳页。
- **filesort 不一定慢，但大结果集要警惕**：排序字段没有合适索引时，MySQL 把结果放排序缓冲区，超了写临时文件做归并；`ORDER BY` 能用索引的前提是排序顺序与索引顺序一致、没有混用 ASC/DESC、WHERE 能用同一索引的最左前缀。
- **`COUNT(*)` 在 InnoDB 要扫索引计数**：MVCC 下不同事务看到的行数不同，不能存全局行数；大表精确 COUNT 贵，分页不一定每次都要精确总数，可用估算/缓存/单独统计表。
- **JSON/表达式排序没有普通索引**：`ORDER BY data->"$.CODE"` 每行都要解析 JSON，200 万行就是 200 万次解析 + 排序；要排序就冗余成物理列/生成列并建索引。

## 现在的规矩

- 分页只查必要列，不 `SELECT *`。
- 排序字段白名单，默认主键/时间倒序。
- JSON 字段不参与排序；需要排序就冗余成物理列。
- COUNT 贵时先问「是不是每次都要精确值」。
