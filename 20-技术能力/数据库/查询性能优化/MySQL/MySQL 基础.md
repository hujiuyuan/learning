## 1. 架构：一条 SQL 怎么跑

**一句话**：连接器 → 解析器 → 优化器 → 执行器 → 存储引擎；优化器基于统计信息选索引和 join 顺序。

要能回答：

- 连接器、解析器、优化器、执行器各做什么？
- Server 层和存储引擎层的边界在哪？
- 优化器为什么会选错索引？

**笔记**：

- 连接器负责认证、权限和连接线程；解析器把 SQL 变成语法树；预处理器检查表/列是否存在、展开 `*`；优化器选索引、join 顺序和访问方式；执行器按执行计划调用存储引擎接口。Server 层管「怎么查」，InnoDB 管「数据在哪、怎么读、事务和锁」。
- 优化器不是「选最好的」，是「按统计信息估算成本最低的」：成本 = 读页的 IO 成本 + 比较行的 CPU 成本。统计信息来自采样（`innodb_stats_persistent`），会过期；表小、数据倾斜、索引列被函数包住、`OR`/`IN` 估算偏差，都会让它选错。
- 判断选错：`EXPLAIN` 看 `possible_keys` 与实际 `key`、`rows` 估算和真实扫描行数；`ANALYZE TABLE` 刷新统计；`FORCE INDEX` 只用于验证，不长期写进业务 SQL。

## 2. 索引

**一句话**：InnoDB 用 B+ 树减少磁盘 IO；聚簇索引叶子存整行，二级索引叶子存主键，查非索引列要回表。

要能回答：

- 为什么用 B+ 树，不用 B 树、哈希、跳表？
- 聚簇索引和二级索引的区别？什么是回表？
- 联合索引的最左前缀、覆盖索引、索引下推？
- 索引选择性怎么看？为什么低选择性列加索引没用？
- 联合索引里，范围查询后面的列为什么通常用不上？

关联：[[索引失效]]

**笔记**：

- B+ 树的优势是「高扇出 + 叶子链表」：非叶子只存键，一个 16KB 页能放几百个键，三层就能覆盖千万级行；叶子按序链表，范围查询和排序不用回到根。B 树把数据存在内部节点，扇出低、范围查询要中序遍历；哈希只支持等值，不支持范围和排序；跳表是内存结构，不按磁盘页组织。
- 聚簇索引的叶子是整行，二级索引的叶子是主键值；二级索引查到主键后要再查聚簇索引，这就是回表。覆盖索引（查询列全在索引里）可以避免回表；`EXPLAIN` 的 `Using index` 就是命中覆盖索引。
- 联合索引 `(a,b,c)` 按 a→b→c 排序。最左前缀：没有 a 就用不上；`a=1 AND b>2` 能用 a 和 b 定位，但 b 是范围，后面的 c 不能继续用于定位（可能用于索引下推过滤）。范围列之后的列失去「有序」优势，这是索引结构决定的，不是优化器偷懒。
- 选择性 = 不同值数 / 总行数。选择性低（`tenant_id`、`deleted`、`status`）说明一个值命中太多行，走索引再回表可能比全表扫描更贵；优化器会选全表扫描，这是正确决策。低选择性列要放在联合索引的后面，或者用部分索引/生成列改变命中范围。
- 索引不是越多越好：每个二级索引都要占空间、每次写都要维护；更新频繁的表尤其要控制。

## 3. 事务与 MVCC

**一句话**：ACID 靠 undo/redo、锁和约束共同保证；InnoDB 默认 RR，快照读靠 MVCC，当前读靠锁。

要能回答：

- ACID 分别靠什么保证？
- 四种隔离级别分别解决什么问题？MySQL 默认哪个？
- 脏读、不可重复读、幻读的区别？
- MVCC 的 Read View 里有什么？可见性怎么判断？
- 快照读和当前读的区别？哪些语句是当前读？
- RR 下幻读怎么解决？

**笔记**：

- 原子性靠 undo log（回滚），持久性靠 redo log（崩溃恢复），隔离性靠锁 + MVCC，一致性是业务约束 + 数据库约束共同保证的结果，不是某一个日志单独给的。
- 隔离级别：RU 允许脏读；RC 解决脏读，但同一事务两次读可能不同（不可重复读）；RR 解决不可重复读，InnoDB 默认；Serializable 串行化。幻读是「同一范围两次读，行数变了」，RR 下快照读靠 MVCC 看不到新插入，当前读靠 Next-Key Lock 锁住间隙。
- Read View 记录 `m_ids`（活跃事务 ID 列表）、`min_trx_id`、`max_trx_id`、`creator_trx_id`。可见性：trx_id < min 可见；>= max 不可见；在 m_ids 里不可见；否则可见；自己的修改总是可见。RC 每次 SELECT 新建 Read View，RR 在事务第一次快照读时建一次，所以 RR 能重复读。
- 快照读：普通 `SELECT`；当前读：`SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`、`UPDATE`、`DELETE`、`INSERT`。当前读读最新已提交版本并加锁，快照读读 Read View 对应的历史版本。
- RR 下幻读不是完全消失：快照读看不到新行；当前读用 Next-Key Lock 锁间隙，阻止别的事务在范围内插入。如果两条语句一条快照读、一条当前读，仍可能看到「不一致」的现象，这是隔离级别和语句类型共同决定的。

## 4. 锁

**一句话**：InnoDB 行锁加在索引上；没有索引会退化成表锁；Next-Key Lock = 记录锁 + 间隙锁。

要能回答：

- 全局锁、表锁、行锁分别用在哪？
- 记录锁、间隙锁、Next-Key Lock 的区别？
- 意向锁解决什么问题？
- 什么情况会死锁？怎么排查？
- 乐观锁和悲观锁在业务里怎么选？
- `SELECT ... FOR UPDATE` 加什么锁？

**笔记**：

- 全局锁 `FLUSH TABLES WITH READ LOCK` 用于全库逻辑备份；表锁（`LOCK TABLES`）锁整表；行锁锁索引记录。InnoDB 的行锁是加在索引项上的：WHERE 没走索引时，要扫全表并锁住所有扫描到的行，效果接近表锁。
- 记录锁锁一条索引记录；间隙锁锁两条记录之间的「空隙」，只阻止插入，不阻止别的间隙锁；Next-Key Lock = 记录锁 + 它前面的间隙锁，RR 下用来防幻读。插入意向锁是插入前对间隙的一种意向，和间隙锁冲突。
- 意向锁是表级标志，表示「这个事务准备在某些行上加共享/排他锁」，让表锁不必逐行检查是否冲突。
- 死锁常见于两个事务以相反顺序锁多行、或间隙锁与插入意向锁交叉。排查：`SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK、`innodb_print_all_deadlocks` 落日志；处理：缩短事务、固定加锁顺序、补索引减少扫描行。
- 乐观锁：业务表加 `version`，`UPDATE ... WHERE id=? AND version=?`，0 行就重试/报冲突；适合读多写少、冲突低。悲观锁：`SELECT ... FOR UPDATE` 先锁再改；适合冲突高、必须强一致。`FOR UPDATE` 是当前读，RR 下加 Next-Key Lock；RC 下主要加记录锁。

## 5. 日志

**一句话**：redo log 保证崩溃恢复（WAL），undo log 保证回滚和 MVCC，binlog 用于复制和归档；两阶段提交保证 redo 和 binlog 一致。

要能回答：

- redo log 为什么是循环写？和 binlog 有什么区别？
- undo log 除了回滚还干什么？
- 两阶段提交的过程？为什么需要？
- crash-safe 靠什么保证？
- binlog 的三种格式（statement/row/mixed）区别？

**笔记**：

- redo log 是物理日志、固定大小、循环写：先写日志再刷脏页（WAL），崩溃后按 LSN 重放未刷盘的页。binlog 是逻辑日志、追加写、可归档，用于主从复制和按时间点恢复。两者职责不同，不能互相替代。
- undo log 存的是「怎么撤销」：回滚时反向执行；MVCC 读旧版本时也靠 undo 版本链 + Read View 判断可见性。
- 两阶段提交：写 redo（prepare）→ 写 binlog → redo（commit）。如果崩溃在 prepare 后、binlog 前，事务回滚；如果 binlog 已写、redo 未 commit，恢复时按 binlog 补 commit。目的是让 redo 和 binlog 对「事务是否提交」达成一致，避免主库和从库/备份不一致。
- crash-safe 不是单靠 redo：还要 `innodb_flush_log_at_trx_commit=1`（每次提交刷 redo）、`sync_binlog=1`（每次提交刷 binlog）、doublewrite（防页断裂）。参数放松性能更好，但崩溃可能丢事务。
- binlog 格式：statement 记录 SQL，日志小但非确定性函数（`NOW()`、`RAND()`）会导致主从不一致；row 记录行变更，最精确但日志大；mixed 让 MySQL 自动选，默认 row 更安全。

## 6. 存储引擎

**一句话**：InnoDB 支持事务、行锁、聚簇索引；MyISAM 不支持事务、表锁；MySQL 5.5 之后默认 InnoDB。

要能回答：

- InnoDB 和 MyISAM 的区别？
- 为什么 InnoDB 必须有主键？没有主键会怎样？
- 聚簇索引和非聚簇索引的区别？
- `count(*)` 在 InnoDB 里为什么慢？

**笔记**：

- InnoDB：事务、行级锁、MVCC、崩溃恢复、外键、聚簇索引；MyISAM：无事务、表锁、非聚簇索引、崩溃后可能要修复表。MyISAM 的 `count(*)` 快，是因为表头存了行数；InnoDB 有 MVCC，不同事务看到的行数不同，不能存一个全局行数。
- InnoDB 必须有主键：没有显式主键就选第一个「非空唯一索引」，都没有就生成 6 字节隐藏 rowid。隐藏 rowid 业务不可见，二级索引都存它；没有主键的表做复制/归档/分页会更麻烦，所以建表要显式主键。
- 聚簇索引：索引和数据存在一起，叶子是整行；非聚簇索引：索引和数据分开，叶子存行地址/主键。InnoDB 的主键是聚簇索引，二级索引是非聚簇索引（叶子存主键）。
- `count(*)` 在 InnoDB 要扫一个最小的二级索引（或主键）逐行计数，不能像 MyISAM 那样 O(1)；大表上 `count(*)` 慢是存储引擎的 MVCC 设计决定的。需要频繁计数就维护计数表/缓存，并接受延迟。

## 7. 表设计与字段

**一句话**：主键尽量短、自增、稳定；字段类型够用就好；范式减少冗余，反范式换查询性能。

要能回答：

- 自增主键和 UUID 怎么选？
- `varchar` 和 `char` 的区别？`varchar(255)` 和 `varchar(20)` 的区别？
- 三范式是什么？什么时候反范式？
- 大字段（TEXT/BLOB）怎么放？
- 金额、时间、枚举字段用什么类型？
- `utf8` 和 `utf8mb4` 的区别？

关联：[[字段调整与冗余]]

**笔记**：

- 自增 `BIGINT UNSIGNED` 顺序插入，聚簇索引页分裂少、二级索引小；UUID 随机插入会导致页分裂和索引膨胀，但全局唯一、不暴露业务量。UUIDv7 把时间放前面，兼顾全局唯一和局部顺序；项目里桌面端用 UUIDv7 做主键、业务编号独立成列，见 [[UUIDv7与业务编号]]。
- `CHAR` 定长，不足补空格；`VARCHAR` 变长，额外 1-2 字节长度前缀。`VARCHAR(255)` 和 `VARCHAR(20)` 的存储按实际长度，不是按最大长度补齐；但最大长度影响行格式、临时表/排序缓冲和索引键长度上限，别随手写 255。
- 三范式：1NF 去重复列，2NF 去部分依赖，3NF 去传递依赖。反范式是「用冗余换读性能」：列表页把展示字段冗余成物理列，避免 JOIN/JSON 解析；代价是写时同步、可能不一致，见 [[出货任务列表去JOIN]]。
- TEXT/BLOB 大字段可能溢出到 off-page 存储，`SELECT *` 会多一次读；列表查询不要带大字段，必要时拆到扩展表。金额用 `DECIMAL`，别用 `FLOAT/DOUBLE`；时间用 `DATETIME`/`TIMESTAMP` 要明确时区语义；枚举可用 `TINYINT` + 字典表，别用字符串枚举；字符集统一 `utf8mb4`，`utf8` 在 MySQL 里不是完整 UTF-8。

## 8. 执行计划与查询优化

**一句话**：用 EXPLAIN 看 type、key、rows、Extra；ALL 是全表扫描，Using filesort / Using temporary 要警惕。

要能回答：

- EXPLAIN 的 type 从好到坏怎么排？
- key、key_len、rows、filtered 怎么看？
- Extra 里常见的值分别什么意思？
- 深分页为什么慢？怎么优化？
- `ORDER BY` 什么时候能用上索引？
- 子查询和 join 怎么选？

关联：[[慢查询定位]]、[[SQL 优化]]、[[分页与排序]]

**笔记**：

- `type` 从好到坏大致是 `system > const > eq_ref > ref > range > index > ALL`；`index` 是全索引扫描，`ALL` 是全表扫描。`key` 是实际用的索引，`key_len` 是用了索引的多少字节（联合索引用了几列），`rows` 是估算扫描行数，`filtered` 是过滤后剩余比例。
- `Extra`：`Using index` 覆盖索引；`Using where` 服务器层过滤；`Using index condition` 索引下推；`Using filesort` 需要额外排序；`Using temporary` 用了临时表（常见于 GROUP BY/UNION/子查询）。`filesort` 不一定慢，但大结果集要警惕。
- 深分页 `LIMIT 100000, 20` 要先扫 100020 行再丢掉前 100000 行；优化：延迟关联（先用覆盖索引取主键，再 JOIN 取整行）或游标分页（`WHERE id > last_id ORDER BY id LIMIT 20`）。游标分页要求稳定排序键，不能跳页。
- `ORDER BY` 能用索引的前提：排序顺序和索引顺序一致、没有混用 ASC/DESC（MySQL 8 支持降序索引）、WHERE 条件能用同一索引的最左前缀。否则 filesort。
- 子查询和 JOIN 不是谁绝对快：MySQL 8 会把很多子查询改写成半连接，`EXISTS`/`IN` 的选择要看执行计划；结论用 `EXPLAIN` 验证，不靠口诀。

## 9. 高可用与运维（边界）

**一句话**：主从复制、读写分离、分库分表、Online DDL 属于架构/运维层；我在项目里没落地过，这里只作为面试知识补。

要能回答：

- 主从复制的过程？主从延迟怎么产生？
- 读写分离后读到旧数据怎么办？
- 分库分表怎么选分片键？跨库 join / 分页怎么办？
- Online DDL 的三种算法？什么时候会锁表？
- 备份恢复有哪些方式？

**笔记**：

- 主从复制：主库写 binlog，从库 IO 线程拉取写 relay log，SQL 线程重放。延迟常见原因：从库单线程重放、大事务、无主键表、从库压力大。MySQL 5.7+ 支持并行复制，但大事务仍会卡。
- 读写分离读到旧数据：写后强制走主库、读己之写（会话粘滞）、等 GTID 追上、或业务接受最终一致。不是所有读都能容忍延迟，账户/权限类读要谨慎。
- 分片键要满足：高基数、分布均匀、大多数查询能带上它；否则跨分片查询/聚合/分页会很难。跨库 JOIN 通常改成应用层拼装或冗余；跨库分页要各分片取前 N 再归并。
- Online DDL 算法：COPY（锁写、重建表）、INPLACE（允许并发 DML，部分操作仍需 brief lock）、INSTANT（只改元数据，MySQL 8.0.12+ 部分场景）。加索引/加列在 InnoDB 上通常 INPLACE/INSTANT，但改类型、加外键等可能退化。
- 备份：逻辑备份 `mysqldump`（慢、可读）、物理备份 XtraBackup（快、物理一致）、binlog 做时间点恢复（PITR）。恢复演练比备份本身重要。
