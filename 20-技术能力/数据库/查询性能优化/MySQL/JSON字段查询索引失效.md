# JSON 字段查询索引失效

技能点：[[MySQL]] · 项目：[[smart WMS]] · 2026-07-16 · 通用技能：[[查询性能优化]]
场景：[[索引失效]]、[[分页与排序]]

## 我想干什么

测试库除了整点卡顿，还有一类「天生昂贵」的查询；把它们和定时任务区分开，避免混为一谈。

## 我干了什么

在同一份排查报告里定位到三类：

| 写法 | 后果 | 实测 |
| --- | --- | --- |
| JSON `LIKE '%x%'` | 前导通配，索引全失效 | 50–120 秒 |
| `ORDER BY data->"$.CODE"` | 对 200 万行排序 | ~50 秒 |
| `SELECT * FROM common` | 撞 `max_execution_time=120000` | 被强制中断 |

## 犯了什么错 / 误判

- 之前把这些统一归成「数据库慢」，没有区分是查询写法问题；慢日志阈值 5 秒还会藏掉一部分。
- 只看到了「卡」，没先问「卡的时间点是不是整点那 57 秒窗口」，容易把两类问题混在一起。

## 怎么解决

本次只定位，修复未落地。可行方向：

- 避免前导 `%` 的 LIKE；需要模糊匹配就上全文索引/搜索引擎。
- 不要对 JSON 字段直接 `ORDER BY`；列表需要的字段冗余成物理列（同 [[出货任务列表去JOIN]]）。
- 禁止 `SELECT *`，只查必要列。
- 必须按 JSON 字段过滤时，用生成列 + 索引，或 `json_extract` 的等值条件。

## 现在的规矩

- JSON 字段不进列表过滤/排序。
- 列表展示字段冗余成物理列，列表查询不解析 JSON。
- 查询只取必要列，不 `SELECT *`。
- 定位慢查询先看 `performance_schema` 总耗时，再看时间点是否撞上定时任务窗口。
