# 查询性能优化

**一句话**：面对任何数据库，先量化「谁在吃时间」，再判断瓶颈在查询写法、索引、数据模型还是任务负载，改完用同一数据集复测。

## 一、理论：数据库怎么执行一条查询

1. **解析 → 优化 → 执行**：优化器基于统计信息估算代价，选择访问路径（全表扫描 / 索引扫描 / 索引覆盖）和连接顺序。
2. **索引不是越多越好**：索引的价值取决于选择性（命中行数 / 总行数）。选择性低时，全表扫描是优化器的正确选择。
3. **查询成本 ≈ 扫描行数 × 单行成本 + 排序/连接/临时表成本**。慢查询通常不是「没索引」，而是「扫了太多行」或「做了大排序」。
4. **负载问题 ≠ 查询问题**：定时任务、锁、连接数、IO 也会让库变慢；先分清是「某条 SQL 慢」还是「整体被拖垮」。
5. **模型问题 ≠ 写法问题**：写法优化到头，才考虑冗余列、生成列、归档、分区、读写分离。

## 三、归纳：通用优化清单

不管 MySQL、PostgreSQL 还是别的库，按这个顺序问：

1. **量化**：按总耗时排，不只看慢日志阈值；先算「谁吃掉了百分之多少」。
2. **分时间窗**：持续慢，还是固定时间/定时任务窗口慢？
3. **分类型**：单条 SQL 慢 / 整体负载高 / 列表页慢 / 写入慢。
4. **看选择性**：WHERE 命中比例多少？低选择性不要加索引。
5. **先改写法**：去 JOIN、去 JSON、去 `SELECT *`、去前导 `%`、限制排序字段、只取必要列。
6. **再改模型**：冗余列、生成列+索引、归档/分区、读写分离。
7. **改任务**：0 行任务停掉/降频/自停；不要用索引掩盖空转。
8. **复测**：同一数据集、同一时间窗；一次只改一个变量。

### 三条红线

- 不要先加索引：先量化，再判断。
- 不要用缓存掩盖慢查询：缓存是第二步。
- 不要一次改多个变量：否则不知道哪个改动有效。

## 四、回到理论：这套规则背后的原理

- 优化器是**基于代价**的：它选全表扫描不是「不会用索引」，而是估算后认为全表扫描更便宜。所以「加索引」不是默认答案。
- 索引的本质是**用空间换随机 IO 的减少**；当命中比例高时，随机 IO 反而比顺序全表扫描贵。
- 数据库的瓶颈经常不在 SQL，而在**工作负载**：一个 0 行任务也能吃掉 66% 的 DB 时间。
- 冗余/反范式是**用写入复杂度和一致性换读取性能**；没有刷新口子的冗余，是把读问题换成数据正确性问题。
- 这些原理适用于所有关系型数据库；换库只换工具和语法，不换判断顺序。

## 五、边界

- 没做过分布式数据库/分库分表/主从切换的性能优化。
- 没做过 MySQL 参数级调优（除了 buffer pool）。
- 这套清单是「单库、单实例」的经验；跨实例/分布式场景要另加网络、分片、一致性成本。
