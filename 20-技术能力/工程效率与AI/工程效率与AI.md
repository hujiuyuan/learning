# 工程效率与AI

**一句话**：工程效率不是工具多，而是把重复劳动换成可重跑的生成/检查链，再让 AI 在链上干活；链子本身要能证明自己没骗人。

## 一、理论：效率来自哪几层

1. **模板生成**：把项目约定写进模板，一次生成契约、实体、DAO、Mapper。收益随表数线性放大，缺陷也线性放大。
2. **补丁链**：原始配置不手改，每处改动写成「断言命中 1 次」的替换片段；顺序固定、可重放、可 diff。
3. **仿真台**：把生成器的渲染、配置拼接、类型映射、落盘语义复刻到本地；桩必须逐字校验，否则「模拟通过」不等于「真项目通过」。
4. **守卫**：编译器不报的错（废 import、重复条件、复合主键 ById 静默跨行）用静态扫描补；判据取自真实 schema 和配置，不靠模板自述。
5. **Agent 编排**：任务拆成可验收的小块，角色（architect / developer / reviewer / writer）拿自包含 brief；判断与执行分开，产出由人复核。
6. **AI 协作的可靠性**：盲审让两个独立样本暴露分歧，裁判只裁决有出处的论据；原文落盘、写入范围核对，防止「看起来对」。
7. **CI 门禁**：把上述检查放进流水线；失败必须硬退出，不能被管道里的 grep、`|| true` 吃掉。

## 二、实际使用：三条链

- **EasyCode 模板链（muou）**：仿真台一条命令跑「桩一致性 → 重建配置 → 五库生成编译 → 两道守卫 → 运行期测试」（`easycode-sim/verify-all.sh:23-121`）。补丁链 58 处文本改动，每处断言命中 1 次（`easycode-sim/report/修复与验证.md:27`；`easycode-sim/build-config.sh:13-21`）。四个库 177 表、2518 个 Java 源码 0 编译错误（`easycode-sim/report/怎么复刻.md:67-73`）；第五个 archive 库也已接入全链（`easycode-sim/verify-all.sh:33-37`）。
- **Agent 链（claude-team）**：角色 = 提示词 + 预加载技能，打包成插件市场（`claude-team/README.md:3-9`、`:211-230`）。辩证裁决是 2 名盲审 + 裁判，分歧题升辩论（`claude-team/roles/team/skills/deliberate/SKILL.md:29-41`、`:78-113`）。本批技能图谱补充实际跑过一轮：盲审原文、裁决、写入范围核对都落盘（`~/.claude-team/runs/20261029-技能图谱补充/rounds/C1-1-甲.md:1-3`、`~/.claude-team/runs/20261029-技能图谱补充/rounds/C1-4-裁判.md:1-9`、`~/.claude-team/runs/20261029-技能图谱补充/checks/C1-1-scope.txt:1-8`）。
- **CI 链（smart / muou）**：smart wms3 的 GitLab CI 把 build 与 deploy 绑在同一台 runner，deploy 直接用本地镜像，不经过 Harbor；部署前跑一次性迁移容器，再做蓝绿切换（`smart-server-wms3/.gitlab-ci.yml:10-18`、`:100-167`；`smart-server-wms3/scripts/deploy/switch.sh:101-130`）。muou 用共享 Maven 模板，服务仓只写差异，另有 3 个 guard 作业（`muou-backend/muou-server-notify/.gitlab-ci.yml:6-23`）。

## 三、归纳：工程效率检查清单

1. **重复动作**：能不能一条命令重跑？重跑要多久？
2. **生成器**：有没有仿真台？桩和真文件逐字一致吗？
3. **配置改动**：是不是补丁链？每处替换能断言命中次数吗？
4. **生成产物**：有没有编译期不报、运行期才炸的错？守卫扫了吗？
5. **守卫判据**：来自产物/schema，还是模板自己写的注释？
6. **失败传播**：检查失败会不会被管道、grep、`|| true` 吞掉？
7. **样本覆盖**：一个库/一类表够吗？复合主键、分区表、特殊类型各覆盖到了吗？
8. **AI 任务**：有可执行的验收命令吗？worker 的汇报能不能当结论？
9. **多 Agent**：有没有独立盲审、裁判、原文落盘、写入范围核对？
10. **人工关卡**：diff 谁看？范围外改动谁批？

### 三条红线

- 不要用「模拟通过」代替「真项目通过」：桩、模板、工作区配置任何一处漂移，结论都不成立。
- 不要把守卫写成永远绿的仪式：判据不独立于被检对象，等于没检。
- 不要让 AI 的汇报当验收结论：汇报是线索，结论以人重跑命令、读 diff 为准。

## 四、回到理论：为什么这些规则成立

- 生成和检查的**固定成本**是一次性的，收益随表数、次数放大；错误也按同样倍率放大，所以守卫必须和生成器同时上线。
- 补丁链把「手改配置」变成**可重放变更**：断言命中 1 次，把静默漂移变成硬错误。
- 仿真台的保真度决定结论上限：复刻的是插件的拼接、渲染、类型映射和落盘语义，不是「大概像」。
- 盲审的价值在**独立性**，不在人多；裁判只认带出处的论据，才能把「两个模型的共识」和「两个模型都猜错」分开。
- CI 是最后执行点，门禁必须硬失败；否则所有本地检查都只是建议。

## 五、边界

- EasyCode 是 IDEA 插件，配置靠手工导入（`easycode-sim/report/修复与验证.md:154-160`）；仿真台不在 muou 仓库里（`easycode-sim/README.md:3`），没有团队采用或生产落地记录。
- 生成器没有正式单测，仿真台靠 shell 脚本串联；没有接进 CI。
- Claude Code 的角色编排只在本机个人使用，没有团队级权限、配额、审计治理。
- 没有用过 MCP；Hook 只在 ccds-panel 里见过注册（`claude-team/roles/ccds-panel/hooks/hooks.json:1`）。
- 没做过统一 CI 平台：smart 与 muou 是两套流水线；生产部署没有落地证据。
- 备份恢复只有文档条目，没有实现代码，不建页。
