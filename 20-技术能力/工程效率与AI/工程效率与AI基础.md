## 1. 构建工具

**一句话**：Maven 用约定目录和生命周期，Gradle 用任务图和增量构建；依赖管理、插件、多模块是核心。

要能回答：

- Maven 的生命周期、阶段、插件、goal 是什么关系？
- `dependencyManagement` 和 `dependencies` 的区别？
- SNAPSHOT 和 release 版本有什么区别？
- 依赖冲突怎么排查？`mvn dependency:tree` 怎么看？
- 多模块项目怎么划分子模块？
- Gradle 的 task、plugin、configuration 怎么理解？

笔记：

- Maven 有三套生命周期：`clean`、`default`（compile→test→package→verify→install→deploy）、`site`；阶段本身不干活，绑定在阶段上的插件 goal 才干活。`mvn package` 会按顺序执行到 `package` 为止的所有阶段。
- `dependencyManagement` 只声明版本/scope，供子模块继承，不引入依赖；`dependencies` 才真正引入。父 POM 用前者统一版本，子模块写后者时不写版本。
- SNAPSHOT 是可变的开发版本，每次构建可能拉到新内容，不能用于生产发布；release 版本不可变。发布用 release，联调用 SNAPSHOT。
- 依赖冲突用 `mvn dependency:tree -Dincludes=groupId:artifactId` 看路径，Maven 按「最短路径优先、同深度先声明优先」选版本；用 `maven-enforcer-plugin` 的 `dependencyConvergence` 把冲突变成构建失败。
- 多模块按「变更频率 + 部署单元 + 团队边界」拆：common/依赖基础、业务服务独立、web 层薄；不要按技术层拆成十几个互相依赖的小模块。
- Gradle 是任务图（DAG）：plugin 往图里加 task，configuration 阶段建图、execution 阶段跑 task；增量构建靠 task 输入输出声明。Maven 是固定生命周期 + 插件绑定，Gradle 更灵活但构建脚本本身要维护。

### 包管理：pnpm/npm/yarn

**一句话**：包管理器解决三件事——从注册源解析版本、把依赖装进磁盘、把「这次装的是哪一版」锁住；pnpm 用内容寻址仓库 + 硬链接复用包，并用严格的 `node_modules` 布局阻止「没声明却能 import」。

要能回答：

- `package.json`、lockfile、`node_modules` 三者各管什么？为什么 lockfile 必须进仓库？
- `^`、`~`、精确版本、workspace 协议分别允许什么漂移？
- pnpm 的全局 store 和硬链接怎么省磁盘？为什么它默认不允许幽灵依赖（phantom dependency）？
- npm、yarn、pnpm 在 lockfile 格式、安装速度、workspace 支持上的差异？
- `--frozen-lockfile` 在 CI 里解决什么问题？不加会怎样？
- 供应链风险怎么管：锁文件、`npm audit`、私有源、依赖冻结、许可证检查各管哪一段？

项目证据（muou 前端）：`muou-web` 与 `muou-admin` 各自在 `package.json` 钉 `"packageManager": "pnpm@10.33.3"`，各自带 `pnpm-lock.yaml`；Dockerfile 用 `corepack enable && corepack install` 从该字段取 pnpm 版本，再 `pnpm install --frozen-lockfile`，避免版本号在两处各写一份、升级时漏改（`muou-web/package.json:4`、`muou-web/Dockerfile:52-60`；`muou-admin/package.json:61`、`muou-admin/docker/Dockerfile:29-37`）。根目录没有 `pnpm-workspace.yaml`，三个前端工程是并列的独立项目，不是 monorepo——这一点容易看错，不能写成「pnpm workspace 管多包」。

**为什么是 pnpm**：同样一份 lockfile，pnpm 安装更快、磁盘占用更小，严格布局能在本地就暴露「依赖没声明」；代价是少数工具假设 npm 的扁平 `node_modules`，遇到时要显式补依赖或调 `node-linker`。**什么时候反悔**：CI 缓存/私有源对 pnpm store 支持不好、或团队工具链只认 npm → 换 npm/yarn，lockfile 和 CI 安装命令一起改；当前两个工程都能稳定 `--frozen-lockfile` 构建。**边界**：项目里没有依赖审计门禁、没有私有源治理，也没有 workspace 实战。

## 2. CI/CD

**一句话**：CI 每次提交自动构建、测试、检查；CD 把通过验证的产物自动部署到目标环境；流水线要快、可重复、失败可定位。

要能回答：

- CI 和 CD 的区别？持续交付和持续部署的区别？
- 流水线一般有哪些阶段？每个阶段的失败策略？
- 构建产物怎么管理？版本号怎么生成？
- 缓存怎么用？缓存失效会怎样？
- 密钥和部署凭证怎么管理？
- 回滚策略有哪些？蓝绿、金丝雀、滚动发布分别适合什么？

关联：[[CI-CD与部署]]

笔记：

- CI：每次提交自动构建、跑测试、做静态检查，目标是「尽早发现集成问题」；CD 分两种——持续交付是「随时可发布，发布由人点」，持续部署是「通过验证自动上生产」。
- 典型阶段：编译 → 单测 → 静态检查 → 集成测试 → 打包/镜像 → 部署到环境 → 冒烟。失败策略：前面的阶段失败就停，不继续浪费资源；部署失败自动回滚或阻断后续环境。
- 产物管理：一次构建产出唯一版本（语义版本 + git sha），同一产物从测试推到生产，不重新构建；产物存制品库，带元数据和校验和。
- 缓存依赖和构建输出能显著提速；缓存 key 要包含 lockfile 哈希，缓存失效会退化为全量下载/全量构建，不能把「缓存命中」当正确性前提。
- 密钥放 CI 的 secret store（或 OIDC 短期凭证），不进仓库、不进镜像、不打日志；不同环境用不同凭证，生产部署加人工审批。
- 回滚：蓝绿两套环境切流量，回滚快但资源翻倍；金丝雀先放小比例流量，观察指标再扩大，适合高风险变更；滚动逐批替换，资源省但新旧版本短期共存，要求接口兼容。数据库变更要向前兼容，否则回滚代码回不去。

## 3. 代码生成

**一句话**：代码生成把重复的 CRUD、模板、DTO 从手写变成配置；模板质量决定生成质量，生成物要能 review、能改、能重新生成。

要能回答：

- 代码生成适合哪些场景？不适合哪些？
- 模板引擎（Velocity/Freemarker）的基本原理？
- 生成物和手写代码怎么隔离？重新生成会不会覆盖修改？
- 数据库元数据怎么驱动生成？
- 生成代码的质量怎么保证？
- 生成器和低代码平台的区别？

关联：[[EasyCode与Velocity]]、[[EasyCode修复]]、[[模板补丁]]

笔记：

- 适合：CRUD、Entity/DTO/Mapper/XML、Controller 骨架、重复的配置和样板；不适合：业务规则、复杂状态流转、需要长期演进的领域逻辑。
- Velocity/Freemarker 都是「模板 + 上下文模型 → 文本」：模板里放占位符和循环，上下文里放表名、字段、类型，输出 Java/XML/SQL。
- 生成物放独立目录（如 `generated/`）或加 `@Generated` 标记，和手写代码物理隔离；重新生成前先 diff，覆盖会丢手改——要么只生成一次，要么用补丁链在生成后做可控修改。
- 元数据来自 `information_schema`（表、列、注释、类型），生成器读元数据建模型；注释质量直接决定生成代码的可读性。
- 质量保证：生成后必须编译、跑测试、人工 review 模板输出；模板本身要有样例测试，改模板要能看出 diff。
- 低代码是运行时的模型驱动 + 页面设计器，改的是平台里的模型；代码生成器是编译期脚手架，产出是普通代码。前者把控制权交给平台，后者保留代码控制权。

## 4. AI 辅助编码

**一句话**：LLM 根据上下文预测下一个 token；它擅长模式化生成和改写，不擅长保证事实正确，所以必须验证。

要能回答：

- LLM 的基本原理是什么？为什么会产生幻觉？
- 上下文窗口、token、温度分别影响什么？
- Prompt 的组成要素？few-shot、chain-of-thought 分别解决什么？
- RAG 是什么？和微调的区别？
- Agent 和普通对话的区别？工具调用怎么工作？
- 怎么让 AI 改代码更可靠？怎么验收？
- 代码补全、代码审查、测试生成分别适合什么？

关联：[[Claude Code与Agent]]

笔记：

- LLM 本质是「根据上下文预测下一个 token」，它优化的是「像不像合理文本」，不是「事实对不对」，所以会生成看起来合理但不存在的方法、版本、配置——这就是幻觉。
- 上下文窗口决定一次能看到多少材料，超出就丢；token 是计费和长度单位；温度控制采样随机性，低温度更确定、高温度更多样。代码任务一般用低温度。
- Prompt 要素：角色/任务、上下文（代码、报错、约束）、输出格式、示例；few-shot 用例子教格式和模式，CoT 让模型分步推理，适合多步问题但不保证正确。
- RAG 是检索外部资料再塞进上下文，知识可更新、可引用；微调是改模型权重，成本高、知识仍可能过期。大多数「让 AI 懂项目」的需求用 RAG/上下文，不是微调。
- Agent 是「模型 + 工具 + 循环」：模型决定调哪个工具，观察结果再决定下一步；普通对话只输出文本。工具调用让 Agent 能读文件、跑命令、查网页，也带来权限和副作用风险。
- 让 AI 改代码可靠：任务拆小、给足上下文（文件路径、约束、验收命令）、要求先读后改、用编译/测试/类型检查验收、逐 diff review；不让它在没跑过的情况下宣称「已完成」。
- 补全适合局部样板和重复模式；审查适合找遗漏和一致性；测试生成适合补边界，但生成的测试必须能失败（先看它能不能抓住一个已知 bug），否则只是摆设。

## 5. 研发流程与协作

**一句话**：分支策略、代码评审、提交规范、发布流程共同决定协作效率；工具只是承载，规则要能执行。

要能回答：

- Git Flow、Trunk-Based、GitHub Flow 的区别？
- 代码评审应该看什么？多大 PR 合适？
- 提交信息规范有什么价值？
- 如何做小步提交和可回滚发布？
- 需求、设计、开发、测试、上线怎么串起来？
- 技术债怎么记录和偿还？

笔记：

- Git Flow：长期 `develop` + `release` + `hotfix` 分支，适合有明确版本发布周期的产品，分支多、合并重；Trunk-Based：所有人提交到主干或极短分支，靠特性开关和 CI 控制风险，适合持续部署；GitHub Flow：主干 + 短分支 + PR，轻量，介于两者之间。
- 代码评审看：正确性、边界与错误处理、测试是否证明行为、接口/数据兼容、安全（注入/权限/密钥）、可维护性（命名/重复/复杂度）；风格交给工具，不占 review。
- PR 越小越好，一般控制在几百行以内；大 PR 拆成「重构」「行为变更」「测试」几个提交，评审者能按提交看。
- 提交信息写「为什么」而不只是「改了什么」；Conventional Commits 让 changelog 和版本号可自动生成，但价值在沟通，不在格式本身。
- 小步提交 + 特性开关 + 可回滚发布：每个提交可独立回滚，未完成功能用开关关掉，发布和上线解耦。
- 需求→设计→开发→测试→上线用同一套编号/链接串起来（需求 ID、PR、测试用例、发布记录），出问题能追溯。
- 技术债记成 issue：写清现状、风险、触发条件、偿还成本，排进迭代；不要只写「重构」这种无法验收的条目。

## 6. 效率度量

**一句话**：效率度量要看交付周期、部署频率、变更失败率、恢复时间，不要用代码行数、提交次数这类代理指标。

要能回答：

- DORA 四个指标分别是什么？
- 为什么代码行数、故事点不能衡量效率？
- 怎么发现流程瓶颈？
- 自动化到什么程度值得？
- 怎么衡量 AI 辅助的实际收益？
- 度量会不会导致行为扭曲？

笔记：

- DORA 四指标：变更前置时间（commit 到上线）、部署频率、变更失败率、故障恢复时间（MTTR）。前两个看速度，后两个看稳定性，要一起看。
- 代码行数、提交次数、故事点是代理指标：写得多人不一定快，拆得细提交多不代表价值，故事点估的是相对复杂度。它们容易被游戏，也不反映交付结果。
- 找瓶颈用价值流图/周期时间：从需求进入到上线，每一段等待多久、返工多少；瓶颈通常在等待、评审、环境、跨团队交接，不在编码速度。
- 自动化的价值 = 节省的重复时间 × 频次 − 维护成本；高频、易错、规则明确的步骤值得自动化，一次性/低频/判断密集的不值得。
- 衡量 AI 收益看交付周期、评审时间、缺陷率、返工率，做前后对比或分组对比；不要用「生成了多少行」。
- 度量会扭曲行为（Goodhart 定律）：指标一旦用于考核，就会被优化而不是被改善。度量用于团队自查和改进，不用于排名惩罚。
