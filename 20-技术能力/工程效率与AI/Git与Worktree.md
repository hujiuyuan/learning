# Git 与 Worktree

所属通用技能：[[工程效率与AI]]

**一句话**：Git 的核心是「提交是不可变快照，分支只是指针」；项目里最有用的三个动作是分支隔离、revert 回滚和 worktree 并行开发。

## 方法总纲

1. **先看状态再动手**：`git status`、`git log --oneline --graph`、`git diff` 三件套，确认当前分支和未提交改动。
2. **分支是指针**：切分支不会复制文件；未提交改动会跟着走，切之前先 stash 或提交。
3. **回滚分两种**：`revert` 生成反向提交，适合已推送；`reset` 改指针，适合本地未推送。
4. **worktree 隔离并行任务**：同一个仓库多个工作目录，各自分支，不用来回 stash。
5. **冲突是内容冲突**：先看懂两边改了什么，再决定保留哪边；不要无脑 `--ours`/`--theirs`。
6. **提交信息写「为什么」**：标题说结果，正文说原因和影响；方便以后 `git log` 找线索。

## 我会的部分

- **提交归属**：用 `git log --author=hujiuyuan` 区分自己的提交；smart-web-wms 11 条、smart-web-omp 31 条（`smart-web页面` 有逐条记录）。
- **回滚**：三个前端修复被 revert——`7057a51` 回滚列表勾选、`023f088` 回滚多行文本、`884446e` 回滚签到页顺序；被回滚的改动不算「现在生效」。
- **分支流向**：提交后确认当前分支和远端分支，避免在 test 分支重复提交 dev 已有的改动。
- **worktree**：muou-server-iam 用 `.wt/s2iam`、`.wt/tpath` 两个工作目录并行改不同特性分支（`git worktree list` 可见）。
- **冲突处理**：先 `git diff` 看两边改动，再决定合并；冲突解决后跑构建/测试再提交。
- **提交拆分**：一个提交只做一件事；格式化、重命名、功能改动分开，方便 review 和 revert。
- **找回丢失提交**：`git reflog` 找 HEAD 移动记录；`git fsck --lost-found` 找悬空对象。

## 选型与取舍

| 选择 | 为什么 | 代价/失败模式 | 什么时候反悔 |
| --- | --- | --- | --- |
| worktree 而不是多份 clone | 共享对象库/配置，不用重新 fetch；每个任务一个目录、各自分支 | 同一仓库的 hooks/配置共享；目录多了要记得清理；IDE 索引可能重复 | 需要完全隔离的环境/权限 → 多 clone 或容器 |
| worktree 而不是 stash | stash 是串行的，多个任务来回切容易漏/冲突；worktree 各自独立 | 每个 worktree 占磁盘、要单独装依赖/起服务 | 只切一下看代码 → stash 更快 |
| merge 而不是 rebase（已推送分支） | 不改写历史，协作者不用重新拉；冲突解决一次 | 历史分叉多、graph 乱 | 个人未推送分支、追求线性历史 → rebase |
| revert 而不是 reset（已推送） | 生成反向提交，别人能拉到；审计留痕 | 历史多一条回滚提交 | 本地未推送、要彻底丢弃 → reset |
| 一个提交只做一件事 | review/revert/二分定位都容易 | 提交次数多，需要写清信息 | 紧急修复可合并，但要在信息里说明 |

判断顺序：先问「提交推没推」→ 推了用 revert；再问「是不是并行任务」→ 是就 worktree；再问「分支有没有别人用」→ 有就用 merge；最后问「历史要不要线性」→ 要且未推送才 rebase。

## 边界

- 没有做过 Git 服务端运维（GitLab/GitHub 权限、hooks、保护分支配置）。

- 没有做过分支策略的团队级设计，只按现有仓库分支工作。
