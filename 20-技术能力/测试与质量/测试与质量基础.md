# 测试与质量基础

通用技能：[[测试与质量]] · 定位：基础知识挂载页

**一句话**：测试基础题的分类索引。这里回答「应该会什么」，不冒充「我做过什么」；做过的事仍记在实践卡。

## 怎么用

- 自测：看每一块的「要能回答」，能用自己的话讲清楚才算过。
- 挂笔记：新写一篇八股文，在对应块的「笔记」后加 `笔记名`，笔记里链回本页。
- 分边界：原理和机制放这里；具体故障、排查过程、修复方案放场景/实践卡。

## 1. 测试分层

**一句话**：单测证分支，切片证一层契约，集成证真实依赖协作，E2E 证用户路径；每层只证明它能证明的事。

要能回答：

- 测试金字塔和冰淇淋筒的区别？为什么反模式会出现？
- 单元、集成、端到端测试的边界怎么划？
- 每一层分别应该断言什么？
- 测试数量配比应该怎么定？
- 哪些行为必须用真实依赖测？

关联：[[测试与质量]]、[[单测与集成测试]]

笔记：

- 金字塔：底层大量单测、中层少量切片/集成、顶层极少量 E2E；冰淇淋筒反过来，大量手工/UI 测试、少量单测。反模式出现通常是因为「UI 测试最像用户」的直觉 + 单测写起来费劲 + 没有测试分层规范，结果反馈慢、维护贵、失败定位差。
- 边界按「依赖真实度」划：单测替换所有外部协作方；切片只装一层框架（MVC/MyBatis）；集成装真实 DB/Redis/MQ；E2E 从浏览器到后端全真。不是按代码行数或目录划。
- 每层断言不同：单测断分支结果和协作方调用；切片断序列化/路由/错误处理/插件拼 SQL；集成断真实 SQL、事务、约束、时区；E2E 断用户可见结果。跨层断言（单测断 SQL 文本）通常是错位。
- 配比没有固定数字，按「反馈速度 × 失败定位成本 × 风险」定；核心链路可以多集成，纯计算多单测。项目里 Mockito 证分支、`@MybatisPlusTest` 证 SQL、三容器 E2E 证认证链路。
- 必须真实依赖：SQL 方言与函数、事务回滚、唯一约束、租户/软删插件、序列化与时区、Security 过滤器链、对象存储契约。mock 掉这些，等于把要证明的行为一起 mock 掉。

## 2. 单元测试

**一句话**：单测隔离被测对象，用替身替换协作方；AAA（Arrange-Act-Assert）让测试结构清晰，断言要针对行为而不是实现。

要能回答：

- 一个测试应该有几个断言？断言什么？
- Mock、Stub、Spy、Fake 的区别？
- 什么时候该 mock，什么时候不该？
- 怎么测异常和边界条件？
- 测试命名怎么表达「给定什么、做什么、期望什么」？
- 私有方法要不要直接测？

笔记：

- 一个测试只验证一个行为；同一行为的多条断言可以放一起（如「返回成功 + 状态变为 DONE + 只写了一条记录」），但不要在一个测试里串多个无关场景。断言针对可观察行为，不断内部调用顺序和私有字段。
- Mock 预设返回值并验证交互；Stub 只提供固定返回，不验证；Spy 包真实对象、可选择性打桩；Fake 是有简化实现的替身（内存仓库）。业务测试优先 Stub/Fake，交互验证只在「必须发生某调用」时用 Mock。
- 该 mock 的是「不属于被测对象的协作方」：DAO、HTTP 客户端、消息发送。不该 mock 的是被测对象本身依赖的框架行为（事务、插件、序列化）和要验证的规则。
- 异常用 `assertThrows` 并断言异常类型 + 消息/错误码；边界用参数化测试覆盖空值、0、负数、最大长度、越界；不要只测 happy path。
- 命名写「给定什么_做什么_期望什么」或 `should_..._when_...`；名字要能当失败信息读。
- 私有方法通过 public 入口测；如果私有方法复杂到必须单测，说明它该抽成独立类。反射测私有方法会把重构变脆。

## 3. 切片与集成测试

**一句话**：切片测试只装一层框架，集成测试装真实数据库/缓存/消息；Spring Boot 的 `@WebMvcTest`、`@DataJpaTest`、`@MybatisPlusTest` 都是切片。

要能回答：

- `@WebMvcTest`、`@SpringBootTest`、`@MybatisPlusTest` 分别装了什么？
- 切片测试里哪些 Bean 是真实的、哪些是替身？
- 集成测试怎么准备和清理数据？
- 测试事务回滚和真实提交怎么选？
- 容器化依赖（Testcontainers）怎么启动、复用、清理？
- 测试之间怎么隔离？并发执行要注意什么？

关联：[[JUnit与Testcontainers]]

笔记：

- `@WebMvcTest` 只装 MVC 层（Controller、`@ControllerAdvice`、序列化），Service 默认是 mock；`@MybatisPlusTest` 只装 MyBatis-Plus + 数据源，不装 Web；`@SpringBootTest` 装完整容器，`webEnvironment=RANDOM_PORT` 起真实 HTTP。
- 切片里真实的是被切的那层框架和它的配置；其余 Bean 要么不加载，要么用 `@MockBean` 替身。切片不证明跨层契约，比如 `@WebMvcTest(addFilters=false)` 不证明认证。
- 数据准备：每个用例自己造行（DAO `save` 拿自增 id），不依赖其他用例的残留；需要建表脚本的先跑 `init.sql`。清理用「每个测试类独立库名」或事务回滚；跨线程/异步写不能靠回滚。
- 测试事务默认回滚适合 DAO 层；要验证提交后行为（`afterCommit`、消息发送、异步任务）必须真实提交，再用唯一数据或清库收尾。
- Testcontainers：静态 `@Container` 一个类共用一个容器，`@Testcontainers(disabledWithoutDocker=true)` 无 Docker 整类 skip；容器地址通过 `ApplicationContextInitializer` 注入；容器用完由 Testcontainers 回收，数据靠独立库名/脚本隔离。
- 并发执行：JUnit 默认同类内顺序执行；开并行后共享容器、共享库名、静态状态会互相踩。并行前先保证每个用例数据独立、端口随机、不依赖执行顺序。

## 4. 端到端测试

**一句话**：E2E 驱动真实浏览器和真实后端，证明用户路径；最接近用户，也最慢、最脆、最依赖数据。

要能回答：

- E2E 应该覆盖哪些路径？不应该覆盖哪些？
- Playwright 的定位器、自动等待、断言怎么用？
- 测试数据怎么准备？用完怎么清理？
- 失败时怎么定位？截图、视频、trace 怎么用？
- 怎么降低 flaky？重试算不算通过？
- E2E 要不要进 CI？怎么控制耗时？

关联：[[Playwright]]、[[E2E报告]]

笔记：

- E2E 覆盖「用户必须能完成」的少数路径：登录、核心业务闭环、权限拒绝、支付/导出等高风险流程；不覆盖字段级校验、边界值、内部错误码，这些放单测/切片。
- Playwright 优先用角色/标签定位（`getByRole`、`getByLabel`），少用 CSS/XPath；它有自动等待（元素可操作才动作），断言用 web-first assertion（`expect(locator).toHaveText`），不要手写 `sleep`。
- 数据准备走 API/seed 脚本，不靠上一个用例留下的数据；每个用例用唯一标识（时间戳/UUID）建自己的数据，结束后按标识清理或整库重置。
- 失败定位靠 trace + 截图 + 视频：Playwright 配 `trace: 'on-first-retry'`、`screenshot: 'only-on-failure'`；trace 能回放每一步 DOM 和网络。
- 降 flaky：等状态不等时间、稳定定位器、数据隔离、固定时区/语言、串行跑有共享状态的用例；重试只能掩盖 flaky，重试才过要单列并追根因。
- CI 策略：PR 跑冒烟子集（核心路径 + 受影响模块），全量 nightly；用分片（shard）、并行 worker、只跑受影响项目控制耗时；E2E 失败要能区分产品 bug 和测试自身问题。

## 5. 测试替身与依赖

**一句话**：替身只替换「不属于被测对象」的东西；把被测行为替掉，测试就只剩自我实现。

要能回答：

- 过度 mock 有什么危害？
- 数据库、Redis、HTTP、消息队列分别怎么替身？
- Testcontainers 和 H2/嵌入式数据库怎么选？
- 契约测试解决什么问题？
- 测试替身的行为和真实实现不一致怎么办？

笔记：

- 过度 mock 的危害：测试通过只证明「mock 按我写的返回」，不证明真实协作方行为；重构实现时测试大量红，改真实 bug 时测试照样绿。mock 越多，测试离生产越远。
- 数据库用 Testcontainers 真库；Redis 用容器；HTTP 下游用 WireMock/MockWebServer 起假服务（比 mock 客户端更真，能验证序列化/超时）；消息队列用容器或内存实现，至少验证序列化与 ack 语义。
- Testcontainers vs H2：H2 快但有方言/函数/隔离级别/约束差异，容易「H2 绿、MySQL 挂」；真容器慢但证明的是真行为。项目里集成测试统一真 MySQL，H2 不作为集成库。
- 契约测试（Pact 等）解决「消费者期望」和「提供者实现」不一致：消费者生成契约，提供者 CI 验证；适合跨团队/跨服务 HTTP 契约，不替代端到端。
- 替身与真实不一致时：优先把关键路径改成真依赖；不能改的，用契约测试或定期跑真实依赖的集成测试兜底；并在测试类注明替身假设，别让后来人把 mock 行为当真实契约。

## 6. 覆盖率与质量门禁

**一句话**：覆盖率说明「哪些代码被执行过」，不说明「断言是否正确」；门禁要结合行覆盖、分支覆盖和关键路径。

要能回答：

- 行覆盖、分支覆盖、条件覆盖的区别？
- 覆盖率高但测试无效是什么样子？
- 变异测试解决什么问题？
- 覆盖率门禁应该卡在多少？为什么不能一刀切？
- 怎么统计增量覆盖率？
- 哪些代码不应该计入覆盖率？

笔记：

- 行覆盖：执行过的行占比；分支覆盖：if/switch 的每个分支是否都走到；条件覆盖：复合条件里每个子条件是否取过真假。行覆盖高不代表分支都测了，分支覆盖更接近「逻辑测全」。
- 覆盖率高但无效：只调用不断言、断言 `assertNotNull`、测试 getter/setter、把异常吞掉；代码被执行不等于行为被验证。
- 变异测试（PIT）：自动改代码（取反条件、删调用），看测试会不会红；红说明断言能抓住缺陷，存活变异说明测试太弱。成本高，适合核心模块定期跑。
- 门禁不能一刀切：核心领域/支付/权限要求高，DTO/配置/生成代码不要求；按模块设阈值，并看增量覆盖率（新代码覆盖）而不是全库数字。
- 增量覆盖率：只统计本次 diff 新增/修改的行，避免「老代码拉低整体、新代码没人管」；CI 里用 diff + jacoco 报告比对。
- 不计入：生成的 DTO/Entity、Lombok 生成代码、配置类、启动类、`main`、迁移脚本；排除要写明规则，不能靠感觉。

## 7. 测试稳定性与维护

**一句话**：flaky 测试是测试自身的缺陷；重跑才过不是通过，必须单列、追根因、限期修复。

要能回答：

- flaky 的常见原因有哪些（时序、数据、环境、并发）？
- 怎么发现 flaky？怎么统计 flaky 率？
- 测试代码怎么重构？怎么避免重复？
- 测试数据构造有哪些模式（Builder、Factory、Fixture）？
- 测试太慢怎么优化？
- 旧测试失效了怎么办？

笔记：

- flaky 常见原因：时间（`sleep`、超时太短）、异步（没等状态稳定）、数据（用例间共享/顺序依赖）、环境（时区、端口、Docker、外部服务）、并发（共享静态状态、并行跑同一库）。
- 发现与统计：同一提交重复跑 N 次、CI 记录失败用例历史、按「同用例不同提交成败不一致」算 flaky 率；flaky 用例单独标记，不混在「产品失败」里。
- 测试代码也要重构：抽 Builder/Factory 造数据、抽页面对象/API 客户端、抽断言助手；重复的 setup 用 `@BeforeEach`，但别抽到看不清用例前提。
- 数据构造模式：Builder（链式设字段）、Object Mother（预定义典型对象）、Fixture（固定文件/脚本）；核心是让每个用例只写「与默认值不同的部分」。
- 测试太慢：并行、容器复用、只跑受影响模块、把慢集成从 `mvn test` 拆到独立阶段；不要为了快把关键断言删掉。
- 旧测试失效：需求变了就改断言或删测试，并在提交信息说明；不能靠放宽断言/加重试让它变绿。长期不跑又不敢删的测试，先确认它是否还在默认构建里。

## 常见对比题

- 单测 vs 集成测试 vs E2E
- Mock vs Stub vs Spy vs Fake
- 测试金字塔 vs 冰淇淋筒
- 行覆盖 vs 分支覆盖
- Testcontainers vs 内存数据库
- 重试通过 vs 稳定通过
