# 测试与质量

**一句话**：测试分层不是「越多越好」，而是每一层只证明它能证明的事：单测证分支，切片证一层契约，容器集成证真实 SQL/事务，浏览器 E2E 证用户路径；用错层，断言越多越假。

## 一、理论：四层测试各证明什么

测试金字塔说的是数量配比：单测多、集成少、E2E 更少。但配比不是目的，关键是每层只证明它自己能证明的事。

1. **单测（Mockito）**：被测对象是类/方法，协作方换替身。能证明给定输入和协作方行为下的分支、状态机、异常路径；不能证明 SQL、事务、序列化、过滤器、并发。
2. **切片测试**：只装一层。`@WebMvcTest` 装 MVC + 异常处理，Service 是替身；`@MybatisPlusTest` 装 DAO + 插件，Web 层不存在。证明的是「这一层与真实框架的交互」。
3. **集成 / 全栈**：`@SpringBootTest(RANDOM_PORT)` + Testcontainers 起真实 MySQL/Redis 和 S3（localstack），走真实 HTTP 栈。证明认证过滤器、参数绑定、序列化、DB 约束一起工作；仍不证明浏览器渲染。
4. **浏览器 E2E**：Playwright 驱动真实前端 + 真实后端，证明用户路径和跨端契约。最接近用户，也最慢、最依赖数据、最容易 flaky。
5. **测试替身边界**：替身只该替换「不属于被测对象」的东西。把被测行为本身替掉，测试就只剩自我实现。
6. **flaky**：重跑才过不是通过，是「不稳定」。它说明测试有时序/数据/环境缺陷，必须单列并追根因，不能混进通过率。

- **DAO 集成**：`FilesSoftDeleteItTest.java:48-53` 用 `@MybatisPlusTest` + 真实 MySQL，`FilesSoftDeleteItTest.java:103-120` 同时断言「软删的不回」和「活着的照回」。
- **全栈**：`AuthPermissionE2eTest.java:38-49` 用 `@SpringBootTest(RANDOM_PORT)`，`AuthPermissionE2eTest.java:80-83` 起 MySQL/Redis/localstack 三个容器，走真实登录和权限接口。
- **元测试**：`ResultCodeUniquenessTest.java:14-27,36-56` 遍历枚举守「业务码唯一」，把一次性事故变成长期约束。

### 前端测试：Vitest/RTL/jsdom

路径说明：以下前端路径相对 `/Users/hujiuyuan/workspace/voidtech/muou-client/`；`vitest.config.ts` 在 `muou-web/`、`muou-admin/` 各自根下。

- **规模**：muou 前端共 702 个 `src/**/*.test.{ts,tsx}`（muou-web 345、muou-admin 357，按 `find` 统计，不等于全部通过）。两个工程都用 Vitest 4.x、Testing Library `@testing-library/react` 16.3.2、`user-event` 14.6.3、jsdom 30（`muou-web/package.json:42-55`；`muou-admin/package.json:45-59`）。
- **muou-web 默认 node 环境**：绝大多数用例测 schema 解析、token 合并、props 校验这类纯逻辑，不需要 DOM；需要真实 DOM 的用例在文件顶部用 `// @vitest-environment jsdom` 单独声明，避免全量付 jsdom 启动成本（`muou-web/vitest.config.ts:4-23`）。
- **muou-admin 全 jsdom + 串行**：组件测试依赖 antd 和异步语言包，`fileParallelism: false` 防止资源竞争放大偶发超时；单次渲染 5~25s，超时提到 15s，否则会被判成 `STACK_TRACE_ERROR`（`muou-admin/vitest.config.ts:10-23`）。
- **与 JUnit 的分工**：JUnit/Testcontainers 证 Java 侧 SQL、事务、过滤器；Vitest/RTL 证 TS 逻辑和组件交互（点击、输入、渲染结构）；Playwright 证真实浏览器里的用户路径。三者不互相替代：RTL 不启动真实后端，JUnit 不渲染 DOM，Playwright 不给你组件级定位。

#### 为什么用 Vitest，不用 Jest

- **Vite 原生**：测试和构建共用同一套 transform、alias、TS 配置，不需要再维护一份 Babel/ts-jest 配置；ESM 和 TS 直接跑。
- **代价**：生态比 Jest 小，少数 Jest 专有匹配器/快照习惯要改；Vitest 4 移除了 `environmentMatchGlobs`，按文件声明环境要换写法（`muou-web/vitest.config.ts:15-16` 的注释就是在记这个坑）。
- **为什么仍选它**：两个工程都是 Vite/Next + TS，Jest 要额外配 transform 和模块映射，收益只有「生态大」；当前用例以逻辑和组件为主，Vitest 的 API 足够。
- **什么时候反悔**：团队统一 Jest、或需要 Jest 独有的 React Server Components 测试能力 → 评估迁移；当前没有 RSC 组件测试，只有构建和人工走查。

### 架构测试：ArchUnit

- **规模**：10 个 `*ArchTest.java`，覆盖 common、两个 archive、gateway 和 6 个业务服务（platform/member/billing/content/notify/iam）；公共库把 12 条规则打成一包 `MuouArchRuleSet`，服务引用这一个类即全部生效（`muou-common/muou-common-app/src/test/java/com/voidtech/muou/common/arch/MuouArchRuleSet.java:8-60`）。
- **规则类型**：租户只能来自验签上下文、领域层不依赖框架、租户上下文只有一个出口、Redis 只走 Redisson、只允许 Jackson 3、`@Pii` 之外不许直接用脱敏序列化器、标识符只用英文、业务异常必须带词条 key、公共库不出现库名字面量、时区固定 UTC+8、outbox 只能由 producer 包发布、RocketMQ 监听器只能在 consumer 包（`MuouArchRuleSet.java:13-59`）。
- **规则自身也有测试**：`MuouArchRuleSetCoverageTest` 守「公共库有的规则，服务这一包必须全都在」，防止新增规则只加在 common、服务侧漏挂；`MuouArchRulesTest` 守规则本身的判定行为（`muou-common/muou-common-app/src/test/java/com/voidtech/muou/common/arch/`）。
- **版本**：`archunit-junit5 1.4.1`，由 `muou-build` 统一管理（`muou-build/pom.xml:62`、`:384-386`）。

#### 为什么用 ArchUnit，不用人工 review/Enforcer

- **人工 review**：能看命名和意图，但看不住「新增一个类有没有绕开唯一入口」；规则一多，review 靠记忆，漏一次就进主干。ArchUnit 把规则变成每次构建都跑的断言。
- **Maven Enforcer**：管的是依赖坐标、版本收敛、禁止某组构件，看不到包依赖、注解使用、方法签名、字面量。两者不是替代关系：Enforcer 守「引了什么」，ArchUnit 守「代码长什么样」。
- **代价**：规则误报会逼人加例外，例外一多规则就废；扫描字节码增加测试时间；规则写错会把错误做法固化。项目用覆盖测试和规则自测降低这两类风险，但不能消除。
- **什么时候反悔**：模块/规则数量继续涨，单包规则集编译和扫描变慢 → 按模块拆规则集、只跑本模块相关规则；规则例外多到需要大量 `@ArchIgnore` → 先删规则或改设计，而不是继续加例外。

## 三、归纳：测试检查清单

1. **层对不对**：这条测试要证明的行为，是否真的在这一层？替身有没有替掉要证明的东西？
2. **断言对象**：断言返回集/body code/页面状态，还是 SQL 文本/私有方法？后者会随实现漂移。
3. **正反成对**：只断「删掉的不回」会漏「活着的不回」；过度过滤也能让单向断言变绿（`FilesSoftDeleteItTest.java:41-44`）。
4. **数据隔离**：租户上下文显式设置，每个用例自己造数据，容器/库每次干净。
5. **默认构建会不会跑**：`*IT.java` 不在 surefire 默认匹配里；`*CloudE2eTest` 被显式排除（`smart-server-wms3/pom.xml:351-353`）；无 Docker 时 `disabledWithoutDocker=true` 直接跳过（`FilesSoftDeleteItTest.java:51`）。
6. **失败能不能定位**：错误信息写业务后果；E2E 要有截图、接口记录、trace。
7. **flaky 单列**：重跑才过记「不稳定」，不进稳定通过数。
8. **契约看 body code**：项目统一 HTTP 200，只断状态码等于没断（`CoreControllerAdviceNotFoundTest.java:61-65`）。

### 三条红线

- 不要把「有测试类」写成「测试全部通过」：类存在、注解在、报告旧，都不是通过。
- 不要用 SQL 文本断言代替真库断言：文本只能证明「加了条件」，证明不了「结果对」。
- 不要把重跑才过算成通过：那是在掩盖 flaky。

## 四、回到理论：为什么这些规则成立

- 测试的可信度 = 它没有替身掉「要证明的那部分」。替身越多，跑得越快，证明力越弱。
- 真实依赖越多，越接近生产，也越慢、越脆；分层就是在速度和可信度之间选位置。
- 断言越接近用户可见结果（返回集、body code、页面状态），越不容易被重构打碎。
- flaky 是测试自身的缺陷，不是随机噪音；忽略它等于把「不确定」算成「通过」。
- 这四条换到任何语言和框架都成立：切换的是工具，不是「这层能证明什么」。

## 五、边界

- 没做过覆盖率门禁：jacoco 只 `prepare-agent` + `report`，没有 `check` 阈值（`smart-server-wms3/pom.xml:356-370`）。
- 没做过契约测试、变异测试、性能/压测、视觉回归。
- e2e-hub 没接 CI：仓里没有 `.github/`、`.gitlab-ci.yml`、`Jenkinsfile`，跑法仍是手动 `node bin/run.mjs`（`e2e-hub/README.md:9-12`）。
- 没有可用的 smart 全量回归结论：`target/surefire-reports` 只有 2026-08-28 的 58 份报告（398 次运行），早于当前代码，不能当当前结论。
- 测试栈：Java 侧 JUnit/Testcontainers + ArchUnit（muou 10 个 ArchTest）；前端 Vitest/RTL（muou 702 个测试文件）+ Playwright（e2e-hub 与 muou 17 个 spec）；Vue 项目侧没接前端测试。
