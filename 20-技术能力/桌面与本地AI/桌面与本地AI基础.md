## 1. 桌面应用架构

**一句话**：桌面应用分「原生壳 + WebView 前端 + 本地后端」三层；进程边界、IPC、权限和更新是架构核心。

要能回答：

- 原生桌面、WebView 桌面、纯 Web 应用的区别？
- 主进程、渲染进程、后端进程分别负责什么？
- IPC 的常见方式？消息怎么序列化？
- 桌面应用的权限模型和 Web 有什么不同？
- 自动更新怎么设计？签名和回滚怎么处理？
- 原生桌面：性能/系统集成最好，开发成本高；WebView 桌面：前端技术栈 + 原生壳，跨平台、开发快；纯 Web：零安装但受浏览器沙箱/网络/文件权限限制。
- 主进程管窗口/生命周期/系统 API/更新；渲染进程跑前端 UI，沙箱内、不能直接碰文件系统；后端进程（Tauri 的 Rust 侧）处理业务/IO/数据库，通过 IPC 暴露命令。
- IPC：Tauri 用 `invoke(command, args)` + `emit/listen` 事件；Electron 用 `ipcRenderer.invoke` / `ipcMain.handle`。参数/返回值走 JSON（serde），二进制用 ArrayBuffer/流。
- 桌面权限比 Web 大：能读写文件、起进程、访问网络。要按最小权限配置能力（Tauri capabilities/allowlist），只暴露必要命令，命令参数要校验路径（防目录穿越）。
- 自动更新：检查版本 → 下载签名包 → 校验签名 → 安装 → 失败回滚；签名私钥不能进客户端，更新源要 HTTPS。
- 崩溃/日志：捕获 panic/未处理异常，写本地滚动日志，用户同意后上传；日志脱敏（密钥、路径、内容）。

## 2. Tauri 与 Electron

**一句话**：Electron 打包 Chromium + Node，生态成熟但体积大；Tauri 用系统 WebView + Rust 后端，体积小但依赖系统环境。

要能回答：

- Tauri 和 Electron 的架构区别？
- 各自的体积、内存、启动速度、兼容性代价？
- Tauri 的 `command`、`invoke`、`state` 怎么用？
- Rust 和前端之间怎么传复杂对象？错误怎么传？
- 系统 WebView 版本差异会带来什么问题？
- 关联：[[Tauri与Rust IPC]]

笔记：

- Electron：打包 Chromium + Node.js，前端就是浏览器，生态成熟、行为一致；体积 100MB+、内存高、启动慢。Tauri：用系统 WebView（macOS WKWebView、Windows WebView2、Linux WebKitGTK）+ Rust 后端，体积几 MB，但依赖系统 WebView 版本。
- 代价：Tauri 在不同系统 WebView 上 CSS/JS 行为有差异，老系统可能缺 API；Electron 自己带 Chromium，一致但重。
- Tauri：`#[tauri::command]` 定义命令，前端 `invoke('cmd', {args})` 调用；`State` 注入共享状态（数据库连接、配置）；事件用 `emit`/`listen`。
- Rust 与前端传复杂对象用 `serde`（`Serialize/Deserialize`），字段名用 `#[serde(rename_all = "camelCase")]` 对齐前端；错误返回 `Result<T, E>`，E 实现 `Serialize`，前端拿到错误字符串/对象。
- 系统 WebView 版本差异：老 Windows 可能没有 WebView2（要装运行时），Linux 发行版 WebKitGTK 版本不一；关键功能要做能力检测/降级。
- 选型：体积/内存敏感、需要 Rust 性能/本地能力 → Tauri；需要一致 Chromium、Node 生态、老系统覆盖 → Electron。不适合 Tauri：必须支持很老的系统、依赖 Chromium 特有 API、团队不写 Rust。

## 3. Rust 与 IPC

**一句话**：Rust 用所有权、借用、生命周期保证内存安全；Tauri IPC 把前端调用序列化成命令，Rust 侧处理并返回结果。

要能回答：

- 所有权、借用、生命周期的基本规则？
- `String` 和 `&str`、`Vec<T>` 和 `&[T]` 的区别？
- `Result` 和 `Option` 怎么用？`?` 运算符做什么？
- `async`/`await` 在 Rust 里怎么工作？
- Tauri 命令的同步和异步怎么选？
- 前端调用 Rust 失败时怎么拿到错误信息？
- 关联：[[Tauri与Rust IPC]]

笔记：

- 所有权：每个值有唯一所有者，离开作用域释放；借用：`&T` 共享借用、`&mut T` 可变借用，同一时刻要么多个共享要么一个可变；生命周期标注告诉编译器引用活多久。
- `String` 拥有堆内存、可增长；`&str` 是字符串切片借用；`Vec<T>` 拥有、可增长；`&[T]` 是切片借用。函数参数优先用借用，返回所有权用拥有类型。
- `Option<T>` 表示可能有/没有，`Result<T,E>` 表示成功/失败；`?` 在错误时提前返回（需 `From` 转换错误类型）。不要用 `unwrap()` 处理可恢复错误。
- Rust `async fn` 返回 Future，需要运行时（tokio）驱动；`.await` 挂起不阻塞线程；跨 `await` 持有非 `Send` 类型会编译失败。
- Tauri 命令：快速同步操作可同步；IO/网络/数据库用 `async` 命令，避免阻塞主线程。前端 `invoke` 返回 Promise，失败走 catch。
- 大文件/二进制：不要 base64 塞 JSON（膨胀 33%）；用流式读取、分块传输、自定义协议/`tauri://` 资源、或写入临时文件传路径；传路径要校验在允许目录内。

## 4. 本地存储

**一句话**：桌面应用常用 SQLite 存结构化数据、文件系统存大对象；本地数据库要考虑迁移、备份、并发和损坏恢复。实现细节见 [[SQLite]]。

要能回答：

- SQLite 适合什么场景？并发写入有什么限制？
- WAL 模式解决什么问题？
- 本地数据库怎么做版本迁移？
- 数据存在用户目录还是应用目录？卸载时怎么处理？
- 备份和恢复怎么做？
- 多窗口/多进程同时访问怎么协调？

笔记：

- SQLite 适合单机、读多写少、嵌入式；写是单写者（同一时刻一个写事务），并发写会 `SQLITE_BUSY`。WAL 模式让读不阻塞写、写不阻塞读，但仍是单写者，且多一个 `-wal` 文件。
- 版本迁移：用 `PRAGMA user_version` 或迁移库（如 rusqlite_migration/SeaORM migration），按版本顺序执行，迁移前备份。
- 数据位置：应用数据目录（macOS `~/Library/Application Support/<app>`、Windows `%APPDATA%`）存数据库/配置；用户文档目录存用户可见文件。卸载是否删数据要明确，默认保留用户数据。
- 备份：`VACUUM INTO` 或 SQLite Backup API 做一致性快照；直接复制文件要先 checkpoint WAL，否则丢最新事务。恢复时校验完整性（`PRAGMA integrity_check`）。
- 多窗口/多进程：尽量单进程单连接（或连接池）+ 串行写；必须多进程时开 WAL + `busy_timeout`，避免长时间写事务；不要用文件锁自己造轮子。
- 本地库也要防损坏：异常退出/磁盘满/同步盘（iCloud/Dropbox）可能损坏；定期备份、写入用事务、避免网络盘直接放库文件。

## 5. 向量数据库与检索

**一句话**：向量数据库存 embedding，用近似最近邻（ANN）检索语义相近的内容；索引类型决定速度、召回率和内存。

要能回答：

- embedding 是什么？维度、距离度量怎么选？
- 余弦相似度、内积、欧氏距离的区别？
- ANN 索引有哪些（HNSW、IVF、PQ）？各自取舍？
- LanceDB 的存储格式和索引怎么工作？
- 向量检索和关键词检索怎么混合？
- 关联：[[LanceDB与RAG]]

笔记：

- embedding 是模型把文本/图片映射成高维向量（如 768/1024 维），语义相近的向量距离近。维度由模型决定，换模型要重建索引；距离度量要与模型训练时一致。
- 余弦相似度看方向（长度无关），内积看方向+长度（模型归一化后等价），欧氏距离看绝对距离。文本 embedding 常用余弦/内积。
- ANN 索引：HNSW 是分层图，查询快、召回高、内存大、构建慢；IVF 先聚类再搜少数簇，需要训练、召回受 nprobe 影响；PQ 把向量分段量化压缩，省内存但有精度损失，常与 IVF 组合。
- LanceDB 用 Lance 列式格式存向量 + 元数据，支持 IVF_PQ/HNSW 索引、版本化数据集；适合本地/嵌入式，按目录存。
- 混合检索：关键词（BM25/全文）保精确匹配，向量保语义，结果融合（RRF/加权）+ rerank；纯向量对专有名词/编号不敏感。
- 更新/删除：向量库多为追加+标记删除，索引需要 compaction/重建；频繁更新要按批次重建，别每条都重建。

## 6. RAG 与本地模型

**一句话**：RAG 先检索相关资料再让模型生成；效果取决于切分、embedding、召回、重排和提示词，不是「接个向量库」就完事。

要能回答：

- RAG 的完整流程？每个环节解决什么问题？
- 文档怎么切分？chunk 大小和重叠怎么定？
- 召回不准怎么排查？召回率和精确率怎么权衡？
- 重排（rerank）解决什么问题？
- 本地模型和云端 API 各有什么取舍？
- 怎么防幻觉？怎么让答案带出处？
- 关联：[[LanceDB与RAG]]

笔记：

- 流程：文档解析 → 切分 chunk → embedding → 建索引 → 查询改写/embedding → 召回 top-k → rerank → 拼 prompt（带上下文/引用）→ 生成 → 附出处。
- 切分：按语义段落/标题切，chunk 几百 token，重叠 10–20% 保上下文；太大召回粗、太小丢语义。代码/表格单独处理。
- 召回不准排查：先看召回的 chunk 里有没有答案（召回问题），再看 prompt 是否忽略（生成问题）。召回率（答案在不在 top-k）优先于精确率，再用 rerank 提精确率。
- rerank：用 cross-encoder 对「query + chunk」逐对打分重排，比向量相似度准，但慢；先召回 20–50 条再 rerank 到 3–5 条。
- 本地模型：隐私好、无 API 成本、离线可用；质量/速度受硬件限制。云端 API：质量高、免运维，但有成本/延迟/数据外发。按敏感度和质量要求选，可混合（本地小模型 + 云端大模型）。
- 防幻觉：只让模型基于检索内容回答、要求引用片段、检索不到就明确说不知道、输出结构化引用；用评测集定期测 faithfulness。
- 上下文不够：控制 top-k、压缩/摘要 chunk、分层检索（先摘要再细节）、多轮检索（map-reduce）。

## 7. 密钥与 Provider

**一句话**：API Key 不能明文放配置文件；桌面应用用系统钥匙串（Keychain/Credential Manager）存密钥，按 provider 管理配置。

要能回答：

- 桌面应用有哪些存密钥的方式？各自风险？
- 系统钥匙串怎么读写？跨平台差异？
- 多 provider 怎么抽象？配置怎么隔离？
- 密钥泄露怎么检测和轮换？
- 本地代理/抓包能拿到密钥吗？怎么防？
- 关联：[[keyring与Provider]]

笔记：

- 存密钥方式：明文配置文件（最差，易被备份/同步/误提交）、环境变量（进程可见、可能进日志）、系统钥匙串（OS 加密、按用户隔离，推荐）、应用内加密（密钥又存哪？）。
- 系统钥匙串：macOS Keychain、Windows Credential Manager、Linux Secret Service（GNOME Keyring/KWallet）；用 `keyring` crate 跨平台读写，按 service/user 命名隔离。
- 多 provider 抽象：统一接口（base_url、api_key、model、超时），每个 provider 一个配置 + 密钥引用；密钥存钥匙串，配置存普通文件，二者分离。
- 泄露检测/轮换：密钥带前缀/指纹便于识别，定期轮换，泄露后立即吊销；日志/错误上报做脱敏（只显示后四位）。
- 本地代理/抓包：用户机器上的进程/管理员能读内存和网络，无法完全防；能做的是不明文落盘、不写日志、HTTPS、最小权限、提示用户风险。
- 日志脱敏：统一 redact 函数过滤 `api_key/token/authorization` 字段，异常信息不回显请求头；调试日志默认关闭。

## 8. 本地优先与同步

**一句话**：本地优先（local-first）让应用离线可用、数据归用户；代价是同步、冲突解决和多端一致性。

要能回答：

- local-first 和传统云优先的区别？
- 离线修改怎么同步？冲突怎么检测？
- CRDT 和 OT 分别解决什么问题？
- 同步失败、部分同步、重复同步怎么处理？
- 数据加密和端到端加密怎么影响同步？
- 关联：[[本地优先]]

笔记：

- 本地优先：数据主副本在本地，读写不依赖网络，离线可用；云优先：数据在服务端，本地只是缓存。前者体验好、隐私强，后者一致性和多端简单。
- 离线修改同步：本地记录操作/变更（op log/变更集），联网后推送 + 拉取；冲突检测用版本号/向量时钟/更新时间，冲突解决按业务（后写胜、字段合并、人工）。
- CRDT：数据结构本身可交换合并（如计数器、集合、文本序列），无需中心排序，适合离线多端；OT：中心服务器变换操作顺序，适合实时协同编辑，依赖中心。
- 同步失败/部分同步/重复：操作要幂等（op id）、可重试、断点续传；部分成功要记录游标/确认，不能整批重来。
- 端到端加密：服务端看不到明文，无法做服务端合并/搜索；冲突解决要在客户端，密钥管理更难。
- 多设备最终一致：定义「一致」的粒度（文档/字段/操作），用版本向量检测并发，定期全量校验/修复；UI 要能显示同步状态和冲突。
