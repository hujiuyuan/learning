## 项目级方案取舍

> 说明：项目没有一份完整的架构决策记录；下面按代码、测试和文档能确认的约束整理，决策过程没有原文的部分标「推断」。

### 为什么重写成 Java + Vue 3，而不是在 PHP 上渐进改

- **现状约束**：老系统是 ThinkPHP 5.1 + PHP 8.0，维护级（[[PHP与ThinkPHP]]：160 次本人提交、40 controller、33 model）；新系统是 Java 21 + Spring Boot 3.3 + Vue 3，1256 次 wms3 提交、534 个测试文件。老栈没有类型系统、事务边界靠框架约定、前端工程化和自动化测试都弱。
- **候选**：继续在 PHP 上渐进改；Strangler 逐步替换；全量重写 Java + Vue；换 Go/Node。选全量重写（推断：团队 Java 经验、生态、长期维护），代价是功能对齐、双跑/数据迁移、重写期间需求冻结，以及旧系统还要继续维护。
- **不是「Java 更先进」**：如果只是修几个报表，PHP 渐进改更便宜；重写的收益是类型/事务/测试/前端工程化，代价是一次性大迁移。反悔条件：重写范围失控或核心交易长期对不齐 → 先冻结非核心模块，按 Strangler 把核心留在旧栈，不要为了「全量」硬推。

### 为什么 MySQL + 应用层租户过滤，不上 PostgreSQL/RLS

- 老系统就是 MySQL，团队/运维/备份工具链成熟；换库要重做迁移、SQL 方言、运维和监控。代价是 MySQL 没有 RLS，租户隔离只能靠应用层 `tenant_id` + 拦截器，解析失败/手写 SQL 会漏（[[MySQL租户字段]]）。
- 没有选 schema-per-tenant/独立库：租户多、单租户数据量不大、需要跨租户运营报表，schema/独立库会让迁移和连接路由 ×N。
- 反悔条件：合规要求物理隔离、或跨租户报表成为主查询 → 评估 PostgreSQL RLS/独立库/数仓，而不是继续给业务库加过滤。

### 为什么本地事务 + `afterCommit`，没有上 Outbox

- smart 以单体为主，跨进程写少；能用「同一连接本地事务 + 提交后副作用 + 幂等/CAS」解决，就不引 Outbox 的投递表和延迟。邮件/PDF/S3 放 `afterCommit`，回调写库用 `REQUIRES_NEW`（[[事务与状态一致性]]）。
- 代价：提交后副作用失败没有自动重试/死信，要靠日志/补偿；跨服务一致性没有 Outbox 的「不丢」保证。反悔条件：出现跨服务写、消息可靠性成为主问题 → 引 Outbox/本地消息表，而不是继续在业务里补重试。

### 为什么 Liquibase，不是 Flyway

- 需要 changeset 级回滚、context、`sqlFile` 外置长 SQL；59 个 changelog、50 份 rollback、部署时一次性迁移容器（[[Liquibase]]）。Flyway 的 undo 要自己写/付费版，换过去等于重做回滚体系。
- 代价：文件多、抽象重、`DATABASECHANGELOGLOCK` 无 TTL 出过锁事故。反悔条件：迁移量变小、团队更熟 SQL-first → 评估 Flyway；当前回滚/审计需求还在。

### 什么条件下整体反悔

重写长期对不齐、核心交易不稳定 → 收缩到 Strangler；事务一致性从单库变跨服务 → Outbox/Seata；租户隔离从应用层变合规强隔离 → PG RLS/独立库；前端团队换成 React 生态 → 评估 React/Next（当前 Vue 3 是团队约束）。
