技术能力拆分报告

三种技术能力粒度的对比：技术栈级、能力点级、知识点级。目标不是写教程，而是定下「一张技术卡装多少东西」。

证据：实际用过 + 只读过 只读技术单独标注 推荐：方案 B

0. 结论

推荐方案 B（能力点级，约 40 个节点）。 一个节点刚好能独立说清「这个技术怎么用 + 坑在哪」，查起来不粗不碎。
  1. 方案 A 会把高价值细节埋进大卡，例如「Spring Security 的数据权限」「时区改造」只能当 Spring 卡里的一节。
  2. 方案 C 会把同一个问题的知识拆散，例如时区改造会同时落到 Java 时间、Jackson、MySQL、前端日期四张卡，维护和跳转都变重。
  3. B 是可扩展的：某个知识点以后长胖了（比如时区改造），再单独升成一张卡，不用一开始就拆到底。

1. 三种粒度对比

4. 方案 C：知识点级（约 70 个）

在 B 的基础上，每个节点再按「具体机制」拆开。下面是展开示例：

B 节点C 会拆成张数
Java 并发线程池与参数、CompletableFuture/异步编排、并发安全与锁3
Spring Security认证过滤器链、授权决策、方法级安全、数据权限4
Spring 事务传播行为、回滚规则、事务失效、异步一致性4
PostgreSQL复合主键契约、jsonb 索引、分区/审计表、Flyway 适配4
Vue 3响应式、组件通信、路由守卫、权限菜单4
Playwrightfixture/采集、trace、报告、重试与不稳定4
Claude CodeSkill、Agent、Plugin、Hook、MCP5
numpyshape、axis、广播、@、reshape/视图5

其余 B 节点按同样方式各拆 2–3 个，总数约 70。

问题：同一个问题会横跨多张卡。比如「后端改 UTC 后前端时间错位」要同时改 Java 时间、Jackson、MySQL 时区、前端日期四张卡；查一次要跳四处，且四张卡容易各写一半。

5. 只读技术怎么处理

按你的要求，读过但没上手的技术也收，但卡的类型不同，不能写成「我解决过」。

只读候选

  • yudao-cloud：Spring Cloud、MyBatis、多租户、代码生成器、Vben5 前端模板
  • yudao-ui-admin-vue3：Vue 3 + Vben Admin
  • java-template-engine：Java 模板引擎
  • ebo-admin-cn / ebo-web-nuxt：如果只是看或少量改
  • 其它只读过源码、没有实际排障记录的技术

只读卡模板

# Spring Cloud（只读）

证据类型：只读

我读懂了什么：
- 服务拆分、网关、注册配置中心怎么配合
- 多租户/数据权限在框架里的落点

关键设计：
- ……

和我会的哪里不一样：
- 和我实际改过的 Spring Boot 单体项目相比，……

坑（来自源码/文档）：
- ……
规则：只读卡不写「症状 → 根因 → 我做的动作」，只写「我读懂了什么 / 关键设计 / 和我会的哪里不一样 / 文档里写的坑」。这样不会把读过的当成做过的。

6. 工程能力和技术能力怎么连

工程能力卡不重复技术细节，只列它依赖哪些技术卡。示例：

技术卡反向列 1–3 个「在哪些工程能力里用到」，项目页列全量。这样图有三条边：能力—技术、能力—项目、技术—项目。

7. 建卡顺序

1
先写 3 张样板：Spring Security、PostgreSQL、Playwright（后端 / 数据库 / 测试各一张），你确认格式。
2
按栈批量：Java → Spring → 数据库 → 中间件 → 前端 → 桌面/AI → 测试 → AI 工具链 → 数学/LLM → 工具。
3
技术卡稳定后，再写工程能力卡，引用技术卡。
4
最后补项目证据页、业务索引、能力地图。

8. 需要你选

A技术栈级，约 20 个节点，每个框架/库一张大卡。

B能力点级，约 40 个节点，推荐。

C知识点级，约 70 个节点。

选定后我先出 3 张样板，不一次性铺开。 样板会按你选的粒度写，格式确认后再批量。
