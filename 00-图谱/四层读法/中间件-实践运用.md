# 中间件（实践运用）

**定位**：这一层回答「在哪个项目用过、怎么接、失败怎么处理」。中间件不只是消息队列：缓存/锁、调度、消息、限流熔断、可观测、推送/邮件都算。理论在 [[技术栈-理论]]，故障根因在 [[问题与原理]]，选型与项目位置在 [[项目方案]]。

## 怎么读

1. **先看组页的「六问/清单」**：例如 [[中间件与异步任务]] 的生命周期、背压、线程、锁、幂等、可观测；[[认证与授权]] 的认证/授权/租户三层。
2. **再看实践页的「做法 + 证据」**：实践页只写这次怎么做的、`路径:行号` 在哪，不重写理论。
3. **最后回到项目证据**：[[smart WMS]]、[[muou]] 等页面按业务模块列出实践/场景，能反查「这个决定服务的是哪个模块」。
4. **不要只看成功路径**：每个实践页的「边界/代价」才是可迁移的部分；只抄做法会在下一个项目踩同一个坑。

## 边界

- 实践页的证据强度不一：有代码/测试的写「实战」，只有设计文档的写「设计/方案」，不能混着当「已上线」。
- 同一个技术在不同项目的用法可能不同（例如 Redis 在 smart 是共享缓存 + 锁，在 muou 是 Redisson 客户端），以各页的项目说明为准。
- 中间件的版本和部署形态以项目页为准，不在这一层做产品对比；对比在 [[项目方案]] 的「选型与取舍」。
