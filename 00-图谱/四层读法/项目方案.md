## 跨项目对照

| 决策 | smart WMS | muou | NovelForge |
| --- | --- | --- | --- |
| 一致性 | 本地事务 + `afterCommit`；跨进程靠幂等/CAS | 本地消息表 Outbox + RocketMQ 普通消息；跨服务 5 个服务/11 入口用 Seata XA | 单机 SQLite 本地事务；向量索引可重建，不做跨进程一致 |
| 迁移 | Liquibase（59 changelog、rollback、一次性迁移容器） | Flyway（多仓收集 + `build.sql` 人审执行） | `user_version` 版本化迁移；拒绝打开更新的库 |
| 身份/权限 | JWT + keyVer + 接口权限（开关未开） | Spring Security 7 + Casbin 域内 RBAC | 本地单用户 + 系统 keyring 存 provider key |
| 前端 | Vue 3 + Vite | Next 16/React 19（web）+ React 19/antd（admin） | React 19 + Vite（Tauri WebView） |
| 部署 | 单机 Docker + GitLab CI + 蓝绿 | 多服务 + GitLab 共享模板 + Nacos/网关 | GitHub Actions 多平台安装包；无自动更新 |

这张表是「同一问题在不同约束下的不同答案」，不是「谁更先进」。比如 smart 没有上 Outbox，是因为跨进程场景少、已有幂等/CAS；muou 多服务多租户，才需要 Outbox + XA。

## 怎么读

1. **先看项目证据页的「模块 → 相关节点」**：它告诉你这个项目的方案散在哪些技能点/实践页。
2. **再看技能点页的「选型与取舍」**：四个问题——当时要解决什么、候选有哪些、每个方案的代价、为什么选它/什么条件反悔。
3. **最后看实践页的「边界」**：落地时哪里打了折、哪些是设计不是已上线。
4. **不要只读结论**：同一技术在不同项目的选择可能相反（例如 RocketMQ 在 muou 是事件驱动、不在导出链路；Redis 在 smart 是共享缓存 + 锁），结论必须带项目前提。

## 边界

- 项目证据页只写有证据的部分：没有 git 提交的项目标「项目内使用/学习中」，不写成个人实战。
- 生产方案与测试方案分开：例如 smart 的生产部署清单自述是「测试级部署」，不能当生产已上线。
- 选型不是一次性决定：每个方案页都写了反悔条件；条件触发时要重新走 [[四层读法]] 的理论 → 问题 → 方案。
