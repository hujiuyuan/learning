# 可观测性理论

**一句话**：可观测性不是「多打日志」，而是用日志、指标、链路三种信号回答「系统现在怎么样、这个请求为什么慢/错」；信号之间要靠 traceId/时间/资源关联起来，否则只是三堆数据。

## 一、三种信号

| 信号 | 回答 | 特点 | 代价 |
| --- | --- | --- | --- |
| 日志（logs） | 某个时刻发生了什么 | 高细节、非结构化/半结构化、量大 | 存储/检索成本高；容易漏关键字段 |
| 指标（metrics） | 整体趋势/告警 | 可聚合、低成本、适合长期 | 维度有限，难定位单请求 |
| 链路（traces） | 一个请求经过哪些服务、各段耗时 | 端到端、能定位瓶颈 | 采样/存储成本；埋点/传播要求高 |

三者不是替代关系：指标发现「有问题」，链路定位「哪一段」，日志解释「为什么」。

## 二、链路模型

- **trace**：一次请求的完整调用链，有唯一 `traceId`。
- **span**：链路上的一段操作（HTTP 调用、DB 查询、消息消费），有 `spanId`、`parentSpanId`、开始/结束时间、状态、属性。
- **上下文传播**：跨进程要把 `traceId/spanId` 放进请求头（W3C `traceparent`）、消息头、日志 MDC；任何一跳丢了，链路就断。
- **服务端/客户端 span**：同一 RPC 在客户端和服务端各有一个 span，靠 `spanId` 关联；异步/消息用 link/follows-from 表达因果。
- **baggage**：随链路传播的业务键值（租户/用户），注意隐私和大小限制。

## 三、采样

- **head sampling**：请求开始时按概率决定是否记录；实现简单，但可能漏掉错误/慢请求。
- **tail sampling**：请求结束后按状态/延迟决定；能保留错误和长尾，但要在收集端缓冲完整 trace，成本高。
- **采样率一致**：链路每一跳的采样决定要一致，否则 trace 缺段；通常由入口决定并传播。
- **概率采样 vs 速率限制采样**：前者按比例，后者按每秒上限；高流量下要组合。
- **采样会骗人**：只看采样后的 p99/错误率可能偏差；指标要全量，trace 才采样。

## 四、指标

- **类型**：counter（只增）、gauge（可增可减）、histogram（分布/分位数）、summary。
- **分位数**：p50/p95/p99 比平均值有意义；平均值会被长尾掩盖。histogram 可在服务端聚合分位数，summary 通常客户端计算、不可跨实例聚合。
- **维度/基数**：标签（status、path、tenant）越多，时间序列越多；高基数标签（userId、traceId）会打爆存储。
- **RED**：Rate（请求速率）、Errors（错误率）、Duration（延迟）——面向服务。
- **USE**：Utilization、Saturation、Errors——面向资源（CPU/内存/队列）。
- **告警**：优先告症状（错误率/延迟/SLO），而不是告原因（CPU 高不一定影响用户）；原因指标用于排查。

## 五、日志

- **结构化**：JSON/键值，固定字段（ts、level、logger、traceId、tenantId、msg）；便于检索和聚合。
- **关联**：每行日志带 traceId/spanId；没有关联的日志在微服务里几乎不可用。
- **级别**：ERROR 只给「需要人处理」的错误；大量 ERROR 会稀释告警。
- **采样/降噪**：高频日志采样、同类日志限流；但审计/安全日志不能随便采样。
- **PII**：日志脱敏，异常栈也可能带敏感数据；采集端也要脱敏（见 [[可观测性与OpenTelemetry]] 的 PII appender）。
- **保留**：热日志短保留、冷日志归档；成本和合规平衡。

## 六、SLO/SLI 与错误预算

- **SLI**：可测量的指标（成功率、p99 延迟、新鲜度）。
- **SLO**：SLI 的目标（如 99.9% 成功、p99 < 300ms）。
- **错误预算**：`1 - SLO`；预算用完要停止发布/降风险，而不是继续堆功能。
- **告警**：基于 burn rate（错误预算消耗速率），比静态阈值更能平衡灵敏度和噪音。

## 八、常见误解

- 「日志越多越可观测」：没有结构/关联/采样的日志只是成本。
- 「有 trace 就能定位」：trace 只给耗时和调用关系，业务原因还要日志/指标。
- 「采样率越低越省钱」：可能漏掉错误和长尾；尾部采样按状态保留更稳。
- 「平均延迟正常就行」：p99 可能已经爆了；要看分位数和长尾。
- 「告警越多越安全」：告警疲劳会让人忽略真正的问题；按 SLO/burn rate 告警。

## 九、机制深挖：trace 上下文传播与采样决策

**traceparent 的字节结构。** W3C Trace Context 用一个 HTTP 头传播上下文：

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  └ trace-id（16 字节，32 hex）      └ parent-id（8 字节）└ flags（01 = sampled）
             └ version（00）
```

固定 55 个字符；`tracestate` 放厂商扩展（有序键值，最多 32 项），`baggage` 是另一个头，放业务键值（tenant、用户 ID），注意隐私和大小。flags 的最低位就是 **sampled 决策**——它随请求传播，下游据此决定记不记。

**传播链路每一跳都要显式做。** HTTP header → 进程内 Context/ThreadLocal → 日志 MDC → 下游 header / MQ 消息属性。框架不会自动跨这些边界，断链发生在：

| 断点 | 为什么会断 | 正确做法 |
| --- | --- | --- |
| 线程池 | 提交任务的线程有 context，执行线程没有 | 包装任务（OTel `Context.current().wrap(...)`、Spring `TaskDecorator`） |
| MQ 生产/消费 | 消息不继承发送方的 context | 生产端写消息头，消费端提取后设为 parent 或 link |
| 批量消费 | 一条消费 span 对应多条消息，单 parent 表达不了 | 用 link 指向每条消息的生产 span |
| CompletableFuture / 回调 | 异步回调不自动传播 | 显式捕获 context 再恢复 |
| 定时任务 | 没有上游，本来就没有父 span | 新建 root trace，不要伪造 parent |
| 重试 | 新请求容易生成新 trace | 同一 trace 内新建 span 或 link，保留重试链 |

**采样决策必须一致。** 如果每个服务各自按 10% 掷骰子，一条 3 跳的链路被完整记录的概率是 `0.1³ = 0.1%`，而不是 10%，还会缺段。正确做法是入口决定一次，把 `sampled` flag 沿 traceparent 传下去；或者用 trace-id 做**确定性哈希**（如取 trace-id 后 8 字节 mod 10000 < 采样率×10000），任何节点独立计算都得到同一结论，不需要协调。

**head vs tail 的真实差别。**

| | head sampling | tail sampling |
| --- | --- | --- |
| 决策时机 | 请求开始时 | 整条 trace 结束后 |
| 能看到什么 | 只有入口信息（路径、租户、是否已带错误） | 全部 span：错误、延迟、属性 |
| 能保证留住错误/长尾吗 | 不能，低概率事件会被随机采掉 | 能，可按状态/延迟 100% 保留 |
| 实现成本 | 低，入口一个概率 | 高：collector 要缓冲完整 trace |
| 内存估算 | 接近 0 | QPS × span 数 × span 大小 × 窗口；1 万 span/s × 30s × 1KB ≈ 300MB |
| 路由要求 | 无 | 同一 trace 的所有 span 必须到同一 collector（按 trace-id 一致性哈希），否则拼不完整 |
| 失败模式 | 错误样本太少，排查看不到 | 挂起的请求一直占缓冲；collector 重启丢缓冲中的 trace |

tail sampling 的常见策略是「错误 100% + 慢于阈值 100% + 其余按 1%」，不是单一概率。它的代价概括成一句：**用收集端的钱换「错误和长尾一定在」**。

**全采到底多贵。** trace 量 ≈ QPS × 平均 span 数 × span 大小 × 保留时间。1000 QPS × 20 span × 1KB × 7 天 ≈ 12TB 未压缩（压缩后常见 1/5~1/10）。这就是生产环境很少全采的原因：**指标全量、日志按级别、trace 采样**是成本可承受的分工。项目当前 `probability: 1.0` 全采，流量小的时候没问题，流量上来后第一个要改的就是这里（见 [[可观测性与OpenTelemetry]]）。

## 十、机制深挖：histogram 分位数聚合与标签基数

**classic histogram 就是一组累计计数器。** 一个 histogram 指标展开成 `_bucket{le="..."}`（每个桶一个 series）+ `_sum` + `_count`；12 个桶就是 14 条时间序列。`le` 是「小于等于」，桶是累计的：`le="0.1"` 的计数包含 `le="0.05"` 的计数。

**分位数靠桶内线性插值估出来**：

`q ≈ le_i + (le_{i+1} − le_i) × (q×total − cum_i) / (count_{i+1} − cum_i)`

误差上界是桶宽：所有请求挤在一个宽桶里，插值就是瞎猜。两个推论：

- **桶边界要围绕 SLO 设**。SLO 是 p99 < 300ms，就在 100/200/300/500/1000ms 设桶；最上面必须有有限上界（如 10s），否则 p99 落进 `+Inf` 桶时没有上界可插值，估出来的数字没有意义。
- **桶太少省存储但误差大，桶太多则 series 数翻倍**。12 个桶是常见折中。

**聚合顺序不能反。** 桶计数可加，所以正确做法是先汇总再算分位：

`histogram_quantile(0.99, sum by (le) (rate(http_duration_bucket[5m])))`

**先算各实例 p99 再平均是错的**，误差可能非常大。例：A 实例 990 个请求全是 5ms，B 实例 10 个请求全是 500ms：

- 全局 p99：1000 个请求里第 990 个落在 A，结果是 **5ms**；
- 「各实例 p99 求平均」：A 的 p99=5ms、B 的 p99=500ms，平均 **252ms**，高估 50 倍。

反过来，B 的流量占比高时平均又会低估。summary 是客户端算好的分位，天生不可跨实例合并，只能平均——这也是推荐 histogram 而不是 summary 的原因。

**native/exponential histogram** 用指数桶（桶下标 ≈ log2(value) × 2^scale），不需要提前猜边界，相对误差有上界（scale 越高越准），同 scale 的桶可以直接合并。代价是存储格式和工具链更新，部分老版本 Prometheus/Grafana 支持有限。

**标签基数是乘法，不是加法。** 一个指标的 series 数 = 各标签取值数的乘积 × 指标数：

`20 个服务 × 30 个接口 × 5 个方法 × 8 个状态码 × 3 个地域 = 7.2 万 series`；如果是 14 桶 histogram，就是 **100 万 series**。再加一个 200 个取值的 pod 标签，直接 2 亿。Prometheus 每个活跃 series 大约占 1~3KB 内存（标签、索引、chunk），100 万 series 就是 2~4GB，查询和 compaction 都会变慢。

**高基数的处理原则**：

- `trace_id`、`user_id`、`order_id`、原始 URL 永远不做 label；用 exemplar 把 trace_id 挂到指标样本上，从 p99 直接跳 trace，不增加 series。
- path 归一化：`/orders/123` → `/orders/{id}`；错误码聚成 2~5 类。
- collector 侧 relabel/drop、白名单，或先 recording rule 预聚合再丢弃原始高基数指标。
- 监控 `prometheus_tsdb_head_series` 并设阈值告警，别等 OOM 才发现。
- 确实要按用户/订单查，放日志或 trace 的检索里——**指标系统的成本模型不适合高基数查询**。

没有「又便宜又能按任意维度切」的指标系统：基数守恒，要么在采集端丢维度，要么在存储端付内存。判断标准是你会不会真的按这个维度做聚合——没人用的 label 就是纯成本。

## 边界

- 项目全采（1.0），没有采样调优/尾部采样；没有流量/成本数据。
- 没有 SLO/错误预算实践，告警以基础资源/错误日志为主。
- 日志/指标/链路的存储容量和保留策略没有做过规划。
