# 事务与隔离理论

**一句话**：ACID 是四个独立保证，不是捆绑销售；隔离级别是「允许哪些异常」的约定，不同数据库对同名级别的实现并不相同；分布式事务是在「原子性」和「可用性/性能」之间做取舍。

## 一、ACID 各自靠什么

| 性质 | 含义 | 实现手段 | 容易误解 |
| --- | --- | --- | --- |
| 原子性 A | 一组操作要么全成功、要么全回滚 | undo log / 回滚日志 | 回滚不是「反向执行」，是撤销未提交修改 |
| 一致性 C | 事务前后满足约束（业务规则/唯一键/外键） | 数据库约束 + 应用校验 | 数据库不保证业务一致性，只保证声明过的约束 |
| 隔离性 I | 并发事务互不看到中间状态 | 锁 + MVCC | 隔离级别不是越高越好，越高并发越差 |
| 持久性 D | 提交后崩溃不丢 | redo/WAL + fsync + 副本 | 异步复制/关闭 fsync 时仍可能丢 |

## 二、并发异常

| 异常 | 现象 | 例子 |
| --- | --- | --- |
| 脏读 | 读到别的事务未提交的写 | 读到回滚前的余额 |
| 不可重复读 | 同一事务两次读同一行，值不同 | 第一次读 100，第二次读 80 |
| 幻读 | 同一范围两次查，行数不同 | 第一次 3 条，第二次 4 条 |
| 丢失更新 | 两个事务读同一值、各自写回，后写覆盖前写 | 库存 100，两个请求都写 99，实际卖了 2 件 |
| 写偏斜 | 两个事务读同一组、各写不同行，违反跨行约束 | 两个医生同时值班，都看到「还有 1 人」 |

## 三、隔离级别

SQL 标准四级别与「允许的异常」是下限，不是精确描述：

| 级别 | 脏读 | 不可重复读 | 幻读 | 实现差异 |
| --- | --- | --- | --- | --- |
| Read Uncommitted | 允许 | 允许 | 允许 | PostgreSQL 实际上等同 RC |
| Read Committed | 禁止 | 允许 | 允许 | 每条语句取新快照（PG）；MySQL 默认不是它 |
| Repeatable Read | 禁止 | 禁止 | 标准允许，PG/InnoDB 实际禁止 | PG 整事务一个快照；InnoDB 用 MVCC + next-key lock |
| Serializable | 禁止 | 禁止 | 禁止 | PG 用 SSI（冲突检测）；MySQL 用锁 |

关键：**同名级别在不同数据库行为不同**。MySQL 默认 RR，PostgreSQL 默认 RC；PG 的 RR 不会幻读但可能 `serialization failure`，要重试。

## 四、锁与 MVCC

- **共享锁（S）/排他锁（X）**：读锁/写锁；S 与 S 兼容，X 与任何都不兼容。
- **意向锁**：表级标记「下面有人要加行锁」，避免逐行检查。
- **行锁/间隙锁/next-key**：InnoDB 在 RR 下用 next-key 锁范围，防幻读；RC 下通常只锁行。
- **乐观锁**：版本号/CAS，冲突时更新 0 行；适合冲突少的场景，冲突多会大量重试。
- **悲观锁**：`SELECT ... FOR UPDATE`，先锁再改；适合冲突多、必须成功的场景，代价是等待/死锁。
- **死锁**：互相持有对方需要的锁；数据库检测到会回滚一方。预防：固定加锁顺序、缩短事务、减少锁范围。
- **MVCC**：读不加锁、读写不阻塞；写写仍要锁。快照隔离下写偏斜仍可能发生，需要 Serializable/SSI 或显式锁。

## 五、事务边界

- 事务只包「必须同生共死的数据库写」；HTTP/RPC/文件/消息放事务外。
- 事务越大：锁持有越久、undo/redo 越大、回滚越慢、连接占用越久、主从延迟越大。
- 传播行为：`REQUIRED` 加入当前事务、`REQUIRES_NEW` 独立事务、`NESTED` 保存点；异步线程没有事务上下文。
- 只读事务是提示，不是写保护；`readOnly` 不会阻止写。
- 提交后动作：`afterCommit` 里写库要用新事务（`REQUIRES_NEW`），否则加入已结束的事务是 no-op。

## 六、分布式事务

- **2PC/XA**：prepare 锁定资源、commit 统一提交；协调者故障会阻塞，分区可能部分完成。
- **TCC**：Try 预留、Confirm 确认、Cancel 取消；业务侵入大，要处理空回滚/幂等/悬挂。
- **Saga**：局部事务 + 补偿；适合长流程，中间状态可见，补偿不是回滚。
- **Outbox**：本地事务写业务 + 消息表，后台投递；把分布式事务降级为至少一次 + 幂等。
- **选择顺序**：本地事务 → Outbox/Saga（可接受最终一致）→ XA（强一致且资源支持）→ TCC（需要预留资源）。

## 七、幂等与「恰好一次」

- 至少一次投递 + 幂等键/唯一约束 = 效果上的恰好一次。
- 幂等键要包含业务主键 + 操作类型 + 窗口；占位和副作用同事务；重复请求返回首次结果/409/跳过，接口契约写清。
- 状态推进用 CAS（`WHERE status = from`），0 行要区分「已到目标态」和「非法状态」。

## 十一、常见误解

- 「RR 一定不会幻读」：MySQL InnoDB 的 RR 用 next-key 锁防幻读；PG 的 RR 用快照，也看不到新行；但标准并不要求。
- 「隔离级别越高越好」：Serializable 冲突多、重试多；大多数业务 RC/RR + 乐观锁/CAS 足够。
- 「有了事务就不会丢更新」：读-改-写仍可能丢失更新；要用 `SELECT FOR UPDATE`、CAS 或原子 SQL。
- 「分布式事务必须 2PC」：大多数业务用 Outbox/Saga + 幂等，2PC 只适合强一致且资源支持的场景。
- 「回滚就是撤销一切」：外部 HTTP/消息/文件不会自动回滚；事务边界要先把它们移出去。

## 九、机制深挖：丢失更新与写偏斜的时间线

### 9.1 丢失更新：读-改-写

库存 100，两个请求各卖 1 件：

| 时刻 | 事务 A | 事务 B | 数据库 |
| --- | --- | --- | --- |
| t0 | `SELECT stock FROM t WHERE id=1` → 100 | — | 100 |
| t1 | — | `SELECT stock` → 100 | 100 |
| t2 | 计算 99，`UPDATE t SET stock=99`，提交 | — | 99 |
| t3 | — | 计算 99，`UPDATE t SET stock=99`，提交 | 99 |

结果卖了两件、库存只减一件。RC/RR 的普通 `SELECT` 都不加锁，所以两个事务都读到 100；后写覆盖前写。

修复按代价从低到高：

1. **原子 SQL**：`UPDATE t SET stock = stock - 1 WHERE id=1 AND stock >= 1`，数据库在行锁内完成读改写；影响 0 行说明库存不足。
2. **CAS/版本号**：`UPDATE ... SET stock=99, version=version+1 WHERE id=1 AND version=5`，0 行则重读重试。
3. **悲观锁**：`SELECT ... FOR UPDATE` 先锁行再算；适合冲突多、必须成功的场景，代价是等待/死锁。
4. **Serializable**：数据库检测冲突并 abort 一方，应用重试；吞吐最低。

### 9.2 写偏斜：快照隔离挡不住跨行约束

值班表要求「至少 1 名医生在岗」，当前有 A、B 两人在岗：

| 时刻 | 事务 1（A 请假） | 事务 2（B 请假） | 快照看到的值 |
| --- | --- | --- | --- |
| t0 | `SELECT count(*) WHERE on_call=true` → 2 | — | 2 |
| t1 | — | `SELECT count(*)` → 2 | 2 |
| t2 | `UPDATE SET on_call=false WHERE doctor='A'` | — | 2（自己的快照） |
| t3 | — | `UPDATE SET on_call=false WHERE doctor='B'` | 2 |
| t4 | 提交 | 提交 | 0 人在岗 |

两个事务改的是不同行，写写不冲突，快照隔离（RR）都允许提交；但合起来违反了「至少 1 人」的跨行约束。这不是幻读，是**写偏斜**。

修复：

- **Serializable/SSI**：PG 的 SSI 检测「读集合被并发写改过」的危险结构，abort 一方；应用必须能重试。
- **物化冲突**：把「在岗人数」收敛到一行（如 `on_call_count` 表），两个事务都更新同一行，写写冲突自然串行化。
- **显式锁**：`SELECT ... FOR UPDATE` 锁住相关行/谓词范围；或 `pg_advisory_xact_lock` 锁业务键。

## 十、机制深挖：MVCC 可见性判断

### 10.1 InnoDB：undo 版本链 + Read View

- 每行有隐藏列 `DB_TRX_ID`（最后修改它的事务 id）和 `DB_ROLL_PTR`（指向 undo 里的旧版本）。
- 普通 `SELECT` 不加锁，沿版本链找「对当前 Read View 可见」的版本。
- Read View 记录：`m_ids`（活跃事务 id 集合）、`min_trx_id`、`max_trx_id`、`creator_trx_id`。
- 判断顺序（简化）：
  1. 版本 `trx_id == creator_trx_id` → 自己改的，可见。
  2. `trx_id < min_trx_id` → 事务已提交，可见。
  3. `trx_id >= max_trx_id` → Read View 创建后才开始的事务，不可见。
  4. `trx_id` 在 `m_ids` 里 → 创建 Read View 时还活跃，不可见；否则可见。
- RC 每条语句新建 Read View；RR 整个事务复用第一个 Read View。这就是「RR 同一事务两次读结果一致」的来源。
- 当前读（`SELECT FOR UPDATE`/`UPDATE`/`DELETE`）不沿版本链，读最新提交版本并加锁；所以 RR 下「快照读」和「当前读」可能看到不同数据。

### 10.2 PostgreSQL：元组 xmin/xmax + 快照

- 每行有 `xmin`（插入它的事务）、`xmax`（删除/更新它的事务，0 表示未删）。
- 快照记录 `xmin`（最小活跃事务）、`xmax`（下一个未分配事务）、`xip`（活跃事务列表）。
- 可见性（简化）：插入事务已提交且不在 `xip` → 可见；删除事务未提交/未开始 → 仍可见；否则不可见。
- UPDATE 不原地改，而是写新元组、旧元组标 `xmax`；旧版本留在堆表，VACUUM 清理 dead tuple。
- RR 整个事务一个快照；RC 每条语句一个快照。PG 的 RR 因为快照不更新，看不到并发事务新插入的行，所以不会出现「同一事务内两次范围查询行数不同」的幻读。
- **写冲突**：RR 下更新一行时，如果该行已被并发事务更新，PG 报 `could not serialize access due to concurrent update`，事务必须回滚重试；这是「先提交者赢」的实现方式。

### 10.3 为什么快照隔离仍有写偏斜

快照保证「读到的是一致的历史」，但不保证「我读过的集合在提交前没被别人改」。写偏斜正是两个事务各自读了同一组、各自改了不同行：写写不冲突，读集合却都过期了。SSI 通过跟踪读/写依赖（rw-antidependency）检测环，发现危险结构就 abort；检测是乐观的，所以冲突多时重试率上升。
