# 检索与排序理论

**一句话**：检索系统先在「词面」和「语义」两个空间里尽量多召回，再用便宜的排序函数和贵的重排模型逐步收敛；每一次取舍都是用召回率换延迟、成本或可维护性，不存在一种全面更优的索引。

## 一、问题的形状

- 输入是查询，输出是「按相关性排序的一小段文档」；中间要做三件事：表示（文档/查询变成可比较的形式）、召回（从全量里筛候选）、排序（给候选打分）。
- **召回与排序分离**是检索系统的核心结构：召回要求高召回、低精度、便宜；排序要求高精度、可承受更贵。两段都做对才有用，任何一段的上限都会卡住整体。
- **相关性不是客观量**：同一查询在不同用户/场景下要的结果不同；离线指标只能近似，最终要靠点击/任务完成率验证。
- 检索系统同时是**索引系统**：写入路径（分词、embedding、建索引）和查询路径一样重要，更新/删除/重建往往比查询更难。

## 二、倒排索引

- 结构：`term → posting list`，posting 里存文档 id、词频、位置。查询只访问查询词对应的 posting list，代价与「查询词数 × 命中数」相关，而不是全量文档数。
- **为什么成立**：自然语言词汇量有限、查询很短；绝大多数词只出现在少数文档里（Zipf 分布），posting list 通常不长。
- **位置信息**是短语/邻近查询的前提：`"data base"` 与 `data ... base` 必须靠位置区分；不存位置能省空间，但只能做词袋匹配。
- **写入代价**：一篇文档要更新它包含的每个词的 posting list，写放大与文档长度成正比；所以倒排索引通常按**不可变 segment** 组织（Lucene 模型）：新文档进新 segment，删除记 tombstone，后台 merge 时物理清理。
- **失败模式**：极短文档区分度低；超长文档稀释词频；词表爆炸（URL、ID、日志）让词典和 posting 都膨胀；高频词的 posting list 极长，要靠停用词或 skip list 跳过。
- **前提假设**：查询词能被切出来，且和文档用同一套归一化；否则「词对不上」比「排序不好」更致命。

## 三、分词与归一化

- 归一化先于分词：Unicode NFKC、大小写折叠、全半角、繁简、变音符号、标点处理；任何一步不一致都会造成「索引里有、查询搜不到」。
- 中文没有空格：词典分词准确但依赖词典、OOV 弱；**字级 n-gram（bigram）**召回高、无词典，代价是索引膨胀和误匹配（项目里的本地嵌入就是字符 1–3 gram，属于词面近似）。
- 子词分词（BPE/WordPiece）解决 OOV 和形态变化，是 embedding 模型的标配；但**检索的分词和模型的分词是两套**，不能混用。
- **停用词**要谨慎：去掉「的/是」能省 posting，但会破坏短语和否定（"to be or not to be"）；现代做法是保留词、只降权。
- **同义词/拼写纠错**通常放在查询侧扩展，而不是索引侧合并；索引侧合并会让原始词不可查，且难以回滚。

## 四、TF-IDF 与 BM25

- **TF-IDF**：词频（TF）越高越相关，但要饱和；逆文档频率（IDF）让稀有词权重更大；再乘文档长度归一化，避免长文档靠「词多」占优。
- **BM25** 是 TF-IDF 的工程化修正：`score = Σ IDF(qi) · tf·(k1+1) / (tf + k1·(1-b+b·|d|/avgdl))`。
  - `k1` 控制词频饱和速度：k1 小，出现一两次就到顶；k1 大，词频继续加分。
  - `b` 控制长度归一化强度：b=0 不归一化，b=1 完全按长度惩罚。
- **为什么 BM25 长期是 baseline**：无需训练、可解释、对短查询稳；IDF 让常见词自动降权，长度归一化避免长文霸榜。
- **前提假设**：词袋独立、词频与相关性正相关、文档长度可比。违反时失效：同义改写（「退货」vs「退款」）、否定（「不含糖」命中「含糖」）、精确标识符（订单号被分词切碎）。
- **参数是语料相关的**：k1/b 在长文档语料和短文本语料上的最优值不同；不调参就用默认值，等于接受次优。
- **字段权重**：标题命中通常比正文命中更重要，靠 field boost / BM25F 表达；这是排序调节，不是召回手段。

## 五、向量表示与 embedding

- 把文档和查询映射到同一向量空间，用余弦/内积衡量语义接近；模型决定空间形状，**换模型等于换坐标系**，旧向量和新查询不可比。
- **归一化**：做余弦相似度前把向量 L2 归一，内积就等于余弦；不归一化时内积偏好长向量，排序被模长污染。
- **维度**：维度越高表达能力越强，但存储/计算线性增长；固定维度是硬约束，写入和查询维度不符必须报错而不是截断/补零。
- **为什么有效**：模型在大量文本上学会了「上下文相似 → 向量接近」，能跨同义词、改写、跨语言召回，这是 BM25 做不到的。
- **失败模式**：
  - 领域漂移：通用模型不懂业务黑话/内部编号，这些词在语义空间里挤在一起。
  - 精确匹配弱：订单号、错误码、人名、型号被压成「大致相似」，召回不稳定；这类查询应交给 BM25。
  - 否定和数值：模型对「不」「小于 100」不敏感。
  - 长文档截断：超过模型上下文的部分被截掉，等于没索引。
  - 输入模板不一致：索引时加了标题前缀、查询时没加，向量分布偏移。
- **代价**：embedding 计算（GPU/API 成本、延迟）、维度存储、不可解释、模型升级要全量重建。

### 关键词 vs 向量：一个具体例子

查询「东西不想要了怎么退」。

| 路径 | 行为 | 结果 |
| --- | --- | --- |
| BM25 | 只认「东西/不/想要/怎么/退」；文档《退货政策》写的是「退货」「退款」，词面对不上 | 召回失败或排名很后 |
| 向量 | 「不想要了怎么退」与「退货政策」在语义空间接近 | 能召回，即使没有一个词相同 |
| BM25 查 `ORD-2024-8871` | 分词后精确命中该订单号所在文档 | 精确、可解释 |
| 向量查 `ORD-2024-8871` | 编号被映射成模糊语义，可能召回其他订单 | 不稳定，不能单独用 |

结论不是「向量取代关键词」，而是**两类查询需要两条召回路径**；这就是混合检索存在的理由。

## 六、ANN：用召回率换速度

- 精确最近邻是 O(N·d)；ANN 索引牺牲少量召回换数量级的速度/内存收益。**「近似」是设计前提，不是 bug**。
- **HNSW**：多层可导航小世界图，上层稀疏用于快速跳转、下层稠密用于精细搜索；查询从顶层贪心下行。
  - 参数：`M`（每个节点边数，影响内存和召回）、`efConstruction`（建图搜索宽度，影响建图质量/时间）、`efSearch`（查询搜索宽度，影响召回/延迟）。
  - 优点：查询快、召回高、增量插入友好；代价：图结构常驻内存，删除只能标记（软删除），大量删除后召回和内存都退化，需要重建。
- **IVF**：先 k-means 把向量聚成 `nlist` 个簇，查询只扫最近的 `nprobe` 个簇。
  - 参数：`nlist`（簇数）、`nprobe`（查询扫几个簇）；nprobe 越大召回越高、延迟越大。
  - 前提：训练样本能代表数据分布；**分布漂移后簇边界失效**，要重训练。数据量太小或训练样本不足时，簇质量差。
- **PQ（乘积量化）**：把向量切成 m 段，每段各自 k-means 成 256 个码字，用码字 id 近似原向量，压缩率可达几十倍。
  - 代价：距离是近似值，召回下降；通常用 IVF-PQ 粗筛，再用原始向量 refine 补精度。
  - 前提：各子空间近似独立、码本训练充分；高维、分布不均时精度损失更大。
- **过滤 + ANN 是真正的坑**：带 `WHERE tenant_id = ?` 的向量检索，如果先 ANN 取 top-k 再过滤，选择性高时 top-k 可能一个都不符合，召回直接塌陷；正确做法是索引层支持过滤（filterable HNSW / 分区），或先过滤再在子集里精确扫。
- **flat scan 不是落后**：几千到几万条时暴力扫描延迟可接受，且没有训练、调参、召回损失；索引是规模上来后才划算的复杂度投资。

## 七、混合检索与融合

- **为什么混合**：BM25 强在精确词面/稀有词/标识符，向量强在语义改写/跨语言；两者的失败模式不重叠，融合能互补。
- **分数不可直接相加**：BM25 无上界、余弦在 [-1,1]，量纲和分布随查询变化；直接加权求和需要归一化，而归一化本身不稳定。
- **RRF（Reciprocal Rank Fusion）**：`score(d) = Σ 1/(k + rank_i(d))`，k 常取 60。只用排名不用分数，天然避开量纲问题；实现简单、对单路噪声鲁棒。
  - 代价：丢掉「第一名比第二名强多少」的信息；只在一路出现的文档也能拿分，可能高估单路噪声。
  - 前提：每一路的 top-k 都有基本质量；某一路完全跑偏时 RRF 也会被污染。
- **加权融合 / 学习排序**：需要标注数据训练权重，效果好但维护成本高；权重会随语料和查询分布漂移。两路召回同一文档要按 id 去重，不同分块命中同一原文要聚合到文档级。

## 八、Rerank

- 两阶段：召回拿 top-100~1000（便宜、高召回），rerank 对这几十/几百条精排（贵、高精度）。
- **cross-encoder** 把 query 和 doc 拼在一起过模型，能建模词间交互，精度显著高于「各自编码再算余弦」的 bi-encoder；代价是不能预计算，查询时要跑 k 次前向。
- **前提**：正确答案必须在召回集合里。召回没进来，rerank 无能为力——所以 rerank 不能替代召回优化。
- **代价**：延迟（几十到几百毫秒）、算力、长文档截断、领域不适配时反而降效；线上要限流/降级（rerank 超时就退回召回分数）。LLM rerank 用生成模型做相关性判断或 listwise 排序，更灵活但更贵、更慢、输出不稳定，只适合离线或低 QPS 场景。

## 九、评估指标

| 指标 | 定义 | 适用 | 盲区 |
| --- | --- | --- | --- |
| recall@k | 前 k 命中的相关文档 / 全部相关文档 | 召回阶段、RAG 上下文是否包含答案 | 不关心排序位置；标注不全时失真 |
| precision@k | 前 k 里相关文档比例 | 结果页质量 | 不关心相关文档是否被漏掉 |
| MRR | 第一个相关结果排名的倒数均值 | 只有一个正确答案（问答、导航） | 只看第一个，忽略其余 |
| nDCG@k | 分级相关性按位置折扣（log2(i+1)）累加，再除以理想排序 | 多级相关性、整体排序质量 | 需要相关性等级标注；对标注标准敏感 |

- **离线评估的前提**：标注集代表真实查询分布、标注标准一致、评估集不泄漏进训练。人工标注贵且主观，点击日志有位置偏置（排前面的更容易被点），不能直接当相关性标签。
- **线上评估**：CTR、任务完成率、人工满意度、首条命中率；离线涨点不等于线上涨点。还要同时看成本和延迟——recall 提升 2 个点但 p99 翻倍，通常不值得。

## 十、更新、删除与索引维护

- **倒排侧**：segment 不可变 → 更新 = 删除标记 + 新文档；删除只是 tombstone，空间等 merge 才回收；merge 策略影响写放大和查询延迟。
- **向量侧**：HNSW 删除是标记，大量删除后要重建；IVF/PQ 的码本和簇是训练产物，分布漂移要重训练；embedding 模型升级 → 全量重算 + 重建。
- **一致性与幂等**：索引通常落后于主库（异步构建），查询要能接受「刚写入的搜不到」，或用版本号/水位线判断索引就绪；重建/增量任务要能重跑不重复，删除要在索引里真正生效。
- **重建要可切换**：影子索引 + 原子切换，避免重建期间查询空窗；重建失败要能回滚旧索引。
- **项目里的取舍**：SQLite 存文本镜像、LanceDB 只存向量，索引可丢弃重建；整项目 Overwrite、单章先删后加、空集合 drop 表；embedder 身份写进 `rag_index_meta`，查询必须用同一个 embedder；`index_lock` 串行化同项目的索引写与检索（见 [[LanceDB与RAG]]）。

## 十二、反悔条件

- 分块到十万级或 p99 超标 → 从 flat scan 切 ANN，并补召回评估；索引参数成为新的运维对象。
- 精确标识符/代码类查询占比高 → 必须上 BM25 或混合检索，单靠向量会持续漏召回。
- 多租户/权限过滤变复杂 → 后过滤会塌陷，需要支持过滤的 ANN 或按租户分区；embedding 模型升级则要全量重建 + 影子切换。

## 十三、常见误解

- 「向量检索比关键词检索先进」：语义召回强不代表精确匹配强；订单号/错误码/人名上 BM25 更可靠。
- 「建了 ANN 就一定更快」：小数据量下 flat scan 更快、更准；ANN 还有训练、内存、删除退化的问题。
- 「embedding 模型越新越好」：换模型要全量重建，且查询/索引必须同模型；模型升级是迁移项目，不是换个依赖。
- 「离线指标涨了线上就会涨」：标注集偏置、位置偏置、查询分布漂移都会让离线结论失效。

## 边界

- 项目只做了几千分块的 flat scan 和功能级检索测试，没有 ANN 调参、召回评估、混合检索、rerank。
- 没有大规模语料上的 BM25 参数调优经验，k1/b 只停留在公式理解。
- 评估指标只写过定义，没有在真实业务上标注和计算 recall@k/nDCG。
- 分词只在「字符 n-gram 的本地哈希嵌入」里间接接触，没有做过中文分词器选型。
