# 存储引擎理论

**一句话**：存储引擎在「读放大、写放大、空间放大」三者之间取舍；B+ 树为读优化，LSM 为写优化，WAL 保证崩溃恢复，MVCC 用多版本换并发——没有一种结构全面占优。

## 一、页、缓冲池与 IO

- 数据库按**页**（MySQL 16KB、PostgreSQL 8KB）读写，不是按行；一页包含多行。
- **缓冲池（buffer pool）**：把热页缓存在内存，减少磁盘 IO；命中率决定性能。缓冲池太小会频繁换入换出。
- **随机 IO vs 顺序 IO**：磁盘/SSD 对顺序读写更友好；B+ 树范围扫描是顺序，按主键随机查是随机。
- **写放大**：一次逻辑写可能触发多次物理写（页分裂、日志、双写、 compaction）；**读放大**：一次查询读多页/多文件；**空间放大**：多版本/冗余存储占更多空间。

## 二、B+ 树

- 多叉平衡树，非叶子节点只存键和指针，叶子节点存数据/主键并相互链接。
- **扇出大、树矮**：3~4 层能存千万级行；查一条记录只需几次页访问。
- **范围查询**：叶子链表顺序扫描，适合 `WHERE id > ? ORDER BY id`。
- **聚簇索引（InnoDB）**：主键索引叶子存整行；二级索引叶子存主键值，查非索引列要**回表**。
- **覆盖索引**：查询列都在索引里，不用回表；代价是索引更宽。
- **写代价**：随机插入导致页分裂、页利用率下降；自增主键顺序插入最友好，随机 UUID 会造成分裂（UUIDv7 缓解）。
- **索引选择性**：不同值越多，过滤效果越好；低选择性列（性别/状态）单独建索引通常没用。

## 三、LSM 树

- 写入先进 **memtable**（内存有序结构），满了刷成不可变 **SSTable**（有序文件）；后台 **compaction** 合并文件、清理旧版本。
- **写优化**：所有写是顺序追加，吞吐高；适合写多读少、日志/时序/KV。
- **读放大**：查一个 key 可能要查 memtable + 多层 SSTable；用 **Bloom filter** 快速判断「不在这个文件」。
- **空间放大**：旧版本/删除标记（tombstone）要等 compaction 清理。
- **compaction 代价**：占 CPU/IO，可能造成写停顿；策略（leveled/tiered）在读放大和写放大之间取舍。

B+ 树 vs LSM：不是「新旧」之争，是读写负载之争；MySQL/PostgreSQL 默认 B+ 树，RocksDB/Cassandra/HBase 用 LSM。

## 四、WAL、redo/undo 与崩溃恢复

- **WAL（Write-Ahead Log）**：修改数据页前先写日志；崩溃后用日志重放/回滚。
- **redo**：记录「做了什么修改」，用于重放已提交但未落盘的数据（保证持久性）。
- **undo**：记录「怎么撤销」，用于回滚未提交事务、MVCC 读旧版本。
- **checkpoint**：把内存中的脏页刷盘，缩短恢复时要重放的日志范围。
- **group commit**：多个事务的日志合并一次 fsync，降低持久化成本；`innodb_flush_log_at_trx_commit` 在安全与性能间取舍。
- **binlog**：MySQL 的逻辑日志，用于复制/CDC；与 redo 是两套日志，2PC 保证两者一致。

## 五、MVCC 与版本可见性

- 每行带版本信息（事务 ID/时间戳/undo 指针）；读根据快照判断哪个版本可见，写不阻塞读。
- **快照隔离**：事务开始时取快照，整个事务看到一致的数据；写冲突靠「先提交者赢」或锁。
- **PostgreSQL**：旧版本留在堆表，VACUUM 清理死元组；长事务/长复制槽阻止清理，导致膨胀。
- **InnoDB**：旧版本在 undo log，purge 线程清理；undo 过长会撑大表空间。
- **写偏斜（write skew）**：两个事务读同一组数据、各写不同行，快照隔离下都能提交，但违反业务约束；需要 Serializable/SSI 或显式锁。

## 六、查询优化器

- **成本模型**：按统计信息估算行数、选择扫描/连接方式/索引；统计信息过期会选错计划。
- **可选性（selectivity）**：过滤后剩余行比例；优化器倾向于「过滤后少」的路径。
- **连接算法**：Nested Loop（小表驱动 + 索引）、Hash Join（大表等值、无排序）、Merge Join（已排序）。
- **深分页**：`LIMIT offset, n` 要扫描 offset+n 行；用游标/延迟关联优化。
- **优化器不是万能**：函数包列、隐式类型转换、OR、低选择性会让索引失效；`EXPLAIN` 看实际行数与预估偏差。

## 七、行存、列存与向量索引

- **行存**：一行连续存储，适合 OLTP 点查/更新。
- **列存**：同一列连续存储 + 压缩，适合 OLAP 聚合/扫描；Lance 是列式格式。
- **向量索引**：HNSW（分层图，查询快、内存大）、IVF（聚类 + nprobe）、PQ（量化压缩，精度损失）；都是近似最近邻（ANN），用召回率换速度/内存。
- **向量库不是主库**：embedding 可重建，元数据/权限仍在关系库；要处理更新/删除/重建索引。

## 九、常见误解

- 「LSM 比 B+ 树先进」：LSM 写快但读放大/compaction 复杂；读多写少用 B+ 树更稳。
- 「索引越多查询越快」：索引增加写放大、空间和优化器选择成本；低选择性索引基本无用。
- 「MVCC 不用锁」：MVCC 只解决读写冲突，写写冲突仍要锁/CAS；快照隔离仍有写偏斜。
- 「加了 WAL 就不会丢数据」：还要看 fsync 策略、复制方式、磁盘缓存；异步复制仍可能丢。
- 「向量检索是精确的」：ANN 是近似，召回率受索引参数影响；要评估召回和延迟。

## 十、机制深挖：B+ 树页分裂与写放大计算

**先把一页能装多少行算出来。** InnoDB 页 16KB，去掉页头/页尾、infimum/supremum、页目录等约 700B 固定开销，可用约 15.7KB；每行还有记录头 5B、`trx_id` 6B、`roll_ptr` 7B（约 18B）加变长字段开销。取行宽 200B：

- 叶子页行数 `C ≈ 15700 / (200 + 18) ≈ 72`。
- 非叶子页每条记录 ≈ 主键 8B + 子页号 4B + 记录头/目录 ≈ 20B，扇出 `f ≈ 15700 / 20 ≈ 785`，取 800。
- 三层树（根 → 分支 → 叶）容量 ≈ `f × f × C = 800 × 800 × 72 ≈ 4600 万行`。也就是说 200B 的行、bigint 主键，3 次页访问覆盖 4600 万行；根和分支页只有 801 个，缓冲池装得下时实际磁盘 IO 只剩 1 次（叶子页）。

**顺序插入 vs 随机插入，差在页利用率。**

- 自增主键：新行永远落在最右叶页，满了做「右分裂」——旧页保持接近满，新页接着写。稳态页利用率接近 100%（InnoDB 建索引时 `innodb_fill_factor=100` 仍保留 1/16 空间供后续插入）。
- UUIDv7：按时间有序，插入集中在最右少数页，接近顺序插入；同一毫秒内的随机位造成小范围乱序，利用率略低于自增。
- 随机主键（UUIDv4、随机 ID、哈希值）：插入位置均匀分布，页满时从中间分裂，两页各约 50%；后续随机插入继续填充。**B 树随机插入的稳态页利用率约为 ln2 ≈ 69%**，约 31% 的空间是空的。这是随机主键空间放大的主要来源，不是分裂那一瞬间的两次写。

算一笔账：1000 万行、200B/行、每页 72 行：

| 主键 | 页利用率 | 叶子页数 | 相对空间 |
| --- | --- | --- | --- |
| 自增 / UUIDv7 | ~99% | 10^7 / (72×0.99) ≈ 14.0 万 | 1.0× |
| 随机 UUID | ~69% | 10^7 / (72×0.69) ≈ 20.1 万 | 1.45× |

差 6.1 万个页 × 16KB ≈ 1GB 纯空洞；缓冲池里同样热数据要装更多页，命中率下降，范围扫描多读 45% 的页。

**写放大：一行改动 = 一个整页写。**

- 逻辑写 200B → 缓冲池脏一个 16KB 页 → checkpoint 刷盘：`16384 / 200 ≈ 80×` 页级放大。这是 B+ 树写放大的主项。
- doublewrite：刷页先顺序写 doublewrite buffer 再写数据文件，物理写再 ×2，约 160×；SSD 的 FTL 垃圾回收还会再放大。
- redo/undo：行更新还产生几百 B 的 redo 和旧值 undo；小事务高频更新时，日志量可能超过行本身。
- 页分裂的额外成本：按随机插入从 50% 填到 100% 需要 `C/2 = 36` 次插入，每次分裂至少重写 2 个页，均摊 `2/36 ≈ 5.6%` 的额外页写。分裂不是大头，但它带来页重排、父页连锁分裂和碎片。
- 顺序插入的写放大低，是因为同一个最右页被反复更新，checkpoint 前多次修改只刷一次；随机插入把写打散到大量页，每页都要各自刷盘，缓冲池淘汰也更频繁。

**页大小是「写放大 vs 树高」的取舍。** PostgreSQL 页 8KB，单行随机更新的页级放大减半（约 40×），但扇出减半、树更高、同样行数需要更多页和更多内存元数据；InnoDB 16KB 页用更大的单次写换更矮的树和更高的缓冲池命中。没有免费的选择：页越大，单次写越贵、树越矮；页越小，写越便宜、IO 次数越多。

**索引和删除也会放大。** 二级索引每条都要写一份索引记录；更新被索引的列要删旧项插新项。删除行只是打删除标记，页不会立刻合并，长期增删的表会碎片化，需要 `OPTIMIZE TABLE`/重建回收。

**结论**：OLTP 点查 + 范围查 + 原地更新选 B+ 树；写多读少选 LSM，用读放大和 compaction 换顺序写。聚簇索引主键用自增或 UUIDv7，不用 UUIDv4——除非能接受 45% 空间、更多页和分裂成本。这个选择在建表时就要定，事后改主键要重建整表，代价远大于当初选对。

## 边界

- 项目没有自研存储引擎，也没有 RocksDB/LSM 调优经验。
- MySQL/PostgreSQL 的页结构、undo/purge 细节停留在原理层，没有源码级分析。
- 向量索引只用了 LanceDB 的默认能力，没有做过 HNSW/IVF 参数调优和召回评估。
