# 安全工程理论

**一句话**：安全不是「加一个加密库」，而是在明确的威胁模型下，用多层控制把「资产被谁、通过哪条路径、付出多大代价拿到」持续压到可接受范围；每一层都有成本和失效模式，安全工程管的是这套取舍和它的生命周期。

## 一、先定资产、边界和攻击者

- **资产**：要保护什么（用户数据、凭证、密钥、资金、可用性、审计记录）。没有资产清单，防护就没有优先级。
- **信任边界**：数据/控制流跨过「信任级别变化」的地方——浏览器→网关、网关→服务、服务→数据库、服务→第三方、生产→办公网。**每一次跨边界都要认证、校验、鉴权**。
- **攻击面**：所有能被外部触达的入口——HTTP 接口、消息队列、定时任务、文件上传、管理后台、第三方回调、依赖供应链、运维通道。
- **攻击者能力**：脚本小子（扫描器）、有动机的内部人、供应链投毒、自动化撞库。不同对手对应不同防护强度；对国家级对手做民用系统防护是浪费，对脚本小子不设防是事故。
- **威胁建模的产出不是文档，是决策**：哪些风险接受、哪些缓解、哪些转移（保险/外包）、残余风险谁签字。

## 二、STRIDE 与威胁建模方法

| 威胁 | 破坏的属性 | 典型场景 | 主要控制 |
| --- | --- | --- | --- |
| Spoofing 冒充 | 认证 | 盗用 token、伪造回调 | 强认证、签名校验、mTLS |
| Tampering 篡改 | 完整性 | 改请求参数、改库、改消息 | 参数校验、签名/HMAC、事务、只追加审计 |
| Repudiation 抵赖 | 不可否认 | 否认下过单/改过配置 | 审计日志、操作留痕、时间戳 |
| Information disclosure 泄露 | 机密性 | 越权读、日志带 PII、备份泄露 | 授权、加密、脱敏、最小权限 |
| Denial of service 拒绝服务 | 可用性 | 刷接口、慢查询、大文件 | 限流、配额、超时、熔断、容量 |
| Elevation of privilege 提权 | 授权 | IDOR、角色配置错误、注入 | 服务端授权、最小权限、输入校验 |

- 方法：画数据流图 → 标信任边界 → 对每个跨边界的数据流套 STRIDE → 列缓解措施和残余风险。
- **前提假设**：你画得出来的架构才是被建模的架构；实际部署、配置、临时通道（跳板机、调试端口、共享账号）往往不在图上。
- **代价与失败模式**：时间和人力；对 CRUD 内部系统做全套建模收益有限，重点应放在认证/授权/数据边界。失败模式是变成 checklist 走过场、只建模新系统不改老系统、建模一次就归档。

## 三、纵深防御、最小权限与默认拒绝

- **纵深防御**：假设每一层都会被绕过。网关鉴权 + 服务内方法级授权 + 数据层租户过滤 + 审计 + 监控，任何一层失效还有其他层。
  - 为什么成立：攻击者要连续突破多层，成本和被发现概率上升；单层控制总有配置错误/漏洞/绕过。
  - 代价与失败模式：复杂度和性能开销，每层都可能故障（鉴权服务挂了全站不可用），排障更难；多层共用同一套凭证/配置会一处泄露全线失守，层间信任假设不一致（网关验了，服务就不验）。
- **最小权限**：主体只拿完成当前任务所需的最小权限、最短时限。
  - 落地：服务账号按库/表/操作授权；用户按功能授权；密钥按服务隔离；运维用临时提权（break-glass）+ 审计。代价是权限碎片化、申请变慢、误拒增加，要配套审批、自助申请、过期回收。
- **默认拒绝（fail-safe defaults）**：没有明确允许的一律拒绝；新接口默认不可访问，新字段默认不返回。失败模式是为了「先跑通」默认放行、后面没人收回，或异常分支 catch 住鉴权错误后继续执行（fail-open）。
- **职责分离**：高危操作拆成多人完成（创建角色 vs 授予权限、付款 vs 审批），防止单点账号被攻破后直接走完全链路。

## 四、安全开发生命周期（SDL）

| 阶段 | 活动 | 能发现 | 发现不了 |
| --- | --- | --- | --- |
| 需求 | 数据分级、合规要求、滥用场景 | 方向性错误 | 实现缺陷 |
| 设计 | 威胁建模、架构评审 | 设计级缺陷（缺授权、边界模糊） | 编码错误 |
| 编码 | SAST、secret scanning、依赖固定、代码评审 | 注入、硬编码密钥、危险 API | 运行时配置、逻辑越权 |
| 测试 | DAST、SCA、渗透测试 | 已知 CVE、可触达漏洞、业务逻辑漏洞 | 未覆盖路径、内部威胁 |
| 发布 | 镜像扫描、配置基线、签名、最小镜像 | 环境配置错误 | 运行时行为 |
| 运营 | 漏洞管理、监控告警、事件响应、复盘 | 真实攻击和漂移 | 未监控的资产 |

- **SAST** 扫源码/字节码，不用运行：覆盖全、能定位到行；代价是高误报，且看不到运行时数据和配置。
- **DAST** 扫运行中的应用：能发现真实可触达的问题；代价是覆盖受爬虫和登录态限制，看不到源码，逻辑漏洞靠人。
- **SCA** 查第三方依赖的已知漏洞：便宜、必须做；盲区是「有 CVE 不等于可被利用」（可达性）、传递依赖、供应链投毒（恶意包本身没有 CVE）。
- **渗透测试** 是抽样，不是证明：能发现越权/业务绕过这类工具扫不到的问题，但一次通过不代表安全。
- **共同失败模式**：工具跑在 CI 里但没人看告警；只扫描不修复；为了「清零告警」加忽略规则，把真问题也压掉。

## 五、漏洞分级与修复 SLA

- 分级通常看 **可利用性 × 影响**：能否远程利用、是否需要认证、影响多少数据/用户、是否有现成利用。
- CVSS 是通用分，但**不代表你的环境**：同一个库漏洞，暴露在公网还是内网、是否真的调用了受影响函数，风险差一个量级。EPSS（预测被利用概率）、KEV（已知被利用目录）比裸 CVSS 更接近现实。
- SLA 示例（要写进流程）：严重 24–72 小时、高危 7–14 天、中危 30 天、低危按版本迭代；**例外必须审批并记录补偿控制**（WAF 规则、网络隔离、监控）。
- **SLA 的前提与失败模式**：要有资产清单和依赖清单（SBOM）、升级路径和回归测试，否则不知道在修什么、修复本身引入故障；只按 CVSS 排序会修一堆不可达的高分、漏掉可被利用的中分，到期不修也没有后果。

## 六、事件响应

- 流程：**准备 → 发现 → 分级 → 遏制 → 取证 → 根除 → 恢复 → 复盘**。顺序不能颠倒，尤其「遏制前先保证据」；准备阶段要备好联系人、值班、日志保留、密钥轮换预案、对外沟通模板、法务/合规通道。
- 遏制：隔离主机、禁用账号、吊销 token/密钥、封 IP；动作要可回滚、可记录，不要一上来删日志/重装系统。
- 取证：保留磁盘/内存/日志副本，记录时间线；证据链要能证明「谁在什么时候做了什么」。
- 根除、恢复与复盘：修漏洞、轮换凭证、清理后门、灰度恢复、加强监控；复盘要写根因、影响面、检测为何没生效、改进项和负责人，没有跟进项的复盘等于没做。
- **失败模式**：靠用户投诉才发现；日志保留太短查不到；遏制动作破坏证据；复盘不改进。

## 七、密码学原语与密钥管理

### 对称加密：AES-GCM

- AEAD：一次完成加密 + 完整性认证，篡改在解密时报错，不需要额外 MAC；密钥长度要精确（AES-256 是 32 字节），错误长度直接失败，解密失败不要回退到「当作明文」。
- **nonce 绝不能在同一密钥下重复**：GCM 的 nonce 复用会泄露明文异或关系，并可能让攻击者伪造密文；96 位随机 nonce 在同一密钥下也有使用次数上限。
- **失败模式**：ECB 模式（相同明文块产生相同密文）、固定 IV、自己拼加密协议、错误信息泄露明文结构。

### HMAC、哈希与密码存储

- 哈希不可逆，用于完整性/指纹；**HMAC 是带密钥的哈希**，用于消息认证和「加密字段的盲索引」——只暴露相等性，不暴露原值。
- 密码存储用加盐慢哈希（bcrypt/scrypt/Argon2），不能用 SHA-256；盐防彩虹表，成本因子提高暴力破解成本。
- **比较要用常量时间**：普通 `==` 在密钥/MAC 比较上可能被时序攻击利用；编码不是加密，Base64 只是表示转换，不能用来「保护」数据。

### KMS 与信封加密

- 每条数据用随机 **DEK** 加密，DEK 再用 **KEK** 包裹后随密文存；KEK 留在 KMS/HSM，不出硬件边界。
- **为什么**：轮换 KEK 只需重新包裹 DEK，不用重加密全部数据；DEK 泄露只影响单条；KMS 访问有 IAM 和审计。
- **密文必须带密钥版本**：解密按版本取对应密钥；版本不匹配要失败，而不是用当前密钥重试（否则「密钥配错」被掩盖成一次成功解密）。
- **代价**：每次加解密多一次 KMS 调用（延迟/可用性依赖），要缓存 DEK 并接受缓存与轮换的窗口；KMS 不可用时的降级策略要提前定。
- **失败模式**：KEK 和密文放同一处、密钥硬编码/进镜像、轮换没有演练、删除旧密钥导致旧数据不可解。

## 八、认证与授权协议

- **OAuth2 是授权框架，不是认证协议**；OIDC 在它上面补了身份层（`id_token`）。
- 授权码模式 + **PKCE** 是当前默认：公共客户端（SPA/移动端）没有 client secret，PKCE 用 `code_verifier/code_challenge` 绑定发起方，防授权码被截获。
- 校验要点：`state` 防 CSRF、`nonce` 防重放、`redirect_uri` 精确匹配注册值、`aud` 必须包含自己、`iss` 必须可信、签名算法固定（拒绝 `none` 和算法混淆）。
- **access token / refresh token / id token**：前者访问资源（短期），refresh 换新 access（长期、可撤销、要保护），id token 是给客户端读的身份声明，不能拿去调资源接口。服务端校验 JWT 要拿 JWKS 验签并缓存、处理密钥轮换；只解析 payload 不验签等于没认证。
- **授权模型**：RBAC 打底（用户→角色→权限），ABAC 补属性（部门/密级/时间），ReBAC 补关系（owner/团队）；数据级权限必须落到查询条件，不能查出来再内存过滤。401 是没认证/凭证无效，403 是认证了但没权限，响应不要泄露「用户是否存在」。
- **失败模式**：把 OAuth2 当登录协议直接信任 access token 里的用户信息；`redirect_uri` 前缀匹配；token 存 localStorage 被 XSS 读走；JWT 无法撤销却没有短过期。

## 九、一条攻击/防护链路

以「撞库 → 越权 → 批量导出」为例：

| 步骤 | 攻击者动作 | 依赖的薄弱点 | 对应控制 | 残余风险 |
| --- | --- | --- | --- | --- |
| 1 | 用泄露的账号密码批量登录 | 无 MFA、无限流、无异常检测 | 慢哈希、限流/锁定、MFA、泄露密码库比对 | 用户复用密码，仍可能被撞开 |
| 2 | 拿到会话后遍历资源 id | 只校验登录、不校验归属（IDOR） | 服务端按当前用户/租户过滤，不信任前端传的归属字段 | 新接口漏加过滤 |
| 3 | 调导出接口拉全量数据 | 导出无配额、无审批、无审计 | 导出审批、配额、水印、审计告警 | 内部人正常权限下的批量拉取 |
| 4 | 清理痕迹 | 审计可被应用账号修改 | 只追加、独立存储、哈希链、权限收回 | DBA/云厂商层仍可改 |
| 5 | 数据外带 | 无出站监控 | 出站限流/DLP/异常流量告警 | 加密外带难以识别 |

这条链说明：**单点防护都会被绕过，真正起作用的是「每一跳都增加成本 + 至少有一跳能被发现」**。只做登录限流不做归属校验，攻击者换个已注册账号就能越权；只做审计不做告警，只能事后知道。

## 十一、常见误解

- 「加密了就安全」「HTTPS 就安全」：加密只保护机密性，不防越权/注入/内部人，密钥管理失效等于没做；TLS 只保护传输段，服务端到数据库、日志、备份仍是明文风险点。
- 「内网可信」：横向移动、供应链、内部人让内网不等于可信；零信任的核心是每次访问都验证。
- 「有审计日志就能追责」：能改的审计等于没有；要只追加、独立存储、权限分离。
- 「漏洞扫描通过就安全」：扫描器只覆盖已知模式；越权和业务逻辑漏洞要靠设计和渗透。

## 十二、反悔条件

- 资产/暴露面变了（上公网、接第三方、合并租户）→ 重做威胁建模，原有控制强度不够。
- 合规要求变严（等保/GDPR/PCI）→ 加密范围、审计留存、密钥托管要从应用内升级到 KMS/HSM + 独立审计。
- 发布频率/团队规模上升 → 手工评审撑不住，必须补 SAST/DAST/SCA 流水线和漏洞 SLA；内部低敏系统可按资产分级裁剪，但认证/授权/审计不能省。

## 边界

- 项目做过字段级 AES-GCM 信封加密、HMAC 盲索引、审计日志、JWT 过滤器与 keyVer 踢线；没有做过完整威胁建模、渗透测试、KMS/HSM 接入、OAuth2/OIDC。
- SDL 只接触过局部实践（代码评审、依赖扫描），没有 SAST/DAST 流水线和漏洞 SLA。
- 没有事件响应演练；审计防篡改未闭环（无 WORM/哈希链）。
- 密码学停留在应用层原语使用，没有协议设计/侧信道分析经验。
