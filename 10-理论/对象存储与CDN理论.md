# 对象存储与CDN理论

**一句话**：对象存储用「不可变对象 + 扁平 key」把文件从应用服务器剥离，代价是不能原地改、每次写都是整对象替换；CDN 用「缓存键 + TTL」把内容推到离用户更近的地方，代价是失效不再即时，缓存键和回源设计错了会把源站打穿。

## 一、块、文件、对象

| 维度 | 块存储 | 文件存储 | 对象存储 |
| --- | --- | --- | --- |
| 访问单位 | 固定大小块（512B/4KiB） | 文件（路径） | 整个对象（key） |
| 元数据 | 客户端/文件系统管理 | 目录树 + inode | 服务端扁平命名 + 自定义 metadata |
| 随机写 | 支持（按块偏移） | 支持（按偏移） | 不支持；PUT 整体替换 |
| 扩展方式 | SAN、分布式块设备 | NAS、横向扩展文件系统 | 多副本/纠删码 + 元数据服务 |
| 典型 | 云盘、EBS | NFS、HDFS（近似） | S3、OSS、MinIO |

- 对象存储没有目录：`a/b/c` 只是 key 里的斜杠，前缀列举模拟目录；rename 实际是 copy + delete。
- 为什么必须不可变：不可变对象才能靠「写多份 + 内容哈希」做一致性和去重；允许原地改就要引入块级版本、锁、部分失败，复杂度接近文件系统。
- 代价：改 1 字节也要重传整个对象（或复制后重传）；并发写同一 key 是 last-writer-wins，没有 CAS，除非用条件写（`If-Match`/`If-None-Match`）。
- 适合一次写多次读、大文件、备份/归档/静态资源；不适合数据库文件、需要文件锁或频繁小改的场景。

## 二、对象模型与一致性

- 对象 = key + 字节流 + metadata。系统元数据有 content-type、ETag，用户元数据（`x-amz-meta-*`）有大小上限（S3 为 2KB）。
- PUT 具有原子可见性：完成前不可见，完成后要么整体可见、要么不存在；不会读到半个对象。
- 覆盖写 = 新版本替换旧引用；读到的要么旧对象、要么新对象。删除默认是删引用；开版本控制后是插入 delete marker，「删除」本身也是一次写。
- S3 自 2020-12 起，新对象 PUT、覆盖写、删除都强一致：写成功后立刻读一定读到新值。
- LIST 是强一致但**不是快照**：分页列举期间发生增删，可能漏项或重复，翻页结果不对应任何单一时刻。对象到亿级时维护全局一致快照太贵，这是有意的取舍。
- 跨区域复制是异步的：源区域强一致不代表副本区域立刻可见；副本区域读到旧值是正常语义。
- 条件写（`If-None-Match: *`）能把「只有不存在才创建」变成原子操作，可替代一部分分布式锁；代价是并发失败方要重试并处理已存在。

## 三、multipart upload：为什么成立

一次大 PUT 失败要重传整个对象；multipart 把失败粒度降到单片，片可并行、可断点续传，客户端也不必把整个文件读进内存。

机制：

- initiate 拿 `uploadId`；每个 part 是独立 PUT，带 `partNumber`（1..10000）；响应 ETag 通常是该片 MD5。
- complete 提交 part 列表，服务端按 `partNumber` 升序拼接；除最后一片外，每片至少 5MiB（S3 硬限制），否则 complete 失败。
- 片数与片大小：对象大小 S、片大小 P，片数 N ≈ S/P 且 N ≤ 10000。1TB 切成 10000 片，每片约 105MB；片太小撞上限，片太大放大单次重传。
- 未 complete 的 upload 会一直占存储并计费；必须有 abort 或生命周期规则（AbortIncompleteMultipartUpload）清理。

失败时间线：

```
t0    初始化 uploadId=U，片大小 64MiB，文件 640MiB → 10 片
t10   片 1~8 成功；片 9 网络中断，客户端重试
t11   重试片 9 成功（同一 partNumber 覆盖旧片，ETag 变了）
t12   片 10 成功，客户端发 complete（带 1~10 的 ETag 列表）
t13   complete 请求超时，客户端不知道成功没有
t14   客户端重试 complete
      ├─ 第一次其实成功：第二次返回 NoSuchUpload（upload 已被消费）→ 应视为成功
      └─ 第一次没成功：第二次正常完成
```

- complete 不是天然幂等。重试遇到 `NoSuchUpload` 时，要 HEAD 对象确认是否已存在，再决定成功还是失败；不查就重试会误报失败。
- 重传同一 partNumber 是允许的，新片覆盖旧片；但之前拿到的 ETag 列表会失效，complete 必须用最后一次上传返回的 ETag。
- abort 与 complete 有竞态：abort 先到，后续 complete 返回 `NoSuchUpload`；complete 先到，abort 可能成功删除已合并对象，也可能返回 `NoSuchUpload`。所以 abort 最好只交给超时清理，不在业务成功路径上调用。
- 每片 URL 单独签名：长传过程中后面的片 URL 过期会 403。要么按需签名，要么把有效期设成大于最长上传时间。
- 代价：uploadId、已完成片、ETag 必须持久化，否则客户端重启就续不上；最小片大小、片数上限是硬约束；加密和跨区域复制对 multipart 的支持有差异。

## 四、预签名 URL

- 原理：把「谁、在什么条件下、可以做什么、到什么时候」编码进签名。SigV4 对 method、path、query、headers、expiry 做 HMAC；服务端验证签名而不是验证用户身份。
- 前提一：签名密钥不泄露。前提二：客户端与服务端时钟偏差在允许范围内（通常 15 分钟）。前提三：签名覆盖的 header 必须原样发送——AWS 不签 `Content-Type`，OSS V4 会签，所以两边实现不对称，改 header 会签名失败。
- 代价：URL 在过期前是 bearer token，泄露即可用；不能单独撤销（只能轮换密钥，代价是全部 URL 失效）；审计只能到「签了哪个 key」，到不了「谁在用」；URL 会进浏览器历史、代理日志和 Referer。
- 三个必配补丁：短过期、最小权限（只签单个 key、只给 PUT 或 GET）、上传后校验（大小/content-type/哈希）。
- 不该用的场景：需要病毒扫描/内容审查、需要服务端托管加密密钥、需要审计到人。这些要在后端中转或上传回调里做。

## 五、纠删码

- 原理：把对象切成 k 个数据块，计算 m 个校验块，任意 k 块可重建；存储开销 `(k+m)/k`。12+4 是 1.33 倍，3 副本是 3 倍。
- 为什么成立：校验块是数据块的线性组合，丢任意不超过 m 块，用剩余块解方程即可恢复。
- 代价：恢复要读 k 块并计算，跨节点重建流量大；写入要算校验，有 CPU 成本；小对象切 12 份没有意义，通常小对象走副本、大对象走纠删码。
- 故障域：k+m 块必须分散在不同磁盘/机架/可用区，否则一次机架掉电就丢超过 m 块。纠删码防随机坏盘，不防整个可用区失效。
- 重建窗口：盘坏后到重建完成之间冗余度下降，期间再坏一块可能丢数据；大集群必须限速重建，否则打满网络拖慢正常读。
- 反悔条件：小对象占比高、跨区重建带宽不够、CPU 成为瓶颈时，副本方案反而更简单可靠。

## 六、生命周期与归档

- 生命周期规则按前缀/标签/天数触发：转低频、转归档、过期删除、清理未完成 multipart、清理非当前版本。
- 存储层级以 S3 为例：Standard → Infrequent Access → Glacier Instant/Flexible/Deep Archive；取回时间从毫秒到 12 小时，取回按量收费。
- 最小存储时长：IA 30 天、Glacier 90 天、Deep Archive 180 天；提前删除按剩余天数收费。归档便宜的前提是数据真的不再频繁读。
- 归档不是「换个便宜盘」：对象列表和元数据仍在，内容要异步解冻；业务读路径不能直接依赖归档对象。
- 版本控制 + 生命周期：删除产生 delete marker，非当前版本继续占空间；不配「非当前版本过期」规则，存储只增不减。
- 合规场景用 Object Lock/WORM：保留期内不可删改；保留期在开启时就要定死，事后改不了。

## 七、CDN：缓存键、TTL、失效、回源

- 缓存键决定「什么算同一个资源」：默认是 host + path。把 query 加进键会分裂缓存，忽略 query 会把不同内容混在一起。设计原则：只让影响内容的参数进键（如 `?w=200`），过滤 `utm_*` 之类跟踪参数。
- TTL：短 TTL 回源多、旧值窗口短；长 TTL 回源少、失效慢。`Cache-Control: max-age`/`s-maxage`、`stale-while-revalidate`；`Vary` 用错（比如按 User-Agent 分裂）会把命中率打崩。
- 失效：purge 按 URL/前缀清边缘缓存，有秒到分钟的传播延迟；purge 全站等于制造一次回源洪峰。更可靠的是「URL 带内容版本」（`app.abc123.js`），新版本换 URL，旧 URL 自然过期——这是前端构建产物带哈希的原因。
- 回源放大：多个边缘节点同时未命中同一 key，会同时回源；origin shield（中间层缓存）和 request collapsing（同节点合并回源）能收敛。回源失败时 `stale-if-error` 返回旧内容，通常比 5xx 好，但要求业务能接受旧值。
- 雪崩算式：回源 QPS ≈ 边缘 QPS × 未命中率。源站按「命中率 95%、只扛 5%」设计，命中率一旦掉到 50%，回源压力立刻翻 10 倍。对策是 TTL 抖动、分层缓存、源站限流熔断、大促前预热。
- Range 请求：`Range: bytes=0-1023` 用于视频拖动和分片下载；缓存键通常不含 Range（同一对象），但边缘要能缓存整对象或按段回源并拼装。分片上传的每个 part 是独立 PUT，不走 CDN 缓存路径。

## 九、常见误解

- 「对象存储就是网盘/文件系统」：没有目录、没有随机写、rename 是 copy+delete。
- 「S3 是最终一致」：2020-12 后新对象/覆盖/删除都强一致；但跨区域副本和 LIST 翻页仍不是快照。
- 「multipart 只是把文件切块传」：它有独立的 upload 生命周期，不 abort 会一直计费；complete 重试要处理 `NoSuchUpload`。
- 「预签名 URL 等于授权」：它是限时 bearer token，泄露即用，不能单独撤销。
- 「纠删码一定比副本省」：小对象、跨区重建、CPU 成本会把收益吃掉。
- 「CDN 靠 purge 就能即时更新」：purge 有传播延迟和回源洪峰；版本化 URL 更可靠。
- 「TTL 越短越安全」：命中率下降会放大回源，可能先打挂源站。

## 边界

- 项目只用过 S3 兼容接口的预签名和基础 multipart；生命周期、版本控制、跨区域复制、CDN 都没做过。
- 纠删码和各归档层级只读过文档，没有容量/成本实测。
- 失败时间线是推演，不是线上事故；没有分片大小调优和断点续传状态机。
- 没有处理过 S3 限流、重试和跨区域延迟。
