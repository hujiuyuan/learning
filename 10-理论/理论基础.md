# 理论基础

**一句话**：理论页回答「这个特性为什么成立、代价是什么、什么条件下会失效」；中间件页回答「这个产品怎么用、我做过什么」。两者分开写，才不会把产品文档当原理、把配置项当结论。

## 为什么单独拆一层

中间件的很多特性不是厂商发明的，而是某个理论在工程上的近似实现：

- RocketMQ 的顺序/重试/事务消息 → 消息投递语义、分区顺序、两阶段提交与幂等。
- Redis 的哨兵/集群/持久化 → 副本共识、quorum、WAL 与快照。
- XXL-Job 的 misfire/分片/阻塞策略 → 调度触发语义、租约、选主。
- Redis 主从/本地优先同步 → 复制拓扑、冲突解决、会话保证。
- Sentinel 的流控/熔断 → 排队论、令牌桶/漏桶、Little 定律。
- MySQL 的 B+ 树/MVCC/redo → 存储引擎、隔离级别、写前日志。
- LanceDB/RAG 的召回与重排 → 倒排索引、BM25、ANN、混合检索。
- Spring Security/PII 加密 → 威胁建模、认证授权协议、密码学原语。
- S3 的 multipart/预签名 → 对象模型、纠删码、CDN 缓存键。
- Nacos 的注册/配置 → 服务发现、推拉模型、AP/CP 取舍。
- Jackson/RocketMQ 的消息 schema → 序列化兼容性、schema 演进。
- OTel 的 trace/采样 → 分布式追踪模型、采样与上下文传播。

只看产品页，会记住「怎么配」；不知道理论，就判断不了「什么时候不该用」。理论页不写产品操作，只写机制、成立条件、失败模式和反悔条件。

## 怎么读

1. **先读理论的「成立条件」**：任何保证都有前提（同步网络、多数派、单写者、时钟），前提不成立，产品配置再对也没用。
2. **再读「对应到哪个特性」**：带着理论去看产品页的「方法总纲」，看它是在满足前提、还是在绕开限制。
3. **最后读「失效模式」**：理论页列的是常见误解和反例；项目页列的是实际踩过的坑，两边对照。
4. **不要用理论页替代产品页**：理论说「多数派能选主」，产品页说「哨兵 quorum 怎么配、故障转移多久」；缺一不可。

## 理论不是教条

- CAP 不是说「三选二」，而是「分区发生时，只能在一致性/可用性之间做取舍」；没有分区时，延迟和一致性还要再权衡（PACELC）。
- 「最终一致」不是「不管了」，而是要定义收敛时间、冲突解决和可观测的滞后指标。
- 「恰好一次」在工程上通常是「至少一次 + 幂等」，不是队列单独保证的。
- 「加索引/加缓存/加线程」都有写放大、一致性、排队延迟的代价；理论页把这些代价写清楚。
