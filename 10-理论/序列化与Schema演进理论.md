# 序列化与 Schema 演进理论

**一句话**：序列化把对象变成字节，schema 决定这些字节的含义和「哪些改动安全」；兼容性不是格式自带的属性，而是编码规则、读写双方的升级顺序和业务语义共同决定的。

## 一、为什么需要 Schema

- 序列化要回答三件事：**边界**（一条消息到哪结束）、**类型**（这串字节是整数还是字符串）、**语义**（这个整数是分还是元）。schema 只解决前两件，第三件永远靠人。
- 没有显式 schema 不等于没有 schema：JSON 字段名 + 消费方 POJO 就是隐式 schema，只是不校验、不生成代码、不检查变更；数据库 DDL 是另一种显式 schema。同一份数据常有三处 schema（IDL/代码、注册中心、数据库列），三者不一致时，故障形态由「谁说了算」决定。
- 显式 schema 换来代码生成、编译期类型检查、字段编号带来的演进规则和更小的载荷；代价是改字段要先改 IDL → 生成 → 发版，跨团队要对齐版本，IDL 与手写代码会漂移。
- **演进的本质**：让不同版本的读写方在同一段字节上达成一致。靠的是读方能**安全跳过不认识的字段**、为**缺失字段补默认值**——所有格式的兼容规则都是这两条的变体。

## 二、文本格式：JSON 与 XML

- **自描述**：字段名随数据走，读方不需要事先拿到 schema；日志、curl、抓包都能直接看。这是 JSON 统治 API 和配置的根本原因。
- 代价：字段名每条重复；数字是十进制文本；二进制要 base64（体积 +33%）；解析要分词、建树、分配大量字符串。
- **类型系统贫弱**：只有 number/string/bool/null/array/object。int64 超过 2^53 在 JS 客户端丢精度，金额和 ID 通常序列化成字符串；日期、二进制、枚举都没有原生类型，全靠约定。
- **null、缺失、默认值三者难区分**：Jackson 默认把缺失当 null；「把字段清空」和「不改这个字段」在 PATCH 语义里必须显式设计（`Optional`、`JsonNullable`、字符串哨兵）。
- JSON Schema 是**校验器**不是 IDL：能校验结构，不能生成强类型客户端；OpenAPI 偏文档和契约描述，不是运行时 schema。
- XML 用命名空间 + XSD 能表达更复杂的约束，但冗长、解析慢、工具链重；XXE 是它的经典安全问题，现在主要出现在遗留系统和 SOAP 接口。
- 文本格式的兼容靠约定：**读方忽略未知字段 + 新字段有默认**。没有字段编号，改字段名就是破坏性变更；把数字改成字符串也是。

## 三、二进制格式：Protobuf、Thrift、Avro

| 格式 | schema 放哪 | 字段标识 | 兼容性依据 | 典型场景 |
| --- | --- | --- | --- | --- |
| Protobuf | `.proto` 文件、注册中心 | 字段编号 + wire type | 编号不复用、类型不改 | gRPC、跨语言 RPC、MQ 载荷 |
| Thrift | `.thrift` 文件 | 字段 ID + 类型 | `required`/`optional` 声明 | RPC、Hadoop 生态 |
| Avro | 随数据（writer schema）+ 注册中心 | 字段名 | reader/writer schema 解析 | 大数据文件、Kafka |

- **Protobuf**：每个字段 = `key`（字段编号左移 3 位 + wire type，varint 编码）+ 载荷。1–15 号编号只占 1 字节；负数用 zigzag；`string`/`bytes`/嵌套消息用长度前缀。数据里没有字段名只有编号——体积小，但没有 `.proto` 就是不可读的字节。
- **Thrift**：结构类似，但把 `required`/`optional`/有默认值三态写进 IDL。`required` 是演进毒药：给旧数据加一个 required 字段，读取直接失败。
- **Avro**：数据里不带 tag，靠 **writer schema + reader schema 按字段名解析**。schema 存在文件头或注册中心；字段名就是身份，改名等于「删一个 + 加一个」，要在 reader schema 里写 alias。
- 二进制体积和解析速度通常优于文本，但排障必须拿到 schema；`protoc --decode_raw` 只能看到编号和 wire type，猜不出业务含义。

## 四、IDL、代码生成与字段语义

- IDL 是单一事实来源，一次定义生成多语言类；改 IDL 触发编译错误，比运行时才发现字段对不上好得多。漂移有三种来源：手改生成代码、仓库 IDL 与客户端实际版本不一致、注册中心 schema 与仓库不一致；要用 CI breaking check（buf breaking、Avro compatibility checker）挡，而不是靠 review。
- 代码生成解决**类型对齐**，不解决**语义对齐**：字段还叫 `amount`，单位从分变成元，编译器不会报错，线上金额全错。
- 生成代码的行为差异本身是坑：proto3 标量默认没有 presence；枚举未知值的处理随语言/版本不同；proto3 的 JSON 映射用字段名而不是编号，所以「二进制改名安全」不等于「JSON 改名安全」。
- **编号是身份，名字只是给人看**。删除字段必须 `reserved`，编号永不复用；复用编号是排障成本最高的一类事故。
- **默认值不上线**：Protobuf 不传默认值，读方拿到的是语言默认（`0`/`""`/`false`），「没传」和「传了 0」无法区分，除非用 `optional`（proto3 3.15 起恢复 presence）或 message 包装类型。
- `required` 是演进毒药：加 required 会让旧数据读不出来；Avro 则要求新增字段必须带 default，否则旧数据没有该字段就解析失败。
- 可选性和业务语义要一起设计：「空字符串」是未填还是明确为空？「0」是没有还是零值？这三种状态在文本格式里必须显式约定，在二进制里靠 presence 区分。

## 五、兼容性规则

**术语**（不同厂商定义相反，本文按这套）：向后兼容 = 新代码读旧数据（消费方先升级）；向前兼容 = 旧代码读新数据（生产方先升级）；全兼容 = 两个方向都成立，任意顺序滚动发布都安全。

| 变更 | Protobuf | JSON | Avro | 结论 |
| --- | --- | --- | --- | --- |
| 加可选字段（新编号、带默认） | 安全 | 安全（忽略未知） | 安全（reader default） | 全兼容 |
| 删字段 | 安全（编号 reserved） | 读方忽略 | 读方忽略 writer 多余字段 | 结构兼容，语义看消费方 |
| 改字段名 | 二进制按编号安全，JSON 映射破坏 | 破坏 | 破坏（除非 alias） | 不要改名，要改就加新字段 |
| int32 → int64 | 同 wire type，超范围静默截断 | 精度问题 | 安全（int 可提升为 long） | Protobuf 会静默损坏，别做 |
| int32 → string | wire type 变，双方都跳过 | 类型错误 | 报错 | 破坏 |
| 加枚举值 | proto3 开放枚举可读 | 未知字符串看代码 | 需要 default | 消费方要有 default 分支 |

**兼容例子（加 / 删 / 改类型）**：

```
v1: Order { 1: order_id(string), 2: amount_cents(int64), 3: status(string) }
v2: Order { 1: order_id, 2: amount_cents, 4: currency(string, optional), reserved 3 }
```

- 加 `currency`：新读旧数据时字段缺失，代码按「缺失 = CNY」补；旧读新数据时忽略 4 号字段。两个方向都成立，是全兼容的标准做法。
- 删 `status`：先让所有读方停止依赖它，再 `reserved 3`。旧读方读新数据会拿到默认空串，如果它用 status 做分支就会走错——**结构兼容不等于语义兼容**。
- 改 `amount_cents` int64 → int32：线上不报错，超过 21 亿的值被截断，对账时才发现。正确做法是新增 `amount_cents_v2` 双写，而不是原地改类型。

**破坏性例子**：v1 的 `2: coupon_code(string)` 被 v2 改成 `2: user_id(int64)`。旧数据被新代码按 varint 解析成垃圾数字；新数据被旧代码按 string 解析，长度前缀对不上，可能整条失败或读出乱码。更隐蔽的是把 `status` 从 `"PAID"` 改成枚举 `2`：结构都能解析，业务判断全错。JSON 侧的等价事故是把 `amount` 从数字改成字符串，或改名漏了 `@JsonProperty` 别名，字段直接为 null。

## 六、Schema Registry 与版本

- 为什么需要：broker 和文件系统不校验字节，schema 只存在于生产方和消费方代码里；版本一多，「谁在用哪版」就失控。工作方式：subject（通常是 topic 或 record 名）维护版本列表，生产方注册 schema 拿到 ID，消息头带 `magic byte + 4 字节 schema ID`，消费方按 ID 拉取 schema 再解析。
- 兼容性模式：`BACKWARD`（默认）、`FORWARD`、`FULL`、`NONE`，以及针对全部历史版本的 transitive 变体；模式决定注册新版本时校验哪个方向。
- **只能检查声明，不能检查实际**：绕过 registry 直接写字节的生产方管不了；单位从分变元、枚举含义改变这类语义变更也检查不出来。
- 代价：多一个有状态服务，它挂了生产/消费可能失败，只能靠本地缓存降级；每条消息多 5 字节；schema 治理要有人负责。反悔条件：小团队、单一消费方、发布同步时，契约测试 + CI 兼容性检查就够，不必上 registry。

## 七、未知字段保留

- 为什么重要：网关、代理、转发服务会把消息解码再编码；丢弃未知字段等于在链路中间把新字段删了，而且没有任何报错。
- **Protobuf**：未知字段进 `UnknownFieldSet` 并随重新序列化保留（proto3 在 3.5 之前会丢）；但文本/JSON 映射、部分语言的 map 处理仍可能丢。
- **Avro** 的读方按 reader schema 解析，writer 多出来的字段直接忽略，重新序列化就永久丢失——不适合做透传格式；**Jackson** 绑定 POJO 时未知字段被丢弃（Spring Boot 默认关闭 `FAIL_ON_UNKNOWN_PROPERTIES`，只是不报错，不是保留），要透传得用 `JsonNode`/`Map` 或 `@JsonAnySetter`；**Thrift** 生成代码直接跳过，不保留。
- 安全角度：未知字段可以被用来夹带数据绕过校验；透传服务要么显式保留并声明，要么明确拒绝。

## 八、序列化性能与体积

- **体积**：JSON 字段名重复 + 十进制数字 + base64；Protobuf 编号 1 字节起，小整数 varint 只占 1 字节。同结构下二进制常见是 JSON 的 1/3 到 1/10，字符串占比越高差距越小。
- **CPU**：文本要分词、转数字、建树、分配字符串；二进制按编号跳读、分配少。但小消息 + 已预热时，优化良好的 JSON 库可能反超，不能只看格式。
- **压缩**：文本压缩率高，gzip/zstd 之后体积差距会缩小；HTTP 和 MQ 往往已经压缩，别在应用层重复压。
- 代价：二进制不可读，排障要 schema；代码生成增加构建步骤；跨语言默认值、未知枚举、JSON 映射的行为差异要逐个确认。结论：带宽敏感、移动端、高吞吐 RPC 用二进制；内部管理接口、调试频繁、字段变化快用 JSON，先量再换。

## 九、反序列化安全

- 第一原则：**解析器是攻击面，限制资源比信任格式重要**。资源耗尽手段包括深层嵌套、声明超大长度后立刻分配、超大数组、XML 实体展开（billion laughs）、压缩炸弹；必须设最大消息大小、最大嵌套深度、最大字段数、解析超时，Protobuf 的递归深度和消息大小上限也要显式确认。
- **Java 原生序列化**：`ObjectInputStream` 按字节里的类名实例化对象，gadget chain 可以直接 RCE。不可信输入永远不要用；必须用时上 `ObjectInputFilter` 白名单（JEP 290）。
- **Jackson 多态**：已废弃的 `enableDefaultTyping` 和过宽的 `@JsonTypeInfo` 会按输入里的类名加载类，是历史 RCE 源头；用 `PolymorphicTypeValidator` 做白名单，或只允许固定子类型。Fastjson 1.x 的 autotype 是同类问题，RocketMQ starter 会拖入 fastjson 1.x，能排就排（见 [[RocketMQ]]）。
- XML 关闭 DTD 和外部实体（XXE），否则能读本地文件、发 SSRF；YAML 用 safe load，不要能构造任意对象的 loader。
- 结构化格式（Protobuf/Avro）不按类名实例化，天然少一类漏洞，但仍有资源耗尽和「解析成功但语义错误」。

## 十、API、MQ、存储三种场景的演进差异

| 维度 | API | MQ | 存储 |
| --- | --- | --- | --- |
| 谁在读 | 外部客户端，升级不可控 | 多个消费组，版本不同步 | 自己的代码，读所有历史行 |
| 数据寿命 | 请求级 | 保留期内 + 可重放 | 永久，直到归档/删除 |
| 兼容方向 | 主要向后；对外 API 尽量向前 | 滚动发布要求全兼容 | 向后为主；回滚时也要向前 |
| 版本载体 | URL / Header / 媒体类型 | 消息头 schema ID、topic 版本 | 数据库迁移版本（Flyway 等） |
| 失败表现 | 400/500、客户端崩溃 | 反序列化失败 → 重试 → DLQ | 迁移失败、读出错、静默截断 |
| 主要手段 | 加字段、容忍未知、版本化 | registry + 兼容模式 + 只加不改 | expand-contract、双写、backfill |

- **API**：请求和响应都是契约。对外 API 的旧客户端可能永远不升级，「删字段、改语义」实际不可行；版本化是最后手段，能加字段就不要开 v2。
- **MQ**：消息会躺在 broker 和 Outbox 表里跨版本。生产方先升级时旧消费方要能读新消息，消费方先升级时新消费方要能读旧消息——**滚动发布要求全兼容**。事件是既成事实，语义不能改；要改语义就发新事件类型。
- **存储**：schema 不随行传输，数据库自己是权威；旧行没有版本号，新代码必须能解释它，或者迁移时回填。列类型变更可能重写整表、长时间锁；JSONB 把 schema 推给应用，换来灵活但失去约束和统计信息。
- **Outbox 把 MQ 的窗口拉长**：`pending` 行可能在发布后几天才投递，消费方必须能读「上一个版本写的」载荷。

## 十二、常见误解

- 「JSON 不需要 schema」：JSON 只是自描述，字段名和类型仍靠约定；没有版本规则，改名就是破坏性变更。
- 「Protobuf 自动兼容 / 加字段一定安全」：只保证 wire format 能解析，不保证值正确；改类型、复用编号照样静默损坏。加字段要新编号、有默认、消费方容忍未知，三者缺一就出事。
- 「上了 registry 就不会有破坏性变更」：它只检查注册过的 schema，语义变更和绕过 registry 的写入都挡不住。
- 「二进制一定更快」：小消息、已压缩链路、字符串为主的载荷，差距可能很小，要看实测。
- 「未知字段无所谓」：透传链路丢掉未知字段，等于在中间版本把新字段删了，且没有报错。

## 边界

- 项目里没有 Protobuf/Thrift/Avro 的实战，也没有 schema registry；落地过的只有 JSON + Jackson 和数据库迁移。
- 没做过大规模 schema 演进、跨团队 IDL 治理、兼容性 CI。
- 性能数字是公开资料的量级估算，没有本机 benchmark；也没做过反序列化漏洞的利用或防护演练。
