# 缓存理论

**一句话**：缓存用「局部性」换延迟和吞吐，用「容忍旧值」换一致性；命中率决定收益，失效策略决定一致性，过期/降级策略决定故障时会不会雪崩。

## 一、为什么缓存有效

- **时间局部性**：刚访问的数据很可能再被访问（热点商品、用户会话、字典表）。
- **空间局部性**：访问一个数据时，邻近数据也可能被访问（列表、分页、相邻 key）。
- **延迟差**：内存 vs SSD vs 网络 vs 数据库，差几个数量级；命中一次就省一次下游查询。
- **收益公式**：平均延迟 = 命中率 × 缓存延迟 + (1 − 命中率) × 回源延迟。命中率从 90% 提到 99%，回源压力降 10 倍；从 50% 到 90%，收益更大。

缓存不是存储：它是「可重建的副本」；丢了要能回源，不能把唯一数据放缓存。

## 二、缓存模式

| 模式 | 读 | 写 | 适合 | 代价 |
| --- | --- | --- | --- | --- |
| Cache-Aside（旁路） | 先读缓存，未命中读库并回填 | 写库后删缓存（或更新） | 大多数业务 | 回填/删除有竞态；首次未命中 |
| Read-Through | 缓存层负责回源 | — | 缓存客户端统一封装 | 缓存层要懂数据源 |
| Write-Through | 写缓存同时写库 | 同步双写 | 写少读多、强一致要求 | 写延迟高；缓存故障影响写 |
| Write-Behind | 写缓存，异步刷库 | 异步 | 写多、能容忍丢 | 宕机丢写；顺序/幂等复杂 |

业务系统最常用 Cache-Aside：读缓存 → 未命中查库 → 回填；写库 → 删除缓存（不是更新缓存）。

## 三、一致性与失效

缓存和数据库是两份数据，更新就有窗口：

- **先删缓存再写库**：删完、写库前，另一个读请求回填旧值 → 缓存长期旧值。
- **先写库再删缓存**：写库成功、删缓存失败 → 缓存旧值；删缓存一般比更新缓存安全（更新可能写入旧值）。
- **延迟双删**：写库前后各删一次，中间 sleep 一段；sleep 时间靠猜，高并发仍可能漏。
- **版本号/逻辑过期**：缓存值带版本，读时比对；或缓存不设物理 TTL，逻辑过期后异步刷新，避免大量同时失效。
- **订阅 binlog**：用 CDC 删缓存，把「应用双写」变成「数据库变更驱动」，减少漏删；代价是多一套组件和延迟。

一致性强度选择：能容忍秒级旧值 → TTL + 删除；不能容忍 → 读穿/写穿同一存储，或加版本校验；不要宣称「缓存强一致」。

## 四、淘汰与过期

- **LRU**：淘汰最久未使用；实现简单，但偶发全表扫描会冲掉热点。
- **LFU**：淘汰访问频率最低；能抗扫描，但新热点难积累、频率会老化。
- **ARC**：兼顾最近和频率，实现复杂；Redis 默认是近似 LRU（采样若干 key 选最久未用），不是全局链表。
- **TTL**：到期删除；TTL 太短回源多，太长旧值久；TTL 加随机抖动，避免同一时刻大批 key 同时过期。
- **maxmemory 策略**：`noeviction` 写入报错、`allkeys-lru` 淘汰任意 key、`volatile-lru` 只淘汰有 TTL 的 key；选错会把重要 key 淘汰或写失败。

## 五、故障模式

| 问题 | 机制 | 对策 |
| --- | --- | --- |
| 缓存穿透 | 查询不存在的数据，缓存不命中，每次都打库 | 空值缓存（短 TTL）、布隆过滤器、参数校验 |
| 缓存击穿 | 热点 key 过期瞬间，大量请求同时回源 | 互斥锁/单飞（singleflight）、逻辑过期、热点永不过期 |
| 缓存雪崩 | 大量 key 同时过期或缓存集群故障 | TTL 抖动、多级缓存、熔断/降级、集群高可用 |
| 热 key | 单个 key 流量极高，打满一个分片 | 本地缓存、key 打散、读写分离 |
| 大 key | 单个 value 过大，网络/删除阻塞 | 拆分、压缩、异步删除（UNLINK） |

## 六、多级缓存

- **本地缓存（Caffeine/Guava）**：纳秒级、进程内；多实例不一致、容量受堆限制；适合字典/配置/极热数据。
- **分布式缓存（Redis）**：跨实例共享、容量大；网络往返、单点/分片问题。
- **CDN**：静态资源/地理就近；缓存键、回源、刷新策略要设计。
- 多级缓存的一致性更难：本地缓存 TTL 要短，或用消息广播失效；不要假设「Redis 更新了本地缓存就知道」。

## 八、常见误解

- 「缓存一定提升性能」：命中率低、回源更贵、序列化开销大时，缓存可能更慢。
- 「设了 TTL 就一致」：TTL 内是旧值；TTL 只保证最终过期，不保证读到的就是最新。
- 「删了缓存就一致」：删和写之间的并发读仍可能回填旧值；要版本/延迟双删/CDC。
- 「Redis 是单线程所以操作原子」：单条命令原子，多条命令/读改写不是；要用 Lua/事务/原子命令。
- 「缓存挂了降级查库就行」：数据库可能扛不住原来的全量流量；要有熔断、限流、本地缓存兜底。

## 九、机制深挖：Redis 过期与淘汰的内部实现

**键空间是两个 dict。** 每个 db 有一个主 dict（key → value）和一个 `expires` dict（key → 到期时间戳，毫秒）。只有设了 TTL 的 key 才进 `expires`，所以 TTL 不是免费的：每个带 TTL 的 key 多一个 dictEntry（约 24B）加哈希桶均摊（负载因子约 1 时 8B），约 32B/key；1000 万 key 全带 TTL 就是 300MB 量级的额外内存。容量规划按「key 数 × 100B」估，比按 value 大小估更接近真实。

**dict 的 rehash 是增量的。** 两张哈希表 `ht[0]` / `ht[1]`，rehash 时逐步把桶搬过去：每次 dict 操作顺带搬一点，后台 `serverCron` 每轮最多约 1ms。代价是 **rehash 期间两张表同时存在，峰值内存接近 2 倍桶空间**；千万级 key 的扩容会持续一段时间，内存上涨但主线程不会长时间卡住。删除大量 key 后的缩容（used/size < 10% 触发）同样渐进，所以「删了 key 内存不立刻降」是正常现象。

**过期删除有两条路，都不保证及时。**

- **惰性删除**：访问 key 时才查 `expires`，过期就删、按不存在返回。不访问的 key 可以「逻辑过期、物理常驻」很久。
- **主动删除**：`serverCron` 以 `hz`（默认 10 次/秒）跑 `activeExpireCycle`。每轮每个 db 随机采样 20 个带 TTL 的 key，删掉过期的；如果本轮过期比例超过 25%，继续采样下一轮，直到比例降下来或 CPU 预算用完。慢周期单次预算约 25ms（占 100ms tick 的 25%），快周期约 1ms；常量随 Redis 版本有调整。
- 后果：**同一秒大批 key 到期时，主动过期循环反复「采样几乎全过期」，造成 CPU 尖刺，而内存不会立刻回落**。TTL 加随机抖动不只防雪崩，也是把清理成本摊平。
- 复制：从节点不自行物理删除过期 key，等主节点传播 `DEL`/`UNLINK`；所以过期时间在 AOF/复制里写成绝对时间（`PXAT`），否则重放时刻不同、结果不同。
- 删除大 value 优先 `UNLINK`：`DEL` 在主线程释放内存，几十 MB 的 value 会造成停顿；`UNLINK` 把释放交给后台线程。

**淘汰（maxmemory）和过期是两回事。** 过期看 TTL，淘汰看内存水位；超过 `maxmemory` 才触发 `performEvictions`，按 `maxmemory-policy` 选 key。

| 策略 | 候选集合 | 选谁 | 典型坑 |
| --- | --- | --- | --- |
| `noeviction` | — | 不淘汰，写命令报 `OOM command not allowed...` | 读还能用、写全失败；适合「宁可写失败也不丢数据」 |
| `allkeys-lru` | 全键空间 | 近似最久未用 | 一次全量读会把大量 key 标成「刚用过」，热点被挤掉；采样只能降低误伤概率，不能消除 |
| `volatile-lru/lfu/ttl` | 只在 `expires` 里 | 按策略 | **所有 key 都没 TTL 时等价于 noeviction** |
| `allkeys-lfu` | 全键空间 | 访问频率最低 | 新热点要「爬坡」，刚变热的 key 可能先被淘汰 |

**近似 LRU 的具体算法**：不是全局链表，而是每次随机采样 `maxmemory-samples` 个 key（默认 5），按空闲时间塞进一个 16 槽的淘汰池，淘汰池里最久未用的；池在多次淘汰间保留，所以实际效果比「5 选 1」好。Redis 文档的说法是 5 个样本够用、10 个接近精确 LRU，代价是每次淘汰多采样、CPU 更高。

**LFU（Redis 4+）**：`lru` 字段的 24 位拆成 16 位时间 + 8 位计数器。新 key 计数从 5 开始，每次访问以 `1/((counter−5)×lfu-log-factor+1)` 的概率加一（`lfu-log-factor` 默认 10，即 5→6 容易、200→201 很难）；空闲每 `lfu-decay-time` 分钟（默认 1）减一，淘汰时选计数最低的。LFU 抗全表扫描，但新热点需要时间积累，短时爆发的 key 不如 LRU 友好。

**为什么不用精确 LRU**：精确 LRU 每次读都要改链表，单线程 Redis 在热路径上加指针写；每个 key 多两个指针（16B），亿级 key 是 GB 级内存；集群模式下每个节点只看到部分 key，全局 LRU 顺序本来就不存在。采样近似是拿「偶尔淘汰错」换「每次访问零额外开销」，在 Redis 的约束下划算。代价要认：采样越少，越可能误伤热 key；`maxmemory-samples` 调到 10 以上能改善，但省下的内存换成了 CPU。

## 十、机制深挖：回填与删缓存的竞态时间线

Cache-Aside 的经典竞态用时间线看最清楚（读未命中回填 vs 写库删缓存）：

| 时刻 | 读请求 R | 写请求 W | 缓存 | 数据库 |
| --- | --- | --- | --- | --- |
| t0 | 未命中，开始查库（耗时 50ms） | — | 空 | v1 |
| t10 | 查库中 | 写库提交 v2 | 空 | v2 |
| t12 | 查库中 | 删缓存（空，无操作） | 空 | v2 |
| t50 | 拿到 v1，回填 | — | **v1（旧值）** | v2 |

结果：缓存是 v1、库是 v2，而且**不会自愈**——除非 TTL 到期或下一次写。窗口 ≈ 读库 + 回填耗时 `T`；在这个窗口内发生写的概率约 `1 − e^(−λ_w·T)`（泊松近似）。`λ_w = 10 次/秒`、`T = 50ms` 时约 39%；再乘上未命中率才是每次读踩中的概率。读越慢、miss 越多、写越频繁，越容易踩中。这就是「先写库再删缓存」仍然不够的原因。

**为什么删缓存比更新缓存安全**：两个并发写 W1(v1)、W2(v2)，如果都更新缓存，落缓存的顺序可能是 W2 先、W1 后，缓存永久停在 v1；删除只把状态变成「空」，下一次读回填的是当时库里的值，即使错也只错到下一次读。删除表达的是「失效」，更新表达的是「等于某个值」，后者对顺序敏感。

| 补丁 | 堵住什么 | 没堵住什么 / 代价 |
| --- | --- | --- |
| 延迟双删 | 缩小「删缓存→写库」之间的窗口 | sleep 只能按读耗时 p99 估；长 GC、网络抖动、主从延迟仍会漏；多一次删除 |
| 删缓存重试 | 删失败导致的长期旧值 | 重试期间仍是旧值；要幂等 + 上限，避免重试风暴 |
| 订阅 binlog/CDC | 把应用双写变成库变更驱动，漏删少 | 多一套组件；CDC 延迟内仍是旧值；要处理顺序和重复 |
| 值带版本 | 读时发现旧版本就丢弃 | 版本要单调（时间戳会回拨）；每次读多一次比较；旧值仍会短暂返回 |
| 分布式锁 / singleflight | 击穿（同一 key 并发回源） | **不解决本竞态**：锁只让一个读回源，这个读仍会在写之后回填旧值 |
| 逻辑过期 + 异步刷新 | 大量 key 同时过期、刷新期间阻塞 | 明确接受「读旧值 + 后台刷新」，本质是最终一致 |

结论：没有既便宜又强一致的缓存方案。要强一致，就别让缓存成为读路径的权威（读穿到库，或用版本校验挡旧值）；否则就明确接受 TTL/CDC 延迟级的最终一致，并让旧值在业务上无害（幂等、版本、只读展示）。跨进程、跨节点时「缓存强一致」基本是伪需求：网络分区和进程暂停下，低延迟和线性一致不能同时承诺。

## 边界

- 项目以 Redis Cache-Aside 为主，没有多级缓存/CDC 删缓存的生产实践。
- 没有做过缓存命中率/热 key 的线上观测和容量规划。
- 本地缓存只在原理层，没有 Caffeine 落地。
