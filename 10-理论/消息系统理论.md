# 消息系统理论

**一句话**：消息系统的核心不是「发出去」，而是「投递语义 + 消费进度 + 顺序 + 失败处理」四件事；队列产品只是这四件事的一种实现，可靠性最终由消费端幂等决定。

## 一、队列模型与日志模型

| 模型 | 怎么工作 | 适合 | 代价 |
| --- | --- | --- | --- |
| 队列（queue） | 消息被一个消费者取走并删除，多个消费者竞争 | 任务分发、削峰、点对点 | 消费后不可重放；消费者崩溃要靠 ack/重投 |
| 日志（log） | 消息追加到分区日志，消费者维护 offset，可重复读 | 事件流、回放、多消费组 | 要管理保留期/分区/offset；不是「删了就没了」 |

RocketMQ/Kafka 都是日志模型 + 消费位点；「队列」是逻辑视图。重放能力来自日志保留，不是来自「消息没删」。

日志在磁盘上长什么样、消费组怎么分分区，见「九、日志存储与消费组」。

## 二、投递语义

- **至多一次（at-most-once）**：先 ack 再处理，或发后不管；进程崩溃会丢消息。
- **至少一次（at-least-once）**：处理成功再 ack；失败/超时会重投，可能重复。绝大多数业务系统的默认选择。
- **恰好一次（exactly-once）**：端到端「效果只发生一次」，不是 MQ 单方面能保证的；通常 = 至少一次 + 消费端幂等/去重 + 事务性写。

判断顺序：先问「重复会造成什么」（多扣钱/多发通知/多建记录）→ 决定幂等强度；再问「丢失能不能接受」→ 决定 ack 时机；不要先选语义再补业务。

## 三、ack、offset 与重投

- **先处理后 ack**：处理失败不 ack，消息重投；代价是重复，需要幂等。
- **先 ack 后处理**：吞吐高，但处理失败/进程崩溃就丢消息。
- **offset 提交**：日志模型里「消费到哪」是独立状态；自动提交可能「处理没完就提交」，手动提交要处理提交失败。
- **可见性超时/租约**：消息被消费者取走后在一段时间内不可见；超时未 ack 会重新可见，可能被另一个消费者处理。
- **重投上限 + 死信队列（DLQ）**：超过次数进 DLQ，人工/补偿处理；没有 DLQ 的重试会把毒消息反复打给所有消费者。

消息从投递到进死信的完整状态流转见「十、重投与死信状态机」。

## 四、顺序

- **全局顺序**：所有消息一个队列、一个消费者；吞吐最低，故障时全阻塞。
- **分区顺序**：同一分区内有序，跨分区不保证；按业务主键（订单号/用户 ID）选分区键，保证「同一实体有序」。
- **顺序消费的代价**：一个分区同一时刻只能一个消费者处理，失败会阻塞后续消息（head-of-line blocking）；重试也要保持顺序。
- **乱序的代价**：状态推进类消息（创建→支付→发货）乱序会触发非法状态；用状态机/CAS 拒绝或缓冲。

选择：只有「同一业务实体必须按序」才做顺序消费；能用状态机/CAS 容忍乱序的，不要全局顺序。

## 五、事务消息与 Outbox

两者解决同一个问题：**本地事务和发消息不能同生共死**。

| 方案 | 机制 | 优点 | 代价/失败模式 |
| --- | --- | --- | --- |
| 事务消息（半消息） | 先发半消息 → 执行本地事务 → commit/rollback；MQ 回查本地事务状态 | 少一张表；MQ 原生支持 | 依赖 MQ 的回查接口；回查要能查本地事务；只覆盖 MQ 一种副作用 |
| 本地消息表（Outbox） | 业务写 + 消息记录同库同事务；后台投递器轮询发送，成功标 sent | 多通道（MQ/邮件/通知）统一；不依赖 MQ 特性 | 多一张表 + 投递器；要处理租约、重复发送、死信 |

两者都只能保证「至少一次」；消费端仍要幂等。选择看「副作用是否只有 MQ」和「团队是否愿意维护投递器」。

## 六、消费失败与背压

- **重试**：指数退避 + 上限 + 抖动；无上限重试会打爆下游。
- **死信**：无法处理的消息隔离，保留上下文，人工/补偿；不能静默丢弃。
- **消费 lag**：生产速率 > 消费速率时堆积；扩容消费者受分区数限制；先保护下游，再扩容。
- **背压**：消费端有界队列/信号量，满了暂停拉取或降级；没有背压，堆积会变成内存/超时。
- **毒消息**：反序列化失败/业务永远失败的消息，重试无意义；直接进 DLQ 并告警。

## 七、对应到中间件特性

| 理论 | 产品特性 | 项目页 |
| --- | --- | --- |
| 日志模型 + offset | RocketMQ 普通消息、消费位点、重投 | [[RocketMQ]] |
| 至少一次 + 幂等 | Outbox 投递、消费端唯一键/占位 | [[Outbox]]、[[幂等键与占位]] |
| 事务消息 vs Outbox | muou 选 Outbox，不用半消息 | [[RocketMQ]]、[[muou]] |
| 分区顺序 | 项目没有 `ORDERLY`，只保证不依赖顺序 | [[RocketMQ]] |
| 重试/死信 | 投递失败退避、到上限标 dead；消费异常外抛 | [[RocketMQ]]、[[Outbox落地]] |
| 消费 lag/背压 | 导出/导入用信号量限制并发，不靠 MQ 堆积 | [[导出背压]]、[[异步导出]] |

## 八、常见误解

- 「MQ 保证 exactly-once」：多数产品只保证分区内、单次消费语义；端到端效果仍要幂等。
- 「ack 了就是处理成功」：ack 只是「不要再投」，业务失败被吞掉等于丢消息。
- 「顺序消费性能差一点而已」：它会阻塞整个分区，失败重试也阻塞；能用状态机就不要顺序。
- 「消息堆积加消费者就行」：消费者数受分区数限制；下游 DB/第三方可能先被打爆。
- 「事务消息不需要幂等」：回查/重投仍可能重复，消费端必须幂等。

## 九、日志存储与消费组

### 9.1 磁盘上的日志：append-only + 索引

| 概念 | Kafka | RocketMQ |
| --- | --- | --- |
| 物理文件 | 每个分区一个目录，内含多个 segment（`.log` + `.index` + `.timeindex`） | 所有 topic 共用一个 CommitLog，另有按 topic/queue 的 ConsumeQueue |
| 索引 | 稀疏 offset 索引，先二分定位 segment，再顺序扫 | ConsumeQueue 每条 20 字节（8 字节物理 offset + 4 字节长度 + 8 字节 tag hash） |
| 清理 | 按 segment 整段删（`retention.ms` / `retention.bytes`） | CommitLog 按文件过期删（默认 72 小时），ConsumeQueue 跟着清 |

两条性质决定了后面所有行为：

- **append-only**：写永远是顺序追加 + page cache，读靠索引定位后顺序扫。顺序写比随机写快一个数量级，这是日志模型能扛高吞吐的根本。
- **删除是整段的，不按消息**：一条消息不会因为被消费就消失，只有所在 segment 过期才被删。所以「消费」和「删除」是两件独立的事——这正是重放能力的来源。

日志里的位置叫 **offset**：分区内单调递增、不可变。Kafka 的 offset 就是分区内的逻辑位置；RocketMQ 有两套——CommitLog 的物理 offset 和队列内的逻辑 offset，消费位点用的是后者。offset 被清理后会「越界」（offset out of range），消费端只能重置到 earliest/latest，中间那段就永久跳过了。

### 9.2 消费组：并行度上限 = 分区数

- 一个分区在同一时刻只能分配给**同一个消费组内**的一个消费者。
- 不同消费组各自持有一份 offset，互不影响——同一份日志，多个组各自按自己的进度读，这是「一份消息多个下游」的实现方式。
- 组内消费者数 > 分区数：多出来的消费者分不到分区，闲置；< 分区数：有的消费者要承担多个分区。

具体例子：topic 有 3 个分区，消费组起 2 个消费者 → `{P0,P1}` 给 C1、`{P2}` 给 C2，C2 只干一半活；加到 4 个消费者 → 只有 3 个分到分区，第 4 个完全空闲。**加机器不等于加吞吐，上限由分区数卡死。**

还有一个容易踩的坑：分区数通常在创建时定死，事后扩分区会改变 `hash(key) % 分区数` 的映射，历史消息和新消息的「同一个 key 落在同一个分区」不再成立，顺序语义被悄悄破坏。

### 9.3 offset 提交：提交的是「下一条」

- 提交的值是**下一条待消费的位置**，不是「最后消费成功的那条」。消费 `[100, 200)` 并处理完，提交 200；重启后从 200 开始，正好不重不漏。
- 提交时机决定语义：`poll → 处理 → commit` 是至少一次（处理完到提交之间崩溃会重放）；`poll → commit → 处理` 是至多一次（提交后崩溃就丢）。
- 自动提交（Kafka `enable.auto.commit=true`，默认 5 秒一次）的风险：poll 拿到一批，业务还没处理完，后台定时器已经把 offset 提交了 → 崩溃后这批直接丢。更糟的是处理时间超过 `max.poll.interval.ms`（默认 5 分钟），消费者会被踢出组，触发 rebalance，分区交给别人从**上一次提交点**重读。
- 批量提交的取舍：每条都提交 = 每条一次 RPC，吞吐撑不住；攒批提交 = 崩溃时重复的窗口更大。常见做法是「按批提交 + 消费端幂等」。
- 异步提交的坑：commit(150) 和 commit(200) 乱序到达 broker，后到的 150 覆盖 200，offset 回退 → 重复消费。所以异步提交必须保证「只前进不后退」，失败重试也要基于已确认的最大值。

一个具体的重复窗口：

```
t0       poll 回一批 [100, 200)，开始处理
t0+3s    处理到 150，崩溃（offset 仍停在 100）
t0+5s    另一消费者接手，从 100 重新消费
结果     100–149 重复处理；150–199 第一轮已丢，靠这次重放补上
```

要缩小窗口只能缩短「处理完成 → 提交」的间隔，但永远无法消掉，除非消费端幂等。

### 9.4 rebalance：什么时候发生、代价是什么

触发条件：消费者加入/退出、心跳超时（`session.timeout.ms`）、处理超时（`max.poll.interval.ms`）、订阅的 topic 或分区数变化。

Kafka 旧版 eager 协议的时间线：

```
t0     C3 加入组，coordinator 收到 JoinGroup
t1     全组 stop-the-world：所有消费者撤销自己的分区，停止消费
t2     选出一个 leader consumer，按策略（range / round-robin / sticky）重新分配
t3     SyncGroup 下发结果，各自从「自己上次提交的 offset」继续
```

- 停顿时间 = 一次组协调往返，通常几十毫秒到几秒；期间完全停止消费。
- t1 之前「已处理但未提交」的消息，在重分配后会被新 owner 重放。
- cooperative（增量）协议只撤销需要迁移的分区，其余继续消费，避免全组停顿；代价是多轮协商、实现更复杂。

**rebalance 风暴**是一条典型的死亡螺旋：处理慢 → 超过 `max.poll.interval.ms` → 被踢出组 → 触发 rebalance → 剩下的消费者分到更多分区 → 更慢 → 再次超时。修法是减小 `max.poll.records`、把耗时处理挪到异步线程、合理调大超时，而不是继续加消费者。

RocketMQ 的 rebalance 在客户端做：每个消费者每 20 秒拉一次 topic 的队列列表，按策略重新分配，没有组协调者的 stop-the-world；但「新接手的队列从哪个 offset 开始」一样要从 broker 存的消费位点继续，所以重复窗口同样存在。

### 9.5 保留与重放

- 保留策略：按时间（Kafka `retention.ms` 默认 7 天，RocketMQ 默认 72 小时）或按大小；超期按 segment 整段删。磁盘水位也会触发提前清理。
- 重放 = 把 offset 重置到更早的位置：Kafka 用 `kafka-consumer-groups --reset-offsets`（要先停消费者），RocketMQ 用「重置消费位点」。`auto.offset.reset` 只在**没有已提交 offset** 时生效，不能拿来重放已有进度的组。
- 重放成立有三个前提：① 消息还在保留期内；② 消费端幂等（重放本质就是重复投递）；③ 下游扛得住——重放等于瞬间回灌历史流量，必须限速或走影子链路。
- 日志模型能重放，但**不能回到「任意时刻的精确快照」**：重放是从某个 offset 起把后续消息全部再走一遍，消费端的状态必须可重入；依赖「当前时间」「随机数」的处理会让两次重放结果不同。

## 十、重投与死信状态机

### 10.1 一条消息的全部状态

```
                   produce
                      │
                      ▼
                ┌───────────┐   deliver    ┌────────────┐    ack     ┌────────┐
                │   READY   │─────────────▶│  INFLIGHT  │───────────▶│  DONE  │
                └───────────┘              └────────────┘            └────────┘
                      ▲                          │
                      │      可见性超时 / 处理失败  │
                      └──────────────────────────┘
                            deliveryCount += 1
                                   │
                        deliveryCount > maxReceiveCount
                                   │
                                   ▼
                             ┌───────────┐
                             │    DLQ    │
                             └───────────┘
                                   │
                                   └── 人工修复后重放（重置计数）──▶ 回到 READY
```

- **READY**：对消费者可见，可被投递。
- **INFLIGHT**：已被某个消费者取走，在可见性超时内对其他消费者不可见。处理成功 → ack → DONE；超时或显式失败 → 回 READY，投递次数 +1。
- **DLQ**：投递次数超过上限，或遇到不可重试错误（反序列化失败、参数非法）→ 隔离，保留原消息体和失败上下文，人工修复后可重放回 READY。
- **DONE**：从队列删除（队列模型）或 offset 推进（日志模型）。

不同产品的「重投」其实落在不同位置：

| 机制 | 代表 | 触发方式 | 重投粒度 | 代价 / 注意 |
| --- | --- | --- | --- | --- |
| 单条可见性超时 | SQS | 不 ack 到期自动可见 | 单条，可并行重复 | 需要 `ChangeMessageVisibility` 续租 |
| broker 重试队列 | RocketMQ | 消费返回 `RECONSUME_LATER`，或消费超时（默认 15 分钟） | 单条，按等级延迟 | 需要重试 topic / DLQ 配置 |
| offset 回退 | Kafka | 抛异常后 seek 回去，或不提交 | 整批 / 整个分区 | 阻塞后续消息，无内置 DLQ |

### 10.2 时间线：一次重复投递是怎么发生的

```
t0       消费者 A 取走消息 M，M 进入 INFLIGHT（可见性超时 30 秒）
t0+5s    A 处理完业务，数据库已提交
t0+6s    A 进程被 kill，没来得及 ack
t0+30s   可见性超时到期，M 回到 READY，deliveryCount=2
t0+31s   消费者 B 取走 M，业务逻辑再执行一次
```

结果取决于业务写的是什么：

- `INSERT`：第二次报唯一键冲突 → 必须把冲突当成功吞掉，否则又进重试。
- `UPDATE balance = balance - 100`：多扣一次，钱就错了。
- `INSERT` 且无唯一约束：两条记录，事后对账才发现。

所以「至少一次」的真实含义是 `最终效果 = 1 + 重复次数`，能把它压回 1 的只有消费端幂等。

### 10.3 ack 时机与可见性超时

- ack 必须在**业务处理完之后**，但必须**早于可见性超时**。晚了，消息会被别人领走并行处理，两份同时写。
- 处理时间可能超过超时 → 必须续租（SQS 的 `ChangeMessageVisibility`）；RocketMQ 没有单条续租，靠 broker 的消费超时重置，超时后整条重投。
- 超时设太短：频繁重复 + 消费者互相抢消息；设太长：消费者真崩溃后消息长时间不可见，延迟飙升。
- 日志模型没有「单条 ack」，只有「提交 offset」，重复的粒度是整批而不是单条——这是它比单条 ack 模型更容易重复的根本原因。

### 10.4 重试策略：退避、上限、错误分类

- 立即重试：只适合瞬时错误（连接闪断），失败时等于忙等，会放大流量。
- 固定间隔：实现简单，故障时所有实例同一秒重试，形成尖峰。
- **指数退避 + 抖动**：`delay(n) = min(base × 2^n, maxDelay) × random(0.5, 1.5)`。例如 base=1s、maxDelay=5min，得到 1s → 2s → 4s → 8s → … → 5min；抖动让同一批失败的消息错开重试，避免同步风暴。
- 重试上限：按次数（如 16 次）或按总时长（如 24 小时）。次数上限保护下游，时长上限保护业务时效。两个都要有。
- **错误必须分类**：超时、连接拒绝、限流 → 可重试；反序列化失败、参数校验失败、业务规则拒绝（订单已取消）→ 不可重试，直接进 DLQ。对不可重试错误反复重试，是毒消息拖垮整个消费组的常见原因。

RocketMQ 的默认行为可以当参照：消费失败进 `%RETRY%<消费组>`，延迟按等级递增（1s、5s、10s、30s、1m…最长 2h），默认重试 16 次后进 `%DLQ%<消费组>`。Kafka 没有内置重试，要么原地 seek 重试（阻塞分区），要么用 `@RetryableTopic` 生成一串重试 topic + 最终的 DLT。

### 10.5 幂等：重投的唯一兜底

三种常用手段，通常组合使用：

1. **唯一索引 / 去重表**：消费前插入 `message_id` 或业务唯一键，冲突即视为已处理。必须和业务写在同一事务——「去重记录写了、业务没写」会导致消息被永久吞掉。
2. **状态 CAS**：`UPDATE ... WHERE status = '待支付'`，影响行数为 0 就跳过。适合状态机推进，天然幂等，还顺带拒绝乱序。
3. **业务唯一键**：`INSERT ... ON DUPLICATE KEY UPDATE`，要求业务本身有稳定唯一标识（订单号 + 操作类型）。

三条硬约束：

- 去重记录要有**保留期**，且保留期 ≥ 消息可能重复的最长窗口（消息保留期 + 重试总时长）。去重表无限增长会先拖垮数据库。
- **「先查后写」不是幂等**：查和写之间有并发窗口，两个消费者同时查到「不存在」就都写。必须靠唯一索引、行锁或 CAS 兜底。
- 幂等键要从**消息内容**推导（业务 ID + 操作类型），不能用消费时间、随机数这类每次都不同的值。

### 10.6 顺序消费下的重试冲突

- 顺序消费要求分区内严格有序，某条消息失败后**不能跳过**——后面的状态推进会建立在错误前提上。
- 但无限重试会阻塞整个分区（head-of-line blocking），一条毒消息能让整个分区停摆。
- 折中：有限次重试 + 短退避 → 超限进 DLQ 并**记录断点**，由补偿程序修复后从断点重放；或者把顺序范围缩小到单实体（同一 `user_id` 有序），其余并发。
- 判断标准只有一句：**后续消息是否依赖这条成功？** 依赖 → 必须阻塞或补偿；不依赖 → 进 DLQ，让分区继续走。

## 边界

- 项目只用 RocketMQ 普通消息 + Outbox；没有事务消息、顺序消费、延迟消息、消息轨迹的实战。
- 没有做过跨机房/跨集群的消息复制和容灾。
- 消费 lag 的监控和扩容没有生产数据，只有原理和配置。
