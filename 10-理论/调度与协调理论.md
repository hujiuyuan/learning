# 调度与协调理论

**一句话**：调度解决「什么时候由谁执行」，协调解决「同一时刻只能有一个谁」；两者的正确性都不取决于「锁住了」，而取决于租约失效后旧执行者还能不能造成副作用。

## 一、调度的三种时间来源

| 方式 | 机制 | 精度 | 适合 | 代价 |
| --- | --- | --- | --- | --- |
| cron/日历 | 按墙钟规则匹配 | 传统 cron 到分钟，秒级要专门支持 | 固定时刻任务 | 时区/夏令时/漏触发 |
| 延迟队列/时间轮 | 按到期时间排序 | tick 粒度 | 大量短延迟任务 | 不持久化；取消是惰性标记 |
| 轮询扫描 | 周期性查 `next_run_at <= now()` | 轮询间隔 | 持久化、多副本 | DB 压力、延迟抖动 |

- cron 是「匹配墙钟」不是「每隔 N 秒」；进程在 00:03 启动不会补 00:00 的触发。
- cron 的时区：服务器时区变更、夏令时跳变会让任务跳过或重复；跨时区业务要显式指定时区或统一用 UTC。
- 时间轮：固定槽数组 + 指针按 tick 前进，任务按到期时间落槽；多层时间轮处理长延迟。精度受 tick 限制，同一槽是链表；取消通常只打标记，任务多时内存不会立即释放。
- 最小堆/优先队列：O(log n) 插入取出，适合定时器数量中等、精度要求高的场景（Netty、Go runtime timer）。
- 数据库轮询：把「下次执行时间」持久化，多副本用 `FOR UPDATE SKIP LOCKED` 抢占；精度受轮询间隔限制，任务多时 DB 压力大。

调度器只负责「到点产生一次触发」，不负责「业务只执行一次」；后者要靠执行端幂等。

## 二、触发语义与 misfire

- **misfire**：计划触发时间已过，但调度器没有按时触发——停机、暂停、线程池满、时钟跳变、调度中心不可用。
- 四种常见策略：
  1. **忽略**：跳过错过的触发，等下一个周期。适合监控采样、缓存刷新。
  2. **立即补一次**：只补最近一次，适合「状态最终要刷新」的任务。
  3. **逐个补跑**：按原频率补齐所有错过的周期。适合账单/结算，但会形成补偿风暴。
  4. **合并为一个时间窗**：把错过的周期合并成一次「处理 [from, to]」的任务，适合可按区间重算的聚合。
- 选择依据不是「哪个更稳」，而是**任务语义是周期采样还是每期必算**；采样可以丢，结算不能丢，但补跑必须幂等。
- 补偿风暴：停机 12 小时、5 分钟一次 = 144 次触发集中到恢复瞬间；要限速、合并窗口、限制补跑上限。
- 长任务超过调度间隔会重叠：`@Scheduled` 默认单线程，同一 JVM 内不重叠；但多副本、手工触发、线程池调度会。要有并发策略（禁止/丢弃/覆盖）或分布式锁。
- 时钟：NTP 回拨、手动改时间会让「下次触发时间」计算漂移；持久化任务应记录「计划时间」，而不是只记录「上次执行时间」。

**幂等调度的键**：`任务名 + 计划触发时间 + 分片号`。补跑、重试、人工触发都复用同一个键；占位与业务副作用同事务，重复触发返回首次结果或跳过。

## 三、单机到多副本

- 单进程 `@Scheduled`：每个副本都会到点触发；副本数 N 就是 N 倍执行。
- 数据库锁：`SELECT ... FOR UPDATE` 锁一行任务定义，或 `SKIP LOCKED` 抢占待执行行；锁随事务释放，进程崩溃自动释放。
- Redis 锁：`SET NX PX` / Redisson；租约到期自动释放，进程崩溃不会永久占用；但租约可能提前失效（见第五节）。
- 调度中心：XXL-Job 由 admin 统一触发，执行器只接收；admin 单实例挂了任务不触发，需要高可用部署。
- K8s CronJob：`concurrencyPolicy: Forbid` 防重叠，`startingDeadlineSeconds` 控制错过多久不再启动；它不解决「任务本身幂等」。
- 分片：调度中心下发 `(分片序号, 分片总数)`，执行器自己切数据；分片数变化会改变幂等键，要固定映射或记录分片版本。

多副本下的核心问题不是「怎么选一个副本」，而是「选出来之后，旧副本还能不能继续写」。

## 四、leader election 与 lease

leader election 要保证：同一任期最多一个 leader；leader 失效后能换；换的时候旧 leader 不能再造成副作用。

- **heartbeat**：周期发「我还活着」；超时只能怀疑，不能证明死亡（异步网络无法区分慢和死）。
- **lease（租约）**：leader 在 `[t, t+T]` 内有效；必须周期续租；其他节点在租约到期后才竞选。安全性依赖两个前提：**时钟漂移有界**、**进程最大暂停时间 < T**。
- **term/epoch**：每次选举递增；投票和日志携带 term，旧 term 的请求被拒绝。term 是 fencing 的基础。
- **quorum**：选举需要多数派投票；少数派无法单方面选主，避免分区两侧各有一个 leader。
- **fencing token**：选举/锁服务每次发放单调递增的 token；leader 每次写都带 token；存储层拒绝比当前最大值小的写。token 的作用不是「防止旧 leader 以为自己是 leader」，而是「让存储层不认旧 leader 的写」。

### 失败时间线：GC 停顿 + lease 过期

| 时刻 | 事件 |
| --- | --- |
| t0 | A 持有 lease 到 t0+10s，每 3s 续租一次 |
| t0+2 | A 发生 12s 的 Full GC/STW，业务线程和续租线程都停 |
| t0+10 | lease 到期；B 在 t0+10~13 竞选成功，成为新 leader，开始处理任务 |
| t0+14 | A 的 GC 结束，业务线程继续执行；A 本地仍认为「我刚续过租」 |
| t0+15 | A 和 B 同时写同一份数据/发同一批消息 |

结果取决于防护：只有 Redis 锁 → A 的写很可能成功；有 fencing token → 存储层拒绝 A 的旧 token；任务幂等 → 重复副作用被唯一键/占位吸收。三者都没有，就是一次双写事故。

关键点：**A 不是「忘了检查锁」，而是它没有可靠的方式知道自己的 lease 已过期**。GC 停顿期间它没有执行任何代码，恢复后本地状态仍是「持有中」。

## 五、分布式锁的安全性边界

锁要同时满足：互斥、无死锁、可释放、误删保护。但「互斥」只在锁服务认为锁有效期间成立。

- **watchdog 续租**：Redisson 默认 30s 租约、每 10s 续一次；续租线程活着，锁不过期。但 JVM 整体 STW 时续租也停；网络分区时客户端无法续租，锁会过期，而客户端可能仍在执行。
- **固定租约**：`tryLock(0, 300, SECONDS)` 把「任务最长执行时间」硬编码进锁；任务跑超 5 分钟，锁自动释放，另一个副本进来重复跑。
- **Redis 异步复制**：主库写锁成功、尚未同步到从库就宕机；从库提升后锁不存在，另一个客户端能拿到同一把锁。RedLock 向多个独立实例加锁降低概率，但仍受时钟漂移、进程 pause、网络延迟影响，不是强一致。
- **误删保护**：解锁用 Lua 比较 value 再删；value 必须是本次持有的唯一标识。锁过期后被别人拿走，旧持有者删除会失败，不会误删。
- **可重入**：Hash 存 owner + 重入次数；计数泄漏（异常路径少减一次）会让锁永远不释放。
- **锁等待**：`tryLock(waitTime)` 是有限等待；无界自旋会把线程池打满，抢不到应当跳过或排队到队列。

结论：分布式锁适合「短临界区 + 失败可跳过 + 有幂等兜底」；不能把它当强一致互斥。真正不可重复的写入要靠数据库唯一约束、状态机 CAS、fencing token。

### 什么条件下反悔

- 临界区从秒级升到分钟级、锁竞争导致大量跳过 → 改数据库状态机/队列，不把长任务塞进租约。
- 锁误释放不可接受、又没法加 fencing → 换 ZooKeeper/etcd 或数据库唯一约束，不靠加长租约。
- 调度精度到秒级以下或任务量到十万级 → 评估专门时间轮/延迟队列，不用 DB 轮询硬扛。

## 六、split brain

- **定义**：两个节点同时认为自己是 leader，同时接受写。
- **成因**：网络分区、GC/VM pause、时钟跳变、lease 续租失败但业务未停、运维误操作（手动启动第二个调度器）。
- **后果**：双写、重复消息、库存超卖、状态机被两个方向推进。
- **防护**：
  - quorum：少数派不能选主；
  - fencing token：存储层拒绝旧 leader；
  - STONITH：物理/网络隔离旧节点；
  - lease 短于最大暂停时间，并监控续租延迟；
  - 业务侧幂等/唯一约束作为最后一道。
- **检测**：两个节点都认为自己是 leader 时，没有「内部信号」能发现；只能靠外部存储的 token/版本、双写冲突、监控告警。

## 八、常见误解

- 「加了分布式锁就不会重复」：锁过期、GC 停顿、主从切换都会让两个持有者同时存在；锁只降低概率。
- 「看门狗能保证锁不过期」：看门狗续的是锁，不是业务；JVM 整体停顿、网络分区、续租线程死亡都会让锁失效。
- 「心跳超时就是节点死了」：异步网络无法区分慢和死；超时只能触发怀疑，不能作为唯一事实。
- 「cron 就是每隔 N 秒」：cron 匹配墙钟，进程启动/时区/夏令时都会影响；固定间隔语义要用延迟调度。
- 「misfire 补跑越全越好」：补跑会形成风暴，且可能重复；先定义任务语义，再选补跑策略。
- 「调度中心高可用等于任务不重复」：调度中心只保证触发，执行端仍要幂等。

## 边界

- 项目没有自研调度器/时间轮；对时间轮的理解停留在 Netty/Kafka 的原理层。
- XXL-Job 只做执行器接入和 PG 适配，没有改调度算法、分片算法、失败重试策略；调度中心是单实例。
- 没有做过 leader election 的生产实现和故障演练；fencing token 只在原理层，项目里靠锁 + 幂等兜底。
- 没有复现过 GC 停顿导致的双写，失败时间线是推演，不是事故记录。
- 多副本场景只覆盖蓝绿部署的 180 秒共存窗口，没有常态多副本压测。
